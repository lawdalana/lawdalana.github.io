# 011 — ประวัติ Latent, Ternary และ Atomic Proof: ต้องระบุว่าจะพิสูจน์อะไร

อ่านเพิ่ม: [ผลตรวจและงานวิจัยรอบ 2](#research-review-2)

ต้นฉบับ: [post.md](../original/post.md) บรรทัด 422–426 · ตรวจแหล่งข้อมูล: 2026-09-20

โพสต์นี้มีข้อความสั้นเพียงส่วนเดียว ไม่มีภาพ ลิงก์ paper โค้ด หรือคำจำกัดความแนบมา จึงไม่สามารถระบุ implementation ที่ผู้เขียนหมายถึงได้แน่นอน

## ข้อมูลที่สกัดได้

ผู้เขียนบอกว่ากำลังทำ “Reconstructing latent historical” และเพิ่มการ “Bake ลงฮาร์ดแวร์” เพื่อทำ “atomic proof” ด้วย “Ternary system” สิ่งที่ทราบคือผู้เขียนเชื่อมประวัติสถานะ การทำงานระดับฮาร์ดแวร์ และการแทนค่าสามระดับเข้าด้วยกัน ส่วนกลไกจริงยังไม่ปรากฏ

บทนี้จึงเสริมพื้นฐานของศัพท์ที่เกี่ยวข้อง โดยไม่ถือว่าทั้งหมดเป็นคำอธิบายระบบของผู้เขียน

## การสร้างสถานะอดีตกลับมา

แนวทางหนึ่งที่ตรวจสอบได้คือ **event sourcing** เก็บเหตุการณ์ตามลำดับแล้วคำนวณสถานะกลับจากจุดเริ่มต้น ใช้ snapshot เป็นจุดตั้งต้นใกล้เวลาที่ต้องการเพื่อไม่ต้องเล่นซ้ำทั้งหมด [Microsoft: Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)

ตัวอย่างออกแบบเอง:

~~~text
snapshot ที่ tick 100: NPC อยู่ A, มีพลังงาน 8
event 101: เดิน A→B, ใช้พลังงาน 1
event 102: กินอาหาร, เพิ่มพลังงาน 3
สถานะที่ tick 102: อยู่ B, พลังงาน 10
~~~

ถ้าระบบใช้ latent ที่ถูกบีบอัดแล้วทิ้งข้อมูล การเก็บเพียง latent ล่าสุดอาจย้อนอดีตไม่ได้ ต้องเก็บเหตุการณ์ รุ่น policy และข้อมูลสุ่มที่จำเป็นต่อ replay ด้วย

## Ternary หมายถึงอะไรได้บ้าง

Ternary หมายถึงมีสามค่า เช่น −1, 0, +1 ตัวอย่างจริงคือ BitNet b1.58 ซึ่งใช้ค่าน้ำหนักสามระดับ งานนั้นเป็นเรื่องการแทนค่าน้ำหนักและการคำนวณโมเดล ไม่ใช่หลักฐานว่าเลขสามค่าทำให้ผล reasoning ถูกต้องเสมอ [BitNet b1.58](https://arxiv.org/abs/2402.17764)

หนึ่งค่ามีทางเลือกสามแบบจึงมีความจุเชิงการเข้ารหัส log₂3 ≈ 1.585 บิตในกรณีอุดมคติ แต่การเก็บจริงอาจจัดเป็นสองบิตหรือแพ็กหลายค่ารวมกัน พร้อม overhead ของ scale และ metadata

## Atomicity กับ proof ไม่ใช่คำเดียวกัน

Atomicity หมายถึงการเปลี่ยนแปลงชุดหนึ่งสำเร็จทั้งหมดหรือไม่เกิดเลย ตัวอย่างที่มีเอกสารชัดคือ atomic commit ใน SQLite ซึ่งต้องออกแบบรองรับการเขียนค้างหรือไฟดับ [SQLite: Atomic Commit](https://www.sqlite.org/atomiccommit.html)

ส่วน proof ต้องระบุข้อความที่จะพิสูจน์ เช่น “ยอดรวมไม่เปลี่ยน” หรือ “action นี้ผ่านกฎเวอร์ชันนี้” checksum อาจช่วยตรวจว่าข้อมูลถูกเปลี่ยน แต่ไม่ได้พิสูจน์ว่าเหตุการณ์ที่บันทึกตรงกับความจริง หรืออัลกอริทึมเลือก action ดีที่สุด

คำว่า bake ลงฮาร์ดแวร์อาจหมายถึงการ specialize หรือ compile ขั้นตอนให้เหมาะกับเครื่อง แต่ข้อความต้นฉบับไม่พอให้เลือกความหมายหนึ่งอย่างมั่นใจ

## แบบฝึกหัดเพื่อทำแนวคิดให้ชัด

กำหนด invariant หนึ่งข้อ เช่น พลังงานรวมก่อนและหลังโอนระหว่าง NPC ต้องเท่าเดิม เก็บเหตุการณ์โอนและ snapshot แล้วลองตัดการบันทึกกลางทาง ถามว่าต้องเพิ่มข้อมูลหรือกลไกอะไรจึงยืนยันได้ว่าการโอนครบทั้งสองฝั่ง

**ข้อสรุปการเรียนรู้:** ก่อนประเมินคำว่า atomic proof ให้เขียนให้ได้ว่าพิสูจน์คุณสมบัติใด ใครเป็นผู้ตรวจ หลักฐานมีข้อมูลอะไร และถือสมมติฐานเรื่องฮาร์ดแวร์หรือการบันทึกไว้อย่างไร

## ตรวจสอบและค้นคว้าเพิ่มเติม — รอบ 2

ตรวจวันที่ 2026-09-20 · อ่านแหล่งต้นทางเพิ่มและเทียบกับคำอธิบายเดิม

### งานและมาตรฐานเพิ่ม: ย้อนการทำงานกับพิสูจน์ประวัติ

**Engineering Record and Replay for Deployability — O’Callahan และคณะ, USENIX ATC 2017** อธิบาย rr ซึ่งบันทึกและเล่นซ้ำการทำงานจริงโดยใช้กลไกของ OS/CPU ควบคุมและบันทึกแหล่ง nondeterminism เช่น system calls, signals และ scheduling มีข้อจำกัดด้านฮาร์ดแวร์และ workload จึงไม่ใช่เพียงตั้ง random seed แล้วรับรอง replay ได้ทุกโปรแกรม [paper ต้นฉบับ](https://www.usenix.org/system/files/conference/atc17/atc17-o_callahan.pdf)

**RFC 9162: Certificate Transparency Version 2.0 — IETF, 2021** กำหนด Merkle inclusion proof เพื่อตรวจว่ารายการอยู่ใน tree ที่อ้าง และ consistency proof เพื่อตรวจความสัมพันธ์ระหว่าง log รุ่นก่อนกับรุ่นใหม่แบบเพิ่มต่อท้าย มาตรฐานเองแยกการตรวจ log ออกจากการป้องกันการออก certificate ที่ไม่เหมาะสม หลักฐานสมาชิกใน log จึงไม่ใช่หลักฐานความจริงของทุกสิ่งที่บันทึก [บท 1 และ 2.1](https://www.rfc-editor.org/rfc/rfc9162.html)

### แยกสิ่งที่จะรับรองเป็นสี่ข้อ

| คุณสมบัติ | คำถามตัวอย่าง | หลักฐานที่เหมาะกับคำถาม |
|---|---|---|
| Replay | เหตุการณ์เดิมให้ state เดิมไหม | input, event order, รุ่นโปรแกรม/กฎ |
| Atomicity | โอนทรัพยากรครบทั้งสองฝั่งไหม | transaction protocol และการกู้คืน |
| Integrity | log ถูกแก้หลังประกาศ root หรือไม่ | trusted checkpoint กับ hash/proof |
| Semantic validity | การโอนนี้ได้รับอนุญาตและยอดถูกไหม | ตัวตรวจสิทธิ์และ invariant |

ตารางนี้เป็นการสังเคราะห์เพื่ออ่านคำว่า atomic proof ในโพสต์ ไม่ได้ยืนยันว่าผู้เขียนใช้ rr หรือ Certificate Transparency จริง

### ตัวอย่างที่แยกข้อผิดพลาดได้

ให้บันทึกว่า A โอนอาหาร 3 หน่วยให้ B พร้อม tick และ rule_version ถ้า attacker เปลี่ยนเป็น 30 หลังผูกไว้กับ root แล้ว การตรวจ integrity อาจจับความเปลี่ยนแปลงได้ แต่ถ้าระบบบันทึก 30 ตั้งแต่แรกทั้งที่ A มีอาหารแค่ 5 หลักฐาน Merkle ที่ถูกต้องก็ยังยืนยันรายการผิดตรรกะนั้นได้ ต้องมี validator ของยอดก่อนรับเหตุการณ์

เช่นเดียวกัน การ replay เหตุการณ์ผิดได้เหมือนเดิมคือประโยชน์ต่อการ debug แต่ไม่ใช่ความถูกต้องทางธุรกิจ และ hash อย่างเดียวไม่มีข้อมูลพอสร้าง state ที่ถูกย่อทิ้งกลับมา

**แบบทดลองต่อ:** สร้าง event log ของตัวอย่างข้างต้น แล้วแยกสามการเปลี่ยน: สลับลำดับ event, เปลี่ยนจำนวนอาหาร, และเปลี่ยน rule_version ตรวจว่ากลไกใดจับได้และกลไกใดทำไม่ได้ จึงจะรู้ว่า “proof” ที่ออกแบบกำลังพิสูจน์เรื่องใด

**ผลการตรวจ:** ข้อความต้นฉบับยังไม่มีรายละเอียดพอระบุสถาปัตยกรรม ข้อมูลเสริมให้รายการคุณสมบัติและรูปแบบหลักฐานที่ใช้แยกคำกล่าวนั้นได้ โดย ternary เป็นอีกการเลือก representation ที่ไม่ได้แทนคุณสมบัติทั้งสี่โดยตัวมันเอง
