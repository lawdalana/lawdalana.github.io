# 018 — Tokenizer หลักล้าน tokens/sec กับเกม 20 Hz วัดคนละส่วนกัน

ต้นฉบับ: [post.md](../original/post.md) บรรทัด 377–383 · ตรวจแหล่งข้อมูล: 2026-09-20

ภาพต้นฉบับ: [image-36.png](../original/image-36.png)

## สกัดสิ่งที่รายงาน

ข้อความโพสต์พูดถึง Rust/SIMD และการทำ game, chain และ reasoning ที่ 20 Hz ส่วนภาพเป็น “KatGPT Tokenizer & Embedding Engine Benchmark” แสดงเวลาสร้าง tokenizer ตามมิติ และ token encoding throughput ประมาณ 22.26 ล้าน tokens/sec, 158.14 MB/sec, รวม 25.5 ล้าน token ในเวลาที่แสดงเป็น 1.14 วินาที

ภาพเป็นผลที่ผู้เขียนนำมาแสดง ยังไม่มี corpus, source ของ benchmark หรือผลรันซ้ำแนบในโพสต์นี้ จึงบันทึกเป็นตัวเลขต้นฉบับโดยไม่ยืนยันว่าทดสอบซ้ำแล้ว

## Tokenization ทำงานอะไร

Tokenization แปลงข้อความเป็นชิ้นส่วนและหมายเลขที่ระบบใช้ เช่น ประโยคหนึ่งอาจแยกเป็นคำย่อยหลายชิ้น ส่วน embedding แปลงหมายเลขเป็นเวกเตอร์ และ generation คือการสร้างผลใหม่ ทั้งสามขั้นมีต้นทุนต่างกัน

เอกสาร Hugging Face ระบุว่าไลบรารี Tokenizers ใช้ Rust และออกแบบเพื่อ tokenization ที่เร็ว อีกทั้ง Python สามารถเรียก implementation ฝั่ง Rust นี้ได้ด้วย จึงไม่ควรใช้ชื่อภาษาชั้น interface ตัดสินว่าคำนวณด้านในทำด้วยภาษาอะไร [Hugging Face Tokenizers](https://huggingface.co/docs/tokenizers/index)

## อ่านหน่วยให้เปรียบเทียบได้

tokens/sec ขึ้นกับว่า tokenizer ตัดละเอียดแค่ไหน ส่วน MB/sec บอกปริมาณข้อความที่ผ่านระบบ การแบ่งข้อความเป็นชิ้นเล็กมากอาจทำให้ tokens/sec ดูสูงทั้งที่ประมวลผลไบต์ไม่ได้มากขึ้น จึงควรรายงานทั้งสองหน่วยและตรวจ token IDs ว่าตรงกับนิยามที่ต้องการ

คำนวณจากค่าที่ปัดเศษในภาพ 25,500,000/1.14 ≈ 22.37 ล้าน tokens/sec ค่าต่างจาก throughput ที่แสดงเล็กน้อยอาจมาจากการปัดเวลา จึงต้องดูเวลาที่ละเอียดกว่านี้ก่อนสรุปว่าตัวเลขขัดกัน

Initialization ยังต่างจาก hot path: ถ้าสร้างตัว tokenizer ใหม่ทุกคำขอ ผลจริงจะต่างจากการสร้างครั้งเดียวแล้วใช้ซ้ำ แม้ throughput ของการ encode จะเหมือนกัน

## เชื่อมกับงบ 20 Hz

20 Hz หมายถึงหนึ่งรอบทุก 50 ms ถ้ามี NPC 1,000 ตัวและให้ reasoning ทำแบบลำดับโดยใช้งบทั้งรอบ จะมีค่าเฉลี่ยได้สูงสุด 50 µs ต่อ NPC ก่อนรวมงานอื่น นี่คือการคำนวณงบเวลา ไม่ใช่ผล benchmark

ตัวอย่างสมมติ ถ้า reasoning ใช้ 10 ms, physics 15 ms และ sync 10 ms เหลือ 15 ms สำหรับงานอื่นและความผันผวน การรู้ tokenizer throughput เพียงค่าเดียวไม่บอกว่างบเหล่านี้ผ่านหรือไม่

## วิธีวัดที่ลองทำได้

1. เตรียมข้อความหลายแบบ รวมไทย อังกฤษ เลข และสัญลักษณ์ พร้อมตรวจจำนวนไบต์
2. แยกเวลาสร้าง tokenizer ออกจาก encode/decode และเวลาอ่านไฟล์
3. ใช้ corpus และกฎตัดคำเดียวกันเมื่อเทียบ implementation
4. หากเป้าหมายคือเกม ให้วัดเวลาแต่ละ tick จริงและเปอร์เซ็นไทล์ที่ช้า เช่น p95/p99 ด้วย

การใช้ Rust หรือ SIMD เป็นวิธีลดต้นทุนบางส่วนที่มีเหตุผล แต่ภาพนี้ยังไม่พิสูจน์ว่าการ reasoning ทั้งระบบได้ throughput เท่ากับ tokenizer

**คำถามทบทวน:** tokenizer ที่เร็วสองเท่าจะทำให้เกมเร็วสองเท่าหรือไม่? ขึ้นกับสัดส่วนเวลาที่เกมใช้ใน tokenizer หากใช้เพียงเล็กน้อย ผลต่อเวลาทั้งเกมก็เล็กตาม

## ตรวจสอบและค้นคว้าเพิ่มเติม — รอบ 2

ตรวจวันที่ 2026-09-20 · อ่านแหล่งต้นทางเพิ่มและเทียบกับคำอธิบายเดิม

### งานวิจัยเพิ่ม: ความเร็วอาจมาจากอัลกอริทึมตัดคำ

**Fast WordPiece Tokenization — Song และคณะ, EMNLP 2021** เสนอวิธีใช้ trie กับลิงก์ช่วยเปลี่ยนสถานะเมื่อจับคู่ต่อไม่ได้ โดยอาศัยแนวคิดจาก Aho–Corasick ทำให้ WordPiece tokenization เป็น O(n) ตามความยาว input ภายใต้กรอบของงาน และรวม pre-tokenization เข้ากับการทำงานหนึ่งรอบได้ ผู้วิจัยเทียบ implementation ที่กำหนดในงานของตน จึงไม่ควรนำอัตราเร็วจากปี 2021 ไปแทนทุกเวอร์ชันปัจจุบัน [paper ต้นทาง](https://arxiv.org/abs/2012.15524)

**SentencePiece — Kudo และ Richardson, EMNLP 2018** เสนอระบบ subword tokenization ที่ฝึกจากประโยคดิบได้โดยไม่ต้องแบ่งคำล่วงหน้า ทดลองกับการแปลอังกฤษ–ญี่ปุ่นและการตั้งค่า segmentation สิ่งที่เกี่ยวกับโพสต์คือ tokenizer ต่างตระกูลมีสมมติฐานเรื่องการแบ่งคำและ preprocessing ต่างกัน จึงต้องเทียบ output contract ก่อนเทียบความเร็ว [paper ต้นทาง](https://arxiv.org/abs/1808.06226)

### จัด benchmark เป็นสองชนิด

**เทียบ implementation:** ใช้ vocabulary, normalization, unknown-token rule และ segmentation เดียวกัน แล้วตรวจ token IDs ให้ตรงทุกกรณี ก่อนวัดว่าทำงานเดิมเร็วขึ้นหรือไม่

**เทียบ tokenizer design:** ยอมเปลี่ยนวิธีแบ่งหรือ vocabulary แต่ต้องวัดผลต่อโมเดลปลายทางด้วย เช่น จำนวน token ต่อข้อความ คุณภาพของโจทย์ และต้นทุน inference เพราะการลดเวลาตัดคำอาจสร้าง sequence ยาวขึ้นจนส่วนอื่นช้าลง

สองแบบนี้ตอบคนละคำถาม การแบ่งตัวอักษรทุกตัวเป็น token ทำให้ตัวเลข tokens/s เปลี่ยนได้ แต่ไม่ใช่การเร่ง BPE/WordPiece เดิมให้เร็วขึ้นโดยคงความหมายทุกอย่าง

### ตัวอย่าง Unicode ที่ช่วยหาขอบเขตงาน

ตัวอักษร é แบบรหัส U+00E9 ใช้ UTF-8 สองไบต์ ส่วน e ตามด้วย combining acute accent ใช้รวมสามไบต์ แม้แสดงผลคล้ายกัน หาก pipeline เลือก normalize แบบ NFC ทั้งคู่สามารถได้รูปแทนเดียวกัน ต้องระบุว่าจับเวลาก่อนหรือหลังขั้นนี้และนับไบต์ชุดใด ตัวอย่างนี้อธิบายการวัด ไม่ได้อ้างว่าทุก tokenizer ใช้ NFC เป็นค่าเริ่มต้น

สำหรับภาษาไทยที่ไม่ได้คั่นทุกคำด้วยช่องว่าง ให้รวมข้อความจริงใน corpus ไม่ใช่สรุปผลจากภาษาอังกฤษล้วน และตรวจกรณีสระ/วรรณยุกต์ emoji และ whitespace ตามข้อตกลงของ tokenizer นั้น

**แบบทดลองต่อ:** วัด bytes/s, tokens/s และจำนวน token ต่อประโยคพร้อมกัน แยก normalization, segmentation และ allocation แล้วนำผลรวมเข้า frame budget ที่ต้องการ การเปลี่ยน algorithm, ภาษา implementation และ SIMD ควรทดลองแยกกันก่อนสรุปสาเหตุ

**ผลการตรวจ:** บทเดิมแยก tokenization กับ reasoning ถูกแล้ว งานเพิ่มทำให้เห็นว่าแม้ภายใน tokenization เองก็ต้องแยก algorithm, preprocessing และความเข้ากันได้ของผลลัพธ์ก่อนเทียบ throughput
