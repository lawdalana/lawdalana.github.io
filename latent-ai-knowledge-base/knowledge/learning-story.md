# Representation และการออกแบบ Reasoning Systems

พื้นฐานสำหรับผู้อ่านด้าน Deep Learning: ข้อมูล → พารามิเตอร์ → การคำนวณ → ข้อจำกัด → การประเมินระบบ

**ระดับผู้อ่าน:** สำหรับผู้อ่านที่มีพื้นฐาน neural networks, gradient descent และ attention และต้องการศึกษาความสัมพันธ์ระหว่างแนวคิดเหล่านี้กับ latent reasoning และการออกแบบระบบ AI

เนื้อหาเรียงตามความสัมพันธ์ของแนวคิดพื้นฐาน เริ่มจากข้อมูลที่ representation จำเป็นต้องรักษา จากนั้นพิจารณาความแตกต่างระหว่างการปรับ weights กับการเพิ่ม computation ระหว่าง inference ก่อนเชื่อม search, verifier, memory และ retrieval เข้ากับการออกแบบระบบ แต่ละบทประกอบด้วยกลไก สมการ ตัวอย่างคำนวณ และขอบเขตของหลักฐาน บทความอ่านเพิ่มเติมอ้างอิงงานวิจัยและ implementation หลายแหล่ง จึงเหมาะสำหรับเปรียบเทียบกลไกเฉพาะส่วน โดยการนำผลจากต่างงานมาใช้ร่วมกันยังต้องตรวจสอบเงื่อนไขของแต่ละงาน

## พื้นฐานที่จำเป็น

- เข้าใจมิติของเทนเซอร์และเงื่อนไขการคูณเมทริกซ์ เช่น เมทริกซ์ขนาด (T×d) คูณกับ (d×m) ให้ผลลัพธ์ขนาด T×m
- เข้าใจบทบาทของ loss และ gradient ในการปรับพารามิเตอร์ รวมถึงความแตกต่างระหว่าง training กับ inference
- มีพื้นฐาน softmax และ Q/K/V attention โดยบทที่ 2 ระบุมิติและบทบาทขององค์ประกอบที่ใช้ในบทถัดไป
- เข้าใจ train/evaluation split และขอบเขตการนำผลประเมินจากชุดข้อมูลหนึ่งไปใช้กับบริบทอื่น

## บท 1 — Representation และข้อมูลที่จำเป็นต่อการตัดสินใจ

[เปิดบทพร้อมห้องทดลอง](../index.html#story/01) · [หัวข้อสังเคราะห์](topics/01-latent-representations-and-geometry.md)

**คำถามหลัก:** เกณฑ์ใดใช้ประเมินว่า latent representation มีข้อมูลเพียงพอสำหรับงานปลายทาง?

**ความเข้าใจที่นำมาใช้:** การออกแบบ representation เริ่มจากข้อมูลนำเข้าและข้อกำหนดของงาน ก่อนพิจารณาสถาปัตยกรรมหรือจำนวนรอบ reasoning



### โจทย์

โมเดล downstream ไม่สามารถใช้ข้อมูลที่ encoder ตัดออกไปแล้วได้ การออกแบบจึงต้องระบุว่าความแตกต่างใดละได้ และความแตกต่างใดจำเป็นต่อการตัดสินใจ

### 1.1 Observation และ state ที่เพียงพอต่อการตัดสินใจ

กำหนด x_t เป็นข้อมูลที่สังเกตได้, s_t เป็นสถานะจริง และ z_t = fθ(x_t) เป็น representation ที่ policy π ใช้เลือก action a_t เมื่อ x_t ครอบคลุมสถานะเพียงบางส่วน ภาพเดียวอาจไม่เพียงพอต่อการตัดสินใจ เช่น วัตถุที่อยู่ตำแหน่งเดียวกันอาจมีความเร็วคนละทิศ จึงจำเป็นต้องใช้ประวัติหรือข้อมูลเพิ่มเติมเพื่อแยกพฤติกรรมในอนาคต

ในระบบที่สังเกตสถานะได้ครบ ความเพียงพอต่อการตัดสินใจพิจารณาได้จาก reward และ transition การรวม s กับ s′ เป็น z เดียวกันตามเงื่อนไข exact state abstraction กำหนดให้ทั้งสองมี reward และการกระจายของ latent ถัดไปเท่ากันภายใต้ action เดียวกัน ส่วนระบบที่เรียนรู้จากข้อมูลมักรักษาเงื่อนไขดังกล่าวได้โดยประมาณ

คุณภาพในการ reconstruct input เป็น objective หนึ่ง แต่ไม่ได้กำหนดให้ encoder รักษา feature ที่สำคัญต่อ action ครบถ้วนเสมอไป ในทางกลับกัน encoder ที่ตัดข้อมูลพื้นหลังออกจำนวนมากอาจเหมาะกับ policy หากยังรักษาข้อมูลเกี่ยวกับผลของ action และข้อกำหนดของงานไว้ได้

$$
z_t=f_{\theta}(x_t)
$$

$$
a_t\sim\pi(\,\cdot\mid z_t)
$$

fθ คือ encoder; π คือการกระจายของ action เมื่อเห็น z_t

**ความหมายของสมการ:** Encoder แปลง observation เป็น representation แล้ว policy กำหนดการกระจายความน่าจะเป็นสำหรับสุ่มเลือก action จาก representation นั้น

**อ่านสัญลักษณ์:**

- **fθ(x_t):** ผลของการส่ง observation เข้า encoder ที่มีพารามิเตอร์ θ
- **π(· | z_t):** การกระจายความน่าจะเป็นของ action โดยมี z_t เป็นเงื่อนไข จุด · แทนตำแหน่งของ action
- **∼:** การสุ่มจากการกระจายที่กำหนด ซึ่งต่างจากการเลือกค่าความน่าจะเป็นสูงสุดเสมอ

**ตัวอย่างการคำนวณ:** ตัวอย่างสมมติ: x_t มี hunger=0.8, threat=0.1 และสีเสื้อ; encoder เก็บเฉพาะสองค่าแรก

1. ผ่าน encoder แล้วได้ z_t=(0.8, 0.1); สีเสื้อไม่ถูกส่งต่อ
2. สมมติ policy ให้ P(eat | z_t)=0.75 และ P(hide | z_t)=0.25 รวมเป็น 1
3. ถ้าสุ่มเลขสม่ำเสมอในช่วง [0,1) แล้วได้ 0.60 จะอยู่ในช่วง eat [0,0.75); ถ้าได้ 0.90 จะเลือก hide

**ผลที่ได้:** ในครั้งที่สุ่มได้ 0.60 จึงได้ a_t=eat แม้ input เดิมอาจสุ่มได้ action อื่นในครั้งถัดไป

**ข้อสรุปจากตัวอย่าง:** Encoder กำหนดข้อมูลที่ส่งให้ policy ส่วน policy กำหนดวิธีเลือก action จากข้อมูลดังกล่าว

$$
f(s)=f(s^{\prime})
$$

ทำให้ทั้งสองเงื่อนไขต่อไปนี้เป็นจริงพร้อมกัน

$$
r(s,a)=r(s^{\prime},a)
$$

$$
\begin{aligned}P(Z_{\mathrm{next}}=u\mid s,a)\\{}=P(Z_{\mathrm{next}}=u\mid s^{\prime},a)\end{aligned}
$$

เงื่อนไขอุดมคติสำหรับทุก action a และทุก latent state u ในระบบจำกัด; r คือ expected reward และ P คือ transition probability

**ความหมายของสมการ:** การรวมสอง state เป็น latent เดียวกันต้องรักษา reward และความน่าจะเป็นของ latent ถัดไปให้เท่ากันสำหรับ action เดียวกัน

**อ่านสัญลักษณ์:**

- **⇒:** ความสัมพันธ์เชิงเงื่อนไขที่ state abstraction ต้องรักษา ไม่ใช่คุณสมบัติอัตโนมัติของ encoder ทุกแบบ
- **r(s,a):** ค่าเฉลี่ย reward ของ action a ใน state s
- **P(Z_next=u | s,a):** ความน่าจะเป็นที่ latent ถัดไปเป็น u หลัง action a
- **s′:** state อีกสถานะหนึ่งที่เปรียบเทียบกับ s

**ตัวอย่างการคำนวณ:** กำหนดระบบตัวอย่างที่มี action eat/wait และ latent ถัดไปเป็น full/hungry โดยสอง state ต่างกันเฉพาะพื้นหลัง

1. รวมสอง state เป็น z เดียวกันโดยตัดสีพื้นหลังออก
2. สำหรับ eat: ทั้งคู่ได้ reward=2 และโอกาส (full, hungry)=(0.9, 0.1)
3. สำหรับ wait: ทั้งคู่ได้ reward=0 และโอกาส (full, hungry)=(0, 1); จึงครอบคลุมทั้งสอง action และทุก latent ปลายทาง

**ผลที่ได้:** การรวมสอง state ในระบบตัวอย่างนี้รักษา reward และ transition ตามเงื่อนไขที่กำหนด

**ข้อสรุปจากตัวอย่าง:** เงื่อนไขของ abstraction ต้องตรวจสำหรับทุก action ในขอบเขตที่กำหนด การให้ผลตรงกันเพียง action เดียวไม่เพียงพอ

### 1.2 Geometry และความสัมพันธ์กับงานปลายทาง

Invariance หมายถึง representation คงเดิมภายใต้การแปลง input บางชนิด เช่น การเปลี่ยน texture ที่ไม่เกี่ยวข้องกับ action ส่วน equivariance หมายถึง representation เปลี่ยนตามกฎที่สอดคล้องกับการแปลง input เช่น เวกเตอร์ทิศทางหมุนตามการหมุนพิกัด การกำหนด invariance จึงต้องคำนึงถึงข้อมูลที่งานจำเป็นต้องใช้

สำหรับ encoder ที่หาอนุพันธ์ได้ Jacobian J_f อธิบายความไวเฉพาะที่ของ latent ต่อ perturbation ในแต่ละทิศของ input การตีความต้องแยกทิศที่เป็นสิ่งรบกวนออกจากทิศที่เกี่ยวข้องกับ feature สำคัญ ระยะใน embedding หรือ rank ของ Jacobian เพียงค่าเดียวจึงยังไม่เพียงพอยืนยัน semantic understanding

โครงสร้างข้อมูลเป็นองค์ประกอบหนึ่งของ representation โดย graph แทน node และ edge ส่วน cell complex เพิ่มหน้าและองค์ประกอบมิติสูงเพื่อแทนความสัมพันธ์ที่มีมากกว่าสององค์ประกอบ การเลือก operator ต้องสอดคล้องกับชนิดข้อมูล ขณะที่ analogy พิจารณาการรักษาบทบาทและความสัมพันธ์เมื่อเปลี่ยนบริบท

$$
f(Tx)=f(x)
$$

หรือ

$$
f(Tx)=\rho(T)f(x)
$$

T คือการแปลง input; แบบแรก invariant แบบหลัง equivariant โดย ρ(T) เป็นการแปลงที่สอดคล้องกันใน latent

**ความหมายของสมการ:** หลังแปลง input แบบ invariant จะให้ latent คงเดิม ส่วนแบบ equivariant จะให้ latent เปลี่ยนตามการแปลงที่สอดคล้องกัน

**อ่านสัญลักษณ์:**

- **T:** การแปลง input เช่น การหมุนพิกัด 90 องศา
- **ρ(T):** การแปลงใน latent ที่สอดคล้องกับ T
- **f(Tx)=f(x):** เงื่อนไข invariance: encoder ให้ค่าเดิมหลังแปลง input
- **f(Tx)=ρ(T)f(x):** เงื่อนไข equivariance: latent เปลี่ยนตามกฎที่กำหนด

**ตัวอย่างการคำนวณ:** ใช้ x=(1,0), T เป็นการหมุนทวนเข็ม 90 องศา จึงได้ Tx=(0,1); เปรียบเทียบ encoder สองแบบ

1. ถ้า encoder เก็บแค่ความยาวเวกเตอร์ จะได้ f(x)=1 และ f(Tx)=1: invariant ต่อการหมุน
2. ถ้า encoder เก็บพิกัดเดิม จะได้ f(x)=(1,0) และ f(Tx)=(0,1)
3. สำหรับ encoder แบบที่สอง เลือก ρ(T) เป็นการหมุน 90 องศาใน latent ด้วย จึงได้ ρ(T)f(x)=(0,1) ตรงกัน

**ผลที่ได้:** การเก็บความยาวไม่รักษาทิศทาง ส่วนการเก็บพิกัดรักษาทิศทางโดยเปลี่ยนตามการหมุน input

**ข้อสรุปจากตัวอย่าง:** การกำหนด invariance หรือ equivariance ขึ้นกับความแตกต่างที่งานจำเป็นต้องรักษา

$$
\Delta z\approx J_f(x)\Delta x
$$

$$
J_f\in\mathbb{R}^{d_z\times d_x}
$$

การประมาณเชิงเส้นเฉพาะบริเวณสำหรับ Δx ขนาดเล็ก; d_x และ d_z คือมิติของ input และ latent

**ความหมายของสมการ:** สำหรับการเปลี่ยน input ขนาดเล็ก ผลคูณของ Jacobian กับ Δx ให้ค่าประมาณเชิงเส้นของการเปลี่ยน latent

**อ่านสัญลักษณ์:**

- **Δx, Δz:** การเปลี่ยนแปลงของ input และ latent เทียบกับจุดตั้งต้น
- **J_f(x):** เมทริกซ์อนุพันธ์ซึ่งแต่ละองค์ประกอบระบุความไวของ output หนึ่งมิติต่อ input หนึ่งมิติ ณ x
- **≈:** ความเท่ากันโดยประมาณเฉพาะบริเวณที่พิจารณา
- **d_z×d_x:** จำนวนแถวเท่ากับมิติ latent และจำนวนคอลัมน์เท่ากับมิติ input

**ตัวอย่างการคำนวณ:** สมมติ f(x₁,x₂)=(x₁²,x₂), เริ่มที่ x=(2,3) และขยับ Δx=(0.01,0.02)

1. ที่จุดนี้ J_f=[[4,0],[0,1]] เพราะความชันของ x₁² ที่ x₁=2 เท่ากับ 4
2. คูณเมทริกซ์กับ Δx ได้การเปลี่ยนแปลงที่ประมาณไว้ (4×0.01, 1×0.02)=(0.04,0.02)
3. คำนวณจริง: f(2.01,3.02)−f(2,3)=(0.0401,0.02); ส่วนที่ประมาณพลาดในมิติแรกคือ 0.0001

**ผลที่ได้:** latent ใหม่ที่ประมาณได้คือ (4.04,3.02) ใกล้กับค่าจริง (4.0401,3.02)

**ข้อสรุปจากตัวอย่าง:** Jacobian อธิบายความไวใกล้จุดที่ประเมิน การประมาณสำหรับ input ที่เปลี่ยนมากอาจต้องประเมิน Jacobian ใหม่

### 1.3 ความจุ ข้อมูล และความสามารถในการเข้าถึง

เวกเตอร์ที่มี 2,560 ค่าและใช้ 16 บิตต่อค่า มีขนาด 40,960 บิต ขณะที่ token หนึ่งตัวจาก vocabulary ขนาด 65,536 สามารถแทนด้วย index 16 บิตได้ การเปรียบเทียบนี้ระบุพื้นที่จัดเก็บตามรูปแบบข้อมูล แต่ยังไม่วัดปริมาณข้อมูลที่เกี่ยวข้องกับโจทย์ซึ่งส่งผ่าน representation ได้จริง

ข้อมูลแต่ละมิติอาจซ้ำซ้อน ถูก noise รบกวน หรืออยู่ในรูปแบบที่ decoder ใช้งานไม่ได้ จึงแยกการวิเคราะห์เป็น represented information หรือสัญญาณที่มีอยู่สำหรับการทำนาย, accessibility หรือความสามารถของกระบวนการที่ใช้ในการดึงสัญญาณ และ stability หรือความคงทนของการใช้งานเมื่อ input เปลี่ยนเล็กน้อย

การประเมินตามงานปลายทางทำได้โดยเปลี่ยนปัจจัยทีละอย่าง เช่น สีพื้นหลังหรือสถานะประตู แล้ววัด action success ร่วมกับระยะใน latent หาก latent เปลี่ยนน้อยแต่ policy ไม่สามารถเปลี่ยน action ตามที่งานต้องการได้ แสดงว่า representation สูญเสียความแตกต่างที่สำคัญ

$$
\operatorname{storage}(z)=d_z\times\mathrm{bits\ per\ value}
$$

ขนาดเชิงรูปแบบของเวกเตอร์ ไม่ใช่ mutual information กับคำตอบหรือปริมาณความรู้ที่เข้าถึงได้

**ความหมายของสมการ:** พื้นที่ payload ของเวกเตอร์เท่ากับจำนวนค่าที่เก็บคูณจำนวนบิตต่อค่า

**อ่านสัญลักษณ์:**

- **d_z:** จำนวนมิติ หรือจำนวนค่าที่เก็บใน latent หนึ่งเวกเตอร์
- **bits_per_value:** จำนวนบิตที่รูปแบบข้อมูลใช้ต่อหนึ่งค่า
- **×:** คูณจำนวนค่าเข้ากับพื้นที่ต่อค่า; 8 บิตเท่ากับ 1 ไบต์

**ตัวอย่างการคำนวณ:** สมมติเก็บ z=(0.2,0.2,0.2,0.2) เป็น float16 โดยยังไม่รวม metadata หรือพื้นที่จัดสรรเพิ่ม

1. เวกเตอร์มี 4 ค่า แต่ละค่าใช้ 16 บิต จึงใช้ 4×16=64 บิต
2. แปลงเป็นไบต์ได้ 64÷8=8 ไบต์ แม้ทั้งสี่ค่าจะเหมือนกัน
3. ถ้ามี 2,560 ค่าในรูปแบบเดิม จะใช้ 2,560×16=40,960 บิต หรือ 5,120 ไบต์

**ผลที่ได้:** พื้นที่จัดเก็บขึ้นกับจำนวนมิติและรูปแบบข้อมูล โดยสูตรนี้ไม่ประเมินความซ้ำซ้อนระหว่างมิติ

**ข้อสรุปจากตัวอย่าง:** พื้นที่จัดเก็บที่เพิ่มขึ้นยังไม่ระบุปริมาณข้อมูลเกี่ยวกับคำตอบที่ decoder สามารถใช้ได้

### 1.4 State aliasing และข้อจำกัดของการเพิ่ม computation

ในห้องทดลอง state A และ B มี hunger เท่ากัน แต่ threat และ action เป้าหมายต่างกัน หาก encoder เก็บเฉพาะ hunger จะได้ z_A = z_B กรณีนี้เรียก state aliasing คือการแทนสถานะที่จำเป็นต้องแยกด้วย representation เดียวกัน

ภายใต้สมมติฐานที่พบ A และ B บ่อยเท่ากันและแต่ละ state มี action ที่ถูกต้องเพียงหนึ่งแบบ policy ที่ได้รับ z เดียวกันมีอัตราถูกสูงสุดครึ่งหนึ่งของสองกรณีนี้ การเพิ่มความลึกหรือจำนวนรอบคำนวณโดยไม่มีข้อมูลเพิ่มเติมไม่สามารถแยกสถานะได้ จึงต้องปรับ representation หรือเพิ่ม observation

การรวม threat ใน representation แยกสถานะคู่ที่มีเป้าหมายขัดกันได้ ส่วนสีเสื้ออาจเพิ่มจำนวนกลุ่มโดยไม่ช่วยการตัดสินใจ การเลือกระดับความซับซ้อนของ representation จึงพิจารณาจากข้อผิดพลาดที่ต้องแก้ ก่อนศึกษาวิธีปรับพารามิเตอร์ในบทถัดไป

$$
f(s_A)=f(s_B),\qquad y_A\ne y_B
$$

เงื่อนไขข้างต้นทำให้ผลลัพธ์สองรายการนี้แยกเป้าหมายทั้งคู่ไม่ได้

$$
g(f(s_A)),\qquad g(f(s_B))
$$

g คือ deterministic predictor และ y คือคำตอบเป้าหมาย; ข้อจำกัดนี้เกิดจากข้อมูลที่สูญหายก่อนถึง g

**ความหมายของสมการ:** เมื่อ encoder ให้ค่าเดียวกันแก่สอง state predictor แบบ deterministic ที่รับเฉพาะค่านั้นจะให้ผลเหมือนกัน จึงไม่สามารถตอบเป้าหมายที่ต่างกันให้ถูกทั้งคู่ได้

**อ่านสัญลักษณ์:**

- **f(s_A)=f(s_B):** สอง state มี representation เดียวกัน
- **y_A≠y_B:** เป้าหมายที่ถูกต้องของสองกรณีมีค่าต่างกัน
- **g:** predictor แบบ deterministic ที่ได้รับเฉพาะ output ของ f

**ตัวอย่างการคำนวณ:** สมมติ state A มี hunger=0.8, threat=0 และควร eat; state B มี hunger=0.8, threat=1 และควร hide

1. ถ้า encoder เก็บเฉพาะ hunger ทั้ง A และ B จะกลายเป็น z=0.8
2. ถ้า g(0.8)=eat จะถูก A แต่ผิด B; ถ้าเปลี่ยนให้เป็น hide จะสลับกรณีที่ผิด
3. เมื่อ A/B พบเท่ากัน และไม่มีข้อมูลอื่นเข้ามา predictor จึงทำถูกได้มากสุด 1 จาก 2 กรณี หรือ 50%

**ผลที่ได้:** การเพิ่มรอบคำนวณให้ g โดยยังเห็นเพียง 0.8 ไม่สร้างข้อมูล threat ที่ถูกตัดทิ้งกลับมา

**ข้อสรุปจากตัวอย่าง:** การแก้ state aliasing ต้องใช้ข้อมูลที่แยกกรณีได้ เช่น threat หรือ observation เพิ่มเติม

### นิยามที่ใช้ในบทนี้

- **state abstraction:** การรวมสถานะโดยรักษาข้อมูลที่จำเป็นต่อ reward, transition หรือเป้าหมายที่กำหนด
- **state aliasing:** การแทนสถานะที่ต้องตัดสินใจต่างกันด้วย representation เดียวกัน
- **invariance / equivariance:** การคงค่า representation หรือการเปลี่ยนค่าอย่างสอดคล้องกับกฎ เมื่อมีการแปลง input
- **Jacobian:** เมทริกซ์อนุพันธ์ที่อธิบายความไวเฉพาะที่ของ output ต่อแต่ละมิติของ input

### ทดลองกลไก

**ขั้นตอนการทดลอง:** ปิด threat และคงสีเสื้อไว้ ตรวจสอบ state A/B แล้วเปิด threat และปิดสีเสื้อเพื่อเปรียบเทียบผล

**ประเด็นที่ศึกษา:** เปรียบเทียบจำนวนกลุ่มที่มี action เป้าหมายขัดกันกับจำนวนกลุ่มทั้งหมด

**ขอบเขตของแบบจำลอง:** ห้องทดลองใช้ projection ที่กำหนดด้วยมือเพื่อแสดง state aliasing โดยตรง ไม่มีการฝึก representation และผลสาธิตไม่ได้พิสูจน์ bisimulation ของระบบจริง

### ตรวจความเข้าใจก่อนต่อยอด

ในกรณีที่ encoder รวมสอง state ซึ่งมี action ที่ถูกต้องต่างกัน การเพิ่ม recurrent passes ให้ policy ช่วยได้ภายใต้เงื่อนไขใด?

<details>
<summary>แนวคำตอบ</summary>

ช่วยได้เมื่อรอบการคำนวณเข้าถึงข้อมูลเพิ่มเติมที่แยกสอง state ได้ หรือเมื่อ representation ยังมีสัญญาณดังกล่าวแต่ policy ยังใช้งานไม่ได้ หากทุก pass รับข้อมูลเหมือนกันและไม่มีข้อมูลเพิ่ม การคำนวณซ้ำไม่สามารถกู้ข้อมูลที่ encoder ตัดออกไปแล้วได้

**ข้อสรุป:** คุณภาพของ representation ขึ้นกับการรักษาความแตกต่างที่จำเป็นต่องาน ส่วนขนาด latent และ geometry เป็นข้อมูลประกอบการวิเคราะห์

## บท 2 — Attention, weights และขอบเขตของการปรับโมเดล

[เปิดบทพร้อมห้องทดลอง](../index.html#story/07) · [หัวข้อสังเคราะห์](topics/07-training-and-model-architecture.md)

**คำถามหลัก:** การลดจำนวนพารามิเตอร์ที่ฝึกส่งผลต่อ computation และความสามารถของโมเดลอย่างไร?

**ความเข้าใจที่นำมาใช้:** เมื่อใช้ z แทนข้อมูลที่เกี่ยวข้องกับงานแล้ว การวิเคราะห์โมเดลต้องแยก activation ที่เกิดจาก input ออกจากพารามิเตอร์ที่ใช้สร้าง activation

- [บท 1](#chapter-01): representation และข้อจำกัดจากการสูญหายของข้อมูล

### โจทย์

คำว่า one layer, low rank และ frozen model อ้างถึงองค์ประกอบต่างกันของ computational graph การพิจารณา tensor shape และเส้นทาง gradient จึงจำเป็นต่อการระบุต้นทุนที่ลดลงจริง

### 2.1 มิติและบทบาทของเทนเซอร์ใน attention

กำหนด H ∈ ℝ^(T×d) เป็นเมทริกซ์ activation ที่มีหนึ่งแถวต่อ token โดย T คือ sequence length และ d คือ model width สำหรับ attention หนึ่ง head กำหนด W_Q,W_K ∈ ℝ^(d×d_k) และ W_V ∈ ℝ^(d×d_v) จึงได้ Q,K ขนาด T×d_k และ V ขนาด T×d_v

QK⊤ มีขนาด T×T โดยแถว i ให้คะแนนความเข้ากันได้ระหว่าง query ตำแหน่ง i กับ key ทุกตำแหน่ง หลังปรับสเกลและทำ softmax ตามแถว น้ำหนักแต่ละแถวรวมเป็นหนึ่งและใช้ผสม V ได้ผลขนาด T×d_v ส่วน mask M มีค่า 0 ในตำแหน่งที่อนุญาตและ −∞ ในตำแหน่งที่ห้ามใช้

Projection weights และพารามิเตอร์อื่นใน θ เป็นค่าที่ปรับระหว่างการฝึก ขณะที่ H,Q,K,V เป็น activation ที่ขึ้นกับ input ในการคำนวณครั้งนั้น Attention weight สูงระบุอิทธิพลต่อการผสมข้อมูลตามกลไกดังกล่าว แต่ยังไม่รับรองความจริงของข้อมูลหรือความถูกต้องของ action

$$
Q=HW_Q,\qquad K=HW_K
$$

$$
V=HW_V
$$

ใช้ convention ที่ activation แต่ละ token เป็นแถว; batch และ head อื่นละไว้เพื่อให้เห็น shape

**ความหมายของสมการ:** ผลคูณของ activation แต่ละ token กับ projection matrices สามชุดให้ query, key และ value สำหรับการคำนวณ attention

**อ่านสัญลักษณ์:**

- **H:** เมทริกซ์ที่แต่ละแถวเป็น activation ของหนึ่ง token
- **W_Q, W_K, W_V:** projection weights ที่เรียนระหว่าง training และนำมาใช้กับ input ปัจจุบัน
- **HW_Q:** คูณแต่ละแถวของ H กับ W_Q เพื่อได้แถว query ที่ตรงกัน

**ตัวอย่างการคำนวณ:** ตัวอย่างหนึ่ง head มี 2 token และทุกมิติเท่ากับ 2: H=[[1,0],[0,1]], W_Q=W_K=[[1,0],[0,1]], W_V=[[2,0],[0,4]]

1. คูณ H กับ W_Q: แถวแรก [1,0] ยังคงเป็น [1,0] และแถวที่สองเป็น [0,1] จึงได้ Q=[[1,0],[0,1]]
2. คูณกับ W_K แบบเดียวกัน ได้ K=[[1,0],[0,1]]
3. คูณกับ W_V ได้ V=[[2,0],[0,4]]: token แรกถือ value [2,0] และ token ที่สองถือ [0,4]

**ผลที่ได้:** Q, K และ V ล้วนมีขนาด 2×2 ในตัวอย่างนี้ แต่ทำหน้าที่คนละอย่าง; สมการถัดไปจะใช้ผลทั้งสามชุดนี้ต่อ

**ข้อสรุปจากตัวอย่าง:** Projection weights เป็นพารามิเตอร์ ส่วน Q/K/V เป็น activation ที่เปลี่ยนตาม H ของ input ปัจจุบัน

$$
O=\operatorname{softmax}_{\mathrm{rows}}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}+M\right)V
$$

$$
O\in\mathbb{R}^{T\times d_v}
$$

M เป็น mask ขนาด T×T ที่ broadcast ได้; ใน causal attention ตำแหน่งอนาคตจะถูกปิด

**ความหมายของสมการ:** Dot product ของ query กับ key ให้คะแนนซึ่งปรับสเกลและ mask ก่อนทำ softmax ตามแถว แล้วใช้ค่าน้ำหนักที่ได้ผสม value

**อ่านสัญลักษณ์:**

- **QK⊤:** transpose เปลี่ยนแถว key เป็นคอลัมน์ เพื่อหา dot product ของทุกคู่ query–key
- **√d_k:** หารด้วยรากที่สองของมิติ key เพื่อปรับสเกลคะแนน
- **softmax_rows:** ทำ softmax แยกแต่ละแถว ให้น้ำหนักที่ไม่ติดลบและรวมเป็น 1
- **M:** mask: บวก 0 เมื่ออ่านได้ และ −∞ เมื่อห้ามอ่าน

**ตัวอย่างการคำนวณ:** ใช้ Q=K=[[1,0],[0,1]], V=[[2,0],[0,4]] จากตัวอย่างก่อน และ d_k=2; เริ่มจากไม่มีตำแหน่งต้องห้าม

1. สำหรับ token แรก dot product กับสอง key คือ [1,0]; หาร √2 แล้วได้ประมาณ [0.707,0]
2. softmax ใช้ [exp(0.707),exp(0)]≈[2.028,1] แล้วหารผลรวม 3.028 จึงได้ประมาณ [0.670,0.330]
3. ผสม value: 0.670×[2,0]+0.330×[0,4]≈[1.34,1.32]; นี่คือ output ของแถวแรก
4. หากใช้ causal mask token แรกอ่าน token ที่สองไม่ได้: คะแนนเป็น [0.707,−∞], น้ำหนักเป็น [1,0] และ output เป็น [2,0]

**ผลที่ได้:** กรณีไม่มี mask ได้ O≈[[1.34,1.32],[0.66,2.68]] ขนาด 2×2; ส่วนตัวอย่าง causal mask ข้างต้นเปลี่ยนเฉพาะแถวแรกให้เป็น [2,0] ค่าทศนิยมปัดเศษเพื่ออ่านง่าย

**ข้อสรุปจากตัวอย่าง:** Attention ผสม value ตามน้ำหนักจาก query/key และ mask โดยน้ำหนักที่สูงไม่ใช่หลักฐานยืนยันความจริงของ value

### 2.2 LoRA และข้อจำกัดของ subspace สำหรับ weight update

สำหรับ linear layer ใช้ convention เวกเตอร์คอลัมน์ y = Wh โดย W ∈ ℝ^(d_out×d_in) LoRA ตรึง W และฝึก A ∈ ℝ^(r×d_in) กับ B ∈ ℝ^(d_out×r) ส่วนปรับ ΔW = (α/r)BA มี rank ไม่เกิน r โดย α เป็นค่าขยายที่กำหนดแยกจาก rank

Adapter มีพารามิเตอร์ r(d_in+d_out) ค่า เทียบกับ d_out d_in ค่าของ W แต่ฐาน W ยังคงเป็นส่วนหนึ่งของ forward เมื่อคำนวณ adapter แยกจะใช้ทั้ง Wh และ B(Ah) ส่วน deployment ที่รองรับสามารถรวม W+ΔW ก่อนใช้งานได้ การรายงานเวลาจึงต้องระบุรูปแบบการคำนวณที่วัด

สำหรับ W ขนาด 16×24 ฐานมี 384 พารามิเตอร์ เมื่อ r=4 adapter มี 160 ค่า ส่วน r=12 มี 480 ค่า เงื่อนไขที่ adapter เล็กกว่าฐานคือ r<384/40=9.6 อย่างไรก็ตาม จำนวนพารามิเตอร์ยังไม่ระบุคุณภาพ เนื่องจาก update ที่งานต้องการอาจอยู่นอก subspace ที่ rank ต่ำแทนได้

$$
y=(W+\Delta W)h
$$

$$
\Delta W=\frac{\alpha}{r}BA
$$

$$
\operatorname{rank}(\Delta W)\le r
$$

h ∈ ℝ^d_in; B มี shape d_out×r และ A มี shape r×d_in; α/r คือ scaling convention ที่ใช้ที่นี่

**ความหมายของสมการ:** Output เป็นผลรวมของผลจาก weight ฐานกับส่วนปรับผ่าน A และ B โดยส่วนปรับมีตัวคูณ α/r

**อ่านสัญลักษณ์:**

- **ΔW:** ส่วนเปลี่ยนแปลงที่บวกเข้า weight ฐาน W
- **Ah แล้ว B(Ah):** ย่อเวกเตอร์จาก d_in เหลือ r ค่า แล้วขยายเป็น d_out ค่า
- **α/r:** ตัวคูณขนาด update; เปลี่ยน α ได้โดยไม่เปลี่ยน rank
- **rank(ΔW)≤r:** update มีจำนวนทิศทางอิสระได้ไม่เกิน r

**ตัวอย่างการคำนวณ:** สมมติ W=[[1,0],[0,1]], h=(2,3), r=1, α=2, A=[1,0] และ B=[[1],[2]]

1. ทางฐานให้ Wh=(2,3)
2. ทาง adapter ให้ Ah=2 แล้ว B(Ah)=(2,4); คูณ α/r=2 ได้ส่วนปรับ (4,8)
3. เมทริกซ์ปรับคือ ΔW=2BA=[[2,0],[4,0]] ซึ่งมี rank=1 เพราะแถวสองเป็นสองเท่าของแถวแรก
4. รวมผลสองทาง: y=(2,3)+(4,8)=(6,11)

**ผลที่ได้:** ได้ output ใหม่ (6,11) โดยฐาน W คงเดิม และส่วนปรับส่งผลผ่านทิศทางอิสระเพียงหนึ่งทิศทาง

**ข้อสรุปจากตัวอย่าง:** Rank r จำกัดโครงสร้างของ update ส่วน α/r กำหนดขนาดของ update จึงมีบทบาทต่างกัน

$$
\frac{\mathrm{adapter}}{\mathrm{base}}=\frac{r(d_{\mathrm{in}}+d_{\mathrm{out}})}{d_{\mathrm{in}}d_{\mathrm{out}}}
$$

อัตราส่วนจำนวนพารามิเตอร์ของเมทริกซ์นี้ ไม่รวม bias, layer อื่น หรือ optimizer state

**ความหมายของสมการ:** อัตราส่วนได้จากผลรวมจำนวนพารามิเตอร์ใน A และ B หารด้วยจำนวนพารามิเตอร์ของ W

**อ่านสัญลักษณ์:**

- **r(d_in+d_out):** จำนวนค่าใน A คือ r·d_in บวกจำนวนค่าใน B คือ d_out·r
- **d_in d_out:** จำนวนค่าของเมทริกซ์ฐาน W
- **adapter/base:** อัตราส่วน; 0.5 หมายถึง adapter มีพารามิเตอร์ครึ่งหนึ่งของฐาน

**ตัวอย่างการคำนวณ:** ใช้ linear layer ที่ d_in=24 และ d_out=16 โดยนับเฉพาะเมทริกซ์นี้ ไม่รวม bias หรือ optimizer state

1. ฐานมี 16×24=384 ค่า
2. ถ้า r=4: A มี 4×24=96 ค่า, B มี 16×4=64 ค่า รวม 160; อัตราส่วน 160/384≈0.417 หรือ 41.7%
3. ถ้า r=12: adapter มี 12×(24+16)=480 ค่า; อัตราส่วน 480/384=1.25 หรือ 125%

**ผลที่ได้:** rank 4 ใช้พารามิเตอร์ adapter น้อยกว่าฐาน แต่ rank 12 ใน shape นี้มี adapter ใหญ่กว่าฐานแล้ว

**ข้อสรุปจากตัวอย่าง:** การเปรียบเทียบขนาด adapter ต้องใช้ shape และ rank ที่กำหนด และยังต้องรวม weight ฐานในการคำนวณ

### 2.3 Trainable parameters และ execution graph

การฝึกหนึ่ง layer กำหนด subset ของ θ ที่รับ update ส่วน layer อื่นอาจยังต้องทำ forward และส่ง gradient ผ่าน activation ไปยังส่วนที่ฝึก การลด trainable parameters จึงลดพื้นที่ gradient และ optimizer state บางส่วนได้ แต่ต้นทุนทั้งหมดไม่ได้ลดตามสัดส่วนเดียวกัน

Architecture กำหนดโครงสร้าง computation ขณะที่ optimizer กำหนดวิธีปรับ θ การอ่านงานเกี่ยวกับ attention variants และ Muon จึงต้องแยกสององค์ประกอบนี้ รวมถึงขั้น data generation, training, checkpoint transfer และ inference เพื่อประเมินขอบเขตผลที่รายงานในแต่ละ phase

แนวทาง operator/compression เช่น HOPE พิจารณาว่าส่วนใดของ learned function แทนด้วย subspace ที่เล็กลงได้ การประมาณ W ด้วย rank ต่ำอาจรักษาผลเฉลี่ยของ output แต่กระทบ rare case จึงต้องประเมิน behavior ที่สนใจหลัง compression เพิ่มเติมจากการนับพารามิเตอร์

$$
\theta_{\mathrm{train}}\subseteq\theta
$$

ไม่ได้กำหนดจำนวน layer ที่ forward ต้องผ่าน

θ_train คือพารามิเตอร์ที่ optimizer อัปเดต; execution graph เป็นอีกข้อกำหนดหนึ่ง

**ความหมายของสมการ:** ชุดพารามิเตอร์ที่ optimizer อัปเดตเป็น subset ของ θ ส่วน forward คำนวณตาม execution graph ซึ่งอาจยังใช้พารามิเตอร์ที่ตรึงไว้

**อ่านสัญลักษณ์:**

- **θ_train:** ชุดพารามิเตอร์ที่อนุญาตให้ optimizer เปลี่ยน
- **⊆:** เป็นส่วนหนึ่งของชุดใหญ่กว่า ไม่ใช่การลบส่วนอื่นออกจากโมเดล
- **forward:** การคำนวณจาก input ไปยัง output ซึ่งยังใช้ weight ที่ frozen ได้

**ตัวอย่างการคำนวณ:** สมมติเครือข่าย scalar มี 3 layer ต่อกัน: x=1, w₁=2, w₂=3, w₃=4 และฝึกเฉพาะ w₂

1. θ={w₁,w₂,w₃} แต่ θ_train={w₂}; นี่คือความสัมพันธ์ของชุดพารามิเตอร์ ไม่ใช่สูตรนับจำนวน layer
2. forward ยังผ่านครบสามขั้น: 1×2=2 → 2×3=6 → 6×4=24
3. ถ้าหลังอัปเดต w₂ เปลี่ยนเป็น 2.5, forward ใหม่เป็น 1×2=2 → 2×2.5=5 → 5×4=20

**ผลที่ได้:** ฝึกเพียงหนึ่ง weight แต่ทั้งสาม layer ยังอยู่ในเส้นทางคำนวณ รวมถึง w₁ และ w₃ ที่ไม่เปลี่ยนค่า

**ข้อสรุปจากตัวอย่าง:** จำนวน trainable parameters อธิบายต้นทุน training บางส่วน ส่วนเวลาคำนวณต้องพิจารณา execution graph ร่วมด้วย

### 2.4 การปรับ activation ระหว่าง inference เมื่อ θ คงที่

การตรึง θ ยังอนุญาตให้ปรับ latent z ของ input ปัจจุบันตาม objective หรือประมวลผล h ผ่าน block ซ้ำได้ ทั้งสองวิธีเพิ่ม computation ระหว่าง inference โดยไม่มี weight update แบบการฝึกโมเดล การอธิบายวิธีจึงต้องระบุ state ที่ปรับและการคง state นั้นข้าม request

การลด output entropy ทำให้ distribution กระจุกตัวมากขึ้น ตัวอย่างสองคลาสที่เปลี่ยนจาก (0.5,0.5) เป็น (0.99,0.01) มี entropy ลดจากประมาณ 0.693 เป็น 0.056 nats แต่หากคำตอบจริงคือคลาสที่สอง การเพิ่มความมั่นใจนี้กลับเพิ่มน้ำหนักให้คำตอบผิด

Capacity ของ weight update, compute สำหรับ input หนึ่งรายการ และเกณฑ์ตัดสิน correctness เป็นประเด็นที่ต้องประเมินแยกกัน หลังจากศึกษาสองประเด็นแรกแล้ว บทถัดไปพิจารณาโครงสร้างของ compute ที่เพิ่มขึ้นผ่าน recurrent hidden state และการขยายทางเลือกใน search tree

$$
z_{k+1}=z_k-\eta\nabla_z L(z_k;\theta_{\mathrm{fixed}})
$$

ตัวอย่าง inference-time latent optimization; η คือ step size และ L คือ objective ที่เลือก ซึ่งต้องตรวจว่าสัมพันธ์กับ task หรือไม่

**ความหมายของสมการ:** Latent ถูกอัปเดตในทิศตรงข้าม gradient ของ objective ด้วย step size η ขณะที่พารามิเตอร์ θ คงที่

**อ่านสัญลักษณ์:**

- **∇z L:** Gradient ต่อ z ระบุทิศที่ objective เพิ่มเร็ว ณ จุดปัจจุบัน
- **−η∇z L:** การเปลี่ยน z ในทิศตรงข้าม gradient โดย η กำหนด step size
- **θ_fixed:** พารามิเตอร์โมเดลที่คงที่ตลอด loop นี้
- **k+1:** ดัชนีรอบถัดไปของ latent สำหรับ input เดิม

**ตัวอย่างการคำนวณ:** สมมติ objective ที่ตรึงไว้คือ L(z)=(z−3)², เริ่ม z₀=1 และใช้ η=0.25

1. ที่ z₀=1 gradient คือ 2(1−3)=−4; จึงได้ z₁=1−0.25×(−4)=2
2. ที่ z₁=2 gradient คือ −2; จึงได้ z₂=2−0.25×(−2)=2.5
3. ค่า L ลดจาก (1−3)²=4 เป็น 1 แล้วเป็น 0.25 โดยเปลี่ยนเพียง z

**ผลที่ได้:** latent เคลื่อนจาก 1 → 2 → 2.5 เข้าใกล้จุดที่ objective ต่ำลง ส่วน θ ยังเป็นชุดเดิม

**ข้อสรุปจากตัวอย่าง:** การลด objective สำเร็จยังต้องมีหลักฐานว่า objective สัมพันธ์กับ correctness ของงาน

$$
H(p)=-\sum_i p_i\ln p_i
$$

entropy ใช้ natural log หน่วย nats; H ต่ำบอกการกระจุกของ distribution ไม่ได้ระบุว่าคลาสที่เดาถูก

**ความหมายของสมการ:** Entropy คือค่าลบของผลรวม p_i ln p_i สำหรับทุกทางเลือก ใช้ระบุความกระจายของความน่าจะเป็น

**อ่านสัญลักษณ์:**

- **p_i:** ความน่าจะเป็นของทางเลือก i; ทุกค่ารวมเป็น 1
- **Σ_i:** รวมผลของทุกทางเลือก
- **ln:** log ฐาน e; entropy ที่ได้ใช้หน่วย nats
- **−:** กลับเครื่องหมาย เพราะ log ของความน่าจะเป็นระหว่าง 0 กับ 1 เป็นลบ

**ตัวอย่างการคำนวณ:** เปรียบเทียบโมเดลสองคลาสก่อนและหลังปรับ latent โดยสมมติว่าคำตอบจริงคือคลาสที่สอง

1. เมื่อ p=(0.5,0.5), แต่ละเทอมคือ 0.5×ln(0.5)≈−0.3466; รวมแล้วกลับเครื่องหมายได้ H≈0.6931 nats
2. เมื่อ p=(0.99,0.01), สองเทอมประมาณ −0.00995 และ −0.04605; จึงได้ H≈0.0560 nats
3. แม้ entropy ลด โมเดลกลับให้น้ำหนัก 0.99 กับคลาสแรกที่ผิดในตัวอย่างนี้

**ผลที่ได้:** H ลดจากประมาณ 0.693 เป็น 0.056 แสดงว่า distribution กระจุกตัวมากขึ้น แต่คลาสที่มีความน่าจะเป็นสูงอาจเป็นคำตอบผิด

**ข้อสรุปจากตัวอย่าง:** Entropy อธิบายความกระจายของคำตอบ ส่วนความถูกต้องต้องประเมินด้วยเป้าหมายหรือ verifier ที่เหมาะกับงาน

### นิยามที่ใช้ในบทนี้

- **activation / parameter:** Activation เป็นค่าที่ขึ้นกับ input และรอบคำนวณ ส่วน parameter เป็นค่าสัมประสิทธิ์ของโมเดลที่ปรับระหว่างการฝึก
- **low-rank update:** ส่วนปรับเมทริกซ์ที่อยู่ใน subspace จำกัดและแทนด้วยผลคูณของเมทริกซ์สองตัวที่มีมิติร่วมขนาดเล็ก
- **execution graph:** ลำดับ operation สำหรับคำนวณ output รวมถึงองค์ประกอบที่มี weights คงที่
- **entropy:** ปริมาณที่อธิบายความกระจายของ probability distribution โดยไม่ระบุความถูกต้องของคำตอบ

### ทดลองกลไก

**ขั้นตอนการทดลอง:** ปรับ rank ตามลำดับ 1 → 4 → 8 → 12 แล้วคำนวณ r(16+24) และตรวจสอบ B, A และ ΔW ที่แสดง โดยห้องทดลองกำหนด α=8

**ประเด็นที่ศึกษา:** เปรียบเทียบ shape ของ factors และจำนวนพารามิเตอร์ตาม r พร้อมพิจารณาว่า scaling α/r ลดลงเมื่อ r เพิ่ม ความเข้มของ heatmap จึงไม่ใช่ตัววัดคุณภาพหรือ rank โดยตรง

**ขอบเขตของแบบจำลอง:** ห้องทดลองคำนวณ ΔW=(8/r)BA จาก factors สังเคราะห์เพื่อแสดง rank(ΔW)≤r และจำนวนพารามิเตอร์ ไม่มีการฝึกหรือวัด task accuracy และ full backbone ยังคงอยู่ใน computation

### โจทย์

Latent reasoning ครอบคลุมหลายกลไก การวิเคราะห์ต้องระบุว่า compute ที่เพิ่มใช้ปรับ representation, ขยาย action branch หรือตัดทางเลือกที่ไม่ผ่านเงื่อนไข

### 3.1 Recurrent depth และการใช้พารามิเตอร์ร่วมกัน

กำหนด h_0 จาก z แล้วคำนวณ h_(k+1)=Fθ(h_k,z) จำนวน K รอบ ก่อน decode h_K เป็นคำตอบ โดย k นับรอบคำนวณของ input เดิม ส่วน t นับตำแหน่ง token หรือเวลาของสิ่งแวดล้อม การเพิ่ม k จึงไม่จำเป็นต้องสร้าง token ใหม่ทุกครั้ง

เมื่อทุก pass ใช้ θ ชุดเดียวกัน จำนวนพารามิเตอร์ไม่เพิ่มตาม K แต่จำนวน operation และเวลาโดยประมาณยังเพิ่มขึ้น การส่ง z ให้แต่ละ pass ช่วยให้ update เข้าถึงข้อมูลตั้งต้นโดยไม่พึ่ง h เพียงอย่างเดียว ส่วนความสามารถในการใช้จำนวนรอบต่างกันขึ้นกับ architecture และ training recipe

Recurrent update อาจใช้ forward computation เพียงอย่างเดียว ขณะที่ latent optimization ในบทก่อนใช้ gradient ต่อ z ด้วย ทั้งสองเปลี่ยน activation โดย θ คงที่ แต่มีต้นทุนต่อรอบและกระบวนการฝึกต่างกัน

$$
h_{k+1}=F_{\theta}(h_k,z)
$$

$$
p(y\mid x)=\operatorname{softmax}(g_{\theta}(h_K))
$$

Fθ คือ recurrent block และ gθ คือ output head; K เป็นงบภายในของ input เดียว

**ความหมายของสมการ:** Block ที่ใช้พารามิเตอร์ร่วมกันอัปเดต hidden state โดยรับ representation ของ input เดิม ก่อน output head แปลง state สุดท้ายเป็นความน่าจะเป็นของคำตอบ

**อ่านสัญลักษณ์:**

- **Fθ:** block สำหรับอัปเดต state โดยใช้พารามิเตอร์ θ ชุดเดิมทุก pass
- **k, K:** k คือรอบปัจจุบัน ส่วน K คือจำนวนรอบทั้งหมดที่ใช้กับ input นี้
- **gθ(h_K):** output head ที่แปลง hidden state สุดท้ายเป็นคะแนนก่อน softmax
- **p(y|x):** การกระจายของคำตอบเมื่อรับ input x

**ตัวอย่างการคำนวณ:** ตัวอย่าง scalar: z=2, h₀=0, F(h,z)=(h+z)/2, K=2 และ output head ให้ logits=[h,0]

1. รอบแรก h₁=(0+2)/2=1 โดย z ยังเท่ากับ 2
2. รอบสอง h₂=(1+2)/2=1.5; ใช้สูตรเดิมกับ h ที่เปลี่ยนไป
3. เมื่อครบ K=2 ได้ logits=[1.5,0]; softmax ให้ประมาณ [0.818,0.182] เพราะ exp(1.5)≈4.482 แล้วหารด้วย 4.482+1

**ผลที่ได้:** โมเดลใช้สอง pass เพื่อเปลี่ยน activation จาก 0 → 1 → 1.5 แล้วจึงออกคำตอบ โดยไม่เพิ่มชุด weight ตามจำนวนรอบ

**ข้อสรุปจากตัวอย่าง:** การใช้ θ ร่วมกันคงจำนวนพารามิเตอร์ไว้ แต่แต่ละ pass ยังมีต้นทุน computation และอาจเปลี่ยนผลลัพธ์

$$
T_{\mathrm{total}}\approx T_{\mathrm{encode}}+K\,T_{\mathrm{pass}}+T_{\mathrm{decode}}
$$

แบบจำลองแบบเรียงลำดับที่เวลาต่อ pass ใกล้เคียงกัน; ต้องรวม backward ด้วยหาก pass ใช้ gradient

**ความหมายของสมการ:** เวลารวมโดยประมาณประกอบด้วยเวลา encode, เวลา pass ที่ทำซ้ำ K ครั้ง และเวลา decode

**อ่านสัญลักษณ์:**

- **K·T_pass:** จำนวน pass คูณเวลาต่อ pass โดยสมมติว่าทำเรียงกันและแต่ละรอบใช้เวลาใกล้เคียงกัน
- **T_encode, T_decode:** ต้นทุนก่อนเข้า loop และหลังออกจาก loop
- **≈:** แบบจำลองเวลาโดยประมาณ; ค่าใช้จ่ายจริงต้องตรงกับขอบเขตที่นับ

**ตัวอย่างการคำนวณ:** สมมติเวลาที่วัดในขอบเขตนี้คือ encode=3 ms, pass=2 ms และ decode=1 ms โดยไม่มีการรัน pass ซ้อนกัน

1. ถ้า K=4 เวลาของ loop คือ 4×2=8 ms
2. บวกต้นทุนหน้าและท้าย: T_total≈3+8+1=12 ms
3. ถ้าเพิ่ม K เป็น 8 จะได้ 3+8×2+1=20 ms; เพิ่ม 4 pass จึงเพิ่มเวลาประมาณ 8 ms

**ผลที่ได้:** จำนวนรอบเพิ่มสองเท่า แต่เวลารวมจาก 12 เป็น 20 ms เพราะ encode/decode เป็นต้นทุนที่จ่ายครั้งเดียว

**ข้อสรุปจากตัวอย่าง:** T_pass ต้องรวม backward หากแต่ละ pass ใช้ gradient และขอบเขตการจับเวลาต้องระบุว่ารวม queue หรือ network หรือไม่

### 3.2 Convergence, เกณฑ์หยุด และความถูกต้อง

Fixed point คือ h* ที่ทำให้ Fθ(h*,z)=h* ตัวอย่าง scalar หรือ vector F(h)=0.5h+0.5b เป็น contraction ซึ่งลดระยะระหว่าง input สองค่าเหลือครึ่งหนึ่งหลังผ่าน F จึงลู่เข้าสู่ b โดย error ลดครึ่งทุก pass แม้จะคำนวณจำนวนรอบที่ทำให้ error ต่ำกว่าเกณฑ์ได้ แต่สูตร update ไม่ได้กำหนดให้ b เป็นคำตอบของโจทย์

เกณฑ์ ∥h_(k+1)−h_k∥<ε ตรวจการเปลี่ยนแปลงของ state ตาม scale และ norm ที่กำหนด การเปลี่ยนแปลงที่น้อยอาจเกิดที่ fixed point ผิด, plateau หรือ state ที่ไม่ช่วยงาน จึงต้องประเมิน output validity แยก โดย validity หมายถึงการผ่านข้อกำหนดของโจทย์ที่ตรวจสอบได้

ระบบใช้งานจึงต้องกำหนด budget K_max, เกณฑ์หยุด และสถานะเมื่อยังยืนยันคำตอบไม่ได้ เช่น unresolved การเพิ่ม K ต้องประเมินทั้งคุณภาพบนโจทย์ยากและเวลาที่เพิ่มขึ้นในโจทย์ง่าย

$$
F(h)=0.5h+0.5b
$$

$$
\Longrightarrow\quad h_K-b=2^{-K}(h_0-b)
$$

ตัวอย่างแสดงการลู่เข้าสู่ b อย่างชัดเจน; ความถูกของ b เป็นอีกเงื่อนไขหนึ่ง

**ความหมายของสมการ:** Update แต่ละรอบให้ state เป็นค่ากึ่งกลางระหว่างค่าปัจจุบันกับ b ทำให้ error เทียบกับ b ลดลงครึ่งหนึ่งทุกครั้ง

**อ่านสัญลักษณ์:**

- **b:** Fixed point ที่ update นี้ลู่เข้า
- **h_K−b:** Error แบบมีเครื่องหมายหลังคำนวณ K รอบ
- **2^(−K):** อัตราส่วน error ที่เหลือเทียบกับค่าเริ่มต้น มีค่าเท่ากับ 1/2^K
- **⇒:** ความสัมพันธ์ของ error ที่ได้จากสูตร update ในตัวอย่างนี้

**ตัวอย่างการคำนวณ:** กำหนด h₀=0 และ b=8; นี่เป็น toy update ที่คำนวณเส้นทางได้แน่นอน

1. ใช้ F ซ้ำ: h₁=4, h₂=6 และ h₃=7; ระยะถึง 8 ลดจาก 8 → 4 → 2 → 1
2. ตรวจสูตรเมื่อ K=3: h₃−8=2^(−3)×(0−8)=−1 จึงได้ h₃=7 ตรงกัน
3. เมื่อ K=6 error เหลือ −8/64=−0.125 จึงได้ h₆=7.875

**ผลที่ได้:** state เข้าใกล้ 8 ตามอัตราที่คำนวณได้ แต่ถ้าคำตอบจริงของ task คือ 10 loop นี้ก็ยังลู่เข้าสู่ค่าที่ผิด

**ข้อสรุปจากตัวอย่าง:** Convergence ระบุพฤติกรรมการลู่เข้า ส่วนความถูกต้องขึ้นกับการที่จุดปลายทางสอดคล้องกับเป้าหมายของงาน

หยุด (stop) เมื่อเงื่อนไขต่อไปนี้เป็นจริง หรือ budget หมด

$$
\operatorname{validity}(y)=\mathrm{true}
$$

stability เป็นสัญญาณประกอบ

validity ต้องนิยามตาม task; ถ้าตรวจได้เพียงบางเงื่อนไข ให้ระบุว่าการผ่านครอบคลุมอะไร

**ความหมายของสมการ:** Loop หยุดเมื่อคำตอบผ่าน validity หรือเมื่อ budget หมด โดยสองกรณีต้องมีสถานะผลลัพธ์ต่างกัน

**อ่านสัญลักษณ์:**

- **validity(y)=true:** คำตอบผ่านข้อกำหนดที่ verifier ตรวจสอบ
- **หรือ:** เงื่อนไข OR ซึ่งเป็นจริงเมื่อมีอย่างน้อยหนึ่งเงื่อนไขเป็นจริง
- **budget:** ขีดจำกัดทรัพยากร เช่น จำนวนรอบ เวลา หรือจำนวน model calls
- **stability:** การเปลี่ยนแปลงของผลลัพธ์ที่ลดลง ใช้เป็นข้อมูลประกอบ validity

**ตัวอย่างการคำนวณ:** ตัวอย่าง solver สร้าง candidate ทีละรอบ: ต้องตอบจำนวนเต็มที่ยกกำลังสองได้ 9 และมีงบมากสุด 3 รอบ

1. รอบแรกเสนอ 2; ตรวจ 2²=4 จึงยังไม่ผ่าน และงบยังเหลือ
2. รอบสองเสนอ 2 อีกครั้ง; output ซ้ำบอกว่ายังไม่เปลี่ยน แต่เงื่อนไข 2²=9 ยังเป็นเท็จ
3. ถ้ารอบสามเสนอ 3 จะผ่าน 3²=9 และคืนคำตอบ; ถ้ายังไม่มี candidate ผ่านเมื่อครบสามรอบ ให้หยุดพร้อมสถานะ unresolved

**ผลที่ได้:** loop หยุดได้ทั้งเพราะสำเร็จและเพราะทรัพยากรหมด จึงต้องเก็บเหตุผลการหยุดไว้ด้วย

**ข้อสรุปจากตัวอย่าง:** เกณฑ์หยุดและสถานะผลลัพธ์ต้องแยกกัน เพื่อไม่รวม timeout หรือ output ที่คงเดิมเป็นคำตอบที่ผ่านการตรวจ

### 3.3 Explicit search และการจัดลำดับทางเลือก

Explicit search เก็บ node ที่แทน state หรือ partial solution แล้วขยาย action ไปยัง node ใหม่ BFS ขยายตามจำนวน edge จากจุดเริ่ม จึงรับรอง shortest path ในกราฟที่ทุก edge มีต้นทุนเท่ากัน ส่วน greedy best-first จัดลำดับตามค่าประมาณระยะถึง goal

ในกราฟจำกัดที่จัดการ visited ถูกต้องและไม่มี budget ตัดจบ greedy สามารถสำรวจจนพบเส้นทางที่มีอยู่ได้ แต่ไม่มี shortest-path guarantee แบบ BFS เมื่อจำกัด budget ลำดับขยายจึงส่งผลต่อ solve rate และคุณภาพของเส้นทางที่พบ

PUCT ใช้ learned prior และ value ในการเลือกกิ่ง โดย P(s,a) เป็น prior ของ action, Q(s,a) เป็น return ที่ประเมินจาก search และ N(s,a) เป็นจำนวน visit ตัว Q ในบริบทนี้หมายถึง action value ของ search ซึ่งต่างจาก query tensor ใน attention

$$
\begin{aligned}a^{*}=\operatorname*{argmax}_{a}\Biggl[&Q(s,a)\\&{}+c\,P(s,a)\,\frac{\sqrt{\sum_b N(s,b)}}{1+N(s,a)}\Biggr]\end{aligned}
$$

รูปแบบคะแนน PUCT ที่ใช้กันทั่วไป; c คุม exploration และ b วิ่งผ่าน action ที่ node s; รายละเอียด initialization/backup ขึ้นกับ implementation

**ความหมายของสมการ:** PUCT เลือก action ที่มีผลรวม action value และ exploration bonus สูงสุด โดย bonus ขึ้นกับ prior และ visit count

**อ่านสัญลักษณ์:**

- **argmax_a:** คืน action ที่ได้คะแนนมากที่สุด ไม่ได้คืนตัวคะแนน
- **Q(s,a):** ค่า action ที่ประเมินจาก search; Q นี้ไม่ใช่ query ของ attention
- **c·P(s,a):** น้ำหนักของโบนัสสำรวจ: c คุมความแรง และ P คือ prior ของ action
- **N และ Σ_b N(s,b):** N นับการเยี่ยมแต่ละ action; Σ รวมทุก action ที่ node นี้

**ตัวอย่างการคำนวณ:** สมมติมี A/B: Q=(0.60,0.55), P=(0.60,0.40), N=(3,1) และ c=1

1. รวม visit ได้ 3+1=4 ดังนั้นรากที่สองในตัวเศษเท่ากับ 2
2. A ได้โบนัส 1×0.60×2/(1+3)=0.30; คะแนนรวม 0.60+0.30=0.90
3. B ได้โบนัส 1×0.40×2/(1+1)=0.40; คะแนนรวม 0.55+0.40=0.95
4. argmax จึงเลือก B ในรอบนี้ แม้ค่า Q ของ B ต่ำกว่า A เล็กน้อย

**ผลที่ได้:** โบนัสช่วยให้ action ที่ยังถูกลองน้อยมีโอกาสถูกสำรวจ; เมื่อ visit เปลี่ยน คะแนนรอบถัดไปต้องคำนวณใหม่

**ข้อสรุปจากตัวอย่าง:** PUCT รวม value กับ exploration bonus โดยความหมายของ visit และวิธี backup ต้องตรงกับ implementation

### 3.4 การประกอบกลไกและการเปรียบเทียบต้นทุน

Search สามารถใช้ policy/value model ที่มี recurrent block ได้ โดย recurrence เพิ่ม computation ในการประเมินแต่ละ node ส่วน tree เพิ่มจำนวนทางเลือกที่พิจารณา สำหรับโจทย์ที่มีกฎ pruning ตัด candidate ที่ไม่ผ่านเงื่อนไขก่อนขยายได้ โดยต้องรักษา candidate ที่ยังเป็นคำตอบได้

Flow-style refinement เป็นกลุ่มวิธีที่ฝึก update ให้ปรับ representation หรือ structured output ตาม recipe เฉพาะ เช่น การปรับตาม state ปัจจุบันและ noise การใช้ชื่อ flow กับ loop เพียงอย่างเดียวจึงไม่เพียงพออ้างผลของ Flow Reasoning Models หรือการรับประกัน convergence

การเปรียบเทียบด้วย budget wall-clock เท่ากันใช้ประเมินคุณภาพตามเวลาที่ใช้ ส่วน budget model calls หรือ node expansions เท่ากันช่วยศึกษาความต่างของกลไก หากต้องการตอบทั้งสองประเด็นควรรายงานทั้งสองรูปแบบ Maze lab ในบทนี้สาธิต search order โดยไม่มี neural scorer, recurrent model หรือ PUCT

budget = เวลา, model calls หรือ node expansions — ต้องเลือกและรายงานหน่วย

K เท่ากันไม่ได้หมายความว่า compute เท่ากัน ถ้า pass หรือ node evaluation มีต้นทุนต่างกัน

**ความหมายของสมการ:** Budget ต้องระบุหน่วยที่ใช้จำกัดการทดลอง ได้แก่ เวลา จำนวน model calls หรือจำนวน node expansions

**อ่านสัญลักษณ์:**

- **budget:** เพดานทรัพยากรที่การทดลองยอมใช้
- **model calls:** จำนวนครั้งที่เรียกโมเดล ซึ่งแต่ละครั้งอาจแพงไม่เท่ากัน
- **node expansions:** จำนวน node ที่ขยายใน search ซึ่งอาจมีหลาย model calls ต่อ node

**ตัวอย่างการคำนวณ:** สมมติวิธี A ใช้ 20 ms ต่อ model call และวิธี B ใช้ 50 ms ต่อ call; ทุก call ทำเรียงกันและละต้นทุนอื่นไว้

1. ให้งบเท่ากันที่ 10 calls: A ใช้ 10×20=200 ms ส่วน B ใช้ 10×50=500 ms
2. หากเปลี่ยนเป็นงบเวลาเท่ากัน 200 ms: A ทำได้ 10 calls ส่วน B ทำได้ 4 calls
3. จากนั้นวัดคุณภาพคำตอบที่แต่ละวิธีทำได้ภายใต้งบที่เลือก พร้อมระบุว่าใช้ calls หรือ ms เป็นข้อจำกัด

**ผลที่ได้:** คำว่าใช้งบเท่ากันให้การทดลองคนละแบบได้ เพราะ 10 calls ไม่ได้เท่ากับเวลารันเท่ากัน

**ข้อสรุปจากตัวอย่าง:** หน่วย budget ต้องสอดคล้องกับประเด็นประเมิน โดยเวลาอธิบายต้นทุนใช้งาน ส่วน calls หรือ expansions ช่วยอธิบายกลไก

### นิยามที่ใช้ในบทนี้

- **recurrence:** การนำ state ภายในกลับผ่าน update function เพื่อคำนวณ pass ถัดไป
- **fixed point:** state ที่คงเดิมเมื่อใช้ update function อีกครั้ง โดยคุณสมบัตินี้ไม่ได้ระบุความถูกต้องของคำตอบ
- **heuristic:** ค่าประมาณสำหรับจัดลำดับ candidate เช่น ระยะถึง goal
- **PUCT:** เกณฑ์เลือกกิ่งใน tree search ที่รวม action value, policy prior และ visit count

### ทดลองกลไก

### โจทย์

ข้อเสนอจากโมเดลกับ action ที่ระบบยอม execute มีเกณฑ์ต่างกัน การออกแบบต้องระบุ property ที่กลไกตรวจสอบแต่ละชั้นรับรอง

### 4.1 Syntax, type และ semantic validity

Pipeline propose → constrain → verify → commit แบ่งหน้าที่เป็นการเสนอ action หรือ structured answer, การจำกัด domain ของตัวเลือก, การตรวจข้อกำหนด และการเปลี่ยน state จริงตามลำดับ เมื่อ candidate ไม่ผ่านการตรวจ ระบบอาจค้นต่อหรือคืน unresolved

Schema ตรวจรูปแบบ เช่น action อยู่ใน enum ที่รองรับและ target มีชนิดข้อมูลถูกต้อง แต่ action Attack ที่ parse ได้อาจยังไม่ผ่านเงื่อนไข เพราะ target อยู่นอกระยะ, cooldown ยังไม่หมด หรือมีสิ่งกีดขวาง line of sight เงื่อนไขเหล่านี้ต้องตรวจในชั้นที่เข้าถึง state ของสิ่งแวดล้อม

ผลการตรวจต้องอ้างอิง state version ที่ใช้ execute หาก target อยู่ในระยะขณะตรวจแต่ state เปลี่ยนก่อน commit ข้อรับรองเดิมอาจใช้ไม่ได้ ระบบอาจใช้ snapshot, lock หรือ revalidation ตามบริบท โดยต้องระบุเวลาหรือเวอร์ชันที่คำว่า valid อ้างถึง

$$
\begin{aligned}\operatorname{accept}(a,s)={}&\operatorname{schema\ ok}(a)\\&{}\land\operatorname{preconditions}(a,s)\end{aligned}
$$

ตัวอย่าง acceptance predicate สำหรับ action a บน state s; มีผลเฉพาะเงื่อนไขที่นำมาเข้ารหัส

**ความหมายของสมการ:** Action ได้รับการยอมรับเมื่อผ่านทั้ง schema และ preconditions ของ state ที่ใช้ตรวจ

**อ่านสัญลักษณ์:**

- **schema_ok(a):** ชื่อ action, ฟิลด์ และชนิดข้อมูลตรง schema ที่ระบบรองรับ
- **preconditions(a,s):** เงื่อนไขก่อน execute action ซึ่งประเมินจาก state s เช่น ระยะหรือ cooldown
- **∧:** Logical AND ซึ่งกำหนดให้ทั้งสองเงื่อนไขเป็นจริง

**ตัวอย่างการคำนวณ:** สมมติ action คือ Attack(target_id=17), target อยู่ห่าง 5 เมตร แต่โจมตีได้ไกลสุด 3 เมตรและ cooldown=0

1. schema ผ่าน เพราะ Attack เป็น action ที่รองรับ และ target_id เป็นจำนวนเต็มตามที่กำหนด
2. preconditions ไม่ผ่าน เพราะแม้ cooldown พร้อม แต่ระยะ 5 เมตรเกินขอบเขต 3 เมตร
3. จึงได้ accept=true ∧ false=false: ระบบปฏิเสธ action นี้

**ผลที่ได้:** action ที่ parse ได้สมบูรณ์ยังถูกปฏิเสธได้เมื่อเงื่อนไขโลกไม่อนุญาตให้ทำ

**ข้อสรุปจากตัวอย่าง:** Preconditions ต้องครอบคลุมข้อกำหนดที่ต้องการรับรอง และ state version ต้องตรงกับการ execute

$$
s_{\mathrm{next}}=\operatorname{transition}(s,a)
$$

เฉพาะเมื่อ

$$
\operatorname{accept}(a,s)=\mathrm{true}
$$

postconditions ของ s_next อาจต้องตรวจเพิ่ม หาก transition ไม่ได้รับประกันไว้แล้ว

**ความหมายของสมการ:** Transition เปลี่ยน state เฉพาะเมื่อ action ผ่าน accept บน state ที่ใช้ execute ส่วน action ที่ถูกปฏิเสธไม่ถูก commit

**อ่านสัญลักษณ์:**

- **s_next:** State หลัง execute action สำเร็จ
- **transition(s,a):** กฎที่กำหนดการเปลี่ยน state จาก action a
- **เฉพาะเมื่อ:** Guard ที่ควบคุมการ execute ตามเงื่อนไข accept

**ตัวอย่างการคำนวณ:** สมมติ snapshot เวอร์ชัน 8 มี target HP=10, ระยะ=2 เมตร, โจมตีได้ไกลสุด 3 เมตร และ damage=4

1. ตรวจ action Attack บน snapshot นี้แล้วผ่าน ทั้งรูปแบบ ระยะ และเงื่อนไขอื่นที่กำหนด
2. commit โดยใช้ state เดียวกับที่ตรวจ: transition ลด HP จาก 10 เป็น 10−4=6
3. ถ้าอีกกรณีเริ่มจาก HP=10 แต่ระยะ=5 เมตร accept จะเป็น false จึงไม่ execute และ HP ยังเท่ากับ 10

**ผลที่ได้:** กรณีแรกได้ s_next ที่ HP=6; กรณีหลังไม่ใช้ transition ของ action ที่ถูกปฏิเสธ

**ข้อสรุปจากตัวอย่าง:** เมื่อ state เปลี่ยนระหว่างการตรวจและ commit ต้อง revalidate หรือรักษา snapshot ตามข้อรับรองที่กำหนด

### 4.2 Soundness, completeness และสมมติฐานของข้อรับรอง

กำหนด C เป็นเซต candidate assignment และ Ω เป็นเซตคำตอบที่ตรงข้อกำหนดทั้งหมด การที่ pruner P ลด C โดยรักษาคำตอบที่ถูกไว้เรียกว่า sound pruning ส่วน sound verifier หมายถึง candidate ทุกตัวที่ยอมรับเป็นสมาชิก Ω คำว่า sound จึงต้องระบุ operation ที่ประเมินร่วมด้วย

เมื่อ C เป็นเซตจำกัดและ P(C)⊆C การ prune ซ้ำย่อมถึงจุดที่เซตไม่เปลี่ยน แต่ fixed point อาจยังมี candidate ผิดหลายตัว หากกฎตรวจครอบคลุมเพียงบางเงื่อนไข มุมมอง candidate sets เป็น lattice ใช้ความสัมพันธ์ subset เพื่อจัดลำดับระดับการจำกัดข้อมูล โดยไม่ได้เพิ่มข้อกำหนดความถูกต้องให้ระบบ

Completeness ของ solver คือการพบคำตอบที่มีอยู่ภายใต้โดเมนและวิธีค้นที่ระบุ เช่น exhaustive backtracking ในโดเมนจำกัด เมื่อไม่ตัดคำตอบถูกและไม่มี timeout ข้อรับรองอาศัยสมมติฐานว่า initial domain ครอบคลุมคำตอบและ specification Ω ตรงกับปัญหาที่ต้องการ

$$
\Omega\cap C\subseteq P(C)\subseteq C
$$

sound pruning รักษาทุกคำตอบถูกที่ยังอยู่ใน C และไม่เพิ่ม candidate

**ความหมายของสมการ:** เซตหลัง prune ต้องเป็น subset ของ candidate ตั้งต้นและยังครอบคลุมคำตอบถูกทุกตัวที่อยู่ใน candidate ตั้งต้น

**อ่านสัญลักษณ์:**

- **Ω:** เซตของคำตอบที่ตรง specification ทั้งหมด
- **∩:** intersection: สมาชิกที่อยู่ในทั้งสองเซต
- **⊆:** เป็น subset: ทุกสมาชิกด้านซ้ายต้องอยู่ด้านขวา
- **P(C):** ชุด candidate ที่เหลือหลังใช้กฎ prune กับ C

**ตัวอย่างการคำนวณ:** ให้ C={a,b,c,d} และคำตอบถูกทั้งหมด Ω={b,d,e}; ตัวอักษรแต่ละตัวแทน candidate assignment หนึ่งชุด

1. คำตอบถูกที่มีอยู่ใน C คือ Ω∩C={b,d}; e ถูกเช่นกันแต่ไม่ได้อยู่ในชุดตั้งต้นนี้
2. สมมติ prune ลบ a ออก จึงเหลือ P(C)={b,c,d}
3. ตรวจ inclusion: {b,d}⊆{b,c,d}⊆{a,b,c,d}; ทั้งสองข้างผ่าน แม้ c ยังเป็น candidate ผิด

**ผลที่ได้:** Pruner รักษาคำตอบถูกที่มีอยู่ใน C แต่ไม่จำเป็นต้องกำจัด candidate ผิดทั้งหมดหรือเพิ่มคำตอบ e ที่อยู่นอก C

**ข้อสรุปจากตัวอย่าง:** Sound pruning รับรองการรักษาคำตอบถูกระหว่างตัดตัวเลือก ส่วน candidate ที่เหลือยังต้องค้นและตรวจเพิ่มเติม

$$
V(u)=\mathrm{accept}\quad\Longrightarrow\quad u\in\Omega
$$

soundness ของ verifier V ต่อ specification Ω; ไม่ได้แปลว่ามันยอมรับหรือค้นพบสมาชิก Ω ครบทุกตัว

**ความหมายของสมการ:** Candidate ทุกตัวที่ verifier ยอมรับต้องอยู่ใน Ω แต่เงื่อนไขนี้ยังอนุญาตให้ verifier ปฏิเสธคำตอบถูกบางตัวได้

**อ่านสัญลักษณ์:**

- **V(u)=accept:** verifier ยอมรับ candidate u
- **⇒:** ทุกกรณีที่ด้านซ้ายเกิด ด้านขวาต้องจริง
- **u∈Ω:** u เป็นสมาชิกของเซตคำตอบที่ตรง specification

**ตัวอย่างการคำนวณ:** ในโดเมน {1,2,3,4} กำหนดคำตอบถูกเป็นเลขคู่ จึงมี Ω={2,4}; verifier ตัวอย่างยอมรับเฉพาะเลข 4

1. ส่ง 4 เข้า V ได้ accept และ 4 อยู่ใน Ω จึงผ่านเงื่อนไขที่สมการต้องการ
2. ส่ง 1 หรือ 3 แล้วถูกปฏิเสธ จึงไม่มีเลขคี่หลุดเข้าไปเป็นคำตอบที่รับรอง
3. ส่ง 2 แล้วก็ถูกปฏิเสธ ทั้งที่ 2 อยู่ใน Ω: verifier นี้พลาดการยอมรับคำตอบถูกหนึ่งตัว

**ผลที่ได้:** verifier นี้ sound ต่อ specification ที่กำหนด แต่ไม่ complete เพราะไม่ได้ยอมรับสมาชิก Ω ครบ

**ข้อสรุปจากตัวอย่าง:** Soundness ของคำตอบที่ยอมรับและความครอบคลุมในการยอมรับหรือค้นคำตอบเป็นคุณสมบัติที่ต้องประเมินแยกกัน

### 4.3 ตัวอย่าง constraint propagation: Sudoku 4×4

แต่ละช่องมี domain {1,2,3,4} และห้ามเลขซ้ำในแถว คอลัมน์ และกล่อง 2×2 หากช่องหนึ่งมีเลข {1,3} ในแถว, {2} ในคอลัมน์ และ {1,2} ในกล่อง การตัดเลขที่ขัดกับเงื่อนไขออกจะเหลือ {4} ซึ่งเป็นค่าเดียวที่อนุญาตตามกฎเฉพาะที่เหล่านี้

หาก domain เหลือ {2,4} การเลือก 2 อาจผ่านกฎเฉพาะที่แต่ทำให้ช่องอื่นไม่มีค่าที่อนุญาตในขั้นถัดไป Local consistency จึงไม่เท่ากับการมี global completion ต้องใช้ propagation เพิ่มหรือ search พร้อม backtracking และตรวจทั้งกระดานก่อนรับเป็นคำตอบ

ห้องทดลองใช้กฎ candidate ที่ตรวจสอบได้โดยไม่มี neural solver ความสัมพันธ์กับ neuro-symbolic อยู่ที่การใช้ neural score จัดลำดับช่องหรือตัวเลขที่จะลอง ขณะที่กฎยังทำหน้าที่จำกัดตัวเลือกและตรวจผลสุดท้าย

$$
\begin{aligned}D_{i,j}={}&\{1,2,3,4\}\\&{}\setminus\bigl(\mathrm{Row}_i\cup\mathrm{Col}_j\cup\mathrm{Box}_{i,j}\bigr)\end{aligned}
$$

D คือเลขที่ยังไม่ชนค่าที่มีอยู่; i,j คือแถวและคอลัมน์ การไม่ชนเฉพาะที่ยังไม่พิสูจน์ว่าต่อเป็นคำตอบเต็มได้

**ความหมายของสมการ:** Domain ของช่องได้จากเซตเลขตั้งต้นลบ union ของเลขที่ปรากฏในแถว คอลัมน์ และกล่องที่เกี่ยวข้อง

**อ่านสัญลักษณ์:**

- **D_(i,j):** domain หรือตัวเลือกที่ยังเหลือของช่องแถว i คอลัมน์ j
- **∪:** union: รวมสมาชิกจากหลายเซต โดยไม่นับตัวซ้ำ
- **∖:** set difference: เอาสมาชิกของเซตทางขวาออกจากเซตทางซ้าย
- **Row, Col, Box:** เลขที่มีอยู่แล้วในแถว คอลัมน์ และกล่องของช่องที่กำลังตรวจ

**ตัวอย่างการคำนวณ:** สมมติช่องว่างใน Sudoku 4×4 เห็น Row={1}, Col={3} และ Box={1,3}

1. รวมเลขที่ชนข้อจำกัด: {1}∪{3}∪{1,3}={1,3}
2. เริ่มจาก {1,2,3,4} แล้วตัด 1 และ 3 ออก จึงได้ D={2,4}
3. ทั้ง 2 และ 4 ยังไม่ชนเลขที่เห็น ณ จุดนี้ ต้อง propagate หรือค้นต่อก่อนรู้ว่าเลือกใดต่อเป็นคำตอบเต็มได้

**ผลที่ได้:** domain ของช่องนี้เหลือสองค่า จึงลดงานค้นได้ แต่ยังไม่ได้บังคับว่าคำตอบต้องเป็นค่าใดค่าหนึ่ง

**ข้อสรุปจากตัวอย่าง:** การผ่าน constraints ในแถว คอลัมน์ และกล่องเป็น local consistency โดยยังต้องตรวจ global completion

$$
\begin{gathered}\{1,2,3,4\}\setminus\bigl(\{1,3\}\cup\{2\}\cup\{1,2\}\bigr)\\=\{4\}\end{gathered}
$$

ตัวอย่างการตัด domain ด้วยข้อจำกัดที่ระบุ ไม่ต้องอาศัย confidence ของโมเดล

**ความหมายของสมการ:** Union ของเลขต้องห้ามทั้งสามเซตคือ {1,2,3} เมื่อลบจาก {1,2,3,4} จึงเหลือ {4}

**อ่านสัญลักษณ์:**

- **∪:** รวมเลขที่ปรากฏในแต่ละเงื่อนไข โดยเลขที่ซ้ำกันนับเป็นสมาชิกเดียว
- **∖:** ตัดสมาชิกที่อยู่ในชุดทางขวาออกจากชุดตั้งต้น
- **{4}:** singleton: ชุดที่เหลือสมาชิกเพียงหนึ่งตัว

**ตัวอย่างการคำนวณ:** พิจารณาช่องที่แถวมี {1,3}, คอลัมน์มี {2} และกล่องมี {1,2} ตามสมการนี้

1. รวมแถวกับคอลัมน์ก่อน: {1,3}∪{2}={1,2,3}
2. รวมกล่อง {1,2} ต่อแล้วก็ยังเป็น {1,2,3} เพราะ 1 และ 2 อยู่ในชุดแล้ว
3. ตัดชุดนี้ออกจาก {1,2,3,4}: ลบ 1, 2, 3 จึงเหลือ {4}

**ผลที่ได้:** 4 เป็นค่าเดียวที่ไม่ชนเลขที่กำหนดอยู่รอบช่องนี้ จึงไม่ต้องใช้คะแนน confidence เลือกระหว่างหลายค่า

**ข้อสรุปจากตัวอย่าง:** Singleton กำหนดค่าได้ภายใต้ constraints ที่ตรวจ แต่ยังไม่รับรองว่าทั้งกระดานมีคำตอบสอดคล้องกัน

### 4.4 Selective accuracy, coverage และข้อจำกัดของการตรวจ

หาก solver ตอบ 20 ข้อและถูกทั้ง 20 แต่คืน unresolved อีก 80 ข้อจากทั้งหมด 100 ข้อ จะมี selective accuracy 100% และ coverage 20% การรายงานเฉพาะ accuracy จึงไม่แสดงขอบเขตงานที่ระบบตอบได้ครบถ้วน การประเมินต้องรวม invalid, timeout และสาเหตุของ abstention

ข้อกำหนดทางโครงสร้าง เช่น type contract หรือกฎ composition ของ transformation ใช้ตรวจ property เฉพาะ เช่น การแปลงสองขั้นให้ผลตรงกับองค์ประกอบตามลำดับ แต่กฎหนึ่งไม่ครอบคลุม specification ทั้งหมด และระบบ deterministic ก็ยังมีข้อผิดพลาดที่เกิดซ้ำได้

การใช้ confidence threshold ต้องแยกคะแนนที่โมเดลรายงานออกจากอัตราถูกจริงในกลุ่มคะแนนนั้น Calibration เปรียบเทียบสองปริมาณบน distribution ที่ประเมิน แต่ไม่แทน hard preconditions ของ action ผลที่ verifier ยอมรับจึงควรบันทึกพร้อมเงื่อนไขและเวอร์ชันสำหรับการใช้ต่อ

$$
\begin{gathered}\operatorname{selective\ accuracy}\\=\frac{N_{\mathrm{correct,answered}}}{N_{\mathrm{answered}}}\end{gathered}
$$

ตัวเศษ = จำนวนข้อที่ตอบถูกในข้อที่ยอมตอบ; ตัวส่วน = จำนวนข้อที่ยอมตอบ

กำหนดเมื่อมีคำตอบอย่างน้อยหนึ่งข้อ; รายงานคู่กับ coverage

**ความหมายของสมการ:** Selective accuracy คือสัดส่วนคำตอบถูกในกลุ่มโจทย์ที่ระบบยอมตอบ

**อ่านสัญลักษณ์:**

- **ถูกในข้อที่ตอบ:** นับเฉพาะคำตอบที่ผ่านเกณฑ์ความถูกต้อง
- **จำนวนข้อที่ตอบ:** ตัวหารรวมทั้งข้อที่ตอบถูกและตอบผิด แต่ไม่รวม abstain
- **/:** นำจำนวนถูกหารด้วยจำนวนที่ตอบ; คูณ 100 เมื่อต้องการหน่วยเปอร์เซ็นต์

**ตัวอย่างการคำนวณ:** สมมติมี 100 โจทย์ ระบบยอมตอบ 20 ข้อ โดยถูก 18 ข้อและผิด 2 ข้อ; อีก 80 ข้อคืน unresolved

1. ตัวตั้งคือจำนวนถูก 18 ไม่ใช่จำนวนที่ระบบมั่นใจ
2. ตัวหารคือจำนวนที่ตอบจริง 20; ข้อ unresolved 80 ข้อไม่เข้าตัวหารนี้
3. คำนวณ 18/20=0.9 จึงได้ selective accuracy=90%

**ผลที่ได้:** 90% หมายถึงความถูกต้องใน 20 ข้อที่ระบบเลือกตอบ ไม่ใช่สัดส่วนที่ทำถูกจากโจทย์ทั้งหมด

**ข้อสรุปจากตัวอย่าง:** Selective accuracy ต้องรายงานร่วมกับ coverage และไม่มีนิยามเมื่อระบบไม่ตอบเลยเพราะตัวหารเป็นศูนย์

$$
\operatorname{coverage}=\frac{N_{\mathrm{answered}}}{N_{\mathrm{all}}}
$$

ตัวเศษ = จำนวนข้อที่ยอมตอบ; ตัวส่วน = จำนวนข้อทั้งหมด

coverage ในที่นี้หมายถึงสัดส่วนที่ solver ยอมตอบ ไม่ใช่ coverage guarantee ของ prediction set ใน conformal prediction

**ความหมายของสมการ:** Coverage คือสัดส่วนโจทย์ที่ระบบยอมตอบจากโจทย์ทั้งหมด โดยรวมทั้งคำตอบถูกและผิด

**อ่านสัญลักษณ์:**

- **จำนวนข้อที่ตอบ:** รวมทั้งคำตอบถูกและผิด; ไม่นับ unresolved หรือ abstain
- **จำนวนข้อทั้งหมด:** ทุกโจทย์ที่อยู่ใน workload ที่กำลังประเมิน
- **coverage:** สัดส่วนการยอมตอบในบทนี้ ซึ่งแยกจาก accuracy ของคำตอบ

**ตัวอย่างการคำนวณ:** ใช้ตัวอย่างเดิม: 100 โจทย์ ตอบ 20 ข้อ โดยถูก 18 และผิด 2; unresolved อีก 80 ข้อ

1. นับข้อที่ตอบได้ 18+2=20 ข้อ แม้ 2 ข้อจะตอบผิด
2. หารด้วยโจทย์ทั้งหมด: 20/100=0.20 หรือ coverage=20%
3. อ่านคู่กับสมการก่อน: selective accuracy=90% ที่ coverage=20%; งานอีก 80% ยังไม่มีคำตอบจากระบบ

**ผลที่ได้:** คู่ตัวเลข 90% / 20% ระบุทั้งคุณภาพของคำตอบที่ส่งกลับและสัดส่วนงานที่ระบบตอบได้

**ข้อสรุปจากตัวอย่าง:** การเพิ่ม threshold อาจเพิ่ม accuracy ในกลุ่มที่ตอบพร้อมลด coverage จึงต้องประเมินสองค่าร่วมกัน

### นิยามที่ใช้ในบทนี้

- **constraint:** ข้อกำหนดที่จำกัด candidate เช่น domain, grammar หรือ invariant ของ state
- **sound pruning:** การตัด candidate โดยรักษาคำตอบถูกทุกตัวที่มีอยู่ในเซตตั้งต้นตาม specification
- **completeness:** การพบคำตอบที่มีอยู่ภายใต้โดเมน วิธีค้น และ budget ที่กำหนด
- **abstention:** การคืนสถานะที่ยังยืนยันคำตอบไม่ได้แทนการเลือก candidate โดยไม่มีข้อรับรอง

**ขั้นตอนการทดลอง:** เลือกช่องว่างใน Sudoku ตรวจสอบ candidate และปุ่มตัวเลขที่ปิดเพราะซ้ำในแถว คอลัมน์ หรือกล่อง แล้วเลือกเลขจากปุ่มที่อนุญาต

### 5.1 ชนิดของ storage และเงื่อนไขการใช้ซ้ำ

Weights θ เป็นพารามิเตอร์ที่ได้จากการเรียน ส่วน h_k เป็น activation ของ computation ปัจจุบัน KV cache เก็บ key/value ที่คำนวณแล้วจากตำแหน่งก่อนหน้าเพื่อนำกลับมาใช้ระหว่าง decode โดยความเข้ากันได้ขึ้นกับ model, prefix, position และรูปแบบการคำนวณ

External memory M_t เก็บข้อมูลที่ระบบเลือกบันทึก เช่น ข้อเท็จจริง เหตุการณ์ หรือบทสรุปพร้อมแหล่งที่มา ส่วน policy/result cache เก็บผลของ computation เพื่อใช้ซ้ำเมื่อ key และเงื่อนไขยัง valid ความคล้ายของ latent เพียงอย่างเดียวไม่รับรองว่า action เดิมยังใช้ได้

สำหรับ attention ที่ key และ value มี head dimension เท่ากัน ขนาด full KV cache แปรตาม batch, layers, sequence length และจำนวน KV heads สูตรด้านล่างคำนวณเฉพาะ tensor payload โดยไม่รวม allocation, metadata หรือรูปแบบ compression เฉพาะ architecture

$$
\mathrm{KV}_{\mathrm{bytes}}\approx 2\,B\,L\,T\,H_{\mathrm{KV}}\,d_{\mathrm{head}}\,b
$$

B=batch size, L=จำนวน layer, T=ตำแหน่งที่ cache, H_KV=จำนวน KV heads, d_head=มิติต่อ head, b=ไบต์ต่อค่า; 2 มาจาก K และ V

**ความหมายของสมการ:** ขนาด full KV cache ได้จากจำนวนค่าของ key และ value ในทุก batch, layer, token และ KV head คูณจำนวนไบต์ต่อค่า

**อ่านสัญลักษณ์:**

- **2:** มีทั้ง key และ value ซึ่งในสูตรนี้ใช้ shape และชนิดข้อมูลที่มีขนาดเท่ากัน
- **B·L·T:** จำนวน batch คูณ layer คูณตำแหน่ง token ที่เก็บ
- **H_KV·d_head:** จำนวน KV heads คูณค่าต่อ head; อาจต่างจากจำนวน query heads
- **b:** จำนวนไบต์ต่อค่า เช่น float16 ใช้ 2 ไบต์

**ตัวอย่างการคำนวณ:** ใช้โมเดลสมมติขนาดเล็ก: B=1, L=2, T=4, H_KV=2, d_head=4 และ b=2 ไบต์

1. นับ key อย่างเดียวได้ 1×2×4×2×4=64 ค่า
2. แต่ละค่าใช้ 2 ไบต์ จึงได้ key cache ขนาด 128 ไบต์; value อีกชุดใช้ 128 ไบต์เท่ากัน
3. รวมสองชุดได้ 256 ไบต์; ถ้าเก็บ token เพิ่มจาก 4 เป็น 8 โดยค่าอื่นคงเดิม ขนาด payload จะเพิ่มเป็น 512 ไบต์

**ผลที่ได้:** ตัวคูณ 2 คือสอง tensor K/V; การเพิ่มความยาว prefix สองเท่าทำให้ payload เพิ่มสองเท่าในรูปแบบนี้

**ข้อสรุปจากตัวอย่าง:** สูตรนี้ระบุเฉพาะ tensor payload ของ full KV cache ส่วนหน่วยความจำจริงต้องพิจารณา metadata, allocation และ compression เพิ่มเติม

$$
\begin{aligned}\mathrm{cache\ key}=(&\mathrm{input\ identity},\\&\mathrm{model\ version},\\&\mathrm{rule\ version},\\&\mathrm{world\ version})\end{aligned}
$$

ตัวอย่างส่วนประกอบของ result-cache key; งานจริงต้องเลือก validity boundary ให้ตรงสิ่งที่ผลลัพธ์ขึ้นกับมัน

**ความหมายของสมการ:** Cache key รวมตัวระบุ input กับเวอร์ชันของ dependency ที่มีผลต่อผลลัพธ์ เพื่อประเมินเงื่อนไขการนำผลเดิมมาใช้

**อ่านสัญลักษณ์:**

- **(...):** tuple: ชุดข้อมูลที่ต้องอ่านร่วมกัน ไม่ใช่การนำค่ามาบวก
- **input_identity:** ตัวระบุ input ที่ต้องแยกได้ตามขอบเขตของงาน
- **model_version, rule_version:** เวอร์ชันโมเดลและกฎที่ใช้สร้างผล
- **world_version:** เวอร์ชันสถานะโลกที่ผลลัพธ์อาศัยอยู่

**ตัวอย่างการคำนวณ:** สมมติ cache เก็บเส้นทางจาก A ไป B โดย key คือ (route:A→B, model:m3, rule:r2, world:v10)

1. เมื่อคำนวณได้เส้นทาง A→D→B ให้เก็บผลคู่กับ key ทั้งสี่ส่วนนี้
2. คำขอเดิมใน world:v10 ใช้ key เดิม จึงค้นพบผลเก่าเพื่อนำไปใช้ภายใต้ validity boundary ที่กำหนด
3. ถ้าประตูที่ D ปิดและโลกเปลี่ยนเป็น v11, key ใหม่ต่างจากเดิม แม้ input ยังเป็น A→B; ต้องหาผลสำหรับ v11 หรือตรวจ/คำนวณใหม่

**ผลที่ได้:** ผลที่ถูกสำหรับ world:v10 ไม่ถูกนำกลับมาใช้โดยอาศัยเพียงชื่อ input ที่เหมือนเดิม

**ข้อสรุปจากตัวอย่าง:** องค์ประกอบ key ต้องสอดคล้องกับ dependency ของผลลัพธ์ และ version ต้องเปลี่ยนเมื่อ dependency ที่มีผลต่อความถูกต้องเปลี่ยน

### 5.2 Priority, confidence และ freshness

Priority ระบุความสำคัญในการนำข้อมูลมาพิจารณา, confidence ระบุระดับความเชื่อในข้อมูล และ freshness ระบุอายุข้อมูลเทียบกับอัตราการเปลี่ยนสิ่งแวดล้อม เช่น ข่าวลือเกี่ยวกับเหตุการณ์อันตรายอาจมี priority สูงพร้อมกับ confidence ต่ำ

ห้องทดลองใช้ weighted average ของสามค่า โดย freshness ลดแบบเชิงเส้นจนเป็นศูนย์เมื่ออายุ 14 วัน ข่าวลือในตัวอย่างมี priority 0.95 และ confidence 0.32 การเพิ่มน้ำหนัก priority อาจเพิ่มอันดับโดยไม่มีหลักฐานใหม่หรือการเปลี่ยนความน่าเชื่อถือ

คะแนน ranking ใช้จัดลำดับข้อมูลที่จะอ่านหรือตรวจต่อ ส่วน hard invalidation ต้องกำหนดแยก เช่น ข้อมูลที่หมดอายุตามเงื่อนไขของสิ่งแวดล้อมต้องไม่กลับมา valid เพราะ priority สูง ห้องทดลองแสดงสถานะเตือนร่วมกับคะแนน แต่ไม่มีการ calibrate confidence จากผลทดลอง

$$
\operatorname{score}_i=\frac{w_P P_i+w_C C_i+w_F F_i}{w_P+w_C+w_F}
$$

P,C,F อยู่ใน [0,1]; น้ำหนักไม่ติดลบและผลรวมมากกว่า 0; เป็น scoring rule สาธิต ไม่ใช่ posterior probability

**ความหมายของสมการ:** คะแนน ranking เป็น weighted average ของ priority, confidence และ freshness โดยหารผลรวมถ่วงน้ำหนักด้วยน้ำหนักรวม

**อ่านสัญลักษณ์:**

- **P_i, C_i, F_i:** priority, confidence และ freshness ของ record i โดยแต่ละค่าอยู่ระหว่าง 0 ถึง 1
- **w_P, w_C, w_F:** น้ำหนักที่กำหนดว่าให้แต่ละมิติมีผลต่ออันดับมากเพียงใด
- **w_P+w_C+w_F:** ตัวหารสำหรับ normalize; ต้องมากกว่า 0 และใช้น้ำหนักไม่ติดลบ

**ตัวอย่างการคำนวณ:** สมมติ record มี P=0.9, C=0.4, F=0.8 และใช้น้ำหนัก (w_P,w_C,w_F)=(2,1,1)

1. คูณและรวมได้ 2×0.9+1×0.4+1×0.8=1.8+0.4+0.8=3.0
2. น้ำหนักรวมคือ 2+1+1=4 จึงได้ score=3.0/4=0.75
3. ถ้าเพิ่ม w_P เป็น 6 โดยข้อมูลเดิมไม่เปลี่ยน จะได้ (5.4+0.4+0.8)/8=0.825

**ผลที่ได้:** คะแนนอันดับเพิ่มจาก 0.75 เป็น 0.825 ทั้งที่ confidence ยังเป็น 0.4 และไม่ได้มีหลักฐานใหม่เพิ่ม

**ข้อสรุปจากตัวอย่าง:** Weighted score ระบุลำดับสำหรับการอ่านหรือตรวจเพิ่มเติม ค่า 0.825 จึงไม่ได้หมายถึงความน่าจะเป็นที่ข้อมูลจริง 82.5%

$$
F_i=\max\!\left(0,\,1-\frac{\mathrm{age}_i}{14}\right)
$$

age_i ใช้หน่วยวันใน lab; ช่วง 14 วันเป็นสมมติฐานสังเคราะห์ ไม่ใช่อายุที่เหมาะกับทุกโดเมน

**ความหมายของสมการ:** Freshness ลดเชิงเส้นตามอายุเทียบกับ 14 วัน โดยจำกัดค่าต่ำสุดไว้ที่ศูนย์

**อ่านสัญลักษณ์:**

- **age_i/14:** อายุเป็นวันหารด้วย 14 เพื่อบอกว่าใช้ช่วงอายุสมมติไปแล้วกี่ส่วน
- **1−age_i/14:** ความสดที่เหลือก่อนจำกัดค่าต่ำสุด
- **max(0, …):** เลือกค่าที่มากกว่าระหว่าง 0 กับผลที่คำนวณ จึงตัดค่าติดลบให้เป็น 0

**ตัวอย่างการคำนวณ:** ใช้กฎสาธิตใน lab ที่ถือว่า freshness เริ่มที่ 1 และหมดเมื่อครบ 14 วัน โดยยังไม่ใช่นโยบายจริงของทุกข้อมูล

1. อายุ 7 วัน: 1−7/14=0.5; max(0,0.5)=0.5
2. อายุ 14 วัน: 1−14/14=0; freshness จึงเป็น 0
3. อายุ 21 วัน: 1−21/14=−0.5 แต่ max(0,−0.5)=0 จึงไม่ติดลบ

**ผลที่ได้:** อายุ 7, 14 และ 21 วันให้ F เท่ากับ 0.5, 0 และ 0 ตามลำดับ

**ข้อสรุปจากตัวอย่าง:** Freshness เป็น scoring assumption สำหรับจัดอันดับ ส่วนเงื่อนไขหมดอายุที่ห้ามใช้ข้อมูลต้องกำหนดตามโดเมน

### 5.3 Versioning, replay และ invalidation

Fact ควรมี source, observed_at, scope และ validity condition กำกับ เช่น path cache ที่ผ่านประตูได้ควรอ้างอิงเวอร์ชันแผนที่หรือสถานะประตู เมื่อประตูปิดต้อง invalidate ผลเดิมหรือตรวจ preconditions ใหม่ก่อนใช้

Event sourcing เก็บลำดับเหตุการณ์เพื่อสร้าง state ย้อนกลับด้วย transition function การ replay ให้ได้ผลตรงกันต้องมีลำดับ event, version ของกฎ และข้อมูล nondeterminism ที่เกี่ยวข้อง เช่น random seed หรือผล external call ส่วน snapshot เพียงอย่างเดียวไม่ระบุเหตุการณ์ทั้งหมดระหว่างสองเวลา

Hash หรือ proof structure อาจใช้ตรวจความสอดคล้องหรือการเปลี่ยน log ภายใต้ trust model ที่กำหนด แต่ไม่รับรองว่า observation ตั้งต้นตรงกับสิ่งแวดล้อมจริง การใช้คำว่า historical proof จึงต้องระบุ property ที่พิสูจน์และหลักฐานที่ใช้

$$
s_{t+1}=F_v(s_t,e_t)
$$

e_t คือ event ที่บันทึก และ v คือ version ของ transition rule; replay ต้องมี input ที่ F_v ใช้ครบ

**ความหมายของสมการ:** Transition rule เวอร์ชัน v ใช้ state ปัจจุบันกับ event เพื่อคำนวณ state ถัดไป โดย replay ทำซ้ำตามลำดับ event เดิม

**อ่านสัญลักษณ์:**

- **s_t, s_(t+1):** state ก่อนและหลังนำ event หนึ่งรายการมาใช้
- **e_t:** event ที่เกิดในขั้นนี้ พร้อมข้อมูลที่ transition ต้องใช้
- **F_v:** ฟังก์ชันเปลี่ยน state ตาม rule เวอร์ชัน v

**ตัวอย่างการคำนวณ:** สมมติมีโควตา 10 units และ log สอง event ตามลำดับคือ use(3), use(2); กฎ v1 หักตามจำนวนที่ใช้

1. เริ่มจาก s₀=10 แล้วใช้ F_v1 กับ use(3) ได้ s₁=10−3=7
2. นำ state 7 เข้า event ถัดไป use(2) ได้ s₂=7−2=5; replay log เดิมด้วย v1 จึงได้ 5 อีกครั้ง
3. ถ้าเผลอ replay ด้วย v2 ที่คิด overhead เพิ่ม 1 unit ต่อ event จะได้ 10−4=6 แล้ว 6−3=3

**ผลที่ได้:** log เดียวกันให้ state สุดท้าย 5 หรือ 3 ได้เมื่อกฎต่างเวอร์ชัน จึงต้องเก็บว่าระบบใช้เวอร์ชันใด

**ข้อสรุปจากตัวอย่าง:** Replay ต้องใช้ event ครบตามลำดับ กฎเวอร์ชันที่ตรงกัน และข้อมูล nondeterminism ที่ transition อาศัย

### 5.4 การประเมินสาเหตุของ self-improvement

ผลประเมินที่ดีขึ้นอาจมาจาก θ เปลี่ยน, prompt/context เปลี่ยน, cache hit เพิ่ม, corpus เพิ่ม หรือ evaluator เปลี่ยน การระบุสาเหตุต้องบันทึก version ของแต่ละส่วนและเปรียบเทียบด้วยชุดอ้างอิงที่ตรึงไว้ มิฉะนั้นคะแนนเพิ่มยังไม่ระบุ capability ที่ดีขึ้น

กรอบ represented → accessible → stable ช่วยจำแนกการมีข้อมูลใน model ออกจากการ route ข้อมูลมาใช้ อย่างไรก็ตาม infographic เกี่ยวกับ trajectory/context routing เป็นสมมติฐานหรือกรอบอธิบายของเจ้าของงาน การยืนยันว่าเป็นกลไกภายในจริงต้องมี measurement เพิ่มเติม

เมื่อ memory มีขนาดเกิน context ที่รองรับ ระบบต้องเลือก record ที่จะใช้และกำหนดสิทธิ์การเข้าถึง Retrieval จึงเป็นขั้นคัดข้อมูลก่อน inference โดยใช้ทั้ง representation และ validity boundary ที่กำหนดไว้

$$
\begin{aligned}\mathrm{measured\ gain}\\={}&\operatorname{score}(\mathrm{agent}_{\mathrm{new}},\mathrm{evaluator}_{\mathrm{fixed}})\\&{}-\operatorname{score}(\mathrm{agent}_{\mathrm{old}},\mathrm{evaluator}_{\mathrm{fixed}})\end{aligned}
$$

เทียบด้วย workload และเงื่อนไขเดียวกัน พร้อมตรึง evaluator; ยังต้องแยกการเปลี่ยน θ, context, cache และ corpus เพื่อระบุสาเหตุของ gain

**ความหมายของสมการ:** Measured gain เป็นผลต่างคะแนนของ agent ใหม่กับ agent เก่าที่ประเมินด้วย evaluator และเงื่อนไขเดียวกัน

**อ่านสัญลักษณ์:**

- **score(agent, evaluator_fixed):** คะแนนจากเกณฑ์ประเมินที่ตรึงไว้ ไม่เปลี่ยนตาม agent
- **agent_new, agent_old:** ระบบสองเวอร์ชันที่นำมาเทียบ ซึ่งอาจต่างที่ weight, context, cache หรือ corpus
- **measured_gain:** ผลต่างที่วัดบน workload นี้ ยังต้องระบุว่าส่วนใดของระบบเปลี่ยน

**ตัวอย่างการคำนวณ:** สมมติใช้โจทย์เดิม 100 ข้อ งบคำนวณและ evaluator เดียวกัน โดยรายงาน accuracy ในช่วง 0–1

1. agent เก่าถูก 60 ข้อ ได้ score=0.60; agent ใหม่ถูก 70 ข้อ ได้ score=0.70
2. ผลต่างคือ 0.70−0.60=0.10 หรือเพิ่ม 10 จุดเปอร์เซ็นต์ (จาก 60% เป็น 70%) บนชุดนี้
3. ถ้าในการเทียบนี้เปลี่ยนเฉพาะ corpus และตรึง θ ไว้ gain ที่เห็นควรอธิบายร่วมกับข้อมูลที่ค้นได้เพิ่ม ไม่ใช่อ้างว่า weight ได้เรียนรู้ใหม่

**ผลที่ได้:** ตัวเลขบอกว่าระบบใหม่ทำคะแนนสูงขึ้นเท่าไรบนเงื่อนไขที่ตรึง แต่ชื่อกลไกที่ดีขึ้นต้องมาจากสิ่งที่เปลี่ยนในการทดลอง

**ข้อสรุปจากตัวอย่าง:** การเชื่อม gain กับสาเหตุต้องบันทึก version ขององค์ประกอบและควบคุมปัจจัยที่เปลี่ยนในการทดลอง

### นิยามที่ใช้ในบทนี้

- **KV cache:** Key/value activations ที่ใช้ซ้ำระหว่าง decoding เมื่อ prefix และ model เข้ากันได้
- **external memory:** ข้อมูลที่ระบบบันทึกภายนอก weights พร้อมบริบทสำหรับการใช้งานภายหลัง
- **cache invalidation:** การยกเลิกการใช้ผลเก่าเมื่อข้อสมมติหรือ version ที่ผลนั้นอาศัยเปลี่ยนแปลง
- **event sourcing:** การสร้าง state จากลำดับ event ด้วย transition rule ที่กำหนด

### ทดลองกลไก

**ขั้นตอนการทดลอง:** กำหนดน้ำหนัก priority, confidence และ freshness เป็น 0.5 เท่ากัน แล้วเพิ่ม priority และกดผ่านไป 1 วันเพื่อเพิ่มอายุข้อมูล

**ประเด็นที่ศึกษา:** เปรียบเทียบอันดับของข่าวลือกับแผนที่เก่า โดยพิจารณาคะแนน ranking แยกจากสถานะที่ต้องตรวจสอบเพิ่ม

**ขอบเขตของแบบจำลอง:** ห้องทดลองใช้ scoring rule ที่กำหนดด้วยมือ อันดับที่เพิ่มขึ้นไม่เพิ่มความถูกต้องของข้อมูล และไม่มี weight learning หรือ probabilistic calibration

## บท 6 — Retrieval: การคัดเลือกหลักฐานภายใต้บริบทและสิทธิ์เข้าถึง

[เปิดบทพร้อมห้องทดลอง](../index.html#story/09) · [หัวข้อสังเคราะห์](topics/09-rag-code-healing-and-privacy.md)

**คำถามหลัก:** ความคล้ายคลึงของเวกเตอร์สัมพันธ์กับหลักฐานที่ใช้สร้างคำตอบหรือดำเนินการอย่างไร?

**ความเข้าใจที่นำมาใช้:** Memory จัดเก็บ record ข้ามช่วงเวลา ส่วน retrieval คัดเลือก record เพื่อประกอบ context โดยต้องคงข้อมูลแหล่งที่มา อายุของข้อมูล และข้อจำกัดด้านสิทธิ์เข้าถึง

- [บท 1](#chapter-01): embedding similarity ขึ้นกับ representation และงาน
- [บท 4](#chapter-03): รูปแบบผ่านกฎยังต้องมี semantic verification
- [บท 5](#chapter-05): external memory, freshness และ version boundary

### โจทย์

เอกสารที่มีความคล้ายคลึงกับ query สูงอาจไม่ตรงบริบท ล้าสมัย หรืออยู่นอกสิทธิ์ของผู้ใช้ การค้นคืนและการตรวจหลักฐานจึงต้องเป็นขั้นตอนที่มีหน้าที่ชัดเจนใน pipeline

### 6.1 การคัดเลือกข้อมูลก่อนการสร้างคำตอบ

Encoder φ แปลง query q และ document d เป็นเวกเตอร์ใน ℝ^m จากนั้น cosine similarity ใช้จัดอันดับความคล้ายคลึงตาม representation ของ embedding model ในระบบ RAG เอกสารที่คัดเลือกแล้วเป็น context ให้ generator ความผิดพลาดจึงเกิดได้ทั้งจากการค้นคืนที่ไม่พบหลักฐานและการสร้างคำตอบที่ใช้หลักฐานไม่ถูกต้อง

เอกสารที่กล่าวถึงอาการเดียวกันอาจระบุสาเหตุต่างกัน การประเมิน applicability จึงต้องพิจารณา version ของระบบ environment และเงื่อนไขในเนื้อหา คะแนน similarity ไม่ได้ยืนยัน entailment ของคำตอบ ขณะเดียวกัน citation ต้องอ้างข้อความที่รองรับ claim นั้นจริง

จำนวนผล K_ret และ context budget ควรกำหนดตามข้อมูลที่จำเป็นต่อคำถาม พร้อมจัดเก็บ provenance ของแต่ละ chunk ได้แก่ document id revision และตำแหน่งข้อความ ข้อมูลเหล่านี้ทำให้ตรวจสอบได้ว่า inference ใช้หลักฐานจากเวอร์ชันใด

$$
\operatorname{sim}(q,d)=\frac{\varphi(q)^{\top}\varphi(d)}{\lVert\varphi(q)\rVert\,\lVert\varphi(d)\rVert}
$$

cosine similarity สำหรับเวกเตอร์ที่ norm ไม่เป็นศูนย์; m คือ embedding dimension

**ความหมายของสมการ:** Cosine similarity คำนวณจาก dot product ของ embedding ของ query และ document หารด้วยผลคูณของ norm ทั้งสอง การหารนี้ใช้เปรียบเทียบทิศของเวกเตอร์โดยลดผลจากขนาดเวกเตอร์

**อ่านสัญลักษณ์:**

- **φ(q)⊤φ(d):** dot product: คูณค่าที่ตำแหน่งตรงกันแล้วรวม
- **∥v∥:** ความยาวเวกเตอร์ เช่น ∥(3,4)∥ = √(3²+4²) = 5
- **sim:** คะแนนไม่มีหน่วย อยู่ระหว่าง −1 ถึง 1 สำหรับเวกเตอร์ที่ไม่เป็นศูนย์

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: embedding ของ query คือ (1,0) และของเอกสารคือ (3,4)

1. คำนวณตัวเศษ: (1×3)+(0×4) = 3
2. คำนวณความยาว: query ยาว 1 และ document ยาว 5 จึงได้ตัวหาร 1×5 = 5
3. หารได้ 3/5 = 0.6; ถ้าขยาย document เป็น (6,8) จะได้ 6/10 = 0.6 เท่าเดิม

**ผลที่ได้:** คะแนน 0.6 บอกความใกล้ด้านทิศของ embedding ไม่ได้แปลว่าเอกสารถูกต้อง 60% หรือรองรับคำตอบแน่นอน

**ข้อสรุปจากตัวอย่าง:** Cosine similarity วัดความคล้ายคลึงด้านทิศของเวกเตอร์ ส่วนความเหมาะสมของหลักฐานต้องตรวจจากเนื้อหาและบริบท

$$
\begin{aligned}D_q=\operatorname{TopK}_{\mathrm{ret}}\Bigl\{\\\operatorname{sim}(q,d):d\in D_{\mathrm{allowed}}(u)\Bigr\}\end{aligned}
$$

D_allowed(u) คือเอกสารที่ผู้ใช้ u มีสิทธิ์ใช้; K_ret แยกจาก K ที่นับ recurrent passes ในบทก่อน

**ความหมายของสมการ:** คำนวณ similarity ระหว่าง query กับเอกสารในชุดที่ผู้ใช้มีสิทธิ์อ่าน แล้วเลือก K_ret รายการที่มีคะแนนสูงสุด โดยคงคู่เอกสารและคะแนนไว้

**อ่านสัญลักษณ์:**

- **d∈D_allowed(u):** พิจารณาเฉพาะเอกสาร d ในชุดที่ผู้ใช้ u ใช้ได้
- **TopK_ret:** ตัวดำเนินการเลือก K_ret อันดับสูงสุดจากรายการ document–score
- **D_q:** ชุดเอกสารที่เลือกได้ ไม่ใช่ชุดตัวเลขคะแนนล้วน

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: K_ret=2; ผู้ใช้มีสิทธิ์อ่าน A:0.91, B:0.73, C:0.82 แต่ไม่มีสิทธิ์อ่าน X:0.99

1. สร้างชุดที่มีสิทธิ์ก่อน จึงเหลือคู่ (A,0.91), (B,0.73), (C,0.82)
2. เรียงตามคะแนนได้ A, C, B แล้วเลือกสองอันดับแรก

**ผลที่ได้:** D_q = {A,C} พร้อมคะแนน 0.91 และ 0.82; X ไม่เข้าร่วมการเลือก แม้ได้คะแนนสูงสุด

**ข้อสรุปจากตัวอย่าง:** สูตรแสดงคะแนนที่ใช้จัดอันดับ ส่วน context ประกอบด้วยเนื้อหาจากเอกสารที่ได้รับอนุญาตและผ่านการคัดเลือก

### 6.2 การตรวจสิทธิ์ก่อนส่งข้อมูลเข้า context

ACL หรือ access-control list ระบุว่า principal ใดมีสิทธิ์อ่าน record ใด ส่วน tenant boundary กำหนดขอบเขตข้อมูลของลูกค้าหรือองค์กร การตรวจสิทธิ์ต้องดำเนินการในส่วนของระบบที่เชื่อถือได้ ก่อนส่ง record snippet หรือ metadata ที่ละเอียดอ่อนให้ reranker generator หรือผู้ใช้

การเลือก top-K จากคลังทั้งหมดแล้วกรองสิทธิ์ให้ผลต่างจากการเลือกภายใน authorized set หากสองอันดับแรกเป็นข้อมูลที่ไม่ได้รับอนุญาตและ K=3 วิธีแรกอาจเหลือเอกสารที่ใช้ได้เพียงหนึ่งรายการ แม้คลังยังมีเอกสารที่ได้รับอนุญาตอีกหลายรายการ นอกจากนี้ข้อมูลที่ถูกกรองออกต้องไม่ปรากฏใน log หรือเข้าสู่ model ระหว่างกระบวนการ

Lab แสดงระยะ Euclidean ในพื้นที่ 2 มิติ โดย query (0.78,0.25) มีระยะจากเอกสารของ tenant B ที่ (0.82,0.24) ประมาณ 0.041 หน่วย อย่างไรก็ตาม ผู้ใช้ tenant A ไม่มีสิทธิ์อ่านเอกสารดังกล่าว ความใกล้ในพื้นที่เวกเตอร์จึงไม่เปลี่ยนข้อกำหนด authorization

$$
\begin{gathered}\operatorname{Filter}_{\mathrm{allowed}}\!\left(\operatorname{TopK}_{\mathrm{ret}}(D)\right)\\\ne\\\operatorname{TopK}_{\mathrm{ret}}\!\left(\operatorname{Filter}_{\mathrm{allowed}}(D)\right)\end{gathered}
$$

โดยทั่วไป

การกรองหลังตัด top-K อาจสูญเสียผลที่ได้รับอนุญาต; ทั้งสองทางต้องป้องกันข้อมูลข้ามขอบเขตก่อนเปิดเผย

**ความหมายของสมการ:** ลำดับของการจัดอันดับและการกรองสิทธิ์มีผลต่อชุดเอกสาร การเลือกอันดับต้นก่อนกรองสิทธิ์อาจเหลือผลน้อยกว่าการกรองสิทธิ์ก่อนเลือกอันดับต้น

**อ่านสัญลักษณ์:**

- **Filter_allowed:** ตัดเอกสารที่ผู้ใช้ไม่มีสิทธิ์ออก
- **TopK_ret:** ตัดรายการให้เหลือ K_ret อันดับ โดยปกติไม่เติมชิ้นถัดไปเองหลังถูกกรอง
- **≠ โดยทั่วไป:** มีกรณีที่ผลต่างกัน ไม่ได้หมายความว่าต้องต่างทุกกรณี

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: K_ret=2 และลำดับคะแนนคือ X:0.99, A:0.95, B:0.90; X ถูกห้าม ส่วน A และ B อ่านได้

1. เลือกก่อน: Top2 ได้ {X,A}; เมื่อกรองสิทธิ์แล้วเหลือ {A}
2. กรองก่อน: ชุดที่ใช้ได้คือ {A,B}; จากนั้น Top2 ได้ {A,B}

**ผลที่ได้:** วิธีแรกได้เอกสาร 1 ชิ้น วิธีที่สองได้ 2 ชิ้น ทั้งที่มีเอกสารอ่านได้เพียงพอ

**ข้อสรุปจากตัวอย่าง:** Retrieval ต้องเลือกผลจาก authorized set และป้องกันข้อมูลที่ไม่ได้รับอนุญาตก่อนส่งไปยัง reranker context หรือ log ที่เปิดเผยได้

$$
\begin{gathered}\operatorname{distance}=\\\sqrt{(0.82-0.78)^2+(0.24-0.25)^2}\\\approx 0.041\end{gathered}
$$

ตัวอย่างจากพิกัดสังเคราะห์ใน lab; ใช้แสดงความเป็นอิสระระหว่างความใกล้กับสิทธิ์เข้าถึง

**ความหมายของสมการ:** ระยะ Euclidean คำนวณจากรากที่สองของผลรวมกำลังสองของผลต่างพิกัดในแต่ละแกน ค่าที่ได้มีหน่วยเดียวกับพิกัดเดิม

**อ่านสัญลักษณ์:**

- **²:** ยกกำลังสอง ทำให้ส่วนต่างติดลบกลายเป็นค่าบวกก่อนรวม
- **√:** รากที่สอง เปลี่ยนผลรวมของระยะกำลังสองกลับเป็นระยะ
- **≈:** ค่าโดยประมาณหลังปัดเศษ ไม่ใช่ค่าเท่ากันพอดี

**ตัวอย่างการคำนวณ:** พิกัดสังเคราะห์จาก lab: query=(0.78,0.25) และเอกสาร tenant B=(0.82,0.24)

1. ส่วนต่างแกน x คือ 0.04 และแกน y คือ −0.01
2. ยกกำลังสองและรวม: 0.04²+(−0.01)² = 0.0016+0.0001 = 0.0017
3. ถอดราก: √0.0017 ≈ 0.04123 จึงแสดงเป็น 0.041 หน่วยพิกัด

**ผลที่ได้:** จุดอยู่ใกล้กันในภาพ แต่ระยะนี้ไม่ใช่ความน่าจะเป็น และไม่ได้บอกว่าผู้ใช้มีสิทธิ์อ่านเอกสาร

**ข้อสรุปจากตัวอย่าง:** คะแนนหรือระยะใช้ประเมินความเกี่ยวข้อง ส่วน ACL กำหนดสิทธิ์ใช้ข้อมูล ทั้งสองเป็นเงื่อนไขที่แยกจากกัน

### 6.3 Embedding และความเสี่ยงต่อข้อมูลส่วนบุคคล

Embedding รักษาสัญญาณเชิงความหมายเพื่อสนับสนุนการค้นคืน การแปลงข้อความเป็นเวกเตอร์จึงไม่ใช่หลักฐานว่าข้อมูลผ่านการทำให้ไม่ระบุตัวตน งาน embedding inversion ศึกษาเงื่อนไขที่ผู้โจมตีสามารถอนุมานหรือกู้คืนเนื้อหาบางส่วนจากเวกเตอร์และข้อมูลประกอบที่เข้าถึงได้

ความสามารถในการกู้คืนขึ้นกับ encoder ข้อมูลฝึก ระดับ access และวิธีโจมตี ผลการศึกษาจึงไม่ได้หมายความว่าทุกเวกเตอร์สามารถย้อนกลับเป็นต้นฉบับได้อย่างสมบูรณ์ ขณะเดียวกัน การ normalize เวกเตอร์หรือจัดเก็บแยกจากข้อความต้นทางก็ไม่ได้ยืนยันว่าความเสี่ยงหมดไป

ขอบเขตการควบคุมข้อมูลจึงครอบคลุม raw text embeddings index cached retrieval results และ telemetry โดยกำหนด scope ของแต่ละรายการให้สัมพันธ์กับข้อมูลต้นทาง Semantic similarity ไม่สามารถใช้เป็นเหตุผลในการข้าม permission boundary

$$
\operatorname{access}(\mathrm{vector})
$$

และ

$$
\operatorname{access}(\mathrm{source\ text})
$$

ต้องมีนโยบายที่สัมพันธ์กัน

embedding เป็น derived data ที่ยังเก็บสัญญาณของต้นทาง; ACL ของ output อย่างเดียวไม่ป้องกันผู้ที่อ่าน index ได้อยู่แล้ว

**ความหมายของสมการ:** ข้อความนี้เป็นข้อกำหนดเชิงนโยบาย ไม่ใช่สมการเชิงตัวเลข เนื่องจากเวกเตอร์ยังเก็บสัญญาณจากต้นทาง สิทธิ์เข้าถึงเวกเตอร์จึงต้องพิจารณาขอบเขตความลับของข้อความต้นทาง

**อ่านสัญลักษณ์:**

- **access(vector):** สิทธิ์อ่านหรือใช้ embedding รวมถึง index และผลที่ cache ไว้
- **access(source text):** สิทธิ์เข้าถึงข้อความต้นทางที่ใช้สร้าง embedding

**ตัวอย่างการคำนวณ:** สถานการณ์สมมติ: เอกสาร D เป็นข้อมูลภายใน tenant A และถูกแปลงเป็น embedding v_D

1. ผู้ใช้ tenant B ขออ่าน D แล้วถูกปฏิเสธตามนโยบายของต้นทาง
2. ตรวจเส้นทาง index, vector export และ cached retrieval ด้วยว่าผู้ใช้ B อ่าน v_D หรือข้อมูลที่เปิดเผยเนื้อหาของ D ได้หรือไม่
3. กำหนดสิทธิ์ของ derived data ให้สอดคล้องกับข้อจำกัดนั้น และตรวจใหม่เมื่อสิทธิ์ต้นทางเปลี่ยน

**ผลที่ได้:** การซ่อนข้อความในหน้าจอเพียงจุดเดียวไม่เพียงพอ หากยังเปิดทางให้อ่านข้อมูลที่ได้จากข้อความนั้น

**ข้อสรุปจากตัวอย่าง:** รายละเอียดนโยบายขึ้นกับระบบ แต่การแปลงเป็น embedding ไม่ได้ยืนยันว่าข้อมูลผ่านการทำให้ไม่ระบุตัวตน

### 6.4 Code healing: การตรวจ rule และ patch ที่ได้จาก retrieval

Pipeline ของ code healer ประกอบด้วยการรับ diagnostic การคัดเลือก rule หรือ corpus ที่เกี่ยวข้อง การเสนอ patch การตรวจ syntax type และ behavior ตามข้อกำหนด และการบันทึกผลรวมถึง miss case การเพิ่ม rule หลังพบข้อผิดพลาดอาจขยาย corpus coverage โดยไม่เปลี่ยน θ

ตัวอย่างที่ต้องพิจารณาอย่างระมัดระวังคือ rule ที่แทน exception หรือ error ด้วย default value แม้ patch จะ compile ผ่าน แต่สัญญาของโปรแกรมอาจเปลี่ยนจากการรายงานความผิดพลาดเป็นการใช้ค่าทดแทน การเลือก rule จึงต้องพิจารณา semantics ของ caller และเงื่อนไขการใช้งาน ควบคู่กับความคล้ายของข้อความ error

ผลการแก้ไขควรบันทึก rule_version corpus_version validator_version และ input revision การผ่าน validator ยืนยันได้เฉพาะ property ที่ตรวจเท่านั้น เมื่อหลาย agent ใช้ rule และข้อมูลร่วมกัน ยังต้องพิจารณาขอบเขตข้อมูลที่แต่ละ agent เข้าถึงและผลกระทบระหว่างการแก้ไข ซึ่งเป็นประเด็นของบทถัดไป

retrieved_rule + applicability_check + semantic_validation → candidate patch ที่ประเมินได้

retrieval ส่งหลักฐานและตัวเลือกให้ pipeline; ไม่ได้ทำให้ patch ถูกโดยอัตโนมัติ

**ความหมายของสมการ:** เครื่องหมาย + แสดงการประกอบขั้นตอน ได้แก่ การค้นคืน rule การตรวจ applicability และการตรวจพฤติกรรม ผลคือ candidate patch ที่มีข้อมูลประกอบการประเมิน

**อ่านสัญลักษณ์:**

- **+:** การประกอบขั้นตอน ไม่ใช่การบวกจำนวน
- **→:** ผลส่งต่อไปยังขั้นถัดไป ไม่ใช่คำรับรองว่าผลถูกเสมอ
- **semantic_validation:** ตรวจพฤติกรรมตามสัญญาของโปรแกรม ครอบคลุมมากกว่าการ compile ผ่าน

**ตัวอย่างการคำนวณ:** สถานการณ์สมมติ: retrieval เสนอ rule ให้แทน exception ด้วยค่า 0 เมื่ออ่านจำนวนสินค้าไม่สำเร็จ

1. ตรวจ applicability: caller แยก “สินค้าเป็นศูนย์” ออกจาก “อ่านข้อมูลไม่ได้” หรือไม่
2. ลองกรณีอ่านข้อมูลล้มเหลว: ถ้า patch ส่งค่า 0 จะทำให้ระบบรายงานว่าสินค้าหมดแทนการแจ้ง error
3. ปฏิเสธ rule นี้สำหรับ caller ดังกล่าว หรือเสนอ patch ที่ยังรักษาการรายงาน error แล้วตรวจใหม่

**ผลที่ได้:** แม้ patch เดิม compile ผ่าน ก็ไม่ผ่านสัญญาด้านพฤติกรรมของตัวอย่างนี้

**ข้อสรุปจากตัวอย่าง:** Retrieval ระบุ candidate ส่วนความถูกต้องของ patch ขึ้นกับเงื่อนไขการใช้งานและตัวตรวจที่ตรงกับสัญญาของโปรแกรม

### นิยามที่ใช้ในบทนี้

- **RAG:** การค้นคืนข้อมูลภายนอกเพื่อประกอบ context ก่อนให้โมเดลสร้างคำตอบ
- **provenance:** ข้อมูลแหล่งที่มา ตำแหน่ง และเวอร์ชันของหลักฐานที่ใช้ตรวจสอบย้อนกลับ
- **ACL / tenant boundary:** ข้อกำหนดสิทธิ์เข้าถึงข้อมูลและขอบเขตการแยกข้อมูลของผู้ใช้หรือองค์กร
- **embedding inversion:** การอนุมานข้อมูลต้นทางจาก embedding ภายใต้ระดับ access และวิธีโจมตีที่ระบุ

### ทดลองกลไก

**ขั้นตอนการทดลอง:** กำหนด query ใกล้จุดของ tenant B สลับการใช้ ACL แล้วปรับตำแหน่ง query ไปยังบริเวณอื่น

**ประเด็นที่ศึกษา:** เปรียบเทียบ top-3 ตามระยะกับ top-3 ภายใน tenant A และตรวจว่าเอกสารที่ใกล้แต่ไม่ได้รับอนุญาตถูกตัดออกก่อนแสดงผลอย่างไร

**ขอบเขตของแบบจำลอง:** Lab ใช้พิกัด Euclidean สังเคราะห์เพื่อแสดงความแตกต่างระหว่าง ranking และ authorization ไม่ได้ทดลอง embedding inversion หรือประเมินระบบรักษาความลับของข้อมูลจริง

### ตรวจความเข้าใจก่อนต่อยอด

การส่งเอกสารที่ผู้ใช้ไม่มีสิทธิ์ให้ LLM แล้วระบุใน prompt ว่าห้ามเปิดเผย ถือเป็นการบังคับ ACL หรือไม่?

<details>
<summary>แนวคำตอบ</summary>

ยังไม่ถือเป็นการบังคับ boundary ในชั้น retrieval เนื่องจากข้อมูลที่ไม่ได้รับอนุญาตเข้าสู่ context แล้ว ต้องตรวจสิทธิ์ก่อนส่งเนื้อหาให้ model หรือ component ที่อยู่นอกขอบเขต และให้ generator ใช้เฉพาะหลักฐานที่ได้รับอนุญาต

</details>

**ข้อสรุป:** Retrieval คัดเลือกหลักฐาน authorization กำหนดสิทธิ์ใช้ข้อมูล และ verification ตรวจความเกี่ยวข้องกับความถูกต้อง การใช้เวกเตอร์ไม่สามารถทดแทนหน้าที่เหล่านี้

### 7.1 Joint dynamics และขอบเขตของ model-free learning

Agent i เลือก a_i จาก observation o_i และ memory m_i ขณะที่ transition ของ environment รับ joint action ของทุก agent หาก policy ของ agent อื่นเปลี่ยน การกระจายผลลัพธ์ที่ agent i พบอาจเปลี่ยนตาม แม้ θ ของ agent i จะคงเดิม การวิเคราะห์จึงต้องตรวจสมมติฐานว่า environment ให้ข้อมูลจากการกระจายเดิมตลอดการเรียนรู้

World model อาจหมายถึงโมเดลที่เรียนเพื่อทำนาย transition ส่วน simulator อาจใช้กฎ explicit ที่ระบุไว้โดยตรง Model-free learner สามารถปรับ policy หรือ value จาก reward โดยไม่เรียน transition model แยกต่างหาก คำว่า model-free จึงไม่ได้หมายถึงการไม่มี state reward หรือ learning

ในตัวอย่าง bandit ระบบเก็บค่าประมาณผลตอบแทน U(a) ของแต่ละ action และปรับเฉพาะ action ที่เลือกตาม reward ที่สังเกต สูตรพื้นฐานนี้ไม่มีการวางแผนผ่าน dynamics ระยะยาว หาก action ส่งผลต่ออนาคตหลายขั้นหรือสถานการณ์เปลี่ยนตามเวลา ต้องใช้ formulation ที่ครอบคลุมผลดังกล่าว

$$
s_{t+1}=F(s_t,a_1,\ldots,a_n)
$$

$$
a_i\sim\pi_i(\,\cdot\mid o_i,m_i)
$$

n คือจำนวน agent; F อาจเป็น simulator หรือ transition model ที่ประมาณขึ้น

**ความหมายของสมการ:** Policy ของแต่ละ agent กำหนดการเลือก action โดยมี observation และ memory เป็นเงื่อนไข จากนั้น F ใช้ state ปัจจุบันและ joint action เพื่อกำหนด state ถัดไป

**อ่านสัญลักษณ์:**

- **a_i ∼ π_i:** สุ่ม action ตามการกระจายของ policy ตัวที่ i ไม่ได้แปลว่าคูณกัน
- **·|o_i,m_i:** จุดแทน action ที่เป็นไปได้ ส่วนหลัง | คือข้อมูลที่ policy มีเงื่อนไขด้วย
- **F(s_t,a_1,…,a_n):** กฎการเปลี่ยนสถานะที่รับ action ร่วมของทุก agent

**ตัวอย่างการคำนวณ:** ระบบสมมติ: agent สองตัวอยู่บนเส้นจำนวนที่ s_t=(0,2); F บวก action เข้าตำแหน่งของแต่ละตัว โดยยังไม่มีกฎกันชน

1. policy ของตัวแรกให้ action +1 ด้วยโอกาส 0.8 และ 0 ด้วยโอกาส 0.2; รอบนี้สุ่มได้ +1
2. policy ของตัวที่สองให้ action −1 ด้วยโอกาส 0.6 และ 0 ด้วยโอกาส 0.4; รอบนี้สุ่มได้ −1
3. ส่ง joint action (+1,−1) เข้า F จึงได้ s_(t+1)=(0+1,2−1)=(1,1)

**ผลที่ได้:** ทั้งสองมาอยู่จุดเดียวกัน ผลนี้ขึ้นกับ action ของทั้งคู่และกฎ F ที่กำหนดไว้

**ข้อสรุปจากตัวอย่าง:** Agent อาจเลือก action แยกกัน แต่ผลลัพธ์ขึ้นกับ dynamics ร่วม หากระบบต้องป้องกันการชน ต้องระบุข้อจำกัดนั้นใน F หรือส่วนที่เกี่ยวข้อง

$$
U_{t+1}(a_t)=U_t(a_t)+\eta\bigl[r_t-U_t(a_t)\bigr]
$$

ตัวอย่าง incremental reward estimate สำหรับ action ที่เลือก; 0<η≤1 คือ step size ไม่ใช่ learned world model

**ความหมายของสมการ:** ค่าประมาณใหม่เท่ากับค่าประมาณเดิมบวก η เท่าของผลต่างระหว่าง reward ล่าสุดกับค่าประมาณเดิม โดยปรับเฉพาะ action ที่เลือกในรอบนั้น

**อ่านสัญลักษณ์:**

- **r_t−U_t(a_t):** prediction error: reward จริงสูงหรือต่ำกว่าที่คาดเท่าไร
- **η:** สัดส่วนของความคลาดเคลื่อนที่นำมาแก้ เช่น 0.25 คือแก้หนึ่งในสี่
- **U_(t+1)(a_t):** ค่าประมาณใหม่ของ action ที่เพิ่งเลือก

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: action A มีค่าประมาณ reward เดิม 4 เลือก A แล้วได้ reward 8 และใช้ η=0.25

1. หาความคลาดเคลื่อน: 8−4 = 4
2. ขยับไปหนึ่งในสี่ของความคลาดเคลื่อน: 0.25×4 = 1
3. ค่าประมาณใหม่จึงเป็น 4+1 = 5; action อื่นที่ไม่ได้เลือกยังไม่ถูกอัปเดตจากสูตรนี้

**ผลที่ได้:** U ใหม่ของ A คือ 5 ไม่ใช่ 8 เพราะผสมข้อมูลใหม่กับค่าประมาณเดิม

**ข้อสรุปจากตัวอย่าง:** พจน์ปรับแก้มีขนาดตาม η หาก reward ต่ำกว่าค่าประมาณเดิม พจน์นี้เป็นลบและทำให้ค่าประมาณลดลง

### 7.2 Mean-field approximation และข้อมูลที่สูญเสียจากการสรุป

การพิจารณาปฏิสัมพันธ์แบบครบทุกคู่มีจำนวน n(n−1)/2 คู่ Mean-field approximation แทนผลของ agent หลายตัวด้วย distribution หรือ summary ของประชากรหรือเพื่อนบ้าน แล้วให้ policy ตอบสนองต่อ summary นั้น ความเหมาะสมของวิธีขึ้นกับการรักษารายละเอียดของ interaction ที่จำเป็นต่อ task

Global mean อาจมีค่าเท่ากันทั้งในกรณีที่สองกลุ่มเคลื่อนสวนกันคนละบริเวณและกรณีที่ทั้งสองกลุ่มกำลังเข้าคอขวดเดียวกัน Policy ที่ใช้เฉพาะค่าเฉลี่ยจึงแยกสองสถานการณ์ไม่ได้ นี่คือ state aliasing ในระดับประชากร การเพิ่ม locality role หรือ summary ที่ละเอียดขึ้นต้องพิจารณาตามข้อมูลที่ task ต้องใช้

แม้การอ่าน summary หนึ่งค่าต่อ agent อาจมีต้นทุนต่ำ แต่ยังต้องนับต้นทุนการสร้าง summary และการหาเพื่อนบ้าน หากใช้การเปรียบเทียบทุกคู่เพื่อค้นเพื่อนบ้าน ต้นทุนส่วนนี้ยังเป็น O(n²) การประเมิน scaling จึงต้องรวม aggregation communication และการปรับ neighborhood

$$
m_i=\frac{1}{\lvert N_i\rvert}\sum_{j\in N_i}\psi(z_j)
$$

ตัวอย่าง neighbor summary เมื่อ N_i ไม่ว่าง; ψ เลือก feature ที่ใช้สรุป และต้องกำหนดค่ากรณีไม่มีเพื่อนบ้าน

**ความหมายของสมการ:** Neighbor summary คือค่าเฉลี่ยของ feature ψ(z_j) จากเพื่อนบ้านในชุด N_i โดยรวม feature ของสมาชิกแล้วหารด้วยจำนวนสมาชิก

**อ่านสัญลักษณ์:**

- **Σ_(j∈N_i):** บวกค่าจากเพื่อนบ้าน j ทุกตัวในชุด N_i
- **|N_i|:** จำนวนสมาชิกในชุดเพื่อนบ้าน ไม่ใช่ความยาวเวกเตอร์
- **ψ(z_j):** feature ที่เลือกจากสถานะเพื่อนบ้าน เช่น velocity สองแกน

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: มีเพื่อนบ้าน 3 ตัว และ ψ คืน velocity เป็น (2,0), (0,2), (1,1) เมตร/วินาที

1. รวมแต่ละแกน: (2+0+1,0+2+1) = (3,3) เมตร/วินาที
2. หารด้วยจำนวนเพื่อนบ้าน 3 ตัว ได้ m_i=(1,1) เมตร/วินาที

**ผลที่ได้:** agent เห็นค่าเฉลี่ย (1,1) แม้แต่ละตัวเคลื่อนต่างทิศ; อีกกลุ่มที่ทุกตัวมี velocity (1,1) ก็ให้ค่าเดียวกัน

**ข้อสรุปจากตัวอย่าง:** ค่าเฉลี่ยลดรายละเอียดแต่ไม่สามารถแยกกลุ่มที่มี mean เท่ากันได้ กรณีไม่มีเพื่อนบ้านต้องกำหนด fallback เพื่อหลีกเลี่ยงการหารด้วยศูนย์

$$
\operatorname{pairs}=\frac{n(n-1)}{2}
$$

pairs หมายถึงจำนวนคู่

ใช้กับคู่แบบไม่เรียงลำดับที่พิจารณาครบทุกคู่; ไม่ใช่ต้นทุนที่จำเป็นของระบบ sparse ทุกแบบ

**ความหมายของสมการ:** จำนวนคู่แบบไม่เรียงลำดับคำนวณจาก n(n−1) หารด้วย 2 เนื่องจากการนับคู่ A–B และ B–A แยกกันเป็นการนับซ้ำ

**อ่านสัญลักษณ์:**

- **n(n−1):** จำนวนคู่แบบเรียงลำดับ โดยไม่จับคู่กับตัวเอง
- **/2:** ตัดการนับซ้ำเมื่อคู่ไม่มีทิศทาง

**ตัวอย่างการคำนวณ:** ตัวอย่างสมมติ: agent 4 ตัวชื่อ A, B, C และ D ต้องตรวจระยะระหว่างทุกคู่

1. นับแบบมีลำดับได้ 4×3 = 12 คู่ เช่น A–B และ B–A ถูกนับแยก
2. หารสองเหลือ 6 คู่: AB, AC, AD, BC, BD, CD

**ผลที่ได้:** เมื่อเพิ่มจาก 4 เป็น 8 ตัว จำนวนคู่เพิ่มจาก 6 เป็น 8×7/2 = 28 คู่

**ข้อสรุปจากตัวอย่าง:** จำนวนคู่เพิ่มประมาณกำลังสองเมื่อพิจารณาครบทุกคู่ ระบบ sparse ต้องประเมินจากกราฟ interaction และต้นทุนการหาเพื่อนบ้านจริง

### 7.3 Coordination และเงื่อนไข equilibrium

Coarse correlated equilibrium หรือ CCE เป็นเงื่อนไขด้านแรงจูงใจ ภายใต้ distribution ร่วมของคำแนะนำ ผู้เล่นไม่สามารถเพิ่ม expected payoff ด้วยการเลือก action ทางเลือกคงที่ล่วงหน้าก่อนเห็นคำแนะนำ หากพิจารณาการเบี่ยงเบนที่ขึ้นกับคำแนะนำที่ได้รับ จะเป็นเงื่อนไข correlated equilibrium ที่ละเอียดกว่า

ตัวอย่างมีสอง agent เลือกหนึ่งในสอง resource หากเลือกต่างกัน แต่ละตัวได้ reward 2 หากเลือกซ้ำกันได้ 0 ผู้ประสานสุ่มแนะนำ (ซ้าย,ขวา) หรือ (ขวา,ซ้าย) อย่างละครึ่ง การทำตามคำแนะนำให้ reward 2 เสมอ ส่วนการเลือกซ้ายคงที่ล่วงหน้าให้ reward เฉลี่ย 1 ตัวอย่างนี้แสดงผลของ correlated signal ผ่านการคำนวณ payoff โดยตรง

Mean-field เป็นวิธีประมาณ interaction ส่วน CCE เป็นเงื่อนไขของ incentives การเคลื่อนที่ไปในทิศเดียวกันหรือ runtime ที่เร็วขึ้นจึงไม่เพียงพอสำหรับยืนยัน CCE ต้องระบุ payoff และทางเลือกเบี่ยงเบนตามนิยาม นอกจากนี้ เกมตัวอย่างยังมี pure equilibrium ที่แต่ละ agent เลือกคนละ resource อย่างคงที่และไม่มีผู้เล่นใดได้ประโยชน์จากการเปลี่ยนฝ่ายเดียว จึงไม่สามารถสรุปว่า CCE ให้ผลดีกว่าทุก equilibrium

$$
\begin{gathered}\mathbb{E}_{a\sim\rho}\bigl[u_i(a)\bigr]\\\ge\mathbb{E}_{a\sim\rho}\bigl[u_i(a_i^{\prime},a_{-i})\bigr]\\\forall\,i,a_i^{\prime}\end{gathered}
$$

เงื่อนไขต้องเป็นจริงสำหรับทุก agent และทุก action ทางเลือกที่เลือกไว้ล่วงหน้า

ρ คือ joint-action distribution, u_i คือ payoff และ a_i′ เป็น action ที่เลือกไว้ล่วงหน้าโดยไม่ขึ้นกับคำแนะนำ; นี่คือนิยาม CCE ในเกมจำกัด

**ความหมายของสมการ:** สำหรับผู้เล่นทุกตัว expected payoff จากการทำตามคำแนะนำร่วมต้องไม่น้อยกว่า expected payoff จากการเปลี่ยนเป็น action คงที่ที่เลือกล่วงหน้า สำหรับทุกทางเลือกดังกล่าว

**อ่านสัญลักษณ์:**

- **E_(a∼ρ):** ค่าเฉลี่ยถ่วงน้ำหนักตามโอกาสของ joint action ที่ผู้ประสานแนะนำ
- **a_i′,a_−i:** แทน action ของผู้เล่น i ด้วยตัวเลือกคงที่ a_i′ โดยตัวอื่นยังทำตามคำแนะนำ
- **≥ สำหรับทุก i,a_i′:** ต้องตรวจผู้เล่นทุกตัวและ action คงที่ที่เป็นทางเลือกทุกตัว

**ตัวอย่างการคำนวณ:** เกมสมมติ: เลือก resource ซ้าย/ขวา; ถ้าแยกกันได้คนละ 2 ถ้าซ้ำได้ 0; ρ แนะนำ (ซ้าย,ขวา) และ (ขวา,ซ้าย) อย่างละครึ่ง

1. ทำตามคำแนะนำ: ทั้งสองกรณีได้ 2 จึงมีค่าเฉลี่ย 0.5×2+0.5×2 = 2
2. ผู้เล่น 1 เลือกซ้ายคงที่: อีกตัวอยู่ขวาครึ่งหนึ่งและซ้ายครึ่งหนึ่ง จึงได้ 0.5×2+0.5×0 = 1
3. เลือกขวาคงที่ก็ได้ 1; ผู้เล่น 2 มีผลเหมือนกันจากความสมมาตร

**ผลที่ได้:** ทุกกรณีที่ต้องตรวจได้ 2 ≥ 1 จึงผ่านเงื่อนไข CCE ของเกมนี้

**ข้อสรุปจากตัวอย่าง:** เงื่อนไขนี้พิจารณา action เบี่ยงเบนที่เลือกก่อนเห็นคำแนะนำ ไม่ครอบคลุมกลยุทธ์เบี่ยงเบนที่ขึ้นกับคำแนะนำที่ได้รับ

### 7.4 Local rules ตัววัดพฤติกรรม และระดับความละเอียด

Boids ใช้กฎ separation เพื่อหลีกเลี่ยงเพื่อนบ้านที่ใกล้เกินไป alignment เพื่อปรับความเร็วเข้าหาค่าเฉลี่ยของเพื่อนบ้าน และ cohesion เพื่อเคลื่อนเข้าหาศูนย์กลางของกลุ่ม ใน lab กฎเหล่านี้ปรับ velocity และจำกัด speed ก่อน update position พฤติกรรมรวมเกิดจาก local update ที่ทำซ้ำโดยไม่มี neural training

Coherence ใน lab นิยามเป็น norm ของค่าเฉลี่ย unit velocity จึงมีค่าสูงเมื่อทิศทางสอดคล้องกัน ส่วน collision pairs นับคู่ที่มีระยะต่ำกว่า threshold ตัววัดทั้งสองอาจมี tradeoff เนื่องจาก alignment สูงไม่ได้รับประกันระยะห่างที่ปลอดภัย และ lab ไม่มี payoff หรือ regret สำหรับประเมิน equilibrium

ระบบขนาดใหญ่อาจให้ reflex update ถี่กว่า planning ซึ่ง update เฉพาะเมื่อเกิด event และอาจปรับระดับรายละเอียดตามพื้นที่ วิธีนี้ลดปริมาณงานแต่เปลี่ยนความละเอียดของเวลาและข้อมูล จึงต้องตรวจ stale actions invariant และความคลาดเคลื่อนของพฤติกรรมก่อนรายงานจำนวน agent ที่รองรับ

$$
\operatorname{coherence}=\left\lVert\frac{1}{n}\sum_i\hat{v}_i\right\rVert
$$

$$
\hat{v}_i=\frac{v_i}{\lVert v_i\rVert}
$$

v_i คือ velocity; กำหนด v̂_i=0 หากหยุดนิ่ง ค่าอยู่ใน [0,1] และวัดความสอดคล้องของทิศ

**ความหมายของสมการ:** Coherence คือ norm ของค่าเฉลี่ย unit velocity ของ agent ทุกตัว เมื่อทิศทางตรงกันเวกเตอร์เสริมกัน และเมื่อสวนกันเวกเตอร์หักล้างกัน โดยกำหนด unit velocity เป็นศูนย์สำหรับ agent ที่หยุดนิ่ง

**อ่านสัญลักษณ์:**

- **v̂_i:** unit velocity: หารด้วยความเร็วเพื่อเหลือทิศ; กำหนดเป็นศูนย์เมื่อหยุดนิ่ง
- **Σ_i / n:** เฉลี่ยทุกตัว รวมตัวที่หยุดนิ่งตามนิยามนี้
- **∥…∥:** ความยาวของเวกเตอร์เฉลี่ย จึงไม่ติดลบ

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: agent 2 ตัวมี velocity (2,0) และ (5,0) เมตร/วินาที

1. normalize แล้วได้ (1,0) ทั้งคู่; ค่าเฉลี่ย (1,0) มีความยาว 1 จึง coherence=1
2. ถ้าตัวที่สองเปลี่ยนเป็น (−5,0) จะได้ทิศ (−1,0); ค่าเฉลี่ยเป็น (0,0) จึง coherence=0
3. ถ้าตัวที่สองหยุดนิ่ง จะใช้ (0,0); ค่าเฉลี่ยเป็น (0.5,0) จึง coherence=0.5

**ผลที่ได้:** ความเร็วต่างกันยัง coherence=1 ได้ ส่วน coherence=0 อาจเกิดจากวิ่งสวนกันหรือทุกตัวหยุดก็ได้

**ข้อสรุปจากตัวอย่าง:** Coherence สรุปทิศทางรวม ต้องพิจารณาควบคู่กับ speed และ collision เพื่อแยกการเคลื่อนที่ที่สอดคล้องกันออกจากการหยุดนิ่งหรือระยะห่างที่ไม่ปลอดภัย

$$
\begin{gathered}\mathrm{collision\ pairs}\\=\sum_{i<j}\mathbf{1}\!\left[\lVert x_i-x_j\rVert<d_{\mathrm{min}}\right]\end{gathered}
$$

x_i เป็นตำแหน่งและ d_min คือระยะขั้นต่ำที่ใช้เป็นตัวชี้วัด; lab ใช้ 16 หน่วยพิกัด

**ความหมายของสมการ:** ผลรวมนี้นับคู่ตำแหน่งที่มีระยะต่ำกว่า d_min โดยพิจารณาแต่ละคู่ครั้งเดียวและใช้ indicator 1 เมื่อเงื่อนไขเป็นจริง มิฉะนั้นเป็น 0

**อ่านสัญลักษณ์:**

- **i<j:** เลือกคู่โดยไม่ซ้ำ และไม่จับ agent กับตัวเอง
- **1[เงื่อนไข]:** indicator: ได้ 1 เมื่อเงื่อนไขจริง มิฉะนั้นได้ 0
- **<d_min:** ต้องน้อยกว่าเกณฑ์แบบ strict; เท่ากับเกณฑ์พอดียังไม่นับ

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: A=(0,0), B=(10,0), C=(26,0) และ d_min=16 หน่วยพิกัดตาม lab

1. คู่ AB ห่าง 10 ซึ่งน้อยกว่า 16 จึงนับ 1
2. คู่ AC ห่าง 26 จึงนับ 0; คู่ BC ห่าง 16 พอดีจึงนับ 0 เช่นกัน
3. รวม 1+0+0 = 1 คู่

**ผลที่ได้:** collision_pairs=1 หมายถึงคู่ที่ต่ำกว่าเกณฑ์ 1 คู่ ไม่ใช่จำนวน agent ที่เกี่ยวข้อง ซึ่งตัวอย่างนี้มี 2 ตัว

**ข้อสรุปจากตัวอย่าง:** Metric นี้ระบุจำนวนคู่ตาม threshold ส่วนการชนทางกายภาพขึ้นกับรูปร่าง ขนาด และนิยาม collision ใน simulation

### นิยามที่ใช้ในบทนี้

- **joint action:** ชุด action ของหลาย agent ที่ร่วมกำหนด transition ของ environment
- **mean-field approximation:** การประมาณปฏิสัมพันธ์จำนวนมากด้วย distribution หรือ summary ของประชากรหรือเพื่อนบ้าน

- **emergent behavior:** พฤติกรรมระดับรวมที่เกิดจากกฎเฉพาะตัวและปฏิสัมพันธ์ที่ทำซ้ำ

[เปิดบทพร้อมห้องทดลอง](../index.html#story/08) · [หัวข้อสังเคราะห์](topics/08-performance-and-benchmarks.md)

- [บท 3](#chapter-02): จำนวน pass, node expansions และ budget ของ search
- [บท 4](#chapter-03): selective accuracy, coverage และ abstention
- [บท 7](#chapter-04): interaction และวงรอบ update ของหลาย agent

### โจทย์

Kernel time tokens/s และจำนวน agent อาจใช้ขอบเขตการวัดต่างกัน การเปรียบเทียบประสิทธิภาพต้องเริ่มจากการกำหนดหน่วยงานและเงื่อนไขความสำเร็จของ request

### 8.1 หน่วยงานและขอบเขตการวัดเวลา

Latency คือระยะเวลาของงานหนึ่งจากจุดเริ่มถึงจุดจบที่กำหนด ส่วน throughput คือจำนวนงานที่เสร็จต่อหน่วยเวลา หน่วยงานต้องระบุอย่างชัดเจน เนื่องจาก tokenizer token generated token verified decision และ completed tick มีปริมาณ computation และเกณฑ์ความสำเร็จต่างกัน

สำหรับ pipeline ที่ทำงานตามลำดับ latency รวมได้จาก queue preprocessing retrieval model verification และ output หากขั้นตอน overlap หรือทำงานขนาน ต้องวัด critical path และ wall-clock จริง ผลรวมเวลาของทุก worker ไม่ใช่ latency ของ request

TTFT หรือ time to first token วัดเวลารอ token แรก ซึ่งขึ้นกับ queue prefill และ cache ส่วนเวลาระหว่าง token ถัดไปสัมพันธ์กับ decode การรายงาน p50 p95 หรือ p99 พร้อมจำนวน sample ช่วยอธิบาย distribution ของ latency ที่ค่าเฉลี่ยเพียงอย่างเดียวอาจไม่แสดง

$$
\begin{aligned}T_{\mathrm{request}}={}&T_{\mathrm{queue}}+T_{\mathrm{pre}}+T_{\mathrm{retrieve}}\\&{}+T_{\mathrm{model}}+T_{\mathrm{verify}}+T_{\mathrm{output}}\end{aligned}
$$

ใช้การบวกตรงเมื่อขั้นตอนอยู่ในเส้นทางเรียงลำดับและไม่ double-count งานที่ overlap

**ความหมายของสมการ:** เวลา request เท่ากับผลรวมเวลารอคิวและเวลาของขั้นตอนตั้งแต่ preprocessing ถึง output เมื่อขั้นตอนทำงานตามลำดับและไม่มีเวลาซ้อนกัน

**อ่านสัญลักษณ์:**

- **T_queue:** เวลาที่ request รอก่อนเริ่มประมวลผล
- **T_model / T_verify:** เวลาสร้างคำตอบ / เวลาตรวจคำตอบ ต้องกำหนดขอบเขตไม่ให้ซ้ำกัน
- **+:** บวกช่วงเวลาที่เรียงต่อกัน โดยทุกพจน์ต้องใช้หน่วยเดียวกัน

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติของ pipeline ที่ทำทีละขั้น: queue 10, pre 5, retrieve 15, model 60, verify 8, output 2 มิลลิวินาที

1. รวมช่วงก่อน model: 10+5+15 = 30 ms
2. รวมทั้งเส้นทาง: 30+60+8+2 = 100 ms
3. ถ้าเร่งเฉพาะ model ให้เหลือ 30 ms โดยส่วนอื่นคงเดิม เวลาใหม่คือ 30+30+8+2 = 70 ms

**ผลที่ได้:** request เดิมใช้ 100 ms แม้การสร้างคำตอบเองใช้ 60 ms; หลังเปลี่ยนใช้ 70 ms

**ข้อสรุปจากตัวอย่าง:** สูตรใช้กับขั้นตอนที่เรียงตามลำดับ หาก retrieval หรือ worker overlap ต้องวัด wall-clock ตามขอบเขตที่กำหนด

$$
\operatorname{throughput}=\frac{N_{\mathrm{completed}}}{T_{\mathrm{elapsed}}}
$$

ตัวเศษ = จำนวนงานที่เสร็จ; ตัวส่วน = เวลาที่ผ่านไป (elapsed time)

ต้องระบุเงื่อนไขสำเร็จและหน่วย เช่น verified decisions/s; ไม่เอาหน่วยคนละชนิดมาเทียบ speedup

**ความหมายของสมการ:** Throughput คือจำนวนงานที่เสร็จตามเกณฑ์หารด้วย elapsed time โดยต้องใช้หน่วยงานและช่วงเวลาที่สอดคล้องกัน

**อ่านสัญลักษณ์:**

- **จำนวนงานที่เสร็จ:** นับหน่วยเดียวกัน เช่น request ที่ผ่านขั้นตอนครบ ไม่ใช่ผสม token กับ request
- **elapsed time:** เวลาบนนาฬิกาตั้งแต่เริ่มถึงจบช่วงวัด รวมช่วงที่มีหลายงานทำพร้อมกัน
- **งาน/s:** หน่วยของ throughput เมื่อใช้เวลาเป็นวินาที

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: ในช่วงวัด 10 วินาที ระบบทำ request เสร็จ 120 รายการ โดยแต่ละรายการมีขอบเขตงานเดียวกัน

1. หารจำนวนงานด้วยเวลา: 120/10 = 12 request/s
2. ถ้าต้องรายงานต่อนาที คูณ 60 จึงได้ 720 request/นาที ภายใต้ค่าเฉลี่ยเดียวกัน

**ผลที่ได้:** Throughput คือ 12 request/s; ยังบอกไม่ได้ว่าแต่ละ request ใช้ latency 1/12 วินาที เพราะอาจทำงานพร้อมกันและรอคิว

**ข้อสรุปจากตัวอย่าง:** การเปรียบเทียบ throughput ต้องระบุหน่วยงาน ช่วงวัด และ concurrency

### 8.2 Amdahl’s law และสัดส่วนเวลาฐาน

ให้ T_0 เป็นเวลาเดิมของ workload คงที่ p เป็นสัดส่วนเวลาที่ปรับปรุงได้ และ s≥1 เป็น local speedup ของส่วนนั้น เวลา pT_0 ลดลงเหลือ pT_0/s ขณะที่ส่วนที่เหลือยังใช้ (1−p)T_0 Speedup รวมจึงคำนวณจากอัตราส่วนของเวลาเดิมต่อเวลาใหม่

สมมติฐานของการคำนวณคือ workload และคุณภาพคงเดิม p อ้างอิงเวลาฐาน ส่วนที่เหลือไม่เปลี่ยน และไม่มี overhead ใหม่หรือการเปลี่ยนรูปแบบ overlap หากการเร่ง kernel เพิ่มต้นทุน copy หรือ synchronization ต้องรวมต้นทุนนั้นในเวลาใหม่

เมื่อ p=0.25 และ s=32 เวลาใหม่เท่ากับ 0.75+0.25/32=0.7578125 ของเวลาเดิม จึงได้ speedup ประมาณ 1.32 เท่า แม้ส่วนนั้นมี speedup เข้าใกล้อนันต์ speedup รวมยังมีเพดาน 1/0.75≈1.33 เท่า การวัดสัดส่วนเวลาแต่ละส่วนจึงเป็นข้อมูลพื้นฐานในการเลือกจุดปรับปรุง

$$
T_1=T_0\!\left[(1-p)+\frac{p}{s}\right]
$$

$$
\operatorname{speedup}=\frac{1}{(1-p)+\frac{p}{s}}
$$

p ไม่มีหน่วย เป็นสัดส่วนของ T_0; s เป็นอัตราส่วนความเร็วเฉพาะส่วน

**ความหมายของสมการ:** เวลาใหม่ประกอบด้วยส่วนที่ไม่เปลี่ยนและส่วนที่มีเวลาลดลง s เท่า Speedup รวมได้จากเวลาเดิมหารเวลาใหม่

**อ่านสัญลักษณ์:**

- **p:** สัดส่วนจากเวลาเดิม เช่น 25% ต้องแทนเป็น 0.25
- **s:** ความเร็วเฉพาะส่วน เช่น เร็วขึ้น 32 เท่า หมายถึงเวลาส่วนนั้นเหลือ 1/32
- **(1−p)+p/s:** เวลาใหม่คิดเป็นสัดส่วนของเวลาเดิม ไม่มีหน่วย

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: T_0=100 ms โดยส่วนที่ปรับใช้ 25 ms จึง p=0.25 และเร่งส่วนนั้นได้ s=32

1. ส่วนที่ไม่เปลี่ยนใช้ (1−0.25)×100 = 75 ms
2. ส่วนที่เร่งเหลือ 25/32 = 0.78125 ms จึงรวมเป็น T_1=75.78125 ms
3. speedup รวม = 100/75.78125 ≈ 1.32 เท่า

**ผลที่ได้:** ความเร็วเฉพาะส่วน 32 เท่าให้ความเร็วทั้ง request ประมาณ 1.32 เท่าในตัวอย่างนี้

**ข้อสรุปจากตัวอย่าง:** พจน์ p/s ลดเฉพาะเวลาสัดส่วน p ของเวลาฐาน การใช้สูตรต้องตรวจสมมติฐานด้าน workload คุณภาพ remainder และ overhead

เมื่อทั้งสองเงื่อนไขนี้เป็นจริง

$$
s\to\infty,\qquad p<1
$$

$$
\operatorname{speedup}_{\mathrm{max}}=\frac{1}{1-p}
$$

เพดานภายใต้ fixed workload และ unchanged remainder; ไม่รวมผลจากการเปลี่ยน algorithm หรือเพิ่ม overhead

**ความหมายของสมการ:** เมื่อเวลาในส่วนที่ปรับเข้าใกล้ศูนย์ เวลาใหม่ยังประกอบด้วยส่วนที่ไม่เปลี่ยน เพดาน speedup จึงเท่ากับหนึ่งหารสัดส่วน 1−p

**อ่านสัญลักษณ์:**

- **s→∞:** สมมติให้ความเร็วเฉพาะส่วนสูงขึ้นไม่จำกัด เพื่อดูขีดจำกัดทางคณิตศาสตร์
- **1−p:** สัดส่วนเวลาเดิมที่ยังต้องจ่าย แม้ส่วนที่ปรับเร็วมาก
- **p<1:** ต้องมีส่วนที่ไม่เปลี่ยนเหลืออยู่ จึงใช้เพดานจำกัดนี้ได้

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: งานเดิมใช้ 100 ms และส่วนที่เร่งได้กิน 25% ของเวลาเดิม

1. เมื่อเร่งส่วน 25 ms จนเวลาเข้าใกล้ 0 ส่วนที่เหลือยังใช้ 75 ms
2. ความเร็วสูงสุดจึงเข้าใกล้ 100/75 = 1/0.75 ≈ 1.33 เท่า

**ผลที่ได้:** การปรับส่วนเดิมต่อไปอย่างเดียวทำให้เร็วเกินประมาณ 1.33 เท่าไม่ได้ภายใต้สมมติฐานนี้

**ข้อสรุปจากตัวอย่าง:** เพดานนี้ใช้ภายใต้สมมติฐานเดิม หาก algorithm workload หรือ overhead เปลี่ยน ต้องปรับแบบจำลองเวลา

### 8.3 ประสิทธิภาพภายใต้เกณฑ์คุณภาพเดียวกัน

ระบบที่ลดจำนวนคำตอบหรือข้าม verifier อาจใช้เวลาน้อยลง แต่เปลี่ยนเงื่อนไขของงาน การประเมินจึงควรรายงาน solve rate invalid output coverage timeout และ latency ร่วมกัน หากวัดเฉพาะ request ที่สำเร็จ ต้องระบุจำนวน request ที่ถูกตัดออกจาก denominator

Batching อาจเพิ่ม throughput จากการใช้ทรัพยากรเครื่องได้มากขึ้น แต่เพิ่มเวลารอรวบ batch และการใช้ memory Concurrency จึงเป็นส่วนหนึ่งของข้อกำหนด workload สำหรับ cache ต้องระบุ cold หรือ warm state hit rate และความถูกต้องของผลที่นำกลับมาใช้

Simulation ที่ update 20 Hz มี budget 50 ms ต่อ tick หาก physics synchronization และงานอื่นใช้รวม 35 ms จะเหลือ 15 ms สำหรับ decision ทั้งหมด การคูณเวลา kernel ต่อ agent ไม่ครอบคลุมต้นทุน aggregation queue invalidation และการประสาน action

$$
\begin{gathered}\operatorname{useful\ throughput}\\=\frac{N_{\mathrm{correct,usable}}}{T_{\mathrm{elapsed}}}\end{gathered}
$$

ตัวเศษ = จำนวนผลที่ถูกและผ่านเงื่อนไขใช้งาน; ตัวส่วน = เวลาที่ผ่านไป (elapsed time)

นับทั้ง correctness และความพร้อมใช้จริง; ต้องมีวิธีตรวจผลที่ถูกอิสระจากตัวระบบ

**ความหมายของสมการ:** Useful throughput นับผลที่ผ่านทั้งเกณฑ์ความถูกต้องและเงื่อนไขการใช้งาน แล้วหารด้วย elapsed time ทั้งหมด

**อ่านสัญลักษณ์:**

- **ถูกและผ่านเงื่อนไข:** เป็นเงื่อนไขร่วม เช่น คำตอบถูกและทัน deadline ต้องผ่านทั้งคู่
- **elapsed time:** รวมเวลาที่ระบบใช้กับผลผิด timeout และงานที่ไม่ผ่านด้วย
- **useful throughput:** หน่วยเป็นผลที่ใช้ได้/s ไม่ใช่ raw outputs/s

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: 10 วินาทีได้ output 100 รายการ; ตรวจอิสระแล้วถูก 90 รายการ แต่ในกลุ่มที่ถูกมี 10 รายการมาช้ากว่า deadline

1. ผลที่ถูกและทันเวลาเหลือ 90−10 = 80 รายการ
2. หารด้วยช่วงวัดทั้งหมด: 80/10 = 8 ผลที่ใช้ได้/s

**ผลที่ได้:** ระบบมี useful throughput 8 ผล/s แม้ส่ง output รวม 10 รายการ/s

**ข้อสรุปจากตัวอย่าง:** ต้องกำหนดเกณฑ์ความถูกต้องและความพร้อมใช้ก่อนวัด เพื่อประเมินว่าการเร่งระบบเพิ่มผลงานที่สำเร็จจริงหรือไม่

$$
\mathrm{tick\ budget}_{\mathrm{ms}}=\frac{1000}{\mathrm{update\ rate}_{\mathrm{Hz}}}
$$

20 Hz ให้ 50 ms ต่อรอบ; budget ของ AI เป็นเวลาที่เหลือหลังส่วนอื่นของวงจร

**ความหมายของสมการ:** เวลาต่อ tick เท่ากับ 1,000 มิลลิวินาทีหารด้วยจำนวนรอบ update ต่อวินาที เป็น budget ของวงจรทั้งหมด

**อ่านสัญลักษณ์:**

- **Hz:** จำนวนรอบต่อวินาที เช่น 20 Hz = 20 รอบ/s
- **1000:** ตัวแปลงหน่วยจากหนึ่งวินาทีเป็น 1,000 ms
- **tick_budget_ms:** เวลาต่อหนึ่งรอบของทั้งวงจร ไม่ใช่เวลาที่มอบให้ AI ได้ทั้งหมด

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: simulation ต้องอัปเดต 20 Hz และ physics กับงานอื่นใช้รวม 35 ms ต่อรอบ

1. หาเวลาต่อรอบ: 1000/20 = 50 ms
2. หักงานอื่นออก จึงเหลือเวลาให้ AI 50−35 = 15 ms ต่อรอบ

**ผลที่ได้:** AI ต้องทำงานที่จำเป็นในรอบนั้นให้เสร็จภายใน 15 ms ตามแบบจำลองที่ไม่มีงาน overlap นี้

**ข้อสรุปจากตัวอย่าง:** เมื่อ update rate เพิ่ม budget ต่อรอบลดลง การประเมินต้องรวม aggregation queue และ synchronization ตามเส้นทางที่ใช้งบจริง

### 8.4 Experimental matrix และการแยกผลของแต่ละปัจจัย

การเปรียบเทียบต้องตรึง input set output contract weights precision และ hardware/runtime version ตามคำถามที่ต้องการตอบ แล้วแยกปัจจัยที่เปลี่ยน เช่น implementation ภาษาเดิมหรือภาษาใหม่ และ greedy หรือ search หากเปลี่ยนสองปัจจัยพร้อมกัน จะไม่สามารถแยกผลของวิธีตัดสินใจออกจากผลของ execution ได้

ข้อมูลประกอบควรครอบคลุม warmup จำนวนรอบ raw timing distribution ของงาน prompt/output length batch concurrency และ cache state ผลที่ได้จึงมีขอบเขตตามเงื่อนไขการทดลอง การประเมิน tail percentile ต้องมี sample เพียงพอและรายงานความละเอียดให้เหมาะกับข้อมูล

Correctness gate ควรมาก่อน performance gate โดยกำหนด threshold ตามคุณสมบัติที่ระบบต้องรักษา และเปรียบเทียบ paired cases ที่ใช้ input และ seed เดียวกัน ผลการวัดช่วยระบุว่าควรปรับ algorithm memory movement หรือ hardware ซึ่งเป็นประเด็นของบทถัดไป

comparison = workload + quality contract + timing boundary + execution conditions

ชุดข้อกำหนดขั้นต่ำที่ทำให้ speedup มีความหมายและย้อนตรวจผลได้

**ความหมายของสมการ:** ข้อความนี้ระบุองค์ประกอบของข้อกำหนดการเปรียบเทียบ เครื่องหมาย = และ + ประกอบนิยามของ workload quality contract timing boundary และ execution conditions ไม่ใช่การบวกเชิงตัวเลข

**อ่านสัญลักษณ์:**

- **workload:** ชุด input และลักษณะงานที่นำมาเปรียบเทียบ
- **quality contract:** เงื่อนไขที่ผลต้องผ่าน เช่น valid path และ deadline
- **timing boundary:** จุดเริ่มและจบการจับเวลา
- **execution conditions:** เครื่อง รุ่น runtime batch concurrency และสถานะ cache

**ตัวอย่างการคำนวณ:** สถานการณ์สมมติ: ต้องการเทียบ runtime A กับ B สำหรับ solver บน maze 200 แผนที่เดียวกัน

1. กำหนดงานและคุณภาพ: ใช้ 200 แผนที่ที่ตรึงไว้ และผลต้องเป็น path ที่ตัวตรวจอิสระยืนยันได้
2. กำหนดเวลา: เริ่มเมื่อรับ request และจบเมื่อผ่าน verifier โดยนับ timeout เหมือนกัน
3. กำหนดเงื่อนไข: เครื่องเดียวกัน precision เดียวกัน concurrency=1 และใช้ cache แบบ cold เหมือนกัน

**ผลที่ได้:** จึงอ่านผลเวลา A/B ร่วมกับ verified success rate ได้บนโจทย์และขอบเขตที่ระบุ

**ข้อสรุปจากตัวอย่าง:** ข้อกำหนดเหล่านี้ช่วยตรวจว่าผลด้านความเร็วสัมพันธ์กับการเปลี่ยนเงื่อนไขใด ก่อนคำนวณ speedup

### นิยามที่ใช้ในบทนี้

- **latency / throughput:** ระยะเวลาต่อหนึ่งงาน / จำนวนงานที่เสร็จต่อหน่วยเวลา ภายใต้ขอบเขตและหน่วยงานที่ระบุ
- **TTFT / prefill / decode:** เวลาถึง token แรก / การประมวลผล prompt / การสร้าง token ถัดไปในแต่ละขั้น
- **tail latency:** ค่าบริเวณปลาย distribution เช่น p95 ซึ่ง 95% ของ sample มีเวลาไม่เกินค่านั้น
- **Amdahl fraction p:** สัดส่วนของเวลาฐานที่ได้รับผลจากการปรับปรุง ภายใต้ workload คงที่

### ทดลองกลไก

**ขั้นตอนการทดลอง:** กำหนด p=0.25 และปรับ s จาก 1 ถึง 32 จากนั้นเปลี่ยนเป็น p=0.75 โดยคำนวณเวลาใหม่ก่อนตรวจ readout

**ประเด็นที่ศึกษา:** เปรียบเทียบส่วนเวลาที่คงเดิมและเพดาน speedup กับ local speedup ที่กำหนด

**ขอบเขตของแบบจำลอง:** Lab คำนวณ Amdahl’s law ภายใต้ workload คงที่ ส่วนที่เหลือไม่เปลี่ยน และไม่มี overhead ใหม่ ค่า p ของระบบจริงต้องมาจากการวัด

### 9.1 Cost model และจุดตัดระหว่าง CPU กับ GPU

กำหนด N เป็นจำนวน work units ชนิดเดียวกัน q_C และ q_G เป็นอัตรางานต่อ microsecond ของ CPU และ GPU และ τ เป็น fixed GPU overhead หน่วย microseconds แบบจำลองพื้นฐานให้เวลา CPU เป็น N/q_C และเวลา GPU เป็น τ+N/q_G

การตั้งเวลาทั้งสองเท่ากันให้จุดตัด N* เมื่อ q_G>q_C และ τ>0 ใน lab ใช้ q_C=420 q_G=2200 และ τ=80 จึงได้ N*≈41,528 work units หากอัตรางานของ GPU ไม่สูงกว่า CPU จะไม่มีจุดตัดบวกภายใต้แบบจำลองนี้

ที่ N=1,000 เวลา CPU ประมาณ 2.38 µs และ GPU 80.45 µs ส่วนที่ N=100,000 เวลา CPU ประมาณ 238.10 µs และ GPU 125.45 µs ค่าทั้งหมดเป็นตัวเลขสังเคราะห์เพื่อแสดงผลของ overhead ไม่ใช่ threshold ของ hardware รุ่นใด นอกจากนี้ throughput จริงอาจเปลี่ยนตาม N

$$
T_{\mathrm{CPU}}=\frac{N}{q_C}
$$

$$
T_{\mathrm{GPU}}=\tau+\frac{N}{q_G}
$$

N เป็น work units; q มีหน่วย work units/µs และ τ มีหน่วย µs จึงได้เวลาทั้งสองเป็น µs

**ความหมายของสมการ:** เวลา computation เท่ากับจำนวน work units หารด้วยอัตรางาน สำหรับ GPU ต้องรวม fixed overhead τ ก่อนการประเมินเวลารวม

**อ่านสัญลักษณ์:**

- **N/q:** จำนวน work units หารด้วย work units/µs จึงเหลือหน่วย µs
- **τ:** fixed overhead ของ GPU ที่ต้องจ่ายแม้งานเล็ก
- **q_C, q_G:** อัตรางาน CPU/GPU ที่สมมติว่าคงที่ในแบบจำลองนี้

**ตัวอย่างการคำนวณ:** ตัวเลขสังเคราะห์ของ lab: N=1,000 work units, q_C=420, q_G=2,200 work units/µs และ τ=80 µs

1. CPU ใช้ 1,000/420 ≈ 2.38 µs
2. ส่วนทำงานบน GPU ใช้ 1,000/2,200 ≈ 0.45 µs
3. รวม overhead แล้ว GPU ใช้ 80+0.45 ≈ 80.45 µs

**ผลที่ได้:** GPU คำนวณส่วนงานได้เร็ว แต่เวลารวมสำหรับงานเล็กนี้ยังมากกว่า CPU เพราะ fixed overhead

**ข้อสรุปจากตัวอย่าง:** N/q ให้เวลา computation ส่วนต้นทุนก่อนและหลัง computation ต้องรวมตามขอบเขตการเปรียบเทียบ

$$
N^{*}=\frac{\tau}{\frac{1}{q_C}-\frac{1}{q_G}}
$$

ใช้เมื่อ q_G>q_C; denominator มีหน่วย µs/work unit ทำให้ N* มีหน่วย work unit

**ความหมายของสมการ:** จุดตัด N* คือขนาดงานที่เวลา CPU และ GPU เท่ากัน คำนวณจาก GPU overhead หารด้วยผลต่างเวลาต่อ work unit ของ CPU และ GPU

**อ่านสัญลักษณ์:**

- **1/q_C − 1/q_G:** เวลาที่ประหยัดได้ต่อหนึ่ง work unit หน่วย µs/work unit
- **N*:** ขนาดงาน ณ จุดตัด ไม่ใช่ระยะเวลาที่จุดตัด
- **q_G>q_C:** เงื่อนไขให้ GPU ประหยัดเวลาต่อหน่วยและมีโอกาสคืนทุน overhead

**ตัวอย่างการคำนวณ:** ใช้ค่าจำลองของ lab: q_C=420, q_G=2,200 work units/µs และ τ=80 µs

1. CPU ใช้ต่อหน่วยประมาณ 0.002381 µs ส่วน GPU ใช้ 0.000455 µs จึงประหยัดได้ประมาณ 0.001926 µs/work unit
2. คำนวณด้วยค่าที่ยังไม่ปัดเศษ: N*=80/(1/420−1/2200) ≈ 41,528 work units
3. แทนกลับที่จุดตัด: CPU≈98.88 µs และ GPU≈80+18.88=98.88 µs

**ผลที่ได้:** ภายใต้แบบจำลองนี้ งานใหญ่กว่าจุดตัดให้ GPU คุ้มเวลารวม ส่วนงานเล็กกว่าจุดตัดให้ CPU คุ้มกว่า

**ข้อสรุปจากตัวอย่าง:** จุดตัดขึ้นกับ overhead และอัตรางานจริง หากอัตรางานเปลี่ยนตาม batch หรือ N ต้องปรับแบบจำลอง

### 9.2 Compute-bound Memory-bound และ access pattern

งาน compute-bound ถูกจำกัดด้วยอัตราคำนวณ ส่วนงาน memory-bound ถูกจำกัดด้วยการเคลื่อนย้ายข้อมูล Arithmetic intensity คือจำนวน FLOPs ต่อ bytes ที่อ่านเขียนผ่าน memory ระดับที่กำลังวิเคราะห์ การใช้ข้อมูลเพียงครั้งเดียวและการ reuse หลายครั้งจึงให้ประสิทธิภาพต่างกัน

SIMD บน CPU ทำ operation เดียวกันกับข้อมูลหลาย lane และอาจได้ประโยชน์จาก memory layout ที่ต่อเนื่องและ branch ที่เหมาะสม ส่วน GPU ใช้หลาย thread ตาม execution model พร้อมต้นทุน dispatch scheduling และ synchronization การใช้ชนิด vector ในภาษาไม่ได้หมายถึงการส่ง computation ไป GPU โดยอัตโนมัติ

หากจัดเก็บ entity เป็น [x,y,vx,vy] ซ้ำกัน แต่ loop อ่านเฉพาะ x ของทุก entity การเข้าถึงอาจมี stride และอ่าน bytes ที่ไม่ได้ใช้ การแยก array ตาม field อาจเหมาะกับงานนี้ ขณะที่ loop ซึ่งใช้ทุก field ของ entity เดียวอาจเหมาะกับรูปแบบเดิม การเลือก layout จึงต้องอ้างอิง access pattern

$$
I=\frac{F}{D}
$$

$$
T_{\mathrm{execution}}\ge\max\!\left(\frac{F}{P_{\mathrm{peak}}},\frac{D}{B_{\mathrm{mem}}}\right)
$$

F=FLOPs, D=bytes ที่เคลื่อนผ่าน memory ระดับที่เลือก, P_peak=FLOPs/s, B_mem=bytes/s; เป็นขอบล่างเชิงอุดมคติที่ยังไม่รวม overhead

**ความหมายของสมการ:** Arithmetic intensity คำนวณจาก FLOPs หารด้วย bytes ที่เคลื่อนย้าย ส่วนขอบล่างของ execution time เป็นค่าสูงสุดระหว่างเวลาขั้นต่ำด้าน compute และด้าน memory

**อ่านสัญลักษณ์:**

- **I=F/D:** arithmetic intensity หน่วย FLOPs/byte
- **F/P_peak:** เวลาอย่างน้อยที่ต้องใช้ทำ arithmetic หากใช้กำลังคำนวณได้เต็ม
- **D/B_mem:** เวลาอย่างน้อยที่ต้องใช้ขนข้อมูลผ่าน memory ระดับที่เลือก
- **max / ≥:** เลือกค่าที่มากกว่าเป็นขอบล่างของเวลา ไม่ใช่บวกสองค่าทันที

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: F=2×10⁹ FLOPs, D=10⁹ bytes, P_peak=10¹¹ FLOPs/s และ B_mem=10¹⁰ bytes/s

1. intensity = (2×10⁹)/10⁹ = 2 FLOPs/byte
2. ขอบล่างจาก compute = (2×10⁹)/10¹¹ = 0.02 s หรือ 20 ms
3. ขอบล่างจาก memory = 10⁹/10¹⁰ = 0.1 s หรือ 100 ms; max(20,100)=100 ms

**ผลที่ได้:** T_execution ≥ 100 ms ในแบบจำลองนี้ โดย memory เป็นข้อจำกัดที่สูงกว่า; เวลาจริงอาจมากกว่านี้จาก overhead และการใช้เครื่องไม่เต็ม

**ข้อสรุปจากตัวอย่าง:** การเพิ่ม peak FLOPs เพียงอย่างเดียวไม่ลดขอบล่าง 100 ms หากปริมาณข้อมูลและ memory bandwidth คงเดิม

$$
\begin{aligned}T_{\mathrm{end\text{-}to\text{-}end}}={}&T_{\mathrm{prepare}}+T_{\mathrm{transfer}}+T_{\mathrm{dispatch}}\\&{}+T_{\mathrm{execute}}+T_{\mathrm{sync}}+T_{\mathrm{finish}}\end{aligned}
$$

ใช้แบ่งรายการต้นทุนก่อนวัด wall-clock; หาก overlap ให้ตรวจ critical path และไม่บวกเวลาซ้ำ

**ความหมายของสมการ:** End-to-end time ประกอบด้วยการเตรียมข้อมูล transfer dispatch execution synchronization และการจัดการผล การแบ่งช่วงต้องหลีกเลี่ยงการนับเวลาซ้ำ

**อ่านสัญลักษณ์:**

- **T_transfer:** เวลาขนข้อมูล เช่น ระหว่าง host กับ device ภายในขอบเขตที่วัด
- **T_dispatch / T_sync:** เวลาส่งงานเข้า runtime / เวลารอหรือประสาน completion ที่ยังไม่นับไว้
- **+:** บวกได้เมื่อแบ่งช่วงเวลาไม่ซ้ำและขั้นตอนเรียงต่อกัน

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติของ trace แบบเรียงขั้นและไม่ซ้อนเวลา: prepare 2, transfer 3, dispatch 1, execute 4, sync เพิ่มเติม 1, finish 1 ms

1. รวมทั้งเส้นทางได้ 2+3+1+4+1+1 = 12 ms
2. หากเร่ง execute จาก 4 เป็น 2 ms โดยส่วนอื่นเท่าเดิม เวลาใหม่เป็น 10 ms

**ผลที่ได้:** kernel เร็วขึ้น 2 เท่า แต่เวลา end-to-end เร็วขึ้น 12/10 = 1.2 เท่า

**ข้อสรุปจากตัวอย่าง:** หากช่วง synchronize รวมเวลาที่ kernel กำลังทำงาน ต้องแยกช่วงเวลาให้ชัดก่อนรวม เพื่อไม่ให้นับ execution ซ้ำ

### 9.3 Zero-copy และข้อกำหนดของข้อมูล

Typed view ของ bytes เดิมลดการ copy ได้เมื่อ layout alignment length และ bit pattern สอดคล้องกับชนิดปลายทาง ตัวอย่างเช่น bit pattern บางค่าไม่ใช่ bool ที่ valid และโครงสร้างอาจมี padding ที่ต้องจัดการ ชื่อ field ที่ตรงกันไม่ได้ยืนยันว่า binary layout ตรงกัน

Native in-memory layout กับ serialized format เป็นคนละ contract Serializer อาจใช้ variable-length encoding หรือกำหนด endian จึงไม่สามารถสมมติว่า serialized bytes ตรงกับ struct สำหรับการ cast ได้ แม้ระบบรองรับการ borrow จาก buffer ก็ยังต้องรักษา lifetime ให้สัมพันธ์กับเจ้าของข้อมูล

การประเมินควรแยกเวลา parse allocation copy และ computation พร้อมตรวจผลลัพธ์ ประสิทธิภาพ zero-copy ภายใน process เดียวไม่ยืนยันความเข้ากันได้กับ protocol ข้ามเครื่องหรือไฟล์ต่างเวอร์ชัน หากเปลี่ยน format ต้องพิจารณา compatibility ของระบบที่อ่านข้อมูลด้วย

typed_view(bytes) ต้องมี layout + alignment + validity + lifetime ที่สอดคล้องกัน

รายการนี้เป็นแกนของ contract; ข้อกำหนดจริงขึ้นกับภาษา ไลบรารี และชนิดข้อมูลที่เลือก

**ความหมายของสมการ:** ข้อความนี้ระบุข้อกำหนดสำหรับการอ่าน bytes เดิมผ่าน typed view เครื่องหมาย + หมายถึงต้องรักษา layout alignment validity และ lifetime ร่วมกัน ไม่ใช่การบวกเชิงตัวเลข

**อ่านสัญลักษณ์:**

- **layout / alignment:** ตำแหน่งและรูปแบบของข้อมูล / ขอบเขต address ที่ชนิดปลายทางต้องการ
- **validity:** bit pattern ต้องเป็นค่าที่ชนิดปลายทางยอมรับ
- **lifetime:** buffer เจ้าของข้อมูลต้องยังมีชีวิตขณะที่ view ถูกใช้งาน

**ตัวอย่างการคำนวณ:** สถานการณ์สมมติ: buffer มี bytes 01 00 00 00 และระบบทั้งสองฝั่งตกลงใช้ u32 แบบ little-endian ที่ต้องการ alignment 4 bytes

1. ตรวจว่ามีข้อมูลครบ 4 bytes เริ่มที่ address ที่จัด alignment ถูก และ layout ตรงกับชนิด u32
2. ตรวจ bit pattern และ endian; ภายใต้ข้อตกลงนี้ข้อมูลแทนจำนวนเต็ม 1
3. สร้าง view โดยรักษาเจ้าของ buffer ไว้ตลอดช่วงที่อ่าน และไม่ใช้ view หลัง buffer หมดอายุ

**ผลที่ได้:** อ่านค่า 1 ได้โดยไม่จำเป็นต้อง copy ในระบบที่รองรับ contract นี้; ถ้า endian ไม่ตรงก็อาจอ่านได้คนละค่า

**ข้อสรุปจากตัวอย่าง:** Zero-copy ต้องอาศัยข้อกำหนดข้อมูลที่ครบถ้วน ไม่ได้อนุญาตให้ cast bytes ใดเป็นชนิดใดก็ได้

### 9.4 Prefill Decode และต้นทุนที่ต่างกันตาม phase

ใน dense attention การคำนวณ score ระหว่าง prefill ที่มีความยาว T พิจารณาความสัมพันธ์ T×T ส่วน decode ของ token ใหม่ใช้ query ใหม่กับ K ที่ cache ไว้ T ตำแหน่ง โครงสร้างต้นทุนจึงต่างกัน การคำนวณนี้ยังไม่รวม projection FFN ซึ่งแปลง feature ของแต่ละตำแหน่ง และ layer อื่น การเร่ง attention kernel จึงอาจให้ผลต่อทั้งสอง phase ไม่เท่ากัน

KV cache ที่ B=1 L=32 T=4096 H_KV=8 d_head=128 และ b=2 มี payload 536,870,912 bytes หรือ 512 MiB ตามสูตรในบท memory การแชร์ KV heads หรือลด precision เปลี่ยนขนาด memory ได้ แต่ต้องตรวจข้อกำหนด architecture และคุณภาพหลังปรับ

Runtime ที่ออกแบบสำหรับ model หรือ hardware เฉพาะอาจรวม operation เปลี่ยน layout หรือจัด cache ให้เหมาะสมขึ้น ข้อสรุปด้านประสิทธิภาพต้องสัมพันธ์กับรุ่นโมเดล phase และ workload ที่ประเมิน ข้อมูลต้นทุนเหล่านี้ช่วยแยกข้อเสนอในงานวิจัยว่าเปลี่ยน representation algorithm หรือ execution

งานคำนวณ attention-score ต่อ head

$$
\mathrm{prefill}:\quad O(T^2d_k)
$$

$$
\mathrm{decode\ (one\ query)}:\quad O(Td_k)
$$

ระบุเฉพาะ dense score computation โดย key ที่ผ่านมาถูก cache แล้ว; ไม่ใช่ complexity ของโมเดลทั้งหมด

**ความหมายของสมการ:** Prefill พิจารณา score ของ query T ตำแหน่งกับ key T ตำแหน่ง จึงมีจำนวนคู่ตาม T² ส่วน decode หนึ่ง query พิจารณา key ที่ cache ไว้ T ตำแหน่ง จึงมีจำนวนคู่ตาม T

**อ่านสัญลักษณ์:**

- **O(…):** บอกการโตตามขนาด input โดยละค่าคงที่ ไม่ใช่เวลารันเป็นวินาที
- **T² / T:** จำนวนคู่ query–key สำหรับ prefill / query ใหม่หนึ่งตัว
- **d_k:** จำนวนองค์ประกอบที่ใช้ใน dot product ของแต่ละคู่

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติต่อ head: T=4 และ d_k=2; นับเฉพาะ scalar multiplications ใน score ไม่รวม additions, mask และขั้นอื่น

1. prefill มี query 4 ตัว × key 4 ตัว = 16 คู่ แต่ละคู่คูณ 2 ค่า จึง 32 multiplications
2. decode ของ query ใหม่หนึ่งตัวที่อ่าน cached keys 4 ตัว มี 4 คู่ จึง 8 multiplications
3. ถ้าเพิ่ม T เป็น 8 โดย d_k คงเดิม จะได้ prefill 8×8×2=128 และ decode 8×2=16 multiplications

**ผลที่ได้:** เพิ่มความยาวเป็นสองเท่าทำให้ score work ของ prefill โตสี่เท่า แต่ของ query ใหม่หนึ่งตัวโตสองเท่าในตัวอย่าง dense นี้

**ข้อสรุปจากตัวอย่าง:** สัดส่วนนี้อธิบายเฉพาะ score work ไม่ใช่ความเร็วของโมเดลทั้งหมด เนื่องจาก projection FFN memory traffic และ kernel implementation ยังมีต้นทุน

$$
\begin{aligned}\mathrm{KV}_{\mathrm{bytes}}&=2\times1\times32\times4096\\&\quad{}\times8\times128\times2\\&=512\,\mathrm{MiB}\end{aligned}
$$

สมมติ K/V มี d_head เท่ากัน เก็บเต็มและไม่บีบอัด; 1 MiB = 2²⁰ bytes

**ความหมายของสมการ:** ขนาด KV payload ได้จากจำนวนค่าของ K และ V ในทุก batch layer token และ KV head คูณด้วยจำนวน bytes ต่อค่า

**อ่านสัญลักษณ์:**

- **2 ตัวแรก:** สองชุดข้อมูลคือ K และ V
- **1×32×4096:** batch 1 × layers 32 × tokens 4096
- **8×128×2 ตัวท้าย:** KV heads 8 × ค่าต่อ head 128 × bytes ต่อค่า 2
- **MiB:** หนึ่ง MiB = 1,048,576 bytes หรือ 2²⁰ bytes

**ตัวอย่างการคำนวณ:** ค่าจำลองตามสมการ: เก็บ K/V เต็ม ไม่บีบอัด ใช้ 2 bytes ต่อค่า และยังไม่นับ metadata หรือพื้นที่สำรองของ allocator

1. หนึ่ง token ในหนึ่ง layer ใช้ 2×8×128×2 = 4,096 bytes สำหรับ K และ V รวมกัน
2. 4,096 tokens ในหนึ่ง layer ใช้ 4,096×4,096 = 16,777,216 bytes หรือ 16 MiB
3. ครบ 32 layers และ batch 1 ใช้ 16×32×1 = 512 MiB

**ผลที่ได้:** KV payload รวมคือ 536,870,912 bytes หรือ 512 MiB; หาก batch เพิ่มเป็น 2 โดยอย่างอื่นคงเดิม payload จะเป็น 1,024 MiB

**ข้อสรุปจากตัวอย่าง:** ตัวคูณแต่ละตัวระบุแกนที่ทำให้ memory เพิ่ม จึงใช้ประเมินผลของ context length batch KV heads และ precision ได้ตามหน่วย

### นิยามที่ใช้ในบทนี้

- **fixed overhead:** ต้นทุนที่เกิดก่อนหรือร่วมกับ computation เช่น dispatch และ synchronization
- **arithmetic intensity:** จำนวน FLOPs ต่อ bytes ที่เคลื่อนผ่าน memory ระดับที่ระบุ
- **SIMD / memory layout:** การทำ operation เดียวกับข้อมูลหลาย lane / รูปแบบการจัดข้อมูลที่กำหนด access pattern
- **zero-copy:** การใช้ storage เดิมผ่าน view หรือ borrow ภายใต้ contract ด้านข้อมูลและ lifetime

### ทดลองกลไก

**ประเด็นที่ศึกษา:** เปรียบเทียบจุดตัดที่เพิ่มประมาณสองเท่าตามสูตร และพิจารณาส่วน fixed overhead ในเวลารวมของ GPU

### โจทย์

งานที่ใช้ศัพท์เดียวกันอาจแก้ปัญหาต่างกัน ขณะที่ผลจากการเปลี่ยนหลายองค์ประกอบพร้อมกันยังไม่ระบุสาเหตุ การวิเคราะห์ claim ต้องเชื่อมกับองค์ประกอบและเงื่อนไขที่เปลี่ยน

### 10.1 การระบุกลไกและระดับของหลักฐาน

การวิเคราะห์เริ่มจาก input → mechanism → output พร้อมระบุ trainable variables state ที่เปลี่ยนระหว่าง inference objective และ stopping condition สำหรับระบบหลาย component dependency graph ต้องแสดงว่าผลจากส่วนหนึ่งเป็นข้อมูลหรือเงื่อนไขของส่วนใด

Claim ว่า latent reasoning เร็วขึ้นต้องระบุว่ามีการเปลี่ยน encoder ลด output tokens ใช้ recurrent passes ลด node expansions หรือปรับ kernel กลไกเหล่านี้มี dependency และ denominator ของ speedup ต่างกัน Tensor shape operation count และ timing boundary ช่วยระบุรายละเอียดที่จำเป็นต่อการตรวจสอบคำอธิบาย

หลักฐานควรแยกเป็นผลจาก paper ต้นทาง ผลจาก implementation หรือ benchmark ของผู้เผยแพร่ และข้อเสนอสำหรับนำไปใช้กับระบบเป้าหมาย ลิงก์ repository หรือชื่อวิดีโอเป็นตำแหน่งสำหรับตรวจสอบเพิ่มเติม แต่ไม่ยืนยันว่า implementation หรือเนื้อหาทั้งหมดตรงกับข้อคาดหมาย

research card = claim, source, mechanism, assumptions, artifact, experiment, unknowns

บันทึกสิ่งที่ยืนยันแล้วแยกจากสมมติฐานที่จะทดลอง เพื่อไม่ส่งต่อ claim เกินหลักฐาน

**ความหมายของสมการ:** Research card เป็นรายการข้อมูลสำหรับวิเคราะห์งานหนึ่งชิ้น ได้แก่ claim source mechanism assumptions artifact experiment และ unknowns เครื่องหมาย = ประกอบนิยามรายการ ไม่ใช่ความเท่ากันเชิงคณิตศาสตร์

**อ่านสัญลักษณ์:**

- **claim / source:** สิ่งที่งานอ้าง / ต้นทางที่ตรวจข้อความนั้นได้
- **mechanism / assumptions:** วิธีที่ทำให้เกิดผล / เงื่อนไขที่วิธีต้องอาศัย
- **artifact / experiment / unknowns:** สิ่งที่ตรวจรันได้ / การทดลอง / คำถามที่ยังไม่มีคำตอบ

**ตัวอย่างการคำนวณ:** สถานการณ์สมมติ: บทความ A อ้างว่าเพิ่ม search แล้วแก้ maze สำเร็จมากขึ้น บทความนี้เป็นตัวอย่าง ไม่ใช่แหล่งอ้างอิงจริง

1. จด claim และตำแหน่ง source แล้วสรุป mechanism ว่าเพิ่ม node expansion โดย scorer เดิม
2. จด assumptions ว่า transition ถูกต้องและ budget เท่ากัน พร้อม artifact เช่น revision ของ solver และไฟล์โจทย์
3. ออกแบบ experiment ด้วย maze ชุดที่ตรึงไว้ แล้วจด unknowns เช่นผลกับ maze ที่ใหญ่กว่าหรือ heuristic คนละแบบ

**ผลที่ได้:** ได้บันทึกที่แยกสิ่งที่ต้นทางรายงานออกจากสิ่งที่ยังต้องทดลองเพิ่มเติม

**ข้อสรุปจากตัวอย่าง:** Unknowns ระบุขอบเขตที่หลักฐานยังไม่รองรับ และประเด็นสำหรับการศึกษาหรือทดลองเพิ่มเติม

### 10.2 Ablation Factorial Comparison และคำถามเชิงสาเหตุ

Ablation คือการปิดหรือนำองค์ประกอบออกเพื่อประเมินบทบาท ส่วน factorial comparison เปลี่ยนหลายปัจจัยในตารางทดลองอย่างเป็นระบบ ตัวอย่างการแยก implementation A/B และ decision rule greedy/search ให้สี่ configuration โดยควบคุม weights input set precision และเงื่อนไข evaluation ที่เกี่ยวข้อง

กำหนด Y_ij เป็น metric ที่มีนิยามเดียวกันในทุก configuration ผลต่าง Y_10−Y_00 แสดงผลของปัจจัยแรกเมื่อปัจจัยที่สองคงเดิม ส่วน difference of differences ประเมินว่าผลของปัจจัยแรกเปลี่ยนตามปัจจัยที่สองหรือไม่ การตีความ interaction ต้องพิจารณา sampling variability ประกอบ

Budget แบบ wall-clock เท่ากันประเมินคุณภาพภายในเวลาที่กำหนด ส่วนจำนวน model calls เท่ากันประเมินผลภายใต้ computation หน่วยนั้น ทั้งสองตอบคำถามต่างกัน ข้อสรุปจึงต้องอ้างอิงรูปแบบ budget ของการทดลองนั้น

$$
\operatorname{interaction}=(Y_{11}-Y_{01})-(Y_{10}-Y_{00})
$$

i ระบุ implementation และ j ระบุ decision rule; ใช้ metric และ scale เดียวกัน เช่น solve rate ที่ budget เท่ากัน

**ความหมายของสมการ:** Interaction คำนวณจากผลต่างระหว่าง implementation เมื่อใช้ decision rule แบบหนึ่ง ลบผลต่างระหว่าง implementation เมื่อใช้ decision rule อีกแบบ โดยใช้ metric และ scale เดียวกัน

**อ่านสัญลักษณ์:**

- **Y_ij:** metric เมื่อเลือก implementation i และ decision rule j
- **Y_11−Y_01:** ผลต่าง implementation 1 กับ 0 ขณะที่ตรึง rule j=1
- **difference of differences:** ผลต่างของผลต่างทั้งสอง ต้องใช้ metric และ scale เดียวกัน

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติที่ budget เท่ากัน: Y_00=60%, Y_10=64% เมื่อ greedy; Y_01=70%, Y_11=80% เมื่อ search โดย Y คือ verified solve rate

1. ผลของ implementation เมื่อใช้ search: 80−70 = 10 จุดเปอร์เซ็นต์
2. ผลของ implementation เมื่อใช้ greedy: 64−60 = 4 จุดเปอร์เซ็นต์
3. interaction = 10−4 = 6 จุดเปอร์เซ็นต์ หรือ 0.06 เมื่อเขียนอัตราในช่วง 0–1

**ผลที่ได้:** implementation ใหม่เพิ่ม solve rate มากกว่าเดิม 6 จุดเปอร์เซ็นต์เมื่อใช้ search เทียบกับ greedy บนตารางสมมตินี้

**ข้อสรุปจากตัวอย่าง:** ค่า 6 จุดเปอร์เซ็นต์เป็น interaction บนสเกลผลต่าง solve rate ไม่ใช่การเพิ่ม 6% แบบสัมพัทธ์ ต้องพิจารณาความแปรปรวนและเงื่อนไขควบคุมก่อนตีความเชิงสาเหตุ

control set = input/seed, θ, precision, output contract, budget, evaluator version

เลือกสิ่งที่ตรึงตาม causal question และบันทึกทุกข้อที่เปลี่ยนโดยหลีกเลี่ยงไม่ได้

**ความหมายของสมการ:** Control set ระบุเงื่อนไขที่ต้องตรึงหรือบันทึกให้สอดคล้องกับคำถามเชิงสาเหตุ เครื่องหมาย = และจุลภาคประกอบรายการ ไม่ใช่การรวมเชิงตัวเลข

**อ่านสัญลักษณ์:**

- **input/seed:** โจทย์และค่าตั้งต้นการสุ่มที่จับคู่เปรียบเทียบกันได้
- **θ / precision:** พารามิเตอร์โมเดล / รูปแบบตัวเลขที่ใช้คำนวณ
- **budget / evaluator version:** งบที่ให้แต่ละวิธี / รุ่นตัวตรวจที่ตัดสินผล

**ตัวอย่างการคำนวณ:** สถานการณ์สมมติ: ต้องการวัดว่าเพิ่ม search ช่วย solver ที่ใช้ scorer เดิมหรือไม่ ภายใต้งบ 30 ms ต่อโจทย์

1. ใช้ maze 100 แผนที่และชุด seed เดียวกัน พร้อม weights revision เดียวกันและ precision เดียวกัน
2. กำหนดสัญญาผลลัพธ์เป็น path ที่ถูกต้อง งบ 30 ms เท่ากัน และใช้ verifier รุ่นเดียวกัน
3. เปลี่ยนเฉพาะ greedy เป็น search แล้วบันทึกจำนวน model calls ที่เกิดจริง เพราะภายใต้งบเวลาเดียวกันจำนวน calls อาจต่างกัน

**ผลที่ได้:** ผลที่ได้ตอบเรื่องคุณภาพภายในเวลาเท่ากัน โดยมีตัวแปรควบคุมที่ตรวจย้อนกลับได้

**ข้อสรุปจากตัวอย่าง:** ตัวแปรควบคุมต้องสัมพันธ์กับคำถาม Budget เวลาเท่ากันและจำนวน calls เท่ากันเป็นคนละเงื่อนไข จึงไม่จำเป็นต้องตรึงทั้งสองพร้อมกัน

### 10.3 Mini-repro Counterexample และขอบเขตผลการทดลอง

Mini-repro ควรเริ่มจากสมมติฐานเฉพาะ เช่น search ช่วยแก้ maze ที่มีทางลวงภายใต้งบเวลาที่กำหนด ระบบทดลองต้องมี solver และตัวตรวจ path ใช้ชุดโจทย์ที่กำหนดก่อนเลือกวิธี และแยกชุดปรับ heuristic ออกจากชุดประเมินสุดท้าย การทดสอบกลไกเดียวไม่จำเป็นต้องสร้าง agent stack ทั้งระบบ

Metric ที่เกี่ยวข้องประกอบด้วย found-valid-path rate path length node expansions timeout และ latency ชุดทดสอบควรมีสถานการณ์ที่อาจหักล้างสมมติฐาน เช่น goal อยู่ใกล้แต่มีสิ่งกีดขวาง หรือ heuristic ให้ทิศทางผิด หากเพิ่ม recurrent scorer ต้องใช้ model ที่ฝึกแล้วและระบุ input/state interface ก่อนเปรียบเทียบกับ search เดิม

ผลที่ดีเฉพาะบางกลุ่มต้องรายงานขอบเขตนั้น โปรแกรมกฎขนาดเล็กและเกมจำกัดช่วยให้สำรวจ case ได้ชัดเจน Counterexample ช่วยวิเคราะห์ว่าข้อจำกัดมาจากข้อมูล algorithm หรือ implementation ซึ่งต้องแก้ไขด้วยวิธีต่างกัน

$$
\begin{gathered}\operatorname{verified\ success\ rate}\\=\frac{N_{\mathrm{verified}}}{N_{\mathrm{all\ problems}}}\end{gathered}
$$

ตัวเศษ = จำนวนโจทย์ที่ได้คำตอบผ่านตัวตรวจอิสระ; ตัวส่วน = จำนวนโจทย์ทั้งหมด

รวม timeout และ abstention ใน denominator เพื่อเห็นความสามารถตลอดชุด; ตัวตรวจยังต้องมี specification ที่ถูกต้อง

**ความหมายของสมการ:** Verified success rate คือจำนวนโจทย์ที่มีคำตอบผ่านตัวตรวจอิสระหารด้วยจำนวนโจทย์ทั้งหมด รวม timeout และ abstention ใน denominator

**อ่านสัญลักษณ์:**

- **ตัวเศษ:** จำนวนโจทย์ที่ได้คำตอบและผ่าน specification ที่ตัวตรวจใช้
- **ตัวส่วน:** จำนวนโจทย์ทั้งหมด ไม่ตัด timeout หรือ abstention ออก
- **rate:** อัตราส่วน 0–1; คูณ 100 เพื่อแสดงเป็นเปอร์เซ็นต์

**ตัวอย่างการคำนวณ:** ตัวเลขสมมติ: ประเมิน 20 maze ได้ path ผ่านตัวตรวจ 12, path ผิด 3, timeout 3 และ abstain 2

1. ตรวจยอดทั้งหมด: 12+3+3+2 = 20 โจทย์
2. ใช้เฉพาะ 12 คำตอบที่ผ่านเป็นตัวเศษ แล้วหารด้วย 20 ได้ 0.6
3. แปลงเป็นเปอร์เซ็นต์: 0.6×100 = 60%

**ผลที่ได้:** verified success rate คือ 60% ของชุดที่ประเมินทั้งหมด

**ข้อสรุปจากตัวอย่าง:** อัตรานี้แสดงความสำเร็จตลอดชุดประเมิน ต้องรายงานจำนวนคำตอบผิด timeout และ abstention เพื่ออธิบายอีก 40% ในตัวอย่าง

### 10.4 Prerequisite และการประเมินความเข้าใจด้วย Recall

การสรุปกลไกต้องระบุ state ตัวแปรที่เปลี่ยน property ที่รับประกัน สมมติฐาน และแหล่งต้นทุน หากข้อมูลไม่ครบต้องกลับไปตรวจ source ในประเด็นนั้น เช่น factor shapes ของ LoRA หรือ update และ halting condition ของ recurrence

การทบทวนด้วย derivation ช่วยตรวจความเข้าใจมากกว่าการจำชื่อ ตัวอย่างได้แก่การนับพารามิเตอร์ LoRA จาก shape การอธิบายว่า fixed point อาจไม่ตรงคำตอบที่ถูก การระบุตำแหน่ง ACL ก่อน context และการคำนวณ Amdahl จากเวลาแต่ละส่วน Lab flashcards ใช้ฝึก recall ก่อนขยายคำตอบด้วยสมการและ failure case

ลำดับการศึกษางานใหม่ควรอ้างอิงคำถามที่ยังไม่ตอบ ความชัดของหลักฐาน และต้นทุนทำซ้ำ พร้อมบันทึก source และ experiment ที่ใช้ตรวจคำถามนั้น Dependency graph ช่วยให้การศึกษาต่อยอดจาก prerequisite ที่มีอยู่และระบุแนวคิดที่ต้องเพิ่มเติม

understanding check = mechanism + assumptions + worked example + failure case

ความสามารถอธิบายสี่ส่วนนี้ช่วยหา prerequisite ที่ขาด; ยังต้องตรวจ implementation และผลวัดแยกต่างหาก

**ความหมายของสมการ:** ข้อความนี้กำหนดองค์ประกอบสำหรับตรวจความเข้าใจ ได้แก่ mechanism assumptions worked example และ failure case เครื่องหมาย + หมายถึงการอธิบายทั้งสี่ส่วน ไม่ใช่ผลบวกเชิงตัวเลข

**อ่านสัญลักษณ์:**

- **mechanism / assumptions:** ระบบทำอะไร / การอธิบายนั้นต้องอาศัยเงื่อนไขใด
- **worked example:** แทนค่าหรือไล่ขั้นตอนจริงจนได้ผล
- **failure case:** กรณีที่แสดงขอบเขตของกลไก ครอบคลุมข้อจำกัดมากกว่าการระบุข้อดี

**ตัวอย่างการคำนวณ:** ตัวอย่างสมมติ: ใช้ LoRA กับ W รูปร่าง 3×4 และ rank r=1 โดยพิจารณาเฉพาะเมทริกซ์ ไม่รวม bias

1. อธิบายกลไกและสมมติฐาน: ตรึง W เดิม แล้วเรียน A ขนาด 1×4 กับ B ขนาด 3×1 เพื่อสร้าง update แบบ low rank
2. คำนวณตัวอย่าง: เรียน 4+3=7 พารามิเตอร์ แทนการเรียน W ทั้ง 3×4=12 พารามิเตอร์
3. ยกข้อจำกัด: หาก update ที่ต้องการมี rank 2 ผลคูณ BA ที่ rank ไม่เกิน 1 จะแทน update นั้นได้ไม่ตรงทุกค่า

**ผลที่ได้:** คำอธิบายครบทั้งรูปแบบการปรับ จำนวนพารามิเตอร์ และข้อจำกัดด้าน rank จึงใช้ระบุประเด็นที่ยังไม่เข้าใจได้

**ข้อสรุปจากตัวอย่าง:** Derivation ของตัวอย่างขนาดเล็กเชื่อมสัญลักษณ์กับกลไก ส่วนคุณภาพโมเดลหลังฝึกต้องประเมินแยกจากการนับพารามิเตอร์

### นิยามที่ใช้ในบทนี้

- **dependency graph:** กราฟที่แสดงความสัมพันธ์ของข้อมูล แนวคิด หรือเงื่อนไขที่องค์ประกอบหนึ่งต้องใช้จากองค์ประกอบอื่น
- **ablation:** การปิดหรือนำองค์ประกอบออกเพื่อประเมินบทบาทภายใต้เงื่อนไขควบคุม
- **factorial comparison:** การทดลองชุดผสมของหลายปัจจัยเพื่อประเมินผลรายปัจจัยและ interaction
- **counterexample / mini-repro:** กรณีที่หักล้าง claim / การทดลองทำซ้ำขนาดเล็กเพื่อทดสอบกลไกหรือข้อสรุปเฉพาะ

### ทดลองกลไก

**ขั้นตอนการทดลอง:** ตอบ flashcard ก่อนดูเฉลย แล้วขยายแต่ละคำตอบด้วยกลไกหนึ่งข้อ สมมติฐานหนึ่งข้อ และ counterexample หนึ่งข้อ

**ประเด็นที่ศึกษา:** แยกการจำคำตอบสั้นออกจากความสามารถ derive สูตรหรืออธิบาย failure case โดยไม่เปิดโน้ต

**ขอบเขตของแบบจำลอง:** Recall ใช้ประเมินความเข้าใจของผู้อ่าน ส่วนการรับรอง implementation หรือ claim ใน paper ต้องใช้หลักฐานและการทดลองที่ตรงคำถาม
