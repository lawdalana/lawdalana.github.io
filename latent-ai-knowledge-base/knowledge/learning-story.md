# จาก Representation สู่ Reasoning Systems

ลำดับความเข้าใจสำหรับคนมีพื้นฐาน DL: ข้อมูล → พารามิเตอร์ → การคำนวณ → ข้อจำกัด → ระบบที่วัดผลได้

**ระดับผู้อ่าน:** สำหรับผู้อ่านที่เคยใช้หรือเรียน neural networks, gradient descent และ attention มาบ้าง และต้องการเชื่อมแนวคิดเหล่านี้กับ latent reasoning และการออกแบบระบบ AI

เส้นทางนี้เรียงตามสิ่งที่ต้องเข้าใจก่อนใช้แนวคิดถัดไป เริ่มจากข้อมูลที่ representation ต้องรักษา แล้วแยกการเปลี่ยน weights ออกจากการเพิ่ม compute ตอน inference ก่อนประกอบ search, verifier, memory และ retrieval เป็นระบบเดียว แต่ละบทให้กลไก สมการ ตัวอย่างคำนวณ และขอบเขตของหลักฐาน โพสต์อ่านต่อมาจากหลายงานวิจัยและหลาย implementation จึงใช้เทียบกลไกทีละส่วน โดยไม่ถือว่าผลของทุกงานย้ายมาใช้ร่วมกันได้ทันที

## พื้นฐานที่ใช้ต่อยอด

- อ่าน tensor shape และ matrix multiplication ได้ เช่น (T×d)·(d×m) ได้ T×m
- รู้ว่า loss ใช้ปรับพารามิเตอร์ด้วย gradient และแยก training ออกจาก inference ได้
- เคยเห็น softmax และ Q/K/V attention; บทที่ 2 จะกำหนด shape และบทบาทที่ใช้ต่อให้ครบ
- รู้จัก train/evaluation split และเข้าใจว่าผลบนชุดข้อมูลหนึ่งมีขอบเขตการนำไปใช้

## บท 1 — Representation ต้องรักษาอะไรไว้ให้การตัดสินใจ

[เปิดบทพร้อมห้องทดลอง](../index.html#story/01) · [หัวข้อสังเคราะห์](topics/01-latent-representations-and-geometry.md)

**คำถามหลัก:** จะรู้ได้อย่างไรว่า latent ที่ย่อข้อมูลแล้ว ยังเพียงพอสำหรับงานปลายทาง?

**ความเข้าใจที่นำมาใช้:** เริ่มที่ input และสิ่งที่งานต้องการ ก่อนเลือกสถาปัตยกรรมหรือเพิ่มจำนวนรอบ reasoning



### โจทย์

โมเดล downstream แก้ข้อมูลที่ถูก encoder ทิ้งไปแล้วไม่ได้ เราจึงต้องนิยามก่อนว่าความแตกต่างใดควรหายไป และความแตกต่างใดต้องยังแยกกันได้

### 1.1 จาก observation ไปสู่ state ที่เพียงพอ

ให้ x_t เป็นข้อมูลที่สังเกตได้, s_t เป็นสถานะจริง และ z_t = fθ(x_t) เป็นตัวแทนที่ส่งให้ policy π เลือก action a_t หาก x_t มองโลกไม่ครบ ภาพเดียวอาจไม่พอ: ตำแหน่งวัตถุเท่ากันอาจเกิดจากความเร็วคนละทิศ ต้องเพิ่มประวัติหรือข้อมูลที่ช่วยแยกอนาคตนั้น

สำหรับระบบที่สังเกตสถานะครบ ความพอเพียงต่อการตัดสินใจตรวจได้จาก reward และ transition: ถ้าจะรวม s กับ s′ เป็น z เดียวกัน ทั้งสองควรให้ reward และการกระจายของ latent ถัดไปเหมือนกันภายใต้ action เดียวกัน นี่เป็นเงื่อนไขแบบ exact state abstraction; ระบบที่เรียนจริงมักรักษาได้เพียงประมาณ

การ reconstruct input ได้ดีเป็น objective หนึ่ง แต่ไม่ได้บังคับว่า feature สำคัญต่อ action จะถูกเก็บครบ ในทางกลับกัน encoder ที่ทิ้งพื้นหลังจำนวนมากอาจเหมาะกับ policy ถ้ายังรักษาผลของ action และเงื่อนไขของงานได้

$$
z_t=f_{\theta}(x_t)
$$

$$
a_t\sim\pi(\,\cdot\mid z_t)
$$

fθ คือ encoder; π คือการกระจายของ action เมื่อเห็น z_t

**อ่านสมการนี้ว่า:** แปลงข้อมูลที่สังเกตเป็นเวกเตอร์ที่ใช้ตัดสินใจ แล้วสุ่ม action ตามความน่าจะเป็นที่ policy ให้เมื่อเห็นเวกเตอร์นั้น

**อ่านสัญลักษณ์:**

- **fθ(x_t):** ส่ง observation เข้า encoder ที่มีพารามิเตอร์ θ
- **π(· | z_t):** แจกความน่าจะเป็นให้ทุก action โดยอาศัย z_t; จุด · คือช่องของ action
- **∼:** สุ่มจากการกระจายนี้ ไม่ได้แปลว่าเลือกค่าที่มากที่สุดเสมอ

**ตัวอย่างทีละขั้น:** ตัวอย่างสมมติ: x_t มี hunger=0.8, threat=0.1 และสีเสื้อ; encoder เก็บเฉพาะสองค่าแรก

1. ผ่าน encoder แล้วได้ z_t=(0.8, 0.1); สีเสื้อไม่ถูกส่งต่อ
2. สมมติ policy ให้ P(eat | z_t)=0.75 และ P(hide | z_t)=0.25 รวมเป็น 1
3. ถ้าสุ่มเลขสม่ำเสมอในช่วง [0,1) แล้วได้ 0.60 จะอยู่ในช่วง eat [0,0.75); ถ้าได้ 0.90 จะเลือก hide

**ผลที่ได้:** ในครั้งที่สุ่มได้ 0.60 จึงได้ a_t=eat แม้ input เดิมอาจสุ่มได้ action อื่นในครั้งถัดไป

**เชื่อมกลับไปที่สมการ:** แยกสองขั้นให้ชัด: encoder กำหนดว่า policy เห็นอะไร ส่วน policy กำหนดว่าจะเลือก action อย่างไร

$$
f(s)=f(s^{\prime})
$$

ทำให้ทั้งสองเงื่อนไขต่อไปนี้เป็นจริงพร้อมกัน

$$
r(s,a)=r(s^{\prime},a)
$$

$$
\begin{aligned}P(Z_{\mathrm{next}}=u\mid s,a)\\{}=P(Z_{\mathrm{next}}=u\mid s^{\prime},a)\end{aligned}
$$

เงื่อนไขอุดมคติสำหรับทุก action a และทุก latent state u ในระบบจำกัด; r คือ expected reward และ P คือ transition probability

**อ่านสมการนี้ว่า:** ถ้าจะยุบสอง state ให้เป็น latent เดียวกันอย่างถูกต้อง ต้องให้ action เดียวกันได้ทั้ง reward และโอกาสไปยัง latent ถัดไปตรงกัน

**อ่านสัญลักษณ์:**

- **⇒:** ในที่นี้เป็นเงื่อนไขที่การยุบ state ต้องรักษา ไม่ใช่สิ่งที่ encoder ใด ๆ ทำได้อัตโนมัติ
- **r(s,a):** reward เฉลี่ยเมื่อทำ action a ใน state s
- **P(Z_next=u | s,a):** โอกาสที่ latent ถัดไปเป็น u หลังทำ action a
- **s′:** อีก state หนึ่งที่กำลังเทียบกับ s

**ตัวอย่างทีละขั้น:** สมมติโลกมี action แค่ eat/wait และ latent ถัดไปมีแค่ full/hungry; สอง state ต่างกันเพียงพื้นหลัง

1. ลองยุบทั้งสอง state เป็น z เดียวกัน โดยตัดสีพื้นหลังออก
2. สำหรับ eat: ทั้งคู่ได้ reward=2 และโอกาส (full, hungry)=(0.9, 0.1)
3. สำหรับ wait: ทั้งคู่ได้ reward=0 และโอกาส (full, hungry)=(0, 1); จึงเทียบครบทั้งสอง action และทุก latent ปลายทาง

**ผลที่ได้:** ในโลกตัวอย่างนี้ การยุบสอง state รักษา reward และ transition ตามเงื่อนไขครบ

**เชื่อมกลับไปที่สมการ:** การเห็นผลเหมือนกันจาก action เดียวไม่พอ ต้องตรวจทุก action ที่อยู่ในขอบเขตของ abstraction

### 1.2 Geometry มีประโยชน์เมื่อสัมพันธ์กับงาน

Invariance หมายถึงการเปลี่ยน input บางแบบแล้ว representation คงเดิม เช่นเปลี่ยน texture ที่ไม่เกี่ยวกับ action ส่วน equivariance หมายถึง representation เปลี่ยนตามกฎที่สอดคล้องกัน เช่นหมุนพิกัดแล้วเวกเตอร์ทิศทางหมุนตาม การบังคับ invariant ต่อทุกอย่างจะลบข้อมูลที่งานต้องใช้

สำหรับ encoder ที่หาอนุพันธ์ได้ Jacobian J_f บอกความไวเฉพาะที่: perturbation ของ input ทิศใดทำให้ latent เปลี่ยนมาก ต้องแยกว่าทิศนั้นเป็นสิ่งรบกวนหรือเป็น feature สำคัญ ระยะใน embedding หรือ rank ของ Jacobian เพียงอย่างเดียวจึงยังไม่ยืนยัน semantic understanding

โครงสร้างข้อมูลก็เป็นส่วนของ representation: graph เก็บ node/edge; cell complex เพิ่มหน้าและองค์ประกอบมิติสูงเพื่อแทนความสัมพันธ์ที่เกินคู่ การเลือก operator ควรตามชนิดข้อมูล ส่วน analogy ถามว่าการย้ายบริบทยังรักษาบทบาทและความสัมพันธ์เดิมหรือไม่

$$
f(Tx)=f(x)
$$

หรือ

$$
f(Tx)=\rho(T)f(x)
$$

T คือการแปลง input; แบบแรก invariant แบบหลัง equivariant โดย ρ(T) เป็นการแปลงที่สอดคล้องกันใน latent

**อ่านสมการนี้ว่า:** เมื่อแปลง input ให้ดูว่า latent ต้องคงเดิม หรือควรเปลี่ยนตามการแปลงเดียวกันในพิกัดของ latent

**อ่านสัญลักษณ์:**

- **T:** การแปลง input เช่นหมุนพิกัด 90 องศา
- **ρ(T):** วิธีแปลง latent ให้สอดคล้องกับ T
- **f(Tx)=f(x):** หลังแปลง input แล้ว encoder ยังให้ค่าเดิม: invariance
- **f(Tx)=ρ(T)f(x):** latent เปลี่ยน แต่เปลี่ยนตามกฎที่กำหนด: equivariance

**ตัวอย่างทีละขั้น:** ใช้ x=(1,0), T เป็นการหมุนทวนเข็ม 90 องศา จึงได้ Tx=(0,1); เปรียบเทียบ encoder สองแบบ

1. ถ้า encoder เก็บแค่ความยาวเวกเตอร์ จะได้ f(x)=1 และ f(Tx)=1: invariant ต่อการหมุน
2. ถ้า encoder เก็บพิกัดเดิม จะได้ f(x)=(1,0) และ f(Tx)=(0,1)
3. สำหรับ encoder แบบที่สอง เลือก ρ(T) เป็นการหมุน 90 องศาใน latent ด้วย จึงได้ ρ(T)f(x)=(0,1) ตรงกัน

**ผลที่ได้:** การเก็บความยาวทิ้งทิศทาง ส่วนการเก็บพิกัดรักษาทิศทางโดยให้มันหมุนตาม input

**เชื่อมกลับไปที่สมการ:** เลือกว่าจะรักษาหรือทิ้งการเปลี่ยนแปลงจากสิ่งที่งานต้องใช้ ไม่ใช่บังคับให้ latent คงเดิมทุกกรณี

$$
\Delta z\approx J_f(x)\Delta x
$$

$$
J_f\in\mathbb{R}^{d_z\times d_x}
$$

การประมาณเชิงเส้นเฉพาะบริเวณสำหรับ Δx ขนาดเล็ก; d_x และ d_z คือมิติของ input และ latent

**อ่านสมการนี้ว่า:** เมื่อขยับ input เล็กน้อย ใช้ตารางความไวของ encoder คูณการขยับนั้น เพื่อประมาณว่า latent จะขยับเท่าไร

**อ่านสัญลักษณ์:**

- **Δx, Δz:** การเปลี่ยนแปลงของ input และ latent เทียบกับจุดเริ่ม
- **J_f(x):** Jacobian: แต่ละช่องบอกว่า output หนึ่งมิติไวต่อ input หนึ่งมิติแค่ไหนที่ x
- **≈:** เป็นค่าประมาณเฉพาะบริเวณ ไม่ใช่เท่ากันเสมอ
- **d_z×d_x:** จำนวนแถวเท่ามิติ latent และจำนวนคอลัมน์เท่ามิติ input

**ตัวอย่างทีละขั้น:** สมมติ f(x₁,x₂)=(x₁²,x₂), เริ่มที่ x=(2,3) และขยับ Δx=(0.01,0.02)

1. ที่จุดนี้ J_f=[[4,0],[0,1]] เพราะความชันของ x₁² ที่ x₁=2 เท่ากับ 4
2. คูณเมทริกซ์กับ Δx ได้การเปลี่ยนแปลงที่ประมาณไว้ (4×0.01, 1×0.02)=(0.04,0.02)
3. คำนวณจริง: f(2.01,3.02)−f(2,3)=(0.0401,0.02); ส่วนที่ประมาณพลาดในมิติแรกคือ 0.0001

**ผลที่ได้:** latent ใหม่ที่ประมาณได้คือ (4.04,3.02) ใกล้กับค่าจริง (4.0401,3.02)

**เชื่อมกลับไปที่สมการ:** Jacobian ช่วยอ่านความไวใกล้จุดหนึ่ง การคาดผลเมื่อ input เปลี่ยนมากอาจต้องคำนวณใหม่ระหว่างทาง

### 1.3 Capacity, information และ accessibility

เวกเตอร์ 2,560 ค่า เก็บค่าละ 16 บิต ใช้พื้นที่ 40,960 บิต ขณะที่ token หนึ่งตัวจาก vocabulary ขนาด 65,536 ใช้ index 16 บิตได้ การนับนี้เปรียบเทียบขนาดที่เก็บ ไม่ได้วัดว่าระบบส่งข้อมูลที่เกี่ยวกับโจทย์ผ่านช่องทางนั้นได้กี่บิตจริง

ค่าหลายมิติอาจซ้ำซ้อน ถูก noise กลบ หรือ decoder ใช้ไม่เป็น จึงควรแยก represented information ว่ามีสัญญาณให้ทำนายได้, accessibility ว่ากระบวนการที่เราใช้ดึงสัญญาณนั้นออกได้ และ stability ว่าการใช้งานยังทำได้เมื่อ input เปลี่ยนเล็กน้อย

วิธีตรวจที่ตรงงานคือเปลี่ยนปัจจัยทีละอย่าง เช่นสีพื้นหลังกับสถานะประตู แล้ววัด action success ควบคู่กับระยะ latent ถ้าระยะเปลี่ยนน้อยแต่ action ที่จำเป็นเปลี่ยนตามไม่ได้ การย่อนั้นเสียข้อมูลที่ต้องใช้

$$
\operatorname{storage}(z)=d_z\times\mathrm{bits\ per\ value}
$$

ขนาดเชิงรูปแบบของเวกเตอร์ ไม่ใช่ mutual information กับคำตอบหรือปริมาณความรู้ที่เข้าถึงได้

**อ่านสมการนี้ว่า:** นับจำนวนค่าที่เก็บในเวกเตอร์ แล้วคูณจำนวนบิตต่อค่า เพื่อหาขนาด payload ของเวกเตอร์นั้น

**อ่านสัญลักษณ์:**

- **d_z:** จำนวนมิติ หรือจำนวนค่าที่เก็บใน latent หนึ่งเวกเตอร์
- **bits_per_value:** จำนวนบิตที่รูปแบบข้อมูลใช้ต่อหนึ่งค่า
- **×:** คูณจำนวนค่าเข้ากับพื้นที่ต่อค่า; 8 บิตเท่ากับ 1 ไบต์

**ตัวอย่างทีละขั้น:** สมมติเก็บ z=(0.2,0.2,0.2,0.2) เป็น float16 โดยยังไม่รวม metadata หรือพื้นที่จัดสรรเพิ่ม

1. เวกเตอร์มี 4 ค่า แต่ละค่าใช้ 16 บิต จึงใช้ 4×16=64 บิต
2. แปลงเป็นไบต์ได้ 64÷8=8 ไบต์ แม้ทั้งสี่ค่าจะเหมือนกัน
3. ถ้ามี 2,560 ค่าในรูปแบบเดิม จะใช้ 2,560×16=40,960 บิต หรือ 5,120 ไบต์

**ผลที่ได้:** ขนาดที่นับได้เปลี่ยนตามจำนวนมิติและรูปแบบเก็บ โดยไม่ตรวจว่าแต่ละมิติให้ข้อมูลใหม่หรือซ้ำกัน

**เชื่อมกลับไปที่สมการ:** เวกเตอร์ใหญ่ขึ้นมีพื้นที่เก็บมากขึ้น แต่ตัวเลขนี้ยังไม่บอกปริมาณข้อมูลเกี่ยวกับคำตอบที่ decoder ดึงใช้ได้

### 1.4 State aliasing: ความผิดที่ reasoning เพิ่มแก้ไม่ได้

ใน lab มี state A และ B ที่ hunger เท่ากัน แต่ threat ต่างกัน และ action เป้าหมายต่างกัน หาก encoder เก็บเฉพาะ hunger จะได้ z_A = z_B ปัญหานี้เรียก state aliasing: input ที่ควรแยกกันชนที่ representation เดียว

สมมติพบ A กับ B บ่อยเท่ากันและแต่ละ state มี action ถูกเพียงหนึ่งแบบ policy ที่เห็น z เดียวกันทำถูกได้มากสุดครึ่งหนึ่งของสองกรณีนี้ แม้เพิ่มความลึกหรือวนคิดหลายครั้ง โดยไม่มีข้อมูลใหม่ก็ยังแยกไม่ได้ ต้องแก้ representation หรือเพิ่ม observation

การเปิด threat จะแยกคู่ที่ขัดกัน ส่วนการเปิดสีเสื้อเพิ่มอาจสร้างกลุ่มมากขึ้นโดยไม่ช่วย decision นี่ทำให้เราเลือกความซับซ้อนของ representation จาก error ที่ต้องแก้ แล้วจึงไปถามในบทต่อไปว่าจะปรับพารามิเตอร์ของโมเดลอย่างไร

$$
f(s_A)=f(s_B),\qquad y_A\ne y_B
$$

เงื่อนไขข้างต้นทำให้ผลลัพธ์สองรายการนี้แยกเป้าหมายทั้งคู่ไม่ได้

$$
g(f(s_A)),\qquad g(f(s_B))
$$

g คือ deterministic predictor และ y คือคำตอบเป้าหมาย; ข้อจำกัดนี้เกิดจากข้อมูลที่สูญหายก่อนถึง g

**อ่านสมการนี้ว่า:** ถ้า encoder ส่งสองกรณีเป็นค่าเดียวกัน predictor ที่รับเฉพาะค่านั้นจะให้ผลเหมือนกัน จึงตอบเป้าหมายที่ต่างกันให้ถูกทั้งคู่ไม่ได้

**อ่านสัญลักษณ์:**

- **f(s_A)=f(s_B):** สอง state ชนกันที่ representation เดียวกัน
- **y_A≠y_B:** เป้าหมายที่ถูกของสองกรณีต่างกัน
- **g:** predictor แบบ deterministic ที่เห็นเพียง output ของ f

**ตัวอย่างทีละขั้น:** สมมติ state A มี hunger=0.8, threat=0 และควร eat; state B มี hunger=0.8, threat=1 และควร hide

1. ถ้า encoder เก็บเฉพาะ hunger ทั้ง A และ B จะกลายเป็น z=0.8
2. ถ้า g(0.8)=eat จะถูก A แต่ผิด B; ถ้าเปลี่ยนให้เป็น hide จะสลับกรณีที่ผิด
3. เมื่อ A/B พบเท่ากัน และไม่มีข้อมูลอื่นเข้ามา predictor จึงทำถูกได้มากสุด 1 จาก 2 กรณี หรือ 50%

**ผลที่ได้:** การเพิ่มรอบคำนวณให้ g โดยยังเห็นเพียง 0.8 ไม่สร้างข้อมูล threat ที่ถูกตัดทิ้งกลับมา

**เชื่อมกลับไปที่สมการ:** เมื่อ error มาจาก state aliasing ต้องเพิ่มข้อมูลที่แยกกรณีได้ เช่นเก็บ threat หรือ observation เพิ่ม

### นิยามที่ใช้ในบทนี้

- **state abstraction:** การรวมสถานะโดยตั้งใจรักษาสิ่งที่จำเป็นต่อ reward, transition หรือเป้าหมายที่กำหนด
- **state aliasing:** สถานะที่ควรตัดสินใจต่างกันถูกแทนเป็นข้อมูลเดียวกัน
- **invariance / equivariance:** ตัวแทนคงเดิม / เปลี่ยนตามกฎที่สอดคล้องกัน เมื่อ input ถูกแปลง
- **Jacobian:** เมทริกซ์อนุพันธ์ที่บอกความไวเฉพาะที่ของ output ต่อแต่ละทิศของ input

### ทดลองกลไก

**ลองทำ:** ปิด threat และคงสีเสื้อไว้ก่อน ตรวจ state A/B จากนั้นเปิด threat และปิดสีเสื้อ

**สังเกต:** นับกลุ่มที่มี action เป้าหมายขัดกัน แยกจากจำนวนกลุ่มทั้งหมด

**ขอบเขตของแบบจำลอง:** lab ใช้ projection ที่กำหนดด้วยมือเพื่อเห็น state aliasing โดยตรง ไม่ได้ฝึก representation หรือพิสูจน์ bisimulation ของระบบจริง

### ตรวจความเข้าใจก่อนต่อยอด

ถ้า encoder รวม state สองแบบที่มี action ถูกต่างกัน การเพิ่ม recurrent passes ให้ policy ช่วยได้ภายใต้เงื่อนไขใด?

<details>
<summary>แนวคำตอบ</summary>

ช่วยได้เมื่อรอบคำนวณเข้าถึงข้อมูลเพิ่มเติมที่แยกสอง state หรือ representation เดิมยังมีสัญญาณนั้นอยู่แต่ policy ยังใช้ไม่เป็น หาก input ให้รอบทั้งหมดเหมือนกันและไม่มีข้อมูลเพิ่ม การวนคิดไม่สามารถคืนข้อมูลที่ถูกทิ้งแล้ว

</details>

**ข้อสรุป:** ประเมิน representation จากความแตกต่างที่งานต้องใช้; ขนาด latent และภาพ geometry เป็นเครื่องมือวิเคราะห์ประกอบ

## บท 2 — Attention, weights และขอบเขตของการปรับโมเดล

[เปิดบทพร้อมห้องทดลอง](../index.html#story/07) · [หัวข้อสังเคราะห์](topics/07-training-and-model-architecture.md)

**คำถามหลัก:** การลดพารามิเตอร์ที่ฝึก เปลี่ยน computation และความสามารถของโมเดลตรงไหน?

**ความเข้าใจที่นำมาใช้:** เราใช้ z แทนข้อมูลที่เกี่ยวกับงาน ต่อไปต้องแยกตัวแปรภายในที่เกิดจาก input ออกจากพารามิเตอร์ที่สร้างตัวแปรเหล่านั้น

- [บท 1](#chapter-01): representation และข้อจำกัดจากการสูญหายของข้อมูล

### โจทย์

คำว่า one layer, low rank หรือ frozen model อาจหมายถึงคนละส่วนของ computational graph การอ่าน tensor shape และเส้นทาง gradient ช่วยระบุว่าอะไรลดลงจริง

### 2.1 กำหนด tensor contract ของ attention

ใช้ H ∈ ℝ^(T×d) เก็บ activation หนึ่งแถวต่อ token โดย T คือ sequence length และ d คือ model width สำหรับ attention หนึ่ง head กำหนด W_Q,W_K ∈ ℝ^(d×d_k), W_V ∈ ℝ^(d×d_v) จึงได้ Q,K ขนาด T×d_k และ V ขนาด T×d_v

QK⊤ มีขนาด T×T: แถว i ประเมินความเข้ากันได้ของ query ตำแหน่ง i กับ key ทุกตำแหน่ง หลัง scale และ softmax ตามแถว จะได้ค่าน้ำหนักรวมเป็นหนึ่งเพื่อนำไปผสม V ผลมีขนาด T×d_v ส่วน mask M ใช้ค่า 0 ในตำแหน่งที่อ่านได้และ −∞ ในตำแหน่งต้องห้าม

สิ่งที่ฝึกคือ projection weights และพารามิเตอร์อื่นใน θ ขณะที่ H,Q,K,V เป็นค่าที่เกิดจาก input ในครั้งนั้น การมี attention weight สูงหมายถึงอิทธิพลต่อการผสมข้อมูลตามกลไกนี้ ยังไม่ได้ให้เงื่อนไขว่าข้อมูลนั้นจริงหรือ action ที่เลือกถูก

$$
Q=HW_Q,\qquad K=HW_K
$$

$$
V=HW_V
$$

ใช้ convention ที่ activation แต่ละ token เป็นแถว; batch และ head อื่นละไว้เพื่อให้เห็น shape

**อ่านสมการนี้ว่า:** นำ activation ของแต่ละ token ผ่านเมทริกซ์สามชุด เพื่อสร้าง query สำหรับถาม, key สำหรับจับคู่ และ value สำหรับส่งต่อ

**อ่านสัญลักษณ์:**

- **H:** เมทริกซ์ที่แต่ละแถวเป็น activation ของหนึ่ง token
- **W_Q, W_K, W_V:** projection weights ที่เรียนระหว่าง training และนำมาใช้กับ input ปัจจุบัน
- **HW_Q:** คูณแต่ละแถวของ H กับ W_Q เพื่อได้แถว query ที่ตรงกัน

**ตัวอย่างทีละขั้น:** ตัวอย่างหนึ่ง head มี 2 token และทุกมิติเท่ากับ 2: H=[[1,0],[0,1]], W_Q=W_K=[[1,0],[0,1]], W_V=[[2,0],[0,4]]

1. คูณ H กับ W_Q: แถวแรก [1,0] ยังคงเป็น [1,0] และแถวที่สองเป็น [0,1] จึงได้ Q=[[1,0],[0,1]]
2. คูณกับ W_K แบบเดียวกัน ได้ K=[[1,0],[0,1]]
3. คูณกับ W_V ได้ V=[[2,0],[0,4]]: token แรกถือ value [2,0] และ token ที่สองถือ [0,4]

**ผลที่ได้:** Q, K และ V ล้วนมีขนาด 2×2 ในตัวอย่างนี้ แต่ทำหน้าที่คนละอย่าง; สมการถัดไปจะใช้ผลทั้งสามชุดนี้ต่อ

**เชื่อมกลับไปที่สมการ:** projection weights เป็นพารามิเตอร์ ส่วน Q/K/V เป็นค่าจาก input ครั้งนี้ ซึ่งเปลี่ยนเมื่อ H เปลี่ยน

$$
O=\operatorname{softmax}_{\mathrm{rows}}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}+M\right)V
$$

$$
O\in\mathbb{R}^{T\times d_v}
$$

M เป็น mask ขนาด T×T ที่ broadcast ได้; ใน causal attention ตำแหน่งอนาคตจะถูกปิด

**อ่านสมการนี้ว่า:** ให้แต่ละ query ให้คะแนนทุก key จากนั้นปรับสเกล ปิดตำแหน่งที่อ่านไม่ได้ แปลงคะแนนเป็นน้ำหนักรวมหนึ่ง แล้วใช้ผสม value

**อ่านสัญลักษณ์:**

- **QK⊤:** transpose เปลี่ยนแถว key เป็นคอลัมน์ เพื่อหา dot product ของทุกคู่ query–key
- **√d_k:** หารด้วยรากที่สองของมิติ key เพื่อปรับสเกลคะแนน
- **softmax_rows:** ทำ softmax แยกแต่ละแถว ให้น้ำหนักที่ไม่ติดลบและรวมเป็น 1
- **M:** mask: บวก 0 เมื่ออ่านได้ และ −∞ เมื่อห้ามอ่าน

**ตัวอย่างทีละขั้น:** ใช้ Q=K=[[1,0],[0,1]], V=[[2,0],[0,4]] จากตัวอย่างก่อน และ d_k=2; เริ่มจากไม่มีตำแหน่งต้องห้าม

1. สำหรับ token แรก dot product กับสอง key คือ [1,0]; หาร √2 แล้วได้ประมาณ [0.707,0]
2. softmax ใช้ [exp(0.707),exp(0)]≈[2.028,1] แล้วหารผลรวม 3.028 จึงได้ประมาณ [0.670,0.330]
3. ผสม value: 0.670×[2,0]+0.330×[0,4]≈[1.34,1.32]; นี่คือ output ของแถวแรก
4. หากใช้ causal mask token แรกอ่าน token ที่สองไม่ได้: คะแนนเป็น [0.707,−∞], น้ำหนักเป็น [1,0] และ output เป็น [2,0]

**ผลที่ได้:** กรณีไม่มี mask ได้ O≈[[1.34,1.32],[0.66,2.68]] ขนาด 2×2; ส่วนตัวอย่าง causal mask ข้างต้นเปลี่ยนเฉพาะแถวแรกให้เป็น [2,0] ค่าทศนิยมปัดเศษเพื่ออ่านง่าย

**เชื่อมกลับไปที่สมการ:** attention คือการผสม value ตามน้ำหนักที่คำนวณจาก query/key และ mask; น้ำหนักมากยังไม่ได้รับรองความจริงของ value

### 2.2 LoRA จำกัด subspace ของ weight update

สำหรับ linear layer ใช้ convention เวกเตอร์คอลัมน์ y = Wh โดย W ∈ ℝ^(d_out×d_in) LoRA ตรึง W แล้วเรียน A ∈ ℝ^(r×d_in) และ B ∈ ℝ^(d_out×r) ส่วนปรับ ΔW = (α/r)BA จึงมี rank ไม่เกิน r; α คือค่าขยายที่กำหนดแยกจาก rank

จำนวนพารามิเตอร์ adapter เท่ากับ r(d_in+d_out) เทียบกับ d_out d_in ของ W แต่ฐาน W ยังเป็นส่วนหนึ่งของ forward เมื่อแยก adapter จะคำนวณทั้ง Wh และ B(Ah); เมื่อ deployment รองรับ อาจรวม W+ΔW ก่อนใช้งานได้ จึงต้องระบุว่าจับเวลารูปแบบไหน

ตัวอย่าง 16×24 มี 384 พารามิเตอร์ฐาน ถ้า r=4 adapter มี 160 ค่า แต่ r=12 มี 480 ค่า เกินฐานแล้ว จุดที่ adapter เล็กกว่าฐานคือ r<384/40=9.6 การนับนี้ไม่บอกคุณภาพ เพราะ update ที่ task ต้องการอาจไม่อยู่ใน subspace ที่ rank ต่ำแทนได้

$$
y=(W+\Delta W)h
$$

$$
\Delta W=\frac{\alpha}{r}BA
$$

$$
\operatorname{rank}(\Delta W)\le r
$$

h ∈ ℝ^d_in; B มี shape d_out×r และ A มี shape r×d_in; α/r คือ scaling convention ที่ใช้ที่นี่

**อ่านสมการนี้ว่า:** คงผลจาก weight ฐานไว้ แล้วบวกผลปรับที่วิ่งผ่านเมทริกซ์เล็กสองตัว พร้อมคูณสเกล α/r ก่อนรวมเป็น output

**อ่านสัญลักษณ์:**

- **ΔW:** ส่วนเปลี่ยนแปลงที่บวกเข้า weight ฐาน W
- **Ah แล้ว B(Ah):** ย่อเวกเตอร์จาก d_in เหลือ r ค่า แล้วขยายเป็น d_out ค่า
- **α/r:** ตัวคูณขนาด update; เปลี่ยน α ได้โดยไม่เปลี่ยน rank
- **rank(ΔW)≤r:** update มีจำนวนทิศทางอิสระได้ไม่เกิน r

**ตัวอย่างทีละขั้น:** สมมติ W=[[1,0],[0,1]], h=(2,3), r=1, α=2, A=[1,0] และ B=[[1],[2]]

1. ทางฐานให้ Wh=(2,3)
2. ทาง adapter ให้ Ah=2 แล้ว B(Ah)=(2,4); คูณ α/r=2 ได้ส่วนปรับ (4,8)
3. เมทริกซ์ปรับคือ ΔW=2BA=[[2,0],[4,0]] ซึ่งมี rank=1 เพราะแถวสองเป็นสองเท่าของแถวแรก
4. รวมผลสองทาง: y=(2,3)+(4,8)=(6,11)

**ผลที่ได้:** ได้ output ใหม่ (6,11) โดยฐาน W คงเดิม และส่วนปรับส่งผลผ่านทิศทางอิสระเพียงหนึ่งทิศทาง

**เชื่อมกลับไปที่สมการ:** r จำกัดโครงสร้างของ update ส่วน α/r กำหนดขนาดผลของ update; สองค่านี้มีบทบาทต่างกัน

$$
\frac{\mathrm{adapter}}{\mathrm{base}}=\frac{r(d_{\mathrm{in}}+d_{\mathrm{out}})}{d_{\mathrm{in}}d_{\mathrm{out}}}
$$

อัตราส่วนจำนวนพารามิเตอร์ของเมทริกซ์นี้ ไม่รวม bias, layer อื่น หรือ optimizer state

**อ่านสมการนี้ว่า:** นับพารามิเตอร์ใน A และ B รวมกัน แล้วหารด้วยจำนวนพารามิเตอร์ของ W เพื่อดูว่า adapter มีขนาดกี่ส่วนของฐาน

**อ่านสัญลักษณ์:**

- **r(d_in+d_out):** จำนวนค่าใน A คือ r·d_in บวกจำนวนค่าใน B คือ d_out·r
- **d_in d_out:** จำนวนค่าของเมทริกซ์ฐาน W
- **adapter/base:** อัตราส่วน; 0.5 หมายถึง adapter มีพารามิเตอร์ครึ่งหนึ่งของฐาน

**ตัวอย่างทีละขั้น:** ใช้ linear layer ที่ d_in=24 และ d_out=16 โดยนับเฉพาะเมทริกซ์นี้ ไม่รวม bias หรือ optimizer state

1. ฐานมี 16×24=384 ค่า
2. ถ้า r=4: A มี 4×24=96 ค่า, B มี 16×4=64 ค่า รวม 160; อัตราส่วน 160/384≈0.417 หรือ 41.7%
3. ถ้า r=12: adapter มี 12×(24+16)=480 ค่า; อัตราส่วน 480/384=1.25 หรือ 125%

**ผลที่ได้:** rank 4 ใช้พารามิเตอร์ adapter น้อยกว่าฐาน แต่ rank 12 ใน shape นี้มี adapter ใหญ่กว่าฐานแล้ว

**เชื่อมกลับไปที่สมการ:** ต้องแทนค่า shape และ rank ก่อนสรุปเรื่องขนาด ส่วน weight ฐานยังต้องใช้ในการคำนวณด้วย

### 2.3 Trainable parameters กับ execution graph

การฝึกหนึ่ง layer ระบุ subset ของ θ ที่รับ update ส่วน layer อื่นอาจยังต้อง forward และอาจต้องส่ง gradient ผ่าน activation เพื่อให้ถึงส่วนที่ฝึก การลด trainable parameters จึงลด gradient/optimizer storage บางส่วนได้ แต่ไม่ได้ลบทุกต้นทุนตามสัดส่วนเดียวกัน

Architecture กำหนดโครง computation ส่วน optimizer กำหนดวิธีเปลี่ยน θ ตัวอย่างในโพสต์เรื่อง attention variants กับ Muon ต้องแยกสองแกนนี้ และแยก data generation, training, checkpoint transfer และ inference ออกจากกัน เพื่อไม่อ้างผลของ phase หนึ่งให้ทุก phase

มุมมอง operator/compression เช่น HOPE ถามว่าส่วนใดของ learned function แทนด้วย subspace เล็กลงได้ การ approximate W ด้วย rank ต่ำอาจรักษาค่าเฉลี่ยของ output แต่เสีย rare case จึงต้องตรวจ behavior ที่สนใจหลัง compression ไม่ใช้จำนวนพารามิเตอร์ที่ลดเป็นคำตอบสุดท้าย

$$
\theta_{\mathrm{train}}\subseteq\theta
$$

ไม่ได้กำหนดจำนวน layer ที่ forward ต้องผ่าน

θ_train คือพารามิเตอร์ที่ optimizer อัปเดต; execution graph เป็นอีกข้อกำหนดหนึ่ง

**อ่านสมการนี้ว่า:** การเลือกว่าจะอัปเดตพารามิเตอร์ชุดไหนเป็นข้อกำหนดของ optimizer ส่วน forward ยังต้องเดินตาม graph ที่สร้างไว้

**อ่านสัญลักษณ์:**

- **θ_train:** ชุดพารามิเตอร์ที่อนุญาตให้ optimizer เปลี่ยน
- **⊆:** เป็นส่วนหนึ่งของชุดใหญ่กว่า ไม่ใช่การลบส่วนอื่นออกจากโมเดล
- **forward:** การคำนวณจาก input ไปยัง output ซึ่งยังใช้ weight ที่ frozen ได้

**ตัวอย่างทีละขั้น:** สมมติเครือข่าย scalar มี 3 layer ต่อกัน: x=1, w₁=2, w₂=3, w₃=4 และฝึกเฉพาะ w₂

1. θ={w₁,w₂,w₃} แต่ θ_train={w₂}; นี่คือความสัมพันธ์ของชุดพารามิเตอร์ ไม่ใช่สูตรนับจำนวน layer
2. forward ยังผ่านครบสามขั้น: 1×2=2 → 2×3=6 → 6×4=24
3. ถ้าหลังอัปเดต w₂ เปลี่ยนเป็น 2.5, forward ใหม่เป็น 1×2=2 → 2×2.5=5 → 5×4=20

**ผลที่ได้:** ฝึกเพียงหนึ่ง weight แต่ทั้งสาม layer ยังอยู่ในเส้นทางคำนวณ รวมถึง w₁ และ w₃ ที่ไม่เปลี่ยนค่า

**เชื่อมกลับไปที่สมการ:** จำนวนพารามิเตอร์ที่ฝึกช่วยบอกภาระบางส่วนของ training ต้องดู execution graph เพิ่มเมื่อต้องการอธิบายเวลาคำนวณ

### 2.4 Frozen θ ยังเปลี่ยน activation ระหว่าง inference ได้

อีกวิธีหนึ่งตรึง θ แต่ปรับ latent z ของ input ปัจจุบันด้วย objective บางอย่าง หรือส่ง h ผ่าน block ซ้ำ ทั้งสองเพิ่ม computation ขณะใช้งานโดยไม่มี weight update แบบฝึกโมเดล ต้องบอกให้ชัดว่า state ใดถูกปรับและเก็บต่อไปถึง request ถัดไปหรือไม่

การลด output entropy ทำให้ distribution กระจุกตัวมากขึ้น ตัวอย่างสองคลาสเปลี่ยนจาก (0.5,0.5) เป็น (0.99,0.01) entropy ลดจากประมาณ 0.693 เป็น 0.056 nats แต่ถ้าคำตอบจริงคือคลาสที่สอง ความมั่นใจที่เพิ่มขึ้นกลับผิดทิศ

จึงแยก capacity ของ weight update, compute สำหรับ input หนึ่ง และเกณฑ์ตัดสิน correctness เป็นสามเรื่อง บทนี้กำหนดสองเรื่องแรกไว้แล้ว บทต่อไปจะดูโครงสร้างของ compute เพิ่ม: วน hidden state หรือแตกทางเลือกใน search tree

$$
z_{k+1}=z_k-\eta\nabla_z L(z_k;\theta_{\mathrm{fixed}})
$$

ตัวอย่าง inference-time latent optimization; η คือ step size และ L คือ objective ที่เลือก ซึ่งต้องตรวจว่าสัมพันธ์กับ task หรือไม่

**อ่านสมการนี้ว่า:** หา slope ของ objective เมื่อขยับ latent แล้วขยับ latent ย้อนทิศ slope ตามขนาดก้าวที่กำหนด โดยตรึง weight ของโมเดลไว้

**อ่านสัญลักษณ์:**

- **∇z L:** gradient ต่อ z บอกทิศที่ objective เพิ่มเร็ว ณ จุดปัจจุบัน
- **−η∇z L:** ขยับย้อน gradient โดย η คุมขนาดก้าว
- **θ_fixed:** พารามิเตอร์โมเดลที่ไม่ถูกอัปเดตระหว่าง loop นี้
- **k+1:** latent รอบใหม่ของ input เดิม ไม่ใช่การฝึก weight รอบใหม่

**ตัวอย่างทีละขั้น:** สมมติ objective ที่ตรึงไว้คือ L(z)=(z−3)², เริ่ม z₀=1 และใช้ η=0.25

1. ที่ z₀=1 gradient คือ 2(1−3)=−4; จึงได้ z₁=1−0.25×(−4)=2
2. ที่ z₁=2 gradient คือ −2; จึงได้ z₂=2−0.25×(−2)=2.5
3. ค่า L ลดจาก (1−3)²=4 เป็น 1 แล้วเป็น 0.25 โดยเปลี่ยนเพียง z

**ผลที่ได้:** latent เคลื่อนจาก 1 → 2 → 2.5 เข้าใกล้จุดที่ objective ต่ำลง ส่วน θ ยังเป็นชุดเดิม

**เชื่อมกลับไปที่สมการ:** การลด objective นี้สำเร็จไม่ได้บอกว่า objective ตรงกับ correctness ของ task ต้องตรวจความสัมพันธ์นั้นแยกด้วย

$$
H(p)=-\sum_i p_i\ln p_i
$$

entropy ใช้ natural log หน่วย nats; H ต่ำบอกการกระจุกของ distribution ไม่ได้ระบุว่าคลาสที่เดาถูก

**อ่านสมการนี้ว่า:** คูณความน่าจะเป็นแต่ละทางเลือกกับ log ของมัน รวมทุกทาง แล้วกลับเครื่องหมายเพื่อวัดว่าการกระจายกระจุกตัวแค่ไหน

**อ่านสัญลักษณ์:**

- **p_i:** ความน่าจะเป็นของทางเลือก i; ทุกค่ารวมเป็น 1
- **Σ_i:** รวมผลของทุกทางเลือก
- **ln:** log ฐาน e; entropy ที่ได้ใช้หน่วย nats
- **−:** กลับเครื่องหมาย เพราะ log ของความน่าจะเป็นระหว่าง 0 กับ 1 เป็นลบ

**ตัวอย่างทีละขั้น:** เปรียบเทียบโมเดลสองคลาสก่อนและหลังปรับ latent โดยสมมติว่าคำตอบจริงคือคลาสที่สอง

1. เมื่อ p=(0.5,0.5), แต่ละเทอมคือ 0.5×ln(0.5)≈−0.3466; รวมแล้วกลับเครื่องหมายได้ H≈0.6931 nats
2. เมื่อ p=(0.99,0.01), สองเทอมประมาณ −0.00995 และ −0.04605; จึงได้ H≈0.0560 nats
3. แม้ entropy ลด โมเดลกลับให้น้ำหนัก 0.99 กับคลาสแรกที่ผิดในตัวอย่างนี้

**ผลที่ได้:** H ลดจากประมาณ 0.693 เป็น 0.056 แปลว่าการกระจายมั่นใจไปทางหนึ่งมากขึ้น แต่ทางนั้นอาจผิดได้

**เชื่อมกลับไปที่สมการ:** ใช้ entropy อ่านความกระจุกของคำตอบ แล้ววัดความถูกต้องด้วยเป้าหมายหรือ verifier ที่เหมาะกับงาน

### นิยามที่ใช้ในบทนี้

- **activation / parameter:** activation ขึ้นกับ input และรอบคำนวณ; parameter เป็นค่าสัมประสิทธิ์ของโมเดลที่ฝึกไว้
- **low-rank update:** ส่วนปรับเมทริกซ์ที่อยู่ใน subspace จำกัด แทนด้วยผลคูณของสองเมทริกซ์บาง
- **execution graph:** ลำดับ operation ที่ต้องคำนวณเพื่อได้ผลลัพธ์ รวมส่วนที่ weights ถูกตรึง
- **entropy:** ค่าความกระจายของ probability distribution ซึ่งแยกจากความถูกต้องของคำตอบ

**ความเข้าใจที่นำมาใช้:** z คือข้อมูลตั้งต้น, h คือสถานะคำนวณ และ θ คือพารามิเตอร์ของกลไก เราจะใช้สัญลักษณ์เหล่านี้แยกการคิดซ้ำออกจากการเรียน weights

### โจทย์

การใช้คำว่า latent reasoning รวมหลายกลไกทำให้มองไม่เห็นว่า compute ซื้ออะไร: representation ที่ปรับแล้ว, action branch เพิ่ม หรือการตัดทางเลือกที่ใช้ไม่ได้

### 3.1 Recurrent depth ใช้ block เดิมกับ state ใหม่

กำหนด h_0 จาก z แล้วใช้ h_(k+1)=Fθ(h_k,z) จำนวน K รอบ จากนั้น decode h_K เป็นคำตอบ ในที่นี้ k นับรอบของ input เดิม ส่วน t ใช้นับ token หรือการเปลี่ยนของสิ่งแวดล้อม การวน k ไม่จำเป็นต้องสร้าง token ใหม่ทุกครั้ง

หากทุก pass ใช้ θ ชุดเดียวกัน จำนวนพารามิเตอร์ไม่โตตาม K แต่จำนวน operation และเวลาโดยประมาณยังโต การเก็บ z ให้แต่ละ pass ใช้ช่วยไม่ให้ loop ต้องพึ่ง h อย่างเดียว ส่วนการเรียนให้ block ทนจำนวนรอบต่างกันเป็นเงื่อนไขของ architecture/training recipe นั้น

Recurrent update อาจเป็น forward computation ล้วน ในขณะที่ latent optimization ในบทก่อนคำนวณ gradient ต่อ z ด้วย ทั้งคู่เปลี่ยน activation ขณะ θ คงที่ แต่ต้นทุนต่อรอบและวิธีฝึกให้ใช้งานได้ต่างกัน

$$
h_{k+1}=F_{\theta}(h_k,z)
$$

$$
p(y\mid x)=\operatorname{softmax}(g_{\theta}(h_K))
$$

Fθ คือ recurrent block และ gθ คือ output head; K เป็นงบภายในของ input เดียว

**อ่านสมการนี้ว่า:** ใช้ block เดิมปรับ hidden state ทีละรอบ โดยยังรับ representation ของ input เดิม แล้วค่อยนำ state รอบสุดท้ายไปสร้างความน่าจะเป็นของคำตอบ

**อ่านสัญลักษณ์:**

- **Fθ:** block สำหรับอัปเดต state โดยใช้พารามิเตอร์ θ ชุดเดิมทุก pass
- **k, K:** k คือรอบปัจจุบัน ส่วน K คือจำนวนรอบทั้งหมดที่ใช้กับ input นี้
- **gθ(h_K):** output head ที่แปลง hidden state สุดท้ายเป็นคะแนนก่อน softmax
- **p(y|x):** การกระจายของคำตอบเมื่อรับ input x

**ตัวอย่างทีละขั้น:** ตัวอย่าง scalar: z=2, h₀=0, F(h,z)=(h+z)/2, K=2 และ output head ให้ logits=[h,0]

1. รอบแรก h₁=(0+2)/2=1 โดย z ยังเท่ากับ 2
2. รอบสอง h₂=(1+2)/2=1.5; ใช้สูตรเดิมกับ h ที่เปลี่ยนไป
3. เมื่อครบ K=2 ได้ logits=[1.5,0]; softmax ให้ประมาณ [0.818,0.182] เพราะ exp(1.5)≈4.482 แล้วหารด้วย 4.482+1

**ผลที่ได้:** โมเดลใช้สอง pass เพื่อเปลี่ยน activation จาก 0 → 1 → 1.5 แล้วจึงออกคำตอบ โดยไม่เพิ่มชุด weight ตามจำนวนรอบ

**เชื่อมกลับไปที่สมการ:** การวนใช้พารามิเตอร์ร่วมกันช่วยคงจำนวน weight แต่ทุก pass ยังมีต้นทุนการคำนวณและอาจเปลี่ยนคำตอบได้

$$
T_{\mathrm{total}}\approx T_{\mathrm{encode}}+K\,T_{\mathrm{pass}}+T_{\mathrm{decode}}
$$

แบบจำลองแบบเรียงลำดับที่เวลาต่อ pass ใกล้เคียงกัน; ต้องรวม backward ด้วยหาก pass ใช้ gradient

**อ่านสมการนี้ว่า:** รวมเวลาสร้าง representation หนึ่งครั้ง เวลาของ block ที่ต้องทำซ้ำ K ครั้ง และเวลาถอดคำตอบท้ายสุด

**อ่านสัญลักษณ์:**

- **K·T_pass:** จำนวน pass คูณเวลาต่อ pass โดยสมมติว่าทำเรียงกันและแต่ละรอบใช้เวลาใกล้เคียงกัน
- **T_encode, T_decode:** ต้นทุนก่อนเข้า loop และหลังออกจาก loop
- **≈:** แบบจำลองเวลาโดยประมาณ; ค่าใช้จ่ายจริงต้องตรงกับขอบเขตที่นับ

**ตัวอย่างทีละขั้น:** สมมติเวลาที่วัดในขอบเขตนี้คือ encode=3 ms, pass=2 ms และ decode=1 ms โดยไม่มีการรัน pass ซ้อนกัน

1. ถ้า K=4 เวลาของ loop คือ 4×2=8 ms
2. บวกต้นทุนหน้าและท้าย: T_total≈3+8+1=12 ms
3. ถ้าเพิ่ม K เป็น 8 จะได้ 3+8×2+1=20 ms; เพิ่ม 4 pass จึงเพิ่มเวลาประมาณ 8 ms

**ผลที่ได้:** จำนวนรอบเพิ่มสองเท่า แต่เวลารวมจาก 12 เป็น 20 ms เพราะ encode/decode เป็นต้นทุนที่จ่ายครั้งเดียว

**เชื่อมกลับไปที่สมการ:** หาก pass ต้อง backward ให้นับใน T_pass ด้วย และระบุเพิ่มเมื่อขอบเขตเวลาไม่ได้ครอบ queue หรือ network

### 3.2 Convergence ให้เงื่อนไขหยุด แต่ยังต้องมีเงื่อนไขถูก

Fixed point คือ h* ที่ Fθ(h*,z)=h* ตัวอย่าง scalar หรือ vector F(h)=0.5h+0.5b เป็น contraction: ระยะของ input สองตัวหดลงครึ่งเมื่อผ่าน F จึงเข้าใกล้ b โดย error ลดครึ่งทุก pass เราคำนวณจำนวนรอบที่ทำให้ error เล็กได้ แต่ b ถูกกำหนดจากกลไก ไม่ได้ถูกบังคับว่าเป็นคำตอบของโจทย์

เกณฑ์ ∥h_(k+1)−h_k∥<ε ใช้ตรวจว่ารอบใหม่เปลี่ยน state น้อยลง ภายใต้ scale/norm ที่กำหนด มันอาจหยุดที่ fixed point ผิด, plateau หรือ state ที่ไม่ช่วย task ต้องวัด output validity แยก; validity หมายถึงผ่านข้อกำหนดของโจทย์ที่ตรวจได้

ระบบจริงจึงมี budget K_max, เกณฑ์หยุด และทางออกเมื่อยังไม่มั่นใจ เช่นคืนสถานะ unresolved การเพิ่ม K ยังต้องตรวจว่าคุณภาพดีขึ้นบนโจทย์ยาก และไม่ทำให้โจทย์ง่ายเสียเวลาเกินจำเป็น

$$
F(h)=0.5h+0.5b
$$

$$
\Longrightarrow\quad h_K-b=2^{-K}(h_0-b)
$$

ตัวอย่างแสดงการลู่เข้าสู่ b อย่างชัดเจน; ความถูกของ b เป็นอีกเงื่อนไขหนึ่ง

**อ่านสมการนี้ว่า:** ในทุก pass ให้ state ขยับไปครึ่งทางระหว่างค่าปัจจุบันกับ b ทำให้ระยะที่เหลือถึง b หดครึ่งหนึ่งทุกครั้ง

**อ่านสัญลักษณ์:**

- **b:** ค่าปลายทางที่ update นี้ดึงเข้าไปหา
- **h_K−b:** error แบบมีเครื่องหมายหลังทำ K รอบ
- **2^(−K):** เท่ากับ 1/2^K: ส่วนของ error เริ่มต้นที่ยังเหลือ
- **⇒:** สูตร update ด้านซ้ายทำให้ได้ความสัมพันธ์ของ error ด้านขวาในตัวอย่างนี้

**ตัวอย่างทีละขั้น:** กำหนด h₀=0 และ b=8; นี่เป็น toy update ที่คำนวณเส้นทางได้แน่นอน

1. ใช้ F ซ้ำ: h₁=4, h₂=6 และ h₃=7; ระยะถึง 8 ลดจาก 8 → 4 → 2 → 1
2. ตรวจสูตรเมื่อ K=3: h₃−8=2^(−3)×(0−8)=−1 จึงได้ h₃=7 ตรงกัน
3. เมื่อ K=6 error เหลือ −8/64=−0.125 จึงได้ h₆=7.875

**ผลที่ได้:** state เข้าใกล้ 8 ตามอัตราที่คำนวณได้ แต่ถ้าคำตอบจริงของ task คือ 10 loop นี้ก็ยังลู่เข้าสู่ค่าที่ผิด

**เชื่อมกลับไปที่สมการ:** convergence รับรองพฤติกรรมของการวน ส่วนความถูกต้องต้องตรวจว่าจุดที่ลู่เข้าตรงกับเป้าหมายของ task

หยุด (stop) เมื่อเงื่อนไขต่อไปนี้เป็นจริง หรือ budget หมด

$$
\operatorname{validity}(y)=\mathrm{true}
$$

stability เป็นสัญญาณประกอบ

validity ต้องนิยามตาม task; ถ้าตรวจได้เพียงบางเงื่อนไข ให้ระบุว่าการผ่านครอบคลุมอะไร

**อ่านสมการนี้ว่า:** นี่คือเงื่อนไขควบคุม loop: หยุดเมื่อคำตอบผ่านข้อกำหนด หรือเมื่อใช้งบหมด โดยสถานะผลลัพธ์ของสองกรณีต่างกัน

**อ่านสัญลักษณ์:**

- **validity(y)=true:** คำตอบผ่านสิ่งที่ verifier ตรวจ ไม่ใช่แค่มีรูปแบบนิ่ง
- **หรือ:** เงื่อนไข OR: เพียงเงื่อนไขใดเงื่อนไขหนึ่งเป็นจริงก็หยุดได้
- **budget:** เพดานทรัพยากร เช่นจำนวนรอบ เวลา หรือจำนวนการเรียกโมเดล
- **stability:** สัญญาณว่าผลเปลี่ยนน้อย ซึ่งยังต้องอ่านร่วมกับ validity

**ตัวอย่างทีละขั้น:** ตัวอย่าง solver สร้าง candidate ทีละรอบ: ต้องตอบจำนวนเต็มที่ยกกำลังสองได้ 9 และมีงบมากสุด 3 รอบ

1. รอบแรกเสนอ 2; ตรวจ 2²=4 จึงยังไม่ผ่าน และงบยังเหลือ
2. รอบสองเสนอ 2 อีกครั้ง; output ซ้ำบอกว่ายังไม่เปลี่ยน แต่เงื่อนไข 2²=9 ยังเป็นเท็จ
3. ถ้ารอบสามเสนอ 3 จะผ่าน 3²=9 และคืนคำตอบ; ถ้ายังไม่มี candidate ผ่านเมื่อครบสามรอบ ให้หยุดพร้อมสถานะ unresolved

**ผลที่ได้:** loop หยุดได้ทั้งเพราะสำเร็จและเพราะทรัพยากรหมด จึงต้องเก็บเหตุผลการหยุดไว้ด้วย

**เชื่อมกลับไปที่สมการ:** เขียน stop rule กับสถานะผลลัพธ์แยกให้ชัด เพื่อไม่เผลอนับ timeout หรือ fixed output เป็นคำตอบที่ผ่านการตรวจ

### 3.3 Search สร้างกิ่งของทางเลือกที่ตรวจกลับได้

Explicit search เก็บ node ที่แทน state หรือ partial solution แล้วเลือกขยาย action ไปยัง node ใหม่ BFS ขยายตามจำนวน edge จากจุดเริ่ม จึงให้ shortest path ในกราฟที่ทุก edge มีต้นทุนเท่ากัน ส่วน greedy best-first ใช้ค่าประมาณระยะถึง goal เป็นลำดับความสำคัญ

ในกราฟจำกัดที่ตรวจ visited ถูกและไม่มีงบตัดจบ greedy ยังสำรวจจนพบทางที่มีได้ แต่ไม่มี shortest-path guarantee แบบ BFS จึงไม่ควรตีความภาพว่า greedy จำเป็นต้องติดทางตันเสมอ เมื่อมี budget ลำดับขยายจึงสำคัญต่อทั้ง solve rate และคุณภาพทางที่พบ

PUCT เพิ่ม learned prior และค่า value ให้การเลือกกิ่ง: P(s,a) แนะนำ action ที่น่าสนใจ, Q(s,a) เป็น return ที่ประเมินจาก search, N(s,a) เป็นจำนวน visit ตัว Q ในสูตรนี้คือ action value ของ search ไม่ใช่ query tensor ของ attention

$$
\begin{aligned}a^{*}=\operatorname*{argmax}_{a}\Biggl[&Q(s,a)\\&{}+c\,P(s,a)\,\frac{\sqrt{\sum_b N(s,b)}}{1+N(s,a)}\Biggr]\end{aligned}
$$

รูปแบบคะแนน PUCT ที่ใช้กันทั่วไป; c คุม exploration และ b วิ่งผ่าน action ที่ node s; รายละเอียด initialization/backup ขึ้นกับ implementation

**อ่านสมการนี้ว่า:** ให้คะแนนแต่ละ action ด้วยคุณค่าที่ search ประเมิน บวกโบนัสสำรวจที่อาศัย prior และจำนวนครั้งที่เคยลอง แล้วเลือก action ที่คะแนนรวมสูงสุด

**อ่านสัญลักษณ์:**

- **argmax_a:** คืน action ที่ได้คะแนนมากที่สุด ไม่ได้คืนตัวคะแนน
- **Q(s,a):** ค่า action ที่ประเมินจาก search; Q นี้ไม่ใช่ query ของ attention
- **c·P(s,a):** น้ำหนักของโบนัสสำรวจ: c คุมความแรง และ P คือ prior ของ action
- **N และ Σ_b N(s,b):** N นับการเยี่ยมแต่ละ action; Σ รวมทุก action ที่ node นี้

**ตัวอย่างทีละขั้น:** สมมติมี A/B: Q=(0.60,0.55), P=(0.60,0.40), N=(3,1) และ c=1

1. รวม visit ได้ 3+1=4 ดังนั้นรากที่สองในตัวเศษเท่ากับ 2
2. A ได้โบนัส 1×0.60×2/(1+3)=0.30; คะแนนรวม 0.60+0.30=0.90
3. B ได้โบนัส 1×0.40×2/(1+1)=0.40; คะแนนรวม 0.55+0.40=0.95
4. argmax จึงเลือก B ในรอบนี้ แม้ค่า Q ของ B ต่ำกว่า A เล็กน้อย

**ผลที่ได้:** โบนัสช่วยให้ action ที่ยังถูกลองน้อยมีโอกาสถูกสำรวจ; เมื่อ visit เปลี่ยน คะแนนรอบถัดไปต้องคำนวณใหม่

**เชื่อมกลับไปที่สมการ:** อ่าน PUCT เป็น value บวก exploration bonus และกำหนดความหมายของ visit/backup ให้ตรง implementation ที่ใช้

### 3.4 ประกอบกลไกโดยยังแยกต้นทุนและขอบเขต

Search ใช้ policy/value model ที่มี recurrent block ได้: loop ช่วยประเมินหนึ่ง node ส่วน tree ซื้อจำนวนทางเลือกเพิ่ม สำหรับโจทย์ที่มีกฎ ยังใช้ pruning ตัด candidate ที่ผิดเงื่อนไขออกก่อนขยายได้ โดยต้องรักษา candidate ที่ยังมีโอกาสเป็นคำตอบ

Flow-style refinement เป็นกลุ่มวิธีที่ฝึก update ให้ปรับ representation หรือ structured output ตาม recipe เฉพาะ เช่นปรับตาม state ปัจจุบันและ noise อย่าอนุมานว่าการเรียก loop ว่า flow ทำให้มีหลักฐานเดียวกับ Flow Reasoning Models หรือมีการรับประกัน convergence

ทดลองด้วยงบ wall-clock เท่ากันเพื่อถามว่าใช้เวลาคุ้มไหม และงบ model calls/node expansions เท่ากันเพื่อแยกเหตุทางกลไก รายงานทั้งสองแบบเมื่อเป็นคนละคำถาม Maze lab ของบทนี้แสดง search order โดยไม่ใช้ neural scorer, recurrent model หรือ PUCT

budget = เวลา, model calls หรือ node expansions — ต้องเลือกและรายงานหน่วย

K เท่ากันไม่ได้หมายความว่า compute เท่ากัน ถ้า pass หรือ node evaluation มีต้นทุนต่างกัน

**อ่านสมการนี้ว่า:** ข้อความนี้เป็นข้อตกลงเรื่องการวัด: เลือกก่อนว่าจะจำกัดงบด้วยเวลา จำนวนเรียกโมเดล หรือจำนวน node ที่ขยาย แล้วรายงานหน่วยนั้น

**อ่านสัญลักษณ์:**

- **budget:** เพดานทรัพยากรที่การทดลองยอมใช้
- **model calls:** จำนวนครั้งที่เรียกโมเดล ซึ่งแต่ละครั้งอาจแพงไม่เท่ากัน
- **node expansions:** จำนวน node ที่ขยายใน search ซึ่งอาจมีหลาย model calls ต่อ node

**ตัวอย่างทีละขั้น:** สมมติวิธี A ใช้ 20 ms ต่อ model call และวิธี B ใช้ 50 ms ต่อ call; ทุก call ทำเรียงกันและละต้นทุนอื่นไว้

1. ให้งบเท่ากันที่ 10 calls: A ใช้ 10×20=200 ms ส่วน B ใช้ 10×50=500 ms
2. หากเปลี่ยนเป็นงบเวลาเท่ากัน 200 ms: A ทำได้ 10 calls ส่วน B ทำได้ 4 calls
3. จากนั้นวัดคุณภาพคำตอบที่แต่ละวิธีทำได้ภายใต้งบที่เลือก พร้อมระบุว่าใช้ calls หรือ ms เป็นข้อจำกัด

**ผลที่ได้:** คำว่าใช้งบเท่ากันให้การทดลองคนละแบบได้ เพราะ 10 calls ไม่ได้เท่ากับเวลารันเท่ากัน

**เชื่อมกลับไปที่สมการ:** เลือกหน่วยตามคำถาม: การใช้งานจริงมักสนใจเวลา ส่วนการอธิบายกลไกอาจต้องนับ calls หรือ expansions เพิ่ม

### นิยามที่ใช้ในบทนี้

- **recurrence:** การนำ state ภายในกลับผ่าน update function เพื่อทำ pass ถัดไป
- **fixed point:** state ที่ไม่เปลี่ยนเมื่อใช้ update เดิมอีกครั้ง; ไม่ใช่นิยามของคำตอบถูก
- **heuristic:** ค่าประมาณที่จัดลำดับ candidate เช่นระยะถึง goal
- **PUCT:** เกณฑ์เลือกกิ่งใน tree search ที่รวม action value, policy prior และ visit count

## บท 4 — จาก candidate สู่คำตอบที่มีเงื่อนไขรับรอง

[เปิดบทพร้อมห้องทดลอง](../index.html#story/03) · [หัวข้อสังเคราะห์](topics/03-neuro-symbolic-types-and-verification.md)

**คำถามหลัก:** Neural proposal, constraints และ verifier แบ่งหน้าที่กันอย่างไร?

**ความเข้าใจที่นำมาใช้:** Loop และ search สร้างหรือจัดอันดับ candidate ได้ แต่คะแนนสูง ความนิ่ง และจำนวนรอบ ยังไม่ใช่หลักฐานว่า candidate ใช้งานได้

- [บท 3](#chapter-02): candidate, search, pruning และความต่างระหว่าง stability กับ correctness

### โจทย์

ต้องแยกสิ่งที่โมเดลเสนอออกจากสิ่งที่ระบบยอม execute และระบุให้ได้ว่าด่านตรวจแต่ละชั้นรับรอง property ใด

### 4.1 แยก syntax, type และ semantic validity

เริ่มด้วย pipeline propose → constrain → verify → commit โดย proposer สร้าง action หรือ structured answer; constrain จำกัด domain ของตัวเลือก; verifier ตรวจข้อกำหนด; commit เปลี่ยน state จริง ถ้าตรวจไม่ผ่านอาจค้นต่อหรือคืน unresolved

Schema ตรวจรูปแบบ เช่น action อยู่ใน enum ที่รองรับและ target มีชนิดถูกต้อง แต่ action Attack ที่ parse ได้ยังอาจผิดเพราะ target อยู่นอกระยะ, cooldown ยังไม่หมด หรือ line of sight ถูกสิ่งกีดขวางบัง เงื่อนไขเหล่านี้อ้างอิง state ของโลก จึงต้องตรวจในชั้นที่มีข้อมูลนั้น

การตรวจต้องสัมพันธ์กับ state version ที่จะ execute ด้วย หากตรวจตอน target อยู่ในระยะแล้วปล่อยให้โลกเปลี่ยนก่อน commit การรับรองเดิมอาจหมดอายุ จะใช้ snapshot, lock หรือ revalidate ก็ได้ตามระบบ แต่ต้องระบุว่าคำว่า valid หมายถึงเวลาหรือเวอร์ชันใด

$$
\begin{aligned}\operatorname{accept}(a,s)={}&\operatorname{schema\ ok}(a)\\&{}\land\operatorname{preconditions}(a,s)\end{aligned}
$$

ตัวอย่าง acceptance predicate สำหรับ action a บน state s; มีผลเฉพาะเงื่อนไขที่นำมาเข้ารหัส

**อ่านสมการนี้ว่า:** ตรวจทั้งรูปแบบของ action และเงื่อนไขที่ต้องเป็นจริงใน state ปัจจุบัน; ยอมรับได้เมื่อทั้งสองส่วนผ่านพร้อมกัน

**อ่านสัญลักษณ์:**

- **schema_ok(a):** action มีชื่อ ฟิลด์ และชนิดข้อมูลตรงรูปแบบที่ระบบรับ
- **preconditions(a,s):** ข้อกำหนดก่อนทำ action เช่นระยะหรือ cooldown โดยอ่าน state s
- **∧:** logical AND: ทุกด้านต้องจริง เป็น checklist ไม่ใช่การคูณคะแนน

**ตัวอย่างทีละขั้น:** สมมติ action คือ Attack(target_id=17), target อยู่ห่าง 5 เมตร แต่โจมตีได้ไกลสุด 3 เมตรและ cooldown=0

1. schema ผ่าน เพราะ Attack เป็น action ที่รองรับ และ target_id เป็นจำนวนเต็มตามที่กำหนด
2. preconditions ไม่ผ่าน เพราะแม้ cooldown พร้อม แต่ระยะ 5 เมตรเกินขอบเขต 3 เมตร
3. จึงได้ accept=true ∧ false=false: ระบบปฏิเสธ action นี้

**ผลที่ได้:** action ที่ parse ได้สมบูรณ์ยังถูกปฏิเสธได้เมื่อเงื่อนไขโลกไม่อนุญาตให้ทำ

**เชื่อมกลับไปที่สมการ:** ระบุ preconditions ที่ต้องการรับรองให้ครบ และใช้ state เวอร์ชันที่ตรงกับตอน execute

$$
s_{\mathrm{next}}=\operatorname{transition}(s,a)
$$

เฉพาะเมื่อ

$$
\operatorname{accept}(a,s)=\mathrm{true}
$$

postconditions ของ s_next อาจต้องตรวจเพิ่ม หาก transition ไม่ได้รับประกันไว้แล้ว

**อ่านสมการนี้ว่า:** เปลี่ยน state ด้วยกฎ transition เฉพาะ action ที่ผ่านด่านรับรองบน state ที่ใช้จริง ส่วน action ที่ไม่ผ่านจะยังไม่ถูก commit

**อ่านสัญลักษณ์:**

- **s_next:** state หลัง execute action สำเร็จ
- **transition(s,a):** กฎคำนวณว่า action เปลี่ยน state ปัจจุบันอย่างไร
- **เฉพาะเมื่อ:** เป็น guard หรือประตูเงื่อนไขของการ execute ไม่ใช่การคูณ true/false กับ state

**ตัวอย่างทีละขั้น:** สมมติ snapshot เวอร์ชัน 8 มี target HP=10, ระยะ=2 เมตร, โจมตีได้ไกลสุด 3 เมตร และ damage=4

1. ตรวจ action Attack บน snapshot นี้แล้วผ่าน ทั้งรูปแบบ ระยะ และเงื่อนไขอื่นที่กำหนด
2. commit โดยใช้ state เดียวกับที่ตรวจ: transition ลด HP จาก 10 เป็น 10−4=6
3. ถ้าอีกกรณีเริ่มจาก HP=10 แต่ระยะ=5 เมตร accept จะเป็น false จึงไม่ execute และ HP ยังเท่ากับ 10

**ผลที่ได้:** กรณีแรกได้ s_next ที่ HP=6; กรณีหลังไม่ใช้ transition ของ action ที่ถูกปฏิเสธ

**เชื่อมกลับไปที่สมการ:** ถ้าโลกเปลี่ยนระหว่างตรวจและ commit ต้องตรวจใหม่หรือใช้กลไกรักษา snapshot เพื่อคงความหมายของการรับรอง

### 4.2 Soundness กับ completeness ต้องผูกกับสิ่งที่รับรอง

ให้ C เป็นเซต candidate assignment และ Ω เป็นเซตคำตอบที่ตรงข้อกำหนดทั้งหมด Pruner P ลด C โดยไม่ตัดคำตอบที่ถูกออก เรียก sound pruning ภายใต้นิยามนี้ ส่วน sound verifier หมายถึงทุกคำตอบที่มันยอมรับเป็นสมาชิก Ω ทั้งสองใช้คำว่า sound แต่กำลังพูดถึงคนละ operation

หาก C มีจำนวนจำกัดและ P(C)⊆C การ prune ซ้ำย่อมหยุดเปลี่ยนในที่สุด อย่างไรก็ตาม fixed point อาจยังมีหลาย candidate ที่ผิดได้ เพราะกฎตรวจเพียงบางเงื่อนไข การมอง candidate sets เป็น lattice ใช้ความสัมพันธ์แบบ subset จัดว่าชุดใดมีข้อมูลจำกัดมากกว่า ไม่ได้เพิ่มกฎความถูกต้องขึ้นเอง

Completeness ของ solver คือความสามารถพบคำตอบที่มีอยู่ภายใต้โดเมนและวิธีค้นที่ระบุ เช่น exhaustive backtracking ในโดเมนจำกัดที่ไม่ตัดคำตอบถูกและไม่ถูก timeout ข้อรับรองทั้งหมดตั้งอยู่บนสมมติฐานว่า initial domain ครอบคำตอบ และข้อกำหนด Ω ตรงกับปัญหาที่ต้องการจริง

$$
\Omega\cap C\subseteq P(C)\subseteq C
$$

sound pruning รักษาทุกคำตอบถูกที่ยังอยู่ใน C และไม่เพิ่ม candidate

**อ่านสมการนี้ว่า:** หลัง prune ชุดที่เหลือต้องยังมีคำตอบถูกทุกตัวที่มีอยู่เดิม และต้องไม่มี candidate ใหม่ที่ไม่ได้อยู่ในชุดตั้งต้น

**อ่านสัญลักษณ์:**

- **Ω:** เซตของคำตอบที่ตรง specification ทั้งหมด
- **∩:** intersection: สมาชิกที่อยู่ในทั้งสองเซต
- **⊆:** เป็น subset: ทุกสมาชิกด้านซ้ายต้องอยู่ด้านขวา
- **P(C):** ชุด candidate ที่เหลือหลังใช้กฎ prune กับ C

**ตัวอย่างทีละขั้น:** ให้ C={a,b,c,d} และคำตอบถูกทั้งหมด Ω={b,d,e}; ตัวอักษรแต่ละตัวแทน candidate assignment หนึ่งชุด

1. คำตอบถูกที่มีอยู่ใน C คือ Ω∩C={b,d}; e ถูกเช่นกันแต่ไม่ได้อยู่ในชุดตั้งต้นนี้
2. สมมติ prune ลบ a ออก จึงเหลือ P(C)={b,c,d}
3. ตรวจ inclusion: {b,d}⊆{b,c,d}⊆{a,b,c,d}; ทั้งสองข้างผ่าน แม้ c ยังเป็น candidate ผิด

**ผลที่ได้:** pruner นี้ไม่ทำคำตอบถูกที่มีอยู่หายไป แต่ไม่ได้กำจัด candidate ผิดหมดหรือสร้าง e กลับเข้ามา

**เชื่อมกลับไปที่สมการ:** sound pruning เป็นข้อรับรองเรื่องสิ่งที่ต้องรักษาขณะตัดตัวเลือก ยังต้อง search และ verify คำตอบที่เหลือต่อ

$$
V(u)=\mathrm{accept}\quad\Longrightarrow\quad u\in\Omega
$$

soundness ของ verifier V ต่อ specification Ω; ไม่ได้แปลว่ามันยอมรับหรือค้นพบสมาชิก Ω ครบทุกตัว

**อ่านสมการนี้ว่า:** ทุกครั้งที่ verifier ตอบว่ายอมรับ candidate นั้นต้องอยู่ในเซตคำตอบที่ถูก ส่วนคำตอบถูกบางตัวอาจไม่ได้รับการยอมรับ

**อ่านสัญลักษณ์:**

- **V(u)=accept:** verifier ยอมรับ candidate u
- **⇒:** ทุกกรณีที่ด้านซ้ายเกิด ด้านขวาต้องจริง
- **u∈Ω:** u เป็นสมาชิกของเซตคำตอบที่ตรง specification

**ตัวอย่างทีละขั้น:** ในโดเมน {1,2,3,4} กำหนดคำตอบถูกเป็นเลขคู่ จึงมี Ω={2,4}; verifier ตัวอย่างยอมรับเฉพาะเลข 4

1. ส่ง 4 เข้า V ได้ accept และ 4 อยู่ใน Ω จึงผ่านเงื่อนไขที่สมการต้องการ
2. ส่ง 1 หรือ 3 แล้วถูกปฏิเสธ จึงไม่มีเลขคี่หลุดเข้าไปเป็นคำตอบที่รับรอง
3. ส่ง 2 แล้วก็ถูกปฏิเสธ ทั้งที่ 2 อยู่ใน Ω: verifier นี้พลาดการยอมรับคำตอบถูกหนึ่งตัว

**ผลที่ได้:** verifier นี้ sound ต่อ specification ที่กำหนด แต่ไม่ complete เพราะไม่ได้ยอมรับสมาชิก Ω ครบ

**เชื่อมกลับไปที่สมการ:** ต้องแยกคำถามว่าอะไรที่รับแล้วถูก ออกจากคำถามว่าระบบรับหรือค้นพบคำตอบถูกได้ครอบคลุมเพียงใด

### 4.3 Worked example: Sudoku 4×4

แต่ละช่องมี domain {1,2,3,4} กฎห้ามเลขซ้ำในแถว คอลัมน์ และกล่อง 2×2 สมมติช่องหนึ่งเห็นเลข {1,3} ในแถว, {2} ในคอลัมน์ และ {1,2} ในกล่อง เมื่อตัดเลขที่ห้ามออกจะเหลือ {4} จึงเติม 4 ได้ภายใต้กฎเหล่านี้

ถ้าเหลือ {2,4} การเลือก 2 อาจผ่านการตรวจเฉพาะที่แต่ทำให้ช่องอื่นไม่มีค่าในภายหลัง Local consistency จึงไม่เท่ากับมี global completion ต้อง propagate เพิ่มหรือ search พร้อมย้อนกลับ และตรวจทั้งกระดานเมื่อจะรับเป็นคำตอบ

ห้องทดลองใช้กฎ candidate ที่อ่านย้อนกลับได้ ไม่มี neural solver ซ่อนอยู่ ความเชื่อมโยงกับ neuro-symbolic คือเราสามารถให้ neural score เลือกว่าจะลองช่องหรือเลขใดก่อน โดยยังใช้กฎชุดเดิมจำกัดความผิดและตรวจผลสุดท้าย

$$
\begin{aligned}D_{i,j}={}&\{1,2,3,4\}\\&{}\setminus\bigl(\mathrm{Row}_i\cup\mathrm{Col}_j\cup\mathrm{Box}_{i,j}\bigr)\end{aligned}
$$

D คือเลขที่ยังไม่ชนค่าที่มีอยู่; i,j คือแถวและคอลัมน์ การไม่ชนเฉพาะที่ยังไม่พิสูจน์ว่าต่อเป็นคำตอบเต็มได้

**อ่านสมการนี้ว่า:** เริ่มจากเลขที่ใส่ได้ทั้งหมด รวมเลขที่ใช้ไปแล้วในแถว คอลัมน์ และกล่อง แล้วตัดเลขเหล่านั้นออกจากตัวเลือกของช่องนี้

**อ่านสัญลักษณ์:**

- **D_(i,j):** domain หรือตัวเลือกที่ยังเหลือของช่องแถว i คอลัมน์ j
- **∪:** union: รวมสมาชิกจากหลายเซต โดยไม่นับตัวซ้ำ
- **∖:** set difference: เอาสมาชิกของเซตทางขวาออกจากเซตทางซ้าย
- **Row, Col, Box:** เลขที่มีอยู่แล้วในแถว คอลัมน์ และกล่องของช่องที่กำลังตรวจ

**ตัวอย่างทีละขั้น:** สมมติช่องว่างใน Sudoku 4×4 เห็น Row={1}, Col={3} และ Box={1,3}

1. รวมเลขที่ชนข้อจำกัด: {1}∪{3}∪{1,3}={1,3}
2. เริ่มจาก {1,2,3,4} แล้วตัด 1 และ 3 ออก จึงได้ D={2,4}
3. ทั้ง 2 และ 4 ยังไม่ชนเลขที่เห็น ณ จุดนี้ ต้อง propagate หรือค้นต่อก่อนรู้ว่าเลือกใดต่อเป็นคำตอบเต็มได้

**ผลที่ได้:** domain ของช่องนี้เหลือสองค่า จึงลดงานค้นได้ แต่ยังไม่ได้บังคับว่าคำตอบต้องเป็นค่าใดค่าหนึ่ง

**เชื่อมกลับไปที่สมการ:** การไม่ชนในแถว/คอลัมน์/กล่องเป็นข้อจำกัดเฉพาะที่ ต้องตรวจการต่อทั้งกระดานเพิ่มเติม

$$
\begin{gathered}\{1,2,3,4\}\setminus\bigl(\{1,3\}\cup\{2\}\cup\{1,2\}\bigr)\\=\{4\}\end{gathered}
$$

ตัวอย่างการตัด domain ด้วยข้อจำกัดที่ระบุ ไม่ต้องอาศัย confidence ของโมเดล

**อ่านสมการนี้ว่า:** รวมเลขต้องห้ามสามชุดก่อน แล้วลบชุดที่รวมได้ออกจาก {1,2,3,4}; ในตัวอย่างนี้จึงเหลือเพียงเลข 4

**อ่านสัญลักษณ์:**

- **∪:** รวมเลขที่ปรากฏในแต่ละเงื่อนไข โดยเลขที่ซ้ำกันนับเป็นสมาชิกเดียว
- **∖:** ตัดสมาชิกที่อยู่ในชุดทางขวาออกจากชุดตั้งต้น
- **{4}:** singleton: ชุดที่เหลือสมาชิกเพียงหนึ่งตัว

**ตัวอย่างทีละขั้น:** พิจารณาช่องที่แถวมี {1,3}, คอลัมน์มี {2} และกล่องมี {1,2} ตามสมการนี้

1. รวมแถวกับคอลัมน์ก่อน: {1,3}∪{2}={1,2,3}
2. รวมกล่อง {1,2} ต่อแล้วก็ยังเป็น {1,2,3} เพราะ 1 และ 2 อยู่ในชุดแล้ว
3. ตัดชุดนี้ออกจาก {1,2,3,4}: ลบ 1, 2, 3 จึงเหลือ {4}

**ผลที่ได้:** 4 เป็นค่าเดียวที่ไม่ชนเลขที่กำหนดอยู่รอบช่องนี้ จึงไม่ต้องใช้คะแนน confidence เลือกระหว่างหลายค่า

**เชื่อมกลับไปที่สมการ:** singleton ช่วยบังคับค่าภายใต้ constraints ที่ตรวจ แต่ยังต้องตรวจว่าทั้งกระดานมีคำตอบที่สอดคล้องกัน

### 4.4 วัดการยอมตอบและข้อจำกัดของด่านตรวจ

ถ้า solver รับ 20 ข้อและถูกทั้ง 20 แต่คืน unresolved อีก 80 จากทั้งหมด 100 ข้อ selective accuracy เท่ากับ 100% ขณะที่ coverage เท่ากับ 20% การรายงานตัวเลขแรกอย่างเดียวทำให้ระบบดูครบถ้วนเกินจริง ต้องนับ invalid, timeout และสาเหตุ abstain ด้วย

กฎทางโครงสร้าง เช่น type contract หรือกฎ composition ของ transformation ช่วยตรวจ property เฉพาะ เช่นแปลงสองขั้นรวมกันแล้วต้องเท่ากับองค์ประกอบตามลำดับ แต่กฎหนึ่งไม่แทน specification ทั้งหมด ระบบที่ deterministic จึงยังมี deterministic bug ได้

เมื่อเพิ่ม confidence threshold ให้แยกคะแนนที่โมเดลรายงานออกจากอัตราถูกจริงในกลุ่มคะแนนนั้น การ calibrate ช่วยเทียบสองค่านี้บน distribution ที่ตรวจแล้ว แต่ยังไม่แทน hard precondition ของ action ผลของ verifier ที่ผ่านควรถูกบันทึกพร้อมเงื่อนไขและเวอร์ชันเพื่อใช้ต่อ

$$
\begin{gathered}\operatorname{selective\ accuracy}\\=\frac{N_{\mathrm{correct,answered}}}{N_{\mathrm{answered}}}\end{gathered}
$$

ตัวเศษ = จำนวนข้อที่ตอบถูกในข้อที่ยอมตอบ; ตัวส่วน = จำนวนข้อที่ยอมตอบ

กำหนดเมื่อมีคำตอบอย่างน้อยหนึ่งข้อ; รายงานคู่กับ coverage

**อ่านสมการนี้ว่า:** ดูเฉพาะโจทย์ที่ระบบยอมตอบ แล้วนับว่าคำตอบที่ให้มาถูกกี่ส่วนของกลุ่มนั้น

**อ่านสัญลักษณ์:**

- **ถูกในข้อที่ตอบ:** นับเฉพาะคำตอบที่ผ่านเกณฑ์ความถูกต้อง
- **จำนวนข้อที่ตอบ:** ตัวหารรวมทั้งข้อที่ตอบถูกและตอบผิด แต่ไม่รวม abstain
- **/:** นำจำนวนถูกหารด้วยจำนวนที่ตอบ; คูณ 100 เมื่อต้องการหน่วยเปอร์เซ็นต์

**ตัวอย่างทีละขั้น:** สมมติมี 100 โจทย์ ระบบยอมตอบ 20 ข้อ โดยถูก 18 ข้อและผิด 2 ข้อ; อีก 80 ข้อคืน unresolved

1. ตัวตั้งคือจำนวนถูก 18 ไม่ใช่จำนวนที่ระบบมั่นใจ
2. ตัวหารคือจำนวนที่ตอบจริง 20; ข้อ unresolved 80 ข้อไม่เข้าตัวหารนี้
3. คำนวณ 18/20=0.9 จึงได้ selective accuracy=90%

**ผลที่ได้:** 90% หมายถึงความถูกต้องใน 20 ข้อที่ระบบเลือกตอบ ไม่ใช่สัดส่วนที่ทำถูกจากโจทย์ทั้งหมด

**เชื่อมกลับไปที่สมการ:** รายงานคู่กับ coverage ในสมการถัดไป และถ้าไม่ตอบเลยให้ระบุว่า selective accuracy ยังไม่มีนิยามเพราะตัวหารเป็นศูนย์

$$
\operatorname{coverage}=\frac{N_{\mathrm{answered}}}{N_{\mathrm{all}}}
$$

ตัวเศษ = จำนวนข้อที่ยอมตอบ; ตัวส่วน = จำนวนข้อทั้งหมด

coverage ในที่นี้หมายถึงสัดส่วนที่ solver ยอมตอบ ไม่ใช่ coverage guarantee ของ prediction set ใน conformal prediction

**อ่านสมการนี้ว่า:** นับว่างานที่ส่งเข้ามาทั้งหมดมีสัดส่วนเท่าไรที่ระบบยอมส่งคำตอบกลับ โดยยังไม่ตัดสินว่าคำตอบนั้นถูกหรือผิด

**อ่านสัญลักษณ์:**

- **จำนวนข้อที่ตอบ:** รวมทั้งคำตอบถูกและผิด; ไม่นับ unresolved หรือ abstain
- **จำนวนข้อทั้งหมด:** ทุกโจทย์ที่อยู่ใน workload ที่กำลังประเมิน
- **coverage:** สัดส่วนการยอมตอบในบทนี้ ซึ่งแยกจาก accuracy ของคำตอบ

**ตัวอย่างทีละขั้น:** ใช้ตัวอย่างเดิม: 100 โจทย์ ตอบ 20 ข้อ โดยถูก 18 และผิด 2; unresolved อีก 80 ข้อ

1. นับข้อที่ตอบได้ 18+2=20 ข้อ แม้ 2 ข้อจะตอบผิด
2. หารด้วยโจทย์ทั้งหมด: 20/100=0.20 หรือ coverage=20%
3. อ่านคู่กับสมการก่อน: selective accuracy=90% ที่ coverage=20%; งานอีก 80% ยังไม่มีคำตอบจากระบบ

**ผลที่ได้:** คู่ตัวเลข 90% / 20% แยกคุณภาพของคำตอบที่ส่งกลับออกจากขอบเขตงานที่ระบบรับทำได้

**เชื่อมกลับไปที่สมการ:** การเพิ่ม threshold อาจทำให้ accuracy ในกลุ่มที่ตอบสูงขึ้นแต่ coverage ลดลง จึงต้องดูทั้งสองค่าเสมอ

### นิยามที่ใช้ในบทนี้

- **constraint:** ข้อกำหนดที่จำกัด candidate เช่น domain, grammar หรือ invariant ของ state
- **sound pruning:** การตัด candidate ที่ยังคงเก็บคำตอบถูกทั้งหมดซึ่งอยู่ในเซตตั้งต้น ภายใต้ specification
- **completeness:** การพบคำตอบที่มีอยู่ภายใต้โดเมน วิธีค้น และงบที่สมมติไว้
- **abstention:** การคืนสถานะว่ายังยืนยันคำตอบไม่ได้ แทนการบังคับเลือก candidate

**สังเกต:** แยกการตัด candidate ด้วยกฎเฉพาะที่ ออกจากการยืนยันว่ามีคำตอบครบทั้งกระดานหลังเลือกค่านั้น

### โจทย์

คำว่า memory ครอบคลุมสิ่งที่มีอายุและเงื่อนไขใช้ซ้ำต่างกัน การเก็บได้มากขึ้นอาจเพิ่ม stale information หรือผลลัพธ์ที่ใช้ผิดบริบท

### 5.1 แยก storage ตามสิ่งที่เก็บและอายุของมัน

Weights θ เก็บพารามิเตอร์ที่เรียน ส่วน h_k เป็น activation ของการคำนวณปัจจุบัน KV cache เก็บ key/value ที่คำนวณแล้วของตำแหน่งก่อนหน้า เพื่อไม่ต้องสร้างซ้ำขณะ decode มันผูกกับ model, prefix, position และรูปแบบคำนวณที่เข้ากันได้

External memory M_t เก็บสิ่งที่ระบบเลือกบันทึก เช่นข้อเท็จจริง เหตุการณ์ หรือบทสรุปพร้อมแหล่งที่มา ส่วน policy/result cache เก็บคำตอบของ computation เพื่อใช้ซ้ำเมื่อ key และเงื่อนไขยัง valid ความคล้ายใน latent เพียงอย่างเดียวไม่พอรับรองว่า action เก่าใช้ได้

สำหรับ attention ที่ key/value มี head dimension เท่ากัน KV cache แบบเก็บเต็มมีขนาดแปรตาม batch, layers, sequence length และจำนวน KV heads สูตรด้านล่างนับ payload ของ tensor โดยไม่รวม allocation, metadata และรูปแบบบีบอัดเฉพาะ architecture

$$
\mathrm{KV}_{\mathrm{bytes}}\approx 2\,B\,L\,T\,H_{\mathrm{KV}}\,d_{\mathrm{head}}\,b
$$

B=batch size, L=จำนวน layer, T=ตำแหน่งที่ cache, H_KV=จำนวน KV heads, d_head=มิติต่อ head, b=ไบต์ต่อค่า; 2 มาจาก K และ V

**อ่านสมการนี้ว่า:** นับค่าที่ต้องเก็บใน key cache ของทุก batch, layer, token และ head แล้วเผื่อ value cache อีกชุด พร้อมคูณจำนวนไบต์ต่อค่า

**อ่านสัญลักษณ์:**

- **2:** มีทั้ง key และ value ซึ่งในสูตรนี้ใช้ shape และชนิดข้อมูลที่มีขนาดเท่ากัน
- **B·L·T:** จำนวน batch คูณ layer คูณตำแหน่ง token ที่เก็บ
- **H_KV·d_head:** จำนวน KV heads คูณค่าต่อ head; อาจต่างจากจำนวน query heads
- **b:** จำนวนไบต์ต่อค่า เช่น float16 ใช้ 2 ไบต์

**ตัวอย่างทีละขั้น:** ใช้โมเดลสมมติขนาดเล็ก: B=1, L=2, T=4, H_KV=2, d_head=4 และ b=2 ไบต์

1. นับ key อย่างเดียวได้ 1×2×4×2×4=64 ค่า
2. แต่ละค่าใช้ 2 ไบต์ จึงได้ key cache ขนาด 128 ไบต์; value อีกชุดใช้ 128 ไบต์เท่ากัน
3. รวมสองชุดได้ 256 ไบต์; ถ้าเก็บ token เพิ่มจาก 4 เป็น 8 โดยค่าอื่นคงเดิม ขนาด payload จะเพิ่มเป็น 512 ไบต์

**ผลที่ได้:** ตัวคูณ 2 คือสอง tensor K/V; การเพิ่มความยาว prefix สองเท่าทำให้ payload เพิ่มสองเท่าในรูปแบบนี้

**เชื่อมกลับไปที่สมการ:** สูตรนับเฉพาะ tensor payload ของ full KV cache ต้องรวม metadata, allocation และรูปแบบ compression แยกเมื่อต้องการตัวเลขหน่วยความจำจริง

$$
\begin{aligned}\mathrm{cache\ key}=(&\mathrm{input\ identity},\\&\mathrm{model\ version},\\&\mathrm{rule\ version},\\&\mathrm{world\ version})\end{aligned}
$$

ตัวอย่างส่วนประกอบของ result-cache key; งานจริงต้องเลือก validity boundary ให้ตรงสิ่งที่ผลลัพธ์ขึ้นกับมัน

**อ่านสมการนี้ว่า:** สร้างตัวระบุ cache จาก input พร้อมเวอร์ชันของสิ่งที่ผลลัพธ์ขึ้นกับมัน แล้วใช้ชุดตัวระบุทั้งหมดตรวจว่าผลเก่ายังตรงบริบทหรือไม่

**อ่านสัญลักษณ์:**

- **(...):** tuple: ชุดข้อมูลที่ต้องอ่านร่วมกัน ไม่ใช่การนำค่ามาบวก
- **input_identity:** ตัวระบุ input ที่ต้องแยกได้ตามขอบเขตของงาน
- **model_version, rule_version:** เวอร์ชันโมเดลและกฎที่ใช้สร้างผล
- **world_version:** เวอร์ชันสถานะโลกที่ผลลัพธ์อาศัยอยู่

**ตัวอย่างทีละขั้น:** สมมติ cache เก็บเส้นทางจาก A ไป B โดย key คือ (route:A→B, model:m3, rule:r2, world:v10)

1. เมื่อคำนวณได้เส้นทาง A→D→B ให้เก็บผลคู่กับ key ทั้งสี่ส่วนนี้
2. คำขอเดิมใน world:v10 ใช้ key เดิม จึงค้นพบผลเก่าเพื่อนำไปใช้ภายใต้ validity boundary ที่กำหนด
3. ถ้าประตูที่ D ปิดและโลกเปลี่ยนเป็น v11, key ใหม่ต่างจากเดิม แม้ input ยังเป็น A→B; ต้องหาผลสำหรับ v11 หรือตรวจ/คำนวณใหม่

**ผลที่ได้:** ผลที่ถูกสำหรับ world:v10 ไม่ถูกนำกลับมาใช้โดยอาศัยเพียงชื่อ input ที่เหมือนเดิม

**เชื่อมกลับไปที่สมการ:** เลือกองค์ประกอบ key จาก dependency ของผลลัพธ์จริง และเปลี่ยนเวอร์ชันเมื่อ dependency ที่มีผลต่อความถูกต้องเปลี่ยน

### 5.2 Priority ไม่ใช่ความจริง: แยกสามคะแนน

Priority บอกว่าควรหยิบข้อมูลมาพิจารณามากเพียงใด, confidence บอกระดับความเชื่อในข้อมูล และ freshness บอกอายุเมื่อเทียบกับอัตราที่โลกเปลี่ยน เหตุการณ์อันตรายที่ยังเป็นข่าวลืออาจมี priority สูงแต่ confidence ต่ำ

Lab ใช้ weighted average ของสามค่านี้ และให้ freshness ลดเชิงเส้นจนเป็นศูนย์ที่อายุ 14 วัน ข้อมูลข่าวลือมี priority 0.95 และ confidence 0.32 การเพิ่มน้ำหนัก priority อาจเลื่อนมันขึ้นอันดับโดยไม่ได้เพิ่มหลักฐานจริงแม้แต่น้อย

คะแนน ranking ใช้จัดลำดับสิ่งที่จะอ่านหรือตรวจต่อได้ แต่ hard invalidation ควรแยกจากคะแนน เช่น fact หมดอายุตามเงื่อนไขโลกต้องไม่กลับมาใช้ได้เพียงเพราะ priority สูง Lab แสดงสถานะเตือนประกอบ และไม่ได้ calibrate confidence จากผลทดลอง

$$
\operatorname{score}_i=\frac{w_P P_i+w_C C_i+w_F F_i}{w_P+w_C+w_F}
$$

P,C,F อยู่ใน [0,1]; น้ำหนักไม่ติดลบและผลรวมมากกว่า 0; เป็น scoring rule สาธิต ไม่ใช่ posterior probability

**อ่านสมการนี้ว่า:** คูณแต่ละคะแนนด้วยน้ำหนักของมัน รวมผลทั้งหมด แล้วหารด้วยน้ำหนักรวม เพื่อได้คะแนนเฉลี่ยสำหรับจัดอันดับ record

**อ่านสัญลักษณ์:**

- **P_i, C_i, F_i:** priority, confidence และ freshness ของ record i โดยแต่ละค่าอยู่ระหว่าง 0 ถึง 1
- **w_P, w_C, w_F:** น้ำหนักที่กำหนดว่าให้แต่ละมิติมีผลต่ออันดับมากเพียงใด
- **w_P+w_C+w_F:** ตัวหารสำหรับ normalize; ต้องมากกว่า 0 และใช้น้ำหนักไม่ติดลบ

**ตัวอย่างทีละขั้น:** สมมติ record มี P=0.9, C=0.4, F=0.8 และใช้น้ำหนัก (w_P,w_C,w_F)=(2,1,1)

1. คูณและรวมได้ 2×0.9+1×0.4+1×0.8=1.8+0.4+0.8=3.0
2. น้ำหนักรวมคือ 2+1+1=4 จึงได้ score=3.0/4=0.75
3. ถ้าเพิ่ม w_P เป็น 6 โดยข้อมูลเดิมไม่เปลี่ยน จะได้ (5.4+0.4+0.8)/8=0.825

**ผลที่ได้:** คะแนนอันดับเพิ่มจาก 0.75 เป็น 0.825 ทั้งที่ confidence ยังเป็น 0.4 และไม่ได้มีหลักฐานใหม่เพิ่ม

**เชื่อมกลับไปที่สมการ:** weighted score ใช้เลือกว่าอ่านหรือตรวจอะไรต่อ จึงไม่ควรตีความ 0.825 ว่าข้อมูลจริงด้วยความน่าจะเป็น 82.5%

$$
F_i=\max\!\left(0,\,1-\frac{\mathrm{age}_i}{14}\right)
$$

age_i ใช้หน่วยวันใน lab; ช่วง 14 วันเป็นสมมติฐานสังเคราะห์ ไม่ใช่อายุที่เหมาะกับทุกโดเมน

**อ่านสมการนี้ว่า:** ลด freshness เป็นเส้นตรงตามอายุเทียบกับช่วง 14 วัน แล้วบังคับไม่ให้คะแนนต่ำกว่าศูนย์

**อ่านสัญลักษณ์:**

- **age_i/14:** อายุเป็นวันหารด้วย 14 เพื่อบอกว่าใช้ช่วงอายุสมมติไปแล้วกี่ส่วน
- **1−age_i/14:** ความสดที่เหลือก่อนจำกัดค่าต่ำสุด
- **max(0, …):** เลือกค่าที่มากกว่าระหว่าง 0 กับผลที่คำนวณ จึงตัดค่าติดลบให้เป็น 0

**ตัวอย่างทีละขั้น:** ใช้กฎสาธิตใน lab ที่ถือว่า freshness เริ่มที่ 1 และหมดเมื่อครบ 14 วัน โดยยังไม่ใช่นโยบายจริงของทุกข้อมูล

1. อายุ 7 วัน: 1−7/14=0.5; max(0,0.5)=0.5
2. อายุ 14 วัน: 1−14/14=0; freshness จึงเป็น 0
3. อายุ 21 วัน: 1−21/14=−0.5 แต่ max(0,−0.5)=0 จึงไม่ติดลบ

**ผลที่ได้:** อายุ 7, 14 และ 21 วันให้ F เท่ากับ 0.5, 0 และ 0 ตามลำดับ

**เชื่อมกลับไปที่สมการ:** คะแนน freshness เป็นสมมติฐานเรื่องความสดที่ใช้จัดอันดับ ส่วนเงื่อนไขว่าข้อมูลหมดอายุจนห้ามใช้ต้องกำหนดแยกตามโดเมน

### 5.3 Versioning ทำให้ replay และ invalidation มีความหมาย

บันทึก fact พร้อม source, observed_at, scope และ validity condition ตัวอย่าง path cache ที่เคยผ่านประตูได้ควรผูกกับเวอร์ชันของแผนที่หรือสถานะประตู เมื่อประตูปิด action เก่าต้องถูก invalidate หรือตรวจ precondition อีกครั้งก่อนใช้

Event sourcing เก็บเหตุการณ์เพื่อสร้าง state ย้อนกลับด้วย transition function หากต้องการ replay ตรงกัน ต้องมีลำดับ event, version ของกฎ และข้อมูล nondeterminism เช่น random seed หรือผล external call ที่เกี่ยวข้อง Snapshot เพียงอย่างเดียวไม่บอกเหตุทั้งหมดระหว่างสองเวลา

การเก็บ hash หรือ proof structure อาจช่วยตรวจความสอดคล้องหรือการเปลี่ยน log ภายใต้ trust model ที่เลือก แต่ไม่รับรองว่า observation ตั้งต้นตรงโลกจริง คำว่า historical proof จึงต้องมีข้อความกำกับว่าพิสูจน์ property ใดจากหลักฐานอะไร

$$
s_{t+1}=F_v(s_t,e_t)
$$

e_t คือ event ที่บันทึก และ v คือ version ของ transition rule; replay ต้องมี input ที่ F_v ใช้ครบ

**อ่านสมการนี้ว่า:** นำ state ปัจจุบันกับ event ที่เกิดขึ้นเข้า transition rule เวอร์ชันที่กำหนด เพื่อสร้าง state ถัดไป; replay ก็ทำขั้นนี้ซ้ำตามลำดับเดิม

**อ่านสัญลักษณ์:**

- **s_t, s_(t+1):** state ก่อนและหลังนำ event หนึ่งรายการมาใช้
- **e_t:** event ที่เกิดในขั้นนี้ พร้อมข้อมูลที่ transition ต้องใช้
- **F_v:** ฟังก์ชันเปลี่ยน state ตาม rule เวอร์ชัน v

**ตัวอย่างทีละขั้น:** สมมติมีโควตา 10 units และ log สอง event ตามลำดับคือ use(3), use(2); กฎ v1 หักตามจำนวนที่ใช้

1. เริ่มจาก s₀=10 แล้วใช้ F_v1 กับ use(3) ได้ s₁=10−3=7
2. นำ state 7 เข้า event ถัดไป use(2) ได้ s₂=7−2=5; replay log เดิมด้วย v1 จึงได้ 5 อีกครั้ง
3. ถ้าเผลอ replay ด้วย v2 ที่คิด overhead เพิ่ม 1 unit ต่อ event จะได้ 10−4=6 แล้ว 6−3=3

**ผลที่ได้:** log เดียวกันให้ state สุดท้าย 5 หรือ 3 ได้เมื่อกฎต่างเวอร์ชัน จึงต้องเก็บว่าระบบใช้เวอร์ชันใด

**เชื่อมกลับไปที่สมการ:** การ replay ให้ตรงต้องมี event ครบตามลำดับ กฎที่ตรงเวอร์ชัน และข้อมูล nondeterminism ที่ transition ใช้ด้วย

### 5.4 แยกสาเหตุเมื่อบอกว่า self-improvement

ผลดีขึ้นอาจมาจาก θ เปลี่ยน, prompt/context ดีขึ้น, cache hit มากขึ้น, corpus เพิ่ม หรือ evaluator เปลี่ยน ต้อง log version ของแต่ละส่วนและเทียบกับชุดอ้างอิงที่ตรึงไว้ มิฉะนั้นคะแนนที่สูงขึ้นไม่บอกว่า capability ส่วนใดดีขึ้น

แนวคิด represented → accessible → stable ช่วยตั้งคำถามว่าข้อมูลมีอยู่ใน model หรือถูก route มาใช้ได้หรือยัง แต่ infographic เรื่อง trajectory/context routing เป็นสมมติฐานหรือกรอบอธิบายของเจ้าของงาน จะอ้างว่าเป็นกลไกภายในจริงต้องมี measurement เพิ่ม

เมื่อ memory ขยายจนใส่ context ทั้งหมดไม่ได้ ระบบต้องเลือกว่าจะหยิบ record ใดมาใช้และใครมีสิทธิ์เห็น นั่นพาไปสู่ retrieval: ขั้นคัดข้อมูลก่อน inference ซึ่งจะใช้ทั้ง representation จากบทแรกและ validity boundary ที่เพิ่งกำหนด

$$
\begin{aligned}\mathrm{measured\ gain}\\={}&\operatorname{score}(\mathrm{agent}_{\mathrm{new}},\mathrm{evaluator}_{\mathrm{fixed}})\\&{}-\operatorname{score}(\mathrm{agent}_{\mathrm{old}},\mathrm{evaluator}_{\mathrm{fixed}})\end{aligned}
$$

เทียบด้วย workload และเงื่อนไขเดียวกัน พร้อมตรึง evaluator; ยังต้องแยกการเปลี่ยน θ, context, cache และ corpus เพื่อระบุสาเหตุของ gain

**อ่านสมการนี้ว่า:** ให้ evaluator ชุดเดิมวัด agent เก่าและใหม่ภายใต้เงื่อนไขเดียวกัน แล้วลบคะแนนเก่าออกจากคะแนนใหม่เพื่อบอกขนาดผลที่สังเกตได้

**อ่านสัญลักษณ์:**

- **score(agent, evaluator_fixed):** คะแนนจากเกณฑ์ประเมินที่ตรึงไว้ ไม่เปลี่ยนตาม agent
- **agent_new, agent_old:** ระบบสองเวอร์ชันที่นำมาเทียบ ซึ่งอาจต่างที่ weight, context, cache หรือ corpus
- **measured_gain:** ผลต่างที่วัดบน workload นี้ ยังต้องระบุว่าส่วนใดของระบบเปลี่ยน

**ตัวอย่างทีละขั้น:** สมมติใช้โจทย์เดิม 100 ข้อ งบคำนวณและ evaluator เดียวกัน โดยรายงาน accuracy ในช่วง 0–1

1. agent เก่าถูก 60 ข้อ ได้ score=0.60; agent ใหม่ถูก 70 ข้อ ได้ score=0.70
2. ผลต่างคือ 0.70−0.60=0.10 หรือเพิ่ม 10 จุดเปอร์เซ็นต์ (จาก 60% เป็น 70%) บนชุดนี้
3. ถ้าในการเทียบนี้เปลี่ยนเฉพาะ corpus และตรึง θ ไว้ gain ที่เห็นควรอธิบายร่วมกับข้อมูลที่ค้นได้เพิ่ม ไม่ใช่อ้างว่า weight ได้เรียนรู้ใหม่

**ผลที่ได้:** ตัวเลขบอกว่าระบบใหม่ทำคะแนนสูงขึ้นเท่าไรบนเงื่อนไขที่ตรึง แต่ชื่อกลไกที่ดีขึ้นต้องมาจากสิ่งที่เปลี่ยนในการทดลอง

**เชื่อมกลับไปที่สมการ:** บันทึกเวอร์ชันของแต่ละส่วนและเปลี่ยนปัจจัยอย่างมีการควบคุม เพื่อเชื่อม gain กับสาเหตุได้ชัดเจน

### นิยามที่ใช้ในบทนี้

- **KV cache:** key/value activations ที่ใช้ซ้ำกับ prefix และ model ที่เข้ากันได้ระหว่าง decoding
- **external memory:** ข้อมูลที่ระบบบันทึกภายนอก weights พร้อมบริบทสำหรับใช้งานภายหลัง
- **cache invalidation:** การเลิกใช้ผลเก่าเมื่อข้อสมมติหรือ version ที่ผลนั้นพึ่งพาเปลี่ยน
- **event sourcing:** การสร้าง state จากลำดับเหตุการณ์โดยใช้ transition rule ที่กำหนด

### ทดลองกลไก

**ลองทำ:** เลื่อนน้ำหนัก priority, confidence และ freshness ให้เป็น 0.5 เท่ากันก่อน แล้วเพิ่ม priority และกดผ่านไป 1 วันเพื่อเพิ่มอายุข้อมูล

**สังเกต:** ดูว่าอันดับของข่าวลือกับแผนที่เก่าเปลี่ยนอย่างไร และแยกคะแนนสูงออกจากสถานะที่ควรตรวจเพิ่ม

**ขอบเขตของแบบจำลอง:** lab คำนวณ scoring rule ที่กำหนดด้วยมือ การเลื่อนขึ้นอันดับไม่ได้เพิ่มความถูกต้อง และไม่มี weight learning หรือ probabilistic calibration เกิดขึ้น

### โจทย์

เอกสารใกล้ query อาจผิดบริบท ล้าสมัย หรือเป็นข้อมูลของผู้ใช้อื่น การค้นหาและการตรวจหลักฐานต้องมีหน้าที่แยกกันใน pipeline

### 6.1 Retrieval เป็น selection operator ก่อน generation

ให้ encoder φ เปลี่ยน query q และ document d เป็นเวกเตอร์ใน ℝ^m การใช้ cosine similarity จัดอันดับวัดความใกล้ตาม embedding model ส่วน RAG นำผลที่เลือกได้มาเป็น context ให้ generator จึงมีอย่างน้อยสองจุดที่พลาด: retrieval ไม่พบหลักฐาน หรือ generator ใช้หลักฐานผิด

เอกสารที่กล่าวถึงอาการเดียวกันอาจให้สาเหตุต่างกัน จึงต้องตรวจ applicability เช่น version ของระบบ, environment และเงื่อนไขในเนื้อหา คะแนน similarity ไม่ใช่ entailment ว่าเอกสารยืนยันคำตอบ และการมี citation ก็ยังต้องอ่านว่าข้อความที่ cite รองรับ claim นั้นจริง

กำหนดจำนวนผล K_ret และ context budget ตามข้อมูลที่จำเป็น พร้อมเก็บ provenance ของแต่ละ chunk เช่น document id, revision และตำแหน่งข้อความ เพื่อให้ตอบย้อนกลับได้ว่า inference ใช้หลักฐานเวอร์ชันใด

$$
\operatorname{sim}(q,d)=\frac{\varphi(q)^{\top}\varphi(d)}{\lVert\varphi(q)\rVert\,\lVert\varphi(d)\rVert}
$$

cosine similarity สำหรับเวกเตอร์ที่ norm ไม่เป็นศูนย์; m คือ embedding dimension

**อ่านสมการนี้ว่า:** นำ embedding ของคำถามกับเอกสารมาคูณกันทีละตำแหน่งแล้วบวก จากนั้นหารด้วยความยาวของเวกเตอร์ทั้งสอง เพื่อเทียบว่าชี้ไปทิศเดียวกันแค่ไหนโดยลดผลจากขนาดเวกเตอร์

**อ่านสัญลักษณ์:**

- **φ(q)⊤φ(d):** dot product: คูณค่าที่ตำแหน่งตรงกันแล้วรวม
- **∥v∥:** ความยาวเวกเตอร์ เช่น ∥(3,4)∥ = √(3²+4²) = 5
- **sim:** คะแนนไม่มีหน่วย อยู่ระหว่าง −1 ถึง 1 สำหรับเวกเตอร์ที่ไม่เป็นศูนย์

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: embedding ของ query คือ (1,0) และของเอกสารคือ (3,4)

1. คำนวณตัวเศษ: (1×3)+(0×4) = 3
2. คำนวณความยาว: query ยาว 1 และ document ยาว 5 จึงได้ตัวหาร 1×5 = 5
3. หารได้ 3/5 = 0.6; ถ้าขยาย document เป็น (6,8) จะได้ 6/10 = 0.6 เท่าเดิม

**ผลที่ได้:** คะแนน 0.6 บอกความใกล้ด้านทิศของ embedding ไม่ได้แปลว่าเอกสารถูกต้อง 60% หรือรองรับคำตอบแน่นอน

**เชื่อมกลับไปที่สมการ:** อ่าน cosine เป็นการเทียบทิศของเวกเตอร์ ส่วนการตัดสินว่าข้อความใช้ตอบได้จริงยังต้องตรวจเนื้อหาและบริบท

$$
\begin{aligned}D_q=\operatorname{TopK}_{\mathrm{ret}}\Bigl\{\\\operatorname{sim}(q,d):d\in D_{\mathrm{allowed}}(u)\Bigr\}\end{aligned}
$$

D_allowed(u) คือเอกสารที่ผู้ใช้ u มีสิทธิ์ใช้; K_ret แยกจาก K ที่นับ recurrent passes ในบทก่อน

**อ่านสมการนี้ว่า:** เริ่มจากเอกสารที่ผู้ใช้มีสิทธิ์อ่าน คำนวณความใกล้กับ query แล้วเลือกเอกสาร K_ret ชิ้นที่ได้คะแนนสูงสุด โดยเก็บทั้งตัวเอกสารและคะแนนไว้คู่กัน

**อ่านสัญลักษณ์:**

- **d∈D_allowed(u):** พิจารณาเฉพาะเอกสาร d ในชุดที่ผู้ใช้ u ใช้ได้
- **TopK_ret:** ตัวดำเนินการเลือก K_ret อันดับสูงสุดจากรายการ document–score
- **D_q:** ชุดเอกสารที่เลือกได้ ไม่ใช่ชุดตัวเลขคะแนนล้วน

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: K_ret=2; ผู้ใช้มีสิทธิ์อ่าน A:0.91, B:0.73, C:0.82 แต่ไม่มีสิทธิ์อ่าน X:0.99

1. สร้างชุดที่มีสิทธิ์ก่อน จึงเหลือคู่ (A,0.91), (B,0.73), (C,0.82)
2. เรียงตามคะแนนได้ A, C, B แล้วเลือกสองอันดับแรก

**ผลที่ได้:** D_q = {A,C} พร้อมคะแนน 0.91 และ 0.82; X ไม่เข้าร่วมการเลือก แม้ได้คะแนนสูงสุด

**เชื่อมกลับไปที่สมการ:** สูตรย่อแสดงคะแนนเพื่อจัดอันดับ แต่ context ที่ส่งให้ generator คือเนื้อหาจากเอกสารที่ผ่านสิทธิ์และถูกเลือกแล้ว

### 6.2 Authorization ต้องเกิดก่อนข้อมูลเข้า context

ACL หรือ access-control list กำหนดว่า principal ใดอ่าน record ใดได้ ส่วน tenant boundary แยกขอบเขตข้อมูลของลูกค้าหรือองค์กร ตรวจสิทธิ์ในชั้นระบบที่เชื่อถือได้ก่อนส่ง record, snippet หรือ metadata ที่ละเอียดอ่อนให้ reranker, generator หรือผู้ใช้

การค้น top-K ทั้งคลังแล้วค่อยกรองต่างจากค้นใน authorized set: ถ้าสองอันดับแรกเป็นข้อมูลต้องห้ามและ K=3 วิธีแรกอาจเหลือผลใช้ได้เพียงหนึ่งชิ้น แม้ยังมีเอกสารที่ใช้ได้อีกหลายชิ้น และต้องไม่ปล่อยข้อมูลที่กรองทิ้งไหลเข้า log หรือ model ระหว่างทาง

Lab ใช้ระยะ Euclidean ในภาพ 2 มิติ ที่ query (0.78,0.25) อยู่ใกล้เอกสาร tenant B จุด (0.82,0.24) เพียงประมาณ 0.041 หน่วย แต่ผู้ใช้ tenant A ไม่มีสิทธิ์ ระยะที่น้อยลงจึงไม่มีผลเปลี่ยน authorization

$$
\begin{gathered}\operatorname{Filter}_{\mathrm{allowed}}\!\left(\operatorname{TopK}_{\mathrm{ret}}(D)\right)\\\ne\\\operatorname{TopK}_{\mathrm{ret}}\!\left(\operatorname{Filter}_{\mathrm{allowed}}(D)\right)\end{gathered}
$$

โดยทั่วไป

การกรองหลังตัด top-K อาจสูญเสียผลที่ได้รับอนุญาต; ทั้งสองทางต้องป้องกันข้อมูลข้ามขอบเขตก่อนเปิดเผย

**อ่านสมการนี้ว่า:** ลำดับการทำสองขั้นตอนมีผล: เลือกอันดับต้นก่อนแล้วกรองสิทธิ์ อาจได้ผลน้อยกว่าการกรองสิทธิ์ก่อนแล้วเลือกอันดับต้นจากชุดที่เหลือ

**อ่านสัญลักษณ์:**

- **Filter_allowed:** ตัดเอกสารที่ผู้ใช้ไม่มีสิทธิ์ออก
- **TopK_ret:** ตัดรายการให้เหลือ K_ret อันดับ โดยปกติไม่เติมชิ้นถัดไปเองหลังถูกกรอง
- **≠ โดยทั่วไป:** มีกรณีที่ผลต่างกัน ไม่ได้หมายความว่าต้องต่างทุกกรณี

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: K_ret=2 และลำดับคะแนนคือ X:0.99, A:0.95, B:0.90; X ถูกห้าม ส่วน A และ B อ่านได้

1. เลือกก่อน: Top2 ได้ {X,A}; เมื่อกรองสิทธิ์แล้วเหลือ {A}
2. กรองก่อน: ชุดที่ใช้ได้คือ {A,B}; จากนั้น Top2 ได้ {A,B}

**ผลที่ได้:** วิธีแรกได้เอกสาร 1 ชิ้น วิธีที่สองได้ 2 ชิ้น ทั้งที่มีเอกสารอ่านได้เพียงพอ

**เชื่อมกลับไปที่สมการ:** ต้องออกแบบ retrieval ให้เติมผลจาก authorized set และป้องกันข้อมูลต้องห้ามก่อนเข้าถึง reranker, context หรือ log ที่เปิดเผยได้

$$
\begin{gathered}\operatorname{distance}=\\\sqrt{(0.82-0.78)^2+(0.24-0.25)^2}\\\approx 0.041\end{gathered}
$$

ตัวอย่างจากพิกัดสังเคราะห์ใน lab; ใช้แสดงความเป็นอิสระระหว่างความใกล้กับสิทธิ์เข้าถึง

**อ่านสมการนี้ว่า:** หาระยะตรงระหว่างสองจุด โดยหาความต่างแต่ละแกน ยกกำลังสองแล้วบวก ก่อนถอดรากที่สองกลับเป็นหน่วยระยะเดิม

**อ่านสัญลักษณ์:**

- **²:** ยกกำลังสอง ทำให้ส่วนต่างติดลบกลายเป็นค่าบวกก่อนรวม
- **√:** รากที่สอง เปลี่ยนผลรวมของระยะกำลังสองกลับเป็นระยะ
- **≈:** ค่าโดยประมาณหลังปัดเศษ ไม่ใช่ค่าเท่ากันพอดี

**ตัวอย่างทีละขั้น:** พิกัดสังเคราะห์จาก lab: query=(0.78,0.25) และเอกสาร tenant B=(0.82,0.24)

1. ส่วนต่างแกน x คือ 0.04 และแกน y คือ −0.01
2. ยกกำลังสองและรวม: 0.04²+(−0.01)² = 0.0016+0.0001 = 0.0017
3. ถอดราก: √0.0017 ≈ 0.04123 จึงแสดงเป็น 0.041 หน่วยพิกัด

**ผลที่ได้:** จุดอยู่ใกล้กันในภาพ แต่ระยะนี้ไม่ใช่ความน่าจะเป็น และไม่ได้บอกว่าผู้ใช้มีสิทธิ์อ่านเอกสาร

**เชื่อมกลับไปที่สมการ:** คะแนนหรือระยะตอบว่าเกี่ยวข้องแค่ไหน ส่วน ACL ตอบว่าใช้ได้หรือไม่ เป็นเงื่อนไขคนละตัว

### 6.3 Embedding ไม่ใช่การลบความหมายที่เป็นส่วนตัว

Embedding ถูกสร้างให้รักษาสัญญาณเชิงความหมายเพื่อค้นคืน จึงไม่ควรสมมติว่าแปลงข้อความเป็น vector แล้วข้อมูลนั้นกลายเป็น anonymous งาน embedding inversion ศึกษาว่าผู้โจมตีที่เข้าถึง vector และข้อมูลประกอบสามารถอนุมานหรือกู้เนื้อหาบางส่วนได้ภายใต้เงื่อนไขใด

ระดับการกู้คืนขึ้นกับ encoder, ข้อมูลฝึก, access และวิธีโจมตี ไม่ใช่คำรับรองว่าทุก vector ถูกย้อนเป็นต้นฉบับได้พอดี แต่การ normalize vector หรือไม่เก็บข้อความไว้ในตารางเดียวกันก็ไม่ได้เป็นหลักฐานว่าความเสี่ยงหายไป

ขอบเขตควบคุมจึงรวมทั้ง raw text, embeddings, index, cached retrieval results และ telemetry กำหนด scope ให้แต่ละรายการตามข้อมูลต้นทาง และอย่าใช้ semantic similarity เป็นเหตุผลข้าม permission boundary ที่ตั้งไว้

$$
\operatorname{access}(\mathrm{vector})
$$

และ

$$
\operatorname{access}(\mathrm{source\ text})
$$

ต้องมีนโยบายที่สัมพันธ์กัน

embedding เป็น derived data ที่ยังเก็บสัญญาณของต้นทาง; ACL ของ output อย่างเดียวไม่ป้องกันผู้ที่อ่าน index ได้อยู่แล้ว

**อ่านสมการนี้ว่า:** อ่านข้อความนี้เป็นข้อกำหนดเชิงนโยบาย: เมื่อ vector เก็บข้อมูลที่สืบเนื่องจากข้อความต้นทาง สิทธิ์เข้าถึง vector ต้องพิจารณาขอบเขตความลับของต้นทางด้วย ไม่ใช่การคำนวณตัวเลข

**อ่านสัญลักษณ์:**

- **access(vector):** สิทธิ์อ่านหรือใช้ embedding รวมถึง index และผลที่ cache ไว้
- **access(source text):** สิทธิ์เข้าถึงข้อความต้นทางที่ใช้สร้าง embedding

**ตัวอย่างทีละขั้น:** สถานการณ์สมมติ: เอกสาร D เป็นข้อมูลภายใน tenant A และถูกแปลงเป็น embedding v_D

1. ผู้ใช้ tenant B ขออ่าน D แล้วถูกปฏิเสธตามนโยบายของต้นทาง
2. ตรวจเส้นทาง index, vector export และ cached retrieval ด้วยว่าผู้ใช้ B อ่าน v_D หรือข้อมูลที่เปิดเผยเนื้อหาของ D ได้หรือไม่
3. กำหนดสิทธิ์ของ derived data ให้สอดคล้องกับข้อจำกัดนั้น และตรวจใหม่เมื่อสิทธิ์ต้นทางเปลี่ยน

**ผลที่ได้:** การซ่อนข้อความในหน้าจอเพียงจุดเดียวไม่เพียงพอ หากยังเปิดทางให้อ่านข้อมูลที่ได้จากข้อความนั้น

**เชื่อมกลับไปที่สมการ:** นโยบายอาจต่างรายละเอียดตามระบบ แต่การแปลงเป็น embedding ไม่ใช่หลักฐานว่าข้อมูลถูกทำให้ไม่ระบุตัวตนแล้ว

### 6.4 กรณี code healing: จาก retrieved rule ไปสู่ patch

ระบบ code healer รับ diagnostic → เลือก rule/corpus ที่เกี่ยวข้อง → เสนอ patch → ตรวจ syntax/type/behavior ที่กำหนด → บันทึกผลและ miss case การเพิ่ม rule หลังพบข้อผิดพลาดทำให้ corpus coverage ดีขึ้นได้โดยไม่เปลี่ยน θ

ตัวอย่าง pattern ที่ดูคล้ายกันคือการแทน exception หรือ error ด้วย default value Patch อาจ compile ผ่าน แต่เปลี่ยนสัญญาจากต้องรายงานความผิดพลาดเป็นเงียบแล้วใช้ค่าทดแทน จึงต้องอ่าน semantics ของ caller และเงื่อนไขใน rule ก่อนใช้ ไม่เลือกจากข้อความ error คล้ายกันอย่างเดียว

ให้ log rule_version, corpus_version, validator_version และ input revision; การผ่าน validator รับรองเฉพาะ property ที่ตรวจ การให้หลาย agent แชร์ rule และข้อมูลชุดนี้ยังเพิ่มคำถามว่าแต่ละตัวเห็นอะไรและการแก้ของตัวหนึ่งกระทบอีกตัวอย่างไร ซึ่งเป็นบทต่อไป

retrieved_rule + applicability_check + semantic_validation → candidate patch ที่ประเมินได้

retrieval ส่งหลักฐานและตัวเลือกให้ pipeline; ไม่ได้ทำให้ patch ถูกโดยอัตโนมัติ

**อ่านสมการนี้ว่า:** เครื่องหมาย + ในที่นี้หมายถึงขั้นตอนที่ต้องประกอบกัน: ได้ rule มาแล้ว ตรวจว่าใช้กับสถานการณ์นี้ได้ จากนั้นตรวจผลเชิงพฤติกรรม จึงได้ patch ที่มีหลักฐานให้ประเมิน

**อ่านสัญลักษณ์:**

- **+:** การประกอบขั้นตอน ไม่ใช่การบวกจำนวน
- **→:** ผลส่งต่อไปยังขั้นถัดไป ไม่ใช่คำรับรองว่าผลถูกเสมอ
- **semantic_validation:** ตรวจพฤติกรรมตามสัญญาของโปรแกรม ไม่หยุดเพียง compile ผ่าน

**ตัวอย่างทีละขั้น:** สถานการณ์สมมติ: retrieval เสนอ rule ให้แทน exception ด้วยค่า 0 เมื่ออ่านจำนวนสินค้าไม่สำเร็จ

1. ตรวจ applicability: caller แยก “สินค้าเป็นศูนย์” ออกจาก “อ่านข้อมูลไม่ได้” หรือไม่
2. ลองกรณีอ่านข้อมูลล้มเหลว: ถ้า patch ส่งค่า 0 จะทำให้ระบบรายงานว่าสินค้าหมดแทนการแจ้ง error
3. ปฏิเสธ rule นี้สำหรับ caller ดังกล่าว หรือเสนอ patch ที่ยังรักษาการรายงาน error แล้วตรวจใหม่

**ผลที่ได้:** แม้ patch เดิม compile ผ่าน ก็ไม่ผ่านสัญญาด้านพฤติกรรมของตัวอย่างนี้

**เชื่อมกลับไปที่สมการ:** Retrieval ช่วยหา candidate ส่วนความถูกต้องของ patch ต้องอาศัยเงื่อนไขและตัวตรวจที่ตรงกับงาน

### นิยามที่ใช้ในบทนี้

- **RAG:** การดึงข้อมูลภายนอกมาเป็น context ก่อนให้โมเดลสร้างคำตอบ
- **provenance:** ข้อมูลที่ใช้ติดตามว่าหลักฐานมาจากแหล่ง ตำแหน่ง และเวอร์ชันใด
- **ACL / tenant boundary:** กฎสิทธิ์อ่านข้อมูลและขอบเขตแยกข้อมูลของผู้ใช้หรือองค์กร
- **embedding inversion:** การอนุมานข้อมูลต้นทางจาก embedding ภายใต้ access และวิธีโจมตีที่กำหนด

### ทดลองกลไก

**ลองทำ:** ตั้ง query ใกล้จุด tenant B แล้วสลับ ACL จากนั้นขยับ query ไปอีกบริเวณ

**สังเกต:** เปรียบเทียบ top-3 ตามระยะกับ top-3 ภายใน tenant A และติดตามว่าเอกสารที่ใกล้แต่ไม่มีสิทธิ์ถูกตัดก่อนแสดงอย่างไร

- [บท 1](#chapter-01): state abstraction ต้องรักษาความต่างที่ส่งผลต่อการตัดสินใจ
- [บท 4](#chapter-03): precondition และ invariant ของการ execute
- [บท 5](#chapter-05): memory และ state ที่เปลี่ยนข้ามเวลา

### โจทย์

### 7.1 Joint dynamics และความหมายของ model-free

ให้ agent i เลือก a_i จาก observation o_i และ memory m_i ส่วน transition ของสิ่งแวดล้อมรับ joint action ของทุกตัว เมื่อ policy ของตัวอื่นเปลี่ยน การกระจายผลที่ agent i พบก็เปลี่ยนได้ แม้ θ ของตัวมันเองคงที่ จึงต้องระวังสมมติฐานว่าข้อมูลมาจาก environment เดิมตลอด

World model อาจหมายถึงโมเดลที่เรียนเพื่อทำนาย transition ส่วน simulator อาจใช้กฎ explicit ที่เรารู้ และ model-free learner อาจปรับ policy/value จาก reward โดยไม่เรียน transition model แยก คำว่า model-free จึงไม่ได้บอกว่าไม่มี state, reward หรือ learning

ตัวอย่าง bandit เก็บค่าประมาณผลตอบแทน U(a) ของแต่ละ action แล้วอัปเดตเฉพาะ action ที่เลือกจาก reward ที่สังเกต วิธีนี้ไม่มีการวางแผนผ่าน dynamics ระยะยาวในสูตรพื้นฐาน หาก action เปลี่ยนอนาคตหลายขั้นหรือสถานการณ์เปลี่ยนตามเวลา ต้องเลือก formulation ที่ครอบผลนั้น

$$
s_{t+1}=F(s_t,a_1,\ldots,a_n)
$$

$$
a_i\sim\pi_i(\,\cdot\mid o_i,m_i)
$$

n คือจำนวน agent; F อาจเป็น simulator หรือ transition model ที่ประมาณขึ้น

**อ่านสมการนี้ว่า:** แต่ละ agent เลือก action จาก policy โดยใช้สิ่งที่สังเกตและความจำของตัวเอง จากนั้น F รับสถานะปัจจุบันกับ action ของทุกตัวเพื่อคำนวณสถานะถัดไป

**อ่านสัญลักษณ์:**

- **a_i ∼ π_i:** สุ่ม action ตามการกระจายของ policy ตัวที่ i ไม่ได้แปลว่าคูณกัน
- **·|o_i,m_i:** จุดแทน action ที่เป็นไปได้ ส่วนหลัง | คือข้อมูลที่ policy มีเงื่อนไขด้วย
- **F(s_t,a_1,…,a_n):** กฎการเปลี่ยนสถานะที่รับ action ร่วมของทุก agent

**ตัวอย่างทีละขั้น:** ระบบสมมติ: agent สองตัวอยู่บนเส้นจำนวนที่ s_t=(0,2); F บวก action เข้าตำแหน่งของแต่ละตัว โดยยังไม่มีกฎกันชน

1. policy ของตัวแรกให้ action +1 ด้วยโอกาส 0.8 และ 0 ด้วยโอกาส 0.2; รอบนี้สุ่มได้ +1
2. policy ของตัวที่สองให้ action −1 ด้วยโอกาส 0.6 และ 0 ด้วยโอกาส 0.4; รอบนี้สุ่มได้ −1
3. ส่ง joint action (+1,−1) เข้า F จึงได้ s_(t+1)=(0+1,2−1)=(1,1)

**ผลที่ได้:** ทั้งสองมาอยู่จุดเดียวกัน ผลนี้ขึ้นกับ action ของทั้งคู่และกฎ F ที่กำหนดไว้

**เชื่อมกลับไปที่สมการ:** การตัดสินใจอาจเกิดแยกกัน แต่ผลลัพธ์ผ่าน dynamics ร่วมกัน; หากต้องห้ามชน ต้องระบุเงื่อนไขนั้นในระบบด้วย

$$
U_{t+1}(a_t)=U_t(a_t)+\eta\bigl[r_t-U_t(a_t)\bigr]
$$

ตัวอย่าง incremental reward estimate สำหรับ action ที่เลือก; 0<η≤1 คือ step size ไม่ใช่ learned world model

**อ่านสมการนี้ว่า:** นำ reward ล่าสุดมาเทียบกับค่าประมาณเดิม แล้วขยับค่าประมาณไปทาง reward เป็นสัดส่วน η; อัปเดตเฉพาะ action ที่ถูกเลือกในรอบนั้น

**อ่านสัญลักษณ์:**

- **r_t−U_t(a_t):** prediction error: reward จริงสูงหรือต่ำกว่าที่คาดเท่าไร
- **η:** สัดส่วนของความคลาดเคลื่อนที่นำมาแก้ เช่น 0.25 คือแก้หนึ่งในสี่
- **U_(t+1)(a_t):** ค่าประมาณใหม่ของ action ที่เพิ่งเลือก

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: action A มีค่าประมาณ reward เดิม 4 เลือก A แล้วได้ reward 8 และใช้ η=0.25

1. หาความคลาดเคลื่อน: 8−4 = 4
2. ขยับไปหนึ่งในสี่ของความคลาดเคลื่อน: 0.25×4 = 1
3. ค่าประมาณใหม่จึงเป็น 4+1 = 5; action อื่นที่ไม่ได้เลือกยังไม่ถูกอัปเดตจากสูตรนี้

**ผลที่ได้:** U ใหม่ของ A คือ 5 ไม่ใช่ 8 เพราะผสมข้อมูลใหม่กับค่าประมาณเดิม

**เชื่อมกลับไปที่สมการ:** อ่านสูตรเป็น “ค่าเดิม + ก้าวปรับแก้” ถ้า reward ต่ำกว่าที่คาด พจน์แก้ไขจะติดลบและค่าประมาณลดลง

### 7.2 Mean-field ลดรายละเอียดของ interaction

การพิจารณาทุกคู่มี n(n−1)/2 คู่ Mean-field approximation แทนผลของ agent หลายตัวด้วยการกระจายหรือ summary ของประชากร/เพื่อนบ้าน จากนั้น policy ตอบสนองต่อ summary นี้ เงื่อนไขสำคัญคือรายละเอียดที่ทิ้งต้องไม่ทำลาย interaction ที่ task ต้องใช้

ค่าเฉลี่ยระดับ global อาจเท่ากันทั้งกรณีที่สองกลุ่มเดินสวนกันคนละทางและกรณีที่กำลังชนคอขวดเดียวกัน ถ้าใช้ mean อย่างเดียว policy จะแยกไม่ได้ ปัญหานี้เป็น state aliasing จากบทแรกที่เกิดในระดับประชากร แก้ได้ด้วย locality, role หรือ summary ที่ละเอียดขึ้นตาม task

การอ่าน summary หนึ่งค่าต่อ agent อาจถูก แต่ต้นทุนสร้าง summary และหาเพื่อนบ้านยังอยู่ หากค้นเพื่อนบ้านด้วยการเทียบทุกคู่ก็ยังเสีย O(n²) การอ้าง scaling จึงต้องนับ aggregation, communication และการปรับ neighborhood ด้วย

$$
m_i=\frac{1}{\lvert N_i\rvert}\sum_{j\in N_i}\psi(z_j)
$$

ตัวอย่าง neighbor summary เมื่อ N_i ไม่ว่าง; ψ เลือก feature ที่ใช้สรุป และต้องกำหนดค่ากรณีไม่มีเพื่อนบ้าน

**อ่านสมการนี้ว่า:** เลือก feature จากเพื่อนบ้านแต่ละตัว นำ feature เหล่านั้นมาบวกกัน แล้วหารด้วยจำนวนเพื่อนบ้านเพื่อได้ค่าเฉลี่ยที่ agent i ใช้แทนรายละเอียดของกลุ่ม

**อ่านสัญลักษณ์:**

- **Σ_(j∈N_i):** บวกค่าจากเพื่อนบ้าน j ทุกตัวในชุด N_i
- **|N_i|:** จำนวนสมาชิกในชุดเพื่อนบ้าน ไม่ใช่ความยาวเวกเตอร์
- **ψ(z_j):** feature ที่เลือกจากสถานะเพื่อนบ้าน เช่น velocity สองแกน

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: มีเพื่อนบ้าน 3 ตัว และ ψ คืน velocity เป็น (2,0), (0,2), (1,1) เมตร/วินาที

1. รวมแต่ละแกน: (2+0+1,0+2+1) = (3,3) เมตร/วินาที
2. หารด้วยจำนวนเพื่อนบ้าน 3 ตัว ได้ m_i=(1,1) เมตร/วินาที

**ผลที่ได้:** agent เห็นค่าเฉลี่ย (1,1) แม้แต่ละตัวเคลื่อนต่างทิศ; อีกกลุ่มที่ทุกตัวมี velocity (1,1) ก็ให้ค่าเดียวกัน

**เชื่อมกลับไปที่สมการ:** ค่าเฉลี่ยย่อข้อมูลได้ แต่แยกกลุ่มที่มีค่าเฉลี่ยเท่ากันไม่ได้ และกรณีไม่มีเพื่อนบ้านต้องกำหนด fallback เพื่อไม่หารด้วยศูนย์

$$
\operatorname{pairs}=\frac{n(n-1)}{2}
$$

pairs หมายถึงจำนวนคู่

ใช้กับคู่แบบไม่เรียงลำดับที่พิจารณาครบทุกคู่; ไม่ใช่ต้นทุนที่จำเป็นของระบบ sparse ทุกแบบ

**อ่านสมการนี้ว่า:** ถ้าต้องพิจารณา agent ทุกคู่ ให้แต่ละตัวจับคู่กับอีก n−1 ตัวก่อน แล้วหารสองเพราะคู่ A–B กับ B–A คือคู่เดียวกัน

**อ่านสัญลักษณ์:**

- **n(n−1):** จำนวนคู่แบบเรียงลำดับ โดยไม่จับคู่กับตัวเอง
- **/2:** ตัดการนับซ้ำเมื่อคู่ไม่มีทิศทาง

**ตัวอย่างทีละขั้น:** ตัวอย่างสมมติ: agent 4 ตัวชื่อ A, B, C และ D ต้องตรวจระยะระหว่างทุกคู่

1. นับแบบมีลำดับได้ 4×3 = 12 คู่ เช่น A–B และ B–A ถูกนับแยก
2. หารสองเหลือ 6 คู่: AB, AC, AD, BC, BD, CD

**ผลที่ได้:** เมื่อเพิ่มจาก 4 เป็น 8 ตัว จำนวนคู่เพิ่มจาก 6 เป็น 8×7/2 = 28 คู่

**เชื่อมกลับไปที่สมการ:** จำนวนคู่โตประมาณกำลังสองเมื่อเชื่อมทุกคู่; ระบบที่ใช้เพื่อนบ้านบางส่วนต้องนับตามกราฟและต้นทุนการหาเพื่อนบ้านจริง

### 7.3 Coordination กับ equilibrium เป็นคนละเงื่อนไข

Coarse correlated equilibrium หรือ CCE กำหนดแรงจูงใจ: เมื่อมี distribution ร่วมของคำแนะนำ ผู้เล่นไม่คุ้มจะเลือก action ทางเลือกคงที่ไว้ล่วงหน้าก่อนเห็นคำแนะนำ หากอนุญาตให้เปลี่ยนตามคำแนะนำที่เห็นแล้วจะเป็นเงื่อนไข correlated equilibrium ที่ละเอียดกว่า

ตัวอย่างสอง agent เลือกหนึ่งในสอง resource ถ้าแยกกันได้ reward คนละ 2 ถ้าเลือกซ้ำได้ 0 ผู้ประสานสุ่มแนะนำ (ซ้าย,ขวา) หรือ (ขวา,ซ้าย) อย่างละครึ่ง ทำตามได้ 2 เสมอ แต่เลือกซ้ายคงที่ล่วงหน้าได้เฉลี่ย 1 จึงเห็นผลของ correlated signal โดยคำนวณ payoff ได้ตรง ๆ

Mean-field เป็นวิธีย่อ interaction ส่วน CCE เป็นเงื่อนไขของ incentives การสังเกตว่าฝูงไปทิศเดียวกันหรือระบบรันเร็วขึ้นยังไม่พิสูจน์ CCE ต้องระบุ payoff และทางเลือกเบี่ยงเบนให้ตรงนิยาม ตัวอย่างนี้ยังมี pure equilibrium: ทั้งคู่เลือกต่าง resource อย่างคงที่และไม่มีใครได้ประโยชน์เมื่อเปลี่ยนฝ่ายเดียว จึงใช้สรุปว่า CCE ดีกว่าทุก equilibrium ไม่ได้

$$
\begin{gathered}\mathbb{E}_{a\sim\rho}\bigl[u_i(a)\bigr]\\\ge\mathbb{E}_{a\sim\rho}\bigl[u_i(a_i^{\prime},a_{-i})\bigr]\\\forall\,i,a_i^{\prime}\end{gathered}
$$

เงื่อนไขต้องเป็นจริงสำหรับทุก agent และทุก action ทางเลือกที่เลือกไว้ล่วงหน้า

ρ คือ joint-action distribution, u_i คือ payoff และ a_i′ เป็น action ที่เลือกไว้ล่วงหน้าโดยไม่ขึ้นกับคำแนะนำ; นี่คือนิยาม CCE ในเกมจำกัด

**อ่านสมการนี้ว่า:** สำหรับผู้เล่นแต่ละตัว เปรียบเทียบ reward เฉลี่ยเมื่อทำตามคำแนะนำร่วม กับ reward เฉลี่ยเมื่อประกาศล่วงหน้าว่าจะใช้ action เดียวเสมอ ต้องไม่มี action คงที่ใดให้ค่าเฉลี่ยสูงกว่า

**อ่านสัญลักษณ์:**

- **E_(a∼ρ):** ค่าเฉลี่ยถ่วงน้ำหนักตามโอกาสของ joint action ที่ผู้ประสานแนะนำ
- **a_i′,a_−i:** แทน action ของผู้เล่น i ด้วยตัวเลือกคงที่ a_i′ โดยตัวอื่นยังทำตามคำแนะนำ
- **≥ สำหรับทุก i,a_i′:** ต้องตรวจผู้เล่นทุกตัวและ action คงที่ที่เป็นทางเลือกทุกตัว

**ตัวอย่างทีละขั้น:** เกมสมมติ: เลือก resource ซ้าย/ขวา; ถ้าแยกกันได้คนละ 2 ถ้าซ้ำได้ 0; ρ แนะนำ (ซ้าย,ขวา) และ (ขวา,ซ้าย) อย่างละครึ่ง

1. ทำตามคำแนะนำ: ทั้งสองกรณีได้ 2 จึงมีค่าเฉลี่ย 0.5×2+0.5×2 = 2
2. ผู้เล่น 1 เลือกซ้ายคงที่: อีกตัวอยู่ขวาครึ่งหนึ่งและซ้ายครึ่งหนึ่ง จึงได้ 0.5×2+0.5×0 = 1
3. เลือกขวาคงที่ก็ได้ 1; ผู้เล่น 2 มีผลเหมือนกันจากความสมมาตร

**ผลที่ได้:** ทุกกรณีที่ต้องตรวจได้ 2 ≥ 1 จึงผ่านเงื่อนไข CCE ของเกมนี้

**เชื่อมกลับไปที่สมการ:** จุดสำคัญคือเลือก action เบี่ยงเบนก่อนเห็นคำแนะนำ; สูตรนี้ไม่ได้ตรวจกลยุทธ์ที่เปลี่ยน action ตามคำแนะนำที่เห็นแล้ว

### 7.4 Local rules, emergent behavior และระดับความละเอียด

Boids ใช้กฎ separation หลบเพื่อนบ้านใกล้เกินไป, alignment ปรับความเร็วเข้าหาค่าเฉลี่ยเพื่อนบ้าน และ cohesion เคลื่อนเข้าศูนย์กลางของกลุ่ม ใน lab กฎเหล่านี้ปรับ velocity แล้วจำกัด speed ก่อน update position พฤติกรรมรวมเกิดจากการวน local update โดยไม่มี neural training

Coherence ที่ lab แสดงคือ norm ของค่าเฉลี่ย unit velocity จึงสูงเมื่อทิศทางสอดคล้องกัน ส่วน collision pairs นับคู่ที่อยู่ใกล้กว่า threshold ที่กำหนด สองตัววัดอาจขัดกัน: alignment สูงไม่ได้รับประกันว่าระยะห่างปลอดภัย และไม่มี payoff/regret ที่ใช้รับรอง equilibrium

สำหรับระบบใหญ่ อาจให้ reflex อัปเดตถี่และ planning อัปเดตเฉพาะ event พร้อมเปลี่ยนระดับรายละเอียดตามพื้นที่ วิธีนี้ลดงานแต่เปลี่ยนความละเอียดเวลาและข้อมูล ต้องตรวจ stale actions, invariant และความคลาดเคลื่อนของพฤติกรรมก่อนนับจำนวน agent ที่รองรับ

$$
\operatorname{coherence}=\left\lVert\frac{1}{n}\sum_i\hat{v}_i\right\rVert
$$

$$
\hat{v}_i=\frac{v_i}{\lVert v_i\rVert}
$$

v_i คือ velocity; กำหนด v̂_i=0 หากหยุดนิ่ง ค่าอยู่ใน [0,1] และวัดความสอดคล้องของทิศ

**อ่านสมการนี้ว่า:** เปลี่ยน velocity ของแต่ละตัวให้เหลือทิศทางที่ยาวหนึ่งหน่วย นำมาหาค่าเฉลี่ย แล้ววัดความยาวของค่าเฉลี่ยนั้น ทิศตรงกันจะเสริมกัน ทิศสวนกันจะหักล้าง

**อ่านสัญลักษณ์:**

- **v̂_i:** unit velocity: หารด้วยความเร็วเพื่อเหลือทิศ; กำหนดเป็นศูนย์เมื่อหยุดนิ่ง
- **Σ_i / n:** เฉลี่ยทุกตัว รวมตัวที่หยุดนิ่งตามนิยามนี้
- **∥…∥:** ความยาวของเวกเตอร์เฉลี่ย จึงไม่ติดลบ

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: agent 2 ตัวมี velocity (2,0) และ (5,0) เมตร/วินาที

1. normalize แล้วได้ (1,0) ทั้งคู่; ค่าเฉลี่ย (1,0) มีความยาว 1 จึง coherence=1
2. ถ้าตัวที่สองเปลี่ยนเป็น (−5,0) จะได้ทิศ (−1,0); ค่าเฉลี่ยเป็น (0,0) จึง coherence=0
3. ถ้าตัวที่สองหยุดนิ่ง จะใช้ (0,0); ค่าเฉลี่ยเป็น (0.5,0) จึง coherence=0.5

**ผลที่ได้:** ความเร็วต่างกันยัง coherence=1 ได้ ส่วน coherence=0 อาจเกิดจากวิ่งสวนกันหรือทุกตัวหยุดก็ได้

**เชื่อมกลับไปที่สมการ:** ตัววัดนี้สรุปทิศทางรวม จึงควรอ่านคู่กับ speed และ collision เพื่อไม่ตีความว่าฝูงนิ่งหรือปลอดภัยจากค่าเดียว

$$
\begin{gathered}\mathrm{collision\ pairs}\\=\sum_{i<j}\mathbf{1}\!\left[\lVert x_i-x_j\rVert<d_{\mathrm{min}}\right]\end{gathered}
$$

x_i เป็นตำแหน่งและ d_min คือระยะขั้นต่ำที่ใช้เป็นตัวชี้วัด; lab ใช้ 16 หน่วยพิกัด

**อ่านสมการนี้ว่า:** ตรวจคู่ตำแหน่งแต่ละคู่หนึ่งครั้ง ถ้าระยะน้อยกว่าเกณฑ์ให้นับ 1 ถ้าไม่ใช่ให้นับ 0 แล้วบวกทั้งหมดเป็นจำนวนคู่ที่อยู่ใกล้เกินเกณฑ์

**อ่านสัญลักษณ์:**

- **i<j:** เลือกคู่โดยไม่ซ้ำ และไม่จับ agent กับตัวเอง
- **1[เงื่อนไข]:** indicator: ได้ 1 เมื่อเงื่อนไขจริง มิฉะนั้นได้ 0
- **<d_min:** ต้องน้อยกว่าเกณฑ์แบบ strict; เท่ากับเกณฑ์พอดียังไม่นับ

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: A=(0,0), B=(10,0), C=(26,0) และ d_min=16 หน่วยพิกัดตาม lab

1. คู่ AB ห่าง 10 ซึ่งน้อยกว่า 16 จึงนับ 1
2. คู่ AC ห่าง 26 จึงนับ 0; คู่ BC ห่าง 16 พอดีจึงนับ 0 เช่นกัน
3. รวม 1+0+0 = 1 คู่

**ผลที่ได้:** collision_pairs=1 หมายถึงคู่ที่ต่ำกว่าเกณฑ์ 1 คู่ ไม่ใช่จำนวน agent ที่เกี่ยวข้อง ซึ่งตัวอย่างนี้มี 2 ตัว

**เชื่อมกลับไปที่สมการ:** ชื่อ metric เป็นตัวชี้วัดตาม threshold; การชนทางกายภาพจริงยังขึ้นกับขนาดรูปร่างและนิยาม collision ของ simulation

### นิยามที่ใช้ในบทนี้

- **joint action:** ชุด action ของหลาย agent ที่ร่วมกำหนด transition ของสิ่งแวดล้อม
- **mean-field approximation:** การแทนปฏิสัมพันธ์จำนวนมากด้วย distribution หรือ summary ของประชากร/เพื่อนบ้าน
- **CCE:** เงื่อนไขที่การเปลี่ยนเป็นทางเลือกคงที่ก่อนเห็นคำแนะนำไม่ให้ expected payoff ดีขึ้น
- **emergent behavior:** พฤติกรรมระดับรวมที่เกิดจากการใช้กฎเฉพาะตัวและปฏิสัมพันธ์ซ้ำ ๆ

### ทดลองกลไก

**ลองทำ:** เพิ่ม alignment โดยคง separation ต่ำ สังเกตผล แล้วเพิ่ม separation และเปรียบเทียบกับการรีเซ็ตค่าเดิม

**สังเกต:** อ่าน coherence คู่กับ collision pairs และดูว่าการรวมทิศทางดีขึ้นพร้อมความปลอดภัยหรือมี tradeoff

**ขอบเขตของแบบจำลอง:** lab เป็น local-rule simulation ขนาดเล็กและหาเพื่อนบ้านแบบเทียบคู่ ไม่ได้เรียน mean-field policy หรือประเมิน equilibrium/regret

## บท 8 — Benchmark ทั้งเส้นทาง: คุณภาพ เวลา และเพดานของ speedup

[เปิดบทพร้อมห้องทดลอง](../index.html#story/08) · [หัวข้อสังเคราะห์](topics/08-performance-and-benchmarks.md)

**คำถามหลัก:** การปรับส่วนหนึ่งเร็วขึ้น เปลี่ยนเวลารอและผลสำเร็จของระบบจริงเท่าไร?

**ความเข้าใจที่นำมาใช้:** ทุกกลไกที่ผ่านมาแลกคุณภาพกับ computation คนละจุด ตั้งแต่ encoder, loop, search, verifier, memory ไปถึงการประสานหลาย agent

- [บท 3](#chapter-02): จำนวน pass, node expansions และ budget ของ search
- [บท 4](#chapter-03): selective accuracy, coverage และ abstention
- [บท 7](#chapter-04): interaction และวงรอบ update ของหลาย agent

### โจทย์

ตัวเลข kernel time, tokens/s และจำนวน agent อาจนับขอบเขตงานต่างกัน ต้องกำหนดสิ่งที่หนึ่ง request ทำสำเร็จก่อนเปรียบเทียบความเร็ว

### 8.1 กำหนด work unit และขอบเขตเวลา

Latency คือเวลาของงานหนึ่งตั้งแต่จุดเริ่มถึงจุดจบที่กำหนด ส่วน throughput คือจำนวนงานที่เสร็จต่อช่วงเวลา ระบุหน่วยงานให้ชัด: tokenizer token, generated token, verified decision และ completed tick ต่างมี computation และเกณฑ์เสร็จต่างกัน

สำหรับเส้นทางแบบเรียงลำดับ latency รวม queue, preprocessing, retrieval, model, verification และ output ได้ ถ้ามีงาน overlap หรือขนานต้องวัด critical path และ wall-clock จริง ไม่บวกเวลาทุก worker แล้วเรียก latency ของ request

TTFT หรือ time to first token วัดการรอผลแรกและขึ้นกับ queue/prefill/cache ส่วนเวลาระหว่าง token ต่อมาขึ้นกับ decode รายงาน p50, p95 หรือ p99 เพื่อเห็น distribution ของ latency พร้อมจำนวน sample; ค่าเฉลี่ยอาจซ่อน request ช้าที่กระทบผู้ใช้

$$
\begin{aligned}T_{\mathrm{request}}={}&T_{\mathrm{queue}}+T_{\mathrm{pre}}+T_{\mathrm{retrieve}}\\&{}+T_{\mathrm{model}}+T_{\mathrm{verify}}+T_{\mathrm{output}}\end{aligned}
$$

ใช้การบวกตรงเมื่อขั้นตอนอยู่ในเส้นทางเรียงลำดับและไม่ double-count งานที่ overlap

**อ่านสมการนี้ว่า:** เวลาของหนึ่ง request คือเวลารอคิวและเวลาที่ผ่านแต่ละขั้น ตั้งแต่เตรียม input จนส่ง output โดยบวกกันได้ตรง ๆ เมื่อขั้นเหล่านี้ทำต่อกันและไม่ซ้อนเวลา

**อ่านสัญลักษณ์:**

- **T_queue:** เวลาที่ request รอก่อนเริ่มประมวลผล
- **T_model / T_verify:** เวลาสร้างคำตอบ / เวลาตรวจคำตอบ ต้องกำหนดขอบเขตไม่ให้ซ้ำกัน
- **+:** บวกช่วงเวลาที่เรียงต่อกัน โดยทุกพจน์ต้องใช้หน่วยเดียวกัน

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติของ pipeline ที่ทำทีละขั้น: queue 10, pre 5, retrieve 15, model 60, verify 8, output 2 มิลลิวินาที

1. รวมช่วงก่อน model: 10+5+15 = 30 ms
2. รวมทั้งเส้นทาง: 30+60+8+2 = 100 ms
3. ถ้าเร่งเฉพาะ model ให้เหลือ 30 ms โดยส่วนอื่นคงเดิม เวลาใหม่คือ 30+30+8+2 = 70 ms

**ผลที่ได้:** request เดิมใช้ 100 ms แม้การสร้างคำตอบเองใช้ 60 ms; หลังเปลี่ยนใช้ 70 ms

**เชื่อมกลับไปที่สมการ:** อ่านสูตรเป็นแผนที่เวลารอจริง หากมี retrieval หรือ worker ซ้อนกัน ต้องวัด wall-clock ของเส้นทางที่กำหนดแทนการบวกเวลาทุกงาน

$$
\operatorname{throughput}=\frac{N_{\mathrm{completed}}}{T_{\mathrm{elapsed}}}
$$

ตัวเศษ = จำนวนงานที่เสร็จ; ตัวส่วน = เวลาที่ผ่านไป (elapsed time)

ต้องระบุเงื่อนไขสำเร็จและหน่วย เช่น verified decisions/s; ไม่เอาหน่วยคนละชนิดมาเทียบ speedup

**อ่านสมการนี้ว่า:** นับงานที่เสร็จตามนิยาม แล้วหารด้วยเวลาจริงที่ใช้สังเกต เพื่อบอกว่าระบบส่งผลงานได้เฉลี่ยกี่ชิ้นต่อวินาที

**อ่านสัญลักษณ์:**

- **จำนวนงานที่เสร็จ:** นับหน่วยเดียวกัน เช่น request ที่ผ่านขั้นตอนครบ ไม่ใช่ผสม token กับ request
- **elapsed time:** เวลาบนนาฬิกาตั้งแต่เริ่มถึงจบช่วงวัด รวมช่วงที่มีหลายงานทำพร้อมกัน
- **งาน/s:** หน่วยของ throughput เมื่อใช้เวลาเป็นวินาที

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: ในช่วงวัด 10 วินาที ระบบทำ request เสร็จ 120 รายการ โดยแต่ละรายการมีขอบเขตงานเดียวกัน

1. หารจำนวนงานด้วยเวลา: 120/10 = 12 request/s
2. ถ้าต้องรายงานต่อนาที คูณ 60 จึงได้ 720 request/นาที ภายใต้ค่าเฉลี่ยเดียวกัน

**ผลที่ได้:** Throughput คือ 12 request/s; ยังบอกไม่ได้ว่าแต่ละ request ใช้ latency 1/12 วินาที เพราะอาจทำงานพร้อมกันและรอคิว

**เชื่อมกลับไปที่สมการ:** กำหนดทั้งหน่วยงาน ช่วงวัด และ concurrency ก่อนอ่านตัวเลข throughput หรือเทียบข้ามระบบ

### 8.2 Amdahl: derive ผลรวมจากสัดส่วนเวลาฐาน

ให้ T_0 เป็นเวลาเดิมของ workload คงที่, p เป็นสัดส่วนเวลาที่ปรับได้ และ s≥1 เป็น local speedup ของส่วนนั้น เดิมส่วนที่ปรับกิน pT_0 หลังปรับเหลือ pT_0/s ส่วนที่เหลือยังใช้ (1−p)T_0 จึงหารเวลาเดิมด้วยเวลาใหม่เพื่อได้ speedup รวม

สมมติฐานคือทำงานเดิม คุณภาพเดิม, p อิงเวลาฐาน, ส่วนที่เหลือไม่เปลี่ยน และไม่มี overhead ใหม่หรือรูปแบบ overlap เปลี่ยน ถ้าการเร่ง kernel ทำให้มี copy/sync เพิ่ม ต้องนำต้นทุนใหม่นั้นมาเพิ่มในเวลาใหม่ก่อนใช้ผลรวม

ตัวอย่าง p=0.25 และ s=32: เวลาใหม่เป็น 0.75+0.25/32=0.7578125 เท่าของเดิม จึงเร็วขึ้นประมาณ 1.32 เท่า แม้ทำส่วนนั้นเร็วแบบไม่มีขีดจำกัดก็ได้เพียง 1/0.75≈1.33 เท่า เพดานนี้บอกว่าควรวัดก่อนว่าเวลาอยู่ส่วนใด

$$
T_1=T_0\!\left[(1-p)+\frac{p}{s}\right]
$$

$$
\operatorname{speedup}=\frac{1}{(1-p)+\frac{p}{s}}
$$

p ไม่มีหน่วย เป็นสัดส่วนของ T_0; s เป็นอัตราส่วนความเร็วเฉพาะส่วน

**อ่านสมการนี้ว่า:** แบ่งเวลาเดิมเป็นส่วนที่เร่งไม่ได้กับส่วนที่เร่งได้ หารเวลาเฉพาะส่วนหลังด้วย s แล้วรวมกัน จากนั้นนำเวลาเดิมหารเวลาใหม่เพื่อได้ความเร็วรวม

**อ่านสัญลักษณ์:**

- **p:** สัดส่วนจากเวลาเดิม เช่น 25% ต้องแทนเป็น 0.25
- **s:** ความเร็วเฉพาะส่วน เช่น เร็วขึ้น 32 เท่า หมายถึงเวลาส่วนนั้นเหลือ 1/32
- **(1−p)+p/s:** เวลาใหม่คิดเป็นสัดส่วนของเวลาเดิม ไม่มีหน่วย

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: T_0=100 ms โดยส่วนที่ปรับใช้ 25 ms จึง p=0.25 และเร่งส่วนนั้นได้ s=32

1. ส่วนที่ไม่เปลี่ยนใช้ (1−0.25)×100 = 75 ms
2. ส่วนที่เร่งเหลือ 25/32 = 0.78125 ms จึงรวมเป็น T_1=75.78125 ms
3. speedup รวม = 100/75.78125 ≈ 1.32 เท่า

**ผลที่ได้:** ความเร็วเฉพาะส่วน 32 เท่าให้ความเร็วทั้ง request ประมาณ 1.32 เท่าในตัวอย่างนี้

**เชื่อมกลับไปที่สมการ:** ตัวหาร p/s ลดได้เฉพาะเวลาที่อยู่ใน p; ก่อนใช้สูตรต้องตรวจว่างาน คุณภาพ ส่วนที่เหลือ และ overhead ยังตรงสมมติฐาน

เมื่อทั้งสองเงื่อนไขนี้เป็นจริง

$$
s\to\infty,\qquad p<1
$$

$$
\operatorname{speedup}_{\mathrm{max}}=\frac{1}{1-p}
$$

เพดานภายใต้ fixed workload และ unchanged remainder; ไม่รวมผลจากการเปลี่ยน algorithm หรือเพิ่ม overhead

**อ่านสมการนี้ว่า:** ลองให้ส่วนที่ปรับใช้เวลาน้อยจนเข้าใกล้ศูนย์ เวลาใหม่ยังเหลือส่วนที่ปรับไม่ได้ จึงนำหนึ่งหารสัดส่วนเวลาที่เหลือเพื่อหาเพดาน speedup

**อ่านสัญลักษณ์:**

- **s→∞:** สมมติให้ความเร็วเฉพาะส่วนสูงขึ้นไม่จำกัด เพื่อดูขีดจำกัดทางคณิตศาสตร์
- **1−p:** สัดส่วนเวลาเดิมที่ยังต้องจ่าย แม้ส่วนที่ปรับเร็วมาก
- **p<1:** ต้องมีส่วนที่ไม่เปลี่ยนเหลืออยู่ จึงใช้เพดานจำกัดนี้ได้

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: งานเดิมใช้ 100 ms และส่วนที่เร่งได้กิน 25% ของเวลาเดิม

1. เมื่อเร่งส่วน 25 ms จนเวลาเข้าใกล้ 0 ส่วนที่เหลือยังใช้ 75 ms
2. ความเร็วสูงสุดจึงเข้าใกล้ 100/75 = 1/0.75 ≈ 1.33 เท่า

**ผลที่ได้:** การปรับส่วนเดิมต่อไปอย่างเดียวทำให้เร็วเกินประมาณ 1.33 เท่าไม่ได้ภายใต้สมมติฐานนี้

**เชื่อมกลับไปที่สมการ:** เพดานชี้ว่าควรตรวจเวลาส่วนที่เหลือ; ถ้าเปลี่ยน algorithm, workload หรือ overhead ต้องสร้างแบบจำลองเวลาใหม่

### 8.3 ความเร็วต้องผ่านเกณฑ์คุณภาพที่เทียบกันได้

ระบบที่ตอบน้อยลงหรือข้าม verifier อาจเร็วขึ้น แต่แก้งานคนละเงื่อนไข จึงต้องรายงาน solve rate, invalid output, coverage, timeout และ latency ร่วมกัน ถ้าวัดเฉพาะ request ที่สำเร็จ ให้แสดงด้วยว่ากี่ request ถูกตัดออกจาก denominator

Batching อาจเพิ่ม throughput ด้วยการใช้เครื่องได้เต็มขึ้น แต่ request ต้องรอรวบ batch และใช้ memory มากขึ้น การเลือก concurrency จึงเป็นส่วนของ workload ไม่ใช่รายละเอียดที่ละได้ ส่วน cache ต้องระบุ cold/warm, hit rate และ correctness ของผลที่ reuse

ใน simulation 20 Hz มี budget 50 ms ต่อ tick หาก physics, synchronization และงานอื่นใช้รวม 35 ms จะเหลือ 15 ms ให้ decision ทั้งหมด การคูณเวลา kernel ต่อ agent ยังไม่รวม aggregation, queue, invalidation และการประสาน action ที่เกิดจริง

$$
\begin{gathered}\operatorname{useful\ throughput}\\=\frac{N_{\mathrm{correct,usable}}}{T_{\mathrm{elapsed}}}\end{gathered}
$$

ตัวเศษ = จำนวนผลที่ถูกและผ่านเงื่อนไขใช้งาน; ตัวส่วน = เวลาที่ผ่านไป (elapsed time)

นับทั้ง correctness และความพร้อมใช้จริง; ต้องมีวิธีตรวจผลที่ถูกอิสระจากตัวระบบ

**อ่านสมการนี้ว่า:** นับเฉพาะผลที่ทั้งถูกต้องและผ่านเงื่อนไขใช้งาน แล้วหารด้วยเวลาวัดทั้งหมด เพื่อวัดผลงานที่นำไปใช้ได้จริงต่อวินาที

**อ่านสัญลักษณ์:**

- **ถูกและผ่านเงื่อนไข:** เป็นเงื่อนไขร่วม เช่น คำตอบถูกและทัน deadline ต้องผ่านทั้งคู่
- **elapsed time:** รวมเวลาที่ระบบใช้กับผลผิด timeout และงานที่ไม่ผ่านด้วย
- **useful throughput:** หน่วยเป็นผลที่ใช้ได้/s ไม่ใช่ raw outputs/s

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: 10 วินาทีได้ output 100 รายการ; ตรวจอิสระแล้วถูก 90 รายการ แต่ในกลุ่มที่ถูกมี 10 รายการมาช้ากว่า deadline

1. ผลที่ถูกและทันเวลาเหลือ 90−10 = 80 รายการ
2. หารด้วยช่วงวัดทั้งหมด: 80/10 = 8 ผลที่ใช้ได้/s

**ผลที่ได้:** ระบบมี useful throughput 8 ผล/s แม้ส่ง output รวม 10 รายการ/s

**เชื่อมกลับไปที่สมการ:** ประกาศเกณฑ์ความถูกต้องและความพร้อมใช้ก่อนวัด เพื่อให้การเร่งระบบยังตอบคำถามเดิมว่าทำงานสำเร็จได้มากขึ้นหรือไม่

$$
\mathrm{tick\ budget}_{\mathrm{ms}}=\frac{1000}{\mathrm{update\ rate}_{\mathrm{Hz}}}
$$

20 Hz ให้ 50 ms ต่อรอบ; budget ของ AI เป็นเวลาที่เหลือหลังส่วนอื่นของวงจร

**อ่านสมการนี้ว่า:** หนึ่งวินาทีมี 1,000 มิลลิวินาที ถ้าต้องอัปเดตหลายรอบในหนึ่งวินาที ให้นำ 1,000 หารจำนวนรอบ เพื่อหาเวลาที่มีต่อรอบ

**อ่านสัญลักษณ์:**

- **Hz:** จำนวนรอบต่อวินาที เช่น 20 Hz = 20 รอบ/s
- **1000:** ตัวแปลงหน่วยจากหนึ่งวินาทีเป็น 1,000 ms
- **tick_budget_ms:** เวลาต่อหนึ่งรอบของทั้งวงจร ไม่ใช่เวลาที่มอบให้ AI ได้ทั้งหมด

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: simulation ต้องอัปเดต 20 Hz และ physics กับงานอื่นใช้รวม 35 ms ต่อรอบ

1. หาเวลาต่อรอบ: 1000/20 = 50 ms
2. หักงานอื่นออก จึงเหลือเวลาให้ AI 50−35 = 15 ms ต่อรอบ

**ผลที่ได้:** AI ต้องทำงานที่จำเป็นในรอบนั้นให้เสร็จภายใน 15 ms ตามแบบจำลองที่ไม่มีงาน overlap นี้

**เชื่อมกลับไปที่สมการ:** ยิ่งเพิ่ม update rate เวลาต่อรอบยิ่งลดลง; ต้องนับ aggregation, queue และ synchronization ในส่วนที่ใช้งบจริงด้วย

### 8.4 Experimental matrix ที่บอกสาเหตุได้

ตรึง input set, output contract, weights, precision และ hardware/runtime version ตามคำถามที่ต้องการตอบ จากนั้นแยกแกนที่เปลี่ยน เช่น implementation ภาษาเดิม/ใหม่ กับ greedy/search ถ้าเปลี่ยนสองอย่างพร้อมกันจะไม่รู้ว่าผลเกิดจากการตัดสินใจหรือความเร็ว execution

เก็บ warmup, จำนวนรอบ, raw timing และ distribution ของงาน ระบุ prompt/output length, batch, concurrency และ cache state ผลที่ชนะหนึ่งแถวจึงเป็นหลักฐานเฉพาะเงื่อนไขนั้น ส่วน tail percentile ต้องมี sample เพียงพอและอย่ารายงานความละเอียดเกินข้อมูล

ใช้ correctness gate ก่อน performance gate โดยตั้ง threshold จากสิ่งที่ระบบต้องรักษา และดู paired cases ที่ใช้ input/seed เดียวกันเพื่ออ่านความต่าง การวัดเสร็จจะบอกได้ว่าควรปรับ algorithm, memory movement หรือ hardware ซึ่งเป็นคำถามของบทถัดไป

comparison = workload + quality contract + timing boundary + execution conditions

ชุดข้อกำหนดขั้นต่ำที่ทำให้ speedup มีความหมายและย้อนตรวจผลได้

**อ่านสมการนี้ว่า:** นี่เป็นรายการข้อมูลที่ต้องระบุให้ครบในการเปรียบเทียบ เครื่องหมาย = และ + ใช้ประกอบนิยาม ไม่ได้หมายถึงการบวกตัวเลขสี่พจน์

**อ่านสัญลักษณ์:**

- **workload:** ชุด input และลักษณะงานที่นำมาเปรียบเทียบ
- **quality contract:** เงื่อนไขที่ผลต้องผ่าน เช่น valid path และ deadline
- **timing boundary:** จุดเริ่มและจบการจับเวลา
- **execution conditions:** เครื่อง รุ่น runtime batch concurrency และสถานะ cache

**ตัวอย่างทีละขั้น:** สถานการณ์สมมติ: ต้องการเทียบ runtime A กับ B สำหรับ solver บน maze 200 แผนที่เดียวกัน

1. กำหนดงานและคุณภาพ: ใช้ 200 แผนที่ที่ตรึงไว้ และผลต้องเป็น path ที่ตัวตรวจอิสระยืนยันได้
2. กำหนดเวลา: เริ่มเมื่อรับ request และจบเมื่อผ่าน verifier โดยนับ timeout เหมือนกัน
3. กำหนดเงื่อนไข: เครื่องเดียวกัน precision เดียวกัน concurrency=1 และใช้ cache แบบ cold เหมือนกัน

**ผลที่ได้:** จึงอ่านผลเวลา A/B ร่วมกับ verified success rate ได้บนโจทย์และขอบเขตที่ระบุ

**เชื่อมกลับไปที่สมการ:** รายการนี้ช่วยเห็นว่าความเร็วที่รายงานอาจมาจากเงื่อนไขที่เปลี่ยนไปตรงไหน ก่อนนำตัวเลขมาหารเป็น speedup

### นิยามที่ใช้ในบทนี้

- **latency / throughput:** เวลาต่อหนึ่งงาน / จำนวนงานเสร็จต่อเวลา โดยต้องกำหนดขอบเขตและหน่วยงาน

### โจทย์

Peak FLOPs หรือจำนวน layer ไม่ได้บอกเวลาของงานขนาดเล็ก ต้องนับ fixed overhead, throughput ที่ใช้ได้จริง และจำนวน bytes ที่เคลื่อนย้าย

### 9.1 Derive จุดตัด CPU/GPU จาก cost model

ใช้ N เป็นจำนวน work units ชนิดเดียวกัน, q_C และ q_G เป็นอัตรางานต่อ microsecond ของ CPU/GPU และ τ เป็น fixed GPU overhead หน่วย microseconds แบบจำลองง่ายให้ CPU ใช้ N/q_C ส่วน GPU ใช้ τ+N/q_G

ตั้งเวลาสองฝั่งเท่ากันแล้วแก้ N จะได้จุดตัด N* เฉพาะกรณี q_G>q_C และ τ>0 ใน lab q_C=420, q_G=2200 และ τ=80 จึงได้ N*≈41,528 work units ถ้า GPU rate ไม่มากกว่า CPU จะไม่มีจุดตัดบวกภายใต้แบบจำลองนี้

ที่ N=1,000 CPU ใช้ประมาณ 2.38 µs แต่ GPU 80.45 µs; ที่ N=100,000 CPU 238.10 µs และ GPU 125.45 µs ตัวเลขทั้งหมดสังเคราะห์เพื่อให้เห็นผลของ overhead ไม่ใช่ threshold ของ hardware รุ่นใด และ real throughput อาจไม่คงที่ตาม N

$$
T_{\mathrm{CPU}}=\frac{N}{q_C}
$$

$$
T_{\mathrm{GPU}}=\tau+\frac{N}{q_G}
$$

N เป็น work units; q มีหน่วย work units/µs และ τ มีหน่วย µs จึงได้เวลาทั้งสองเป็น µs

**อ่านสมการนี้ว่า:** ฝั่ง CPU หารจำนวนงานด้วยอัตราทำงานได้เลย ส่วน GPU ต้องจ่ายค่าเริ่มงานคงที่ก่อน แล้วจึงบวกเวลาที่ใช้ทำงานตามจำนวน work units

**อ่านสัญลักษณ์:**

- **N/q:** จำนวน work units หารด้วย work units/µs จึงเหลือหน่วย µs
- **τ:** fixed overhead ของ GPU ที่ต้องจ่ายแม้งานเล็ก
- **q_C, q_G:** อัตรางาน CPU/GPU ที่สมมติว่าคงที่ในแบบจำลองนี้

**ตัวอย่างทีละขั้น:** ตัวเลขสังเคราะห์ของ lab: N=1,000 work units, q_C=420, q_G=2,200 work units/µs และ τ=80 µs

1. CPU ใช้ 1,000/420 ≈ 2.38 µs
2. ส่วนทำงานบน GPU ใช้ 1,000/2,200 ≈ 0.45 µs
3. รวม overhead แล้ว GPU ใช้ 80+0.45 ≈ 80.45 µs

**ผลที่ได้:** GPU คำนวณส่วนงานได้เร็ว แต่เวลารวมสำหรับงานเล็กนี้ยังมากกว่า CPU เพราะ fixed overhead

**เชื่อมกลับไปที่สมการ:** หาร N ด้วย q ให้ได้เวลาส่วนทำงานก่อนเสมอ แล้วใส่ต้นทุนที่เกิดก่อนและหลัง computation ตามขอบเขตที่ต้องการเปรียบเทียบ

$$
N^{*}=\frac{\tau}{\frac{1}{q_C}-\frac{1}{q_G}}
$$

ใช้เมื่อ q_G>q_C; denominator มีหน่วย µs/work unit ทำให้ N* มีหน่วย work unit

**อ่านสมการนี้ว่า:** หาขนาดงานที่เวลาของ CPU กับ GPU เท่ากัน โดยนำ overhead ของ GPU หารด้วยเวลาต่อ work unit ที่ GPU ประหยัดได้เมื่อเทียบกับ CPU

**อ่านสัญลักษณ์:**

- **1/q_C − 1/q_G:** เวลาที่ประหยัดได้ต่อหนึ่ง work unit หน่วย µs/work unit
- **N*:** ขนาดงาน ณ จุดตัด ไม่ใช่ระยะเวลาที่จุดตัด
- **q_G>q_C:** เงื่อนไขให้ GPU ประหยัดเวลาต่อหน่วยและมีโอกาสคืนทุน overhead

**ตัวอย่างทีละขั้น:** ใช้ค่าจำลองของ lab: q_C=420, q_G=2,200 work units/µs และ τ=80 µs

1. CPU ใช้ต่อหน่วยประมาณ 0.002381 µs ส่วน GPU ใช้ 0.000455 µs จึงประหยัดได้ประมาณ 0.001926 µs/work unit
2. คำนวณด้วยค่าที่ยังไม่ปัดเศษ: N*=80/(1/420−1/2200) ≈ 41,528 work units
3. แทนกลับที่จุดตัด: CPU≈98.88 µs และ GPU≈80+18.88=98.88 µs

**ผลที่ได้:** ภายใต้แบบจำลองนี้ งานใหญ่กว่าจุดตัดให้ GPU คุ้มเวลารวม ส่วนงานเล็กกว่าจุดตัดให้ CPU คุ้มกว่า

**เชื่อมกลับไปที่สมการ:** จุดตัดขึ้นกับ overhead และ rate ที่วัดได้จริง; ถ้า rate เปลี่ยนตาม batch หรือ N ต้องปรับแบบจำลองตามนั้น

### 9.2 Compute-bound กับ memory-bound

งาน compute-bound ถูกจำกัดด้วยอัตราคำนวณ ส่วน memory-bound ถูกจำกัดด้วยการขนข้อมูล Arithmetic intensity คือจำนวน FLOPs ต่อ bytes ที่อ่านเขียนในระดับ memory ที่กำลังวิเคราะห์ งานที่ใช้ข้อมูลแต่ละชิ้นครั้งเดียวกับงานที่ reuse หลายครั้งจึงใช้เครื่องได้ต่างกัน

SIMD บน CPU ทำ operation แบบเดียวกับหลาย lane ของข้อมูล และได้ประโยชน์เมื่อ memory layout ต่อเนื่องและ branch เหมาะสม ส่วน GPU ใช้หลาย thread ตาม execution model ของมัน ยังมี dispatch, scheduling และ synchronization การใช้ชนิด vector ในภาษาไม่ได้ส่ง computation ไป GPU เอง

เช่นเก็บ entity เป็น [x,y,vx,vy] ซ้ำแต่ใช้ x ทุกตัวเพียง field เดียว อาจเกิด stride และอ่าน bytes ที่ไม่ใช้ การแยก arrays ตาม field อาจช่วยงานนั้น แต่ถ้า loop ต้องใช้ทุก field ของ entity เดียว รูปแบบเดิมอาจเหมาะกว่า ต้องตัดสินตาม access pattern

$$
I=\frac{F}{D}
$$

$$
T_{\mathrm{execution}}\ge\max\!\left(\frac{F}{P_{\mathrm{peak}}},\frac{D}{B_{\mathrm{mem}}}\right)
$$

F=FLOPs, D=bytes ที่เคลื่อนผ่าน memory ระดับที่เลือก, P_peak=FLOPs/s, B_mem=bytes/s; เป็นขอบล่างเชิงอุดมคติที่ยังไม่รวม overhead

**อ่านสมการนี้ว่า:** เริ่มจากดูว่าคำนวณกี่ FLOPs ต่อข้อมูลที่เคลื่อนหนึ่ง byte แล้วคำนวณเวลาขั้นต่ำจากกำลังคำนวณและ bandwidth แยกกัน เวลารันจริงจะต่ำกว่าค่าที่มากกว่าของสองฝั่งไม่ได้

**อ่านสัญลักษณ์:**

- **I=F/D:** arithmetic intensity หน่วย FLOPs/byte
- **F/P_peak:** เวลาอย่างน้อยที่ต้องใช้ทำ arithmetic หากใช้กำลังคำนวณได้เต็ม
- **D/B_mem:** เวลาอย่างน้อยที่ต้องใช้ขนข้อมูลผ่าน memory ระดับที่เลือก
- **max / ≥:** เลือกค่าที่มากกว่าเป็นขอบล่างของเวลา ไม่ใช่บวกสองค่าทันที

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: F=2×10⁹ FLOPs, D=10⁹ bytes, P_peak=10¹¹ FLOPs/s และ B_mem=10¹⁰ bytes/s

1. intensity = (2×10⁹)/10⁹ = 2 FLOPs/byte
2. ขอบล่างจาก compute = (2×10⁹)/10¹¹ = 0.02 s หรือ 20 ms
3. ขอบล่างจาก memory = 10⁹/10¹⁰ = 0.1 s หรือ 100 ms; max(20,100)=100 ms

**ผลที่ได้:** T_execution ≥ 100 ms ในแบบจำลองนี้ โดย memory เป็นข้อจำกัดที่สูงกว่า; เวลาจริงอาจมากกว่านี้จาก overhead และการใช้เครื่องไม่เต็ม

**เชื่อมกลับไปที่สมการ:** การเพิ่ม peak FLOPs อย่างเดียวไม่ลดขอบล่าง 100 ms หากยังเคลื่อนข้อมูลเท่าเดิมด้วย bandwidth เดิม

$$
\begin{aligned}T_{\mathrm{end\text{-}to\text{-}end}}={}&T_{\mathrm{prepare}}+T_{\mathrm{transfer}}+T_{\mathrm{dispatch}}\\&{}+T_{\mathrm{execute}}+T_{\mathrm{sync}}+T_{\mathrm{finish}}\end{aligned}
$$

ใช้แบ่งรายการต้นทุนก่อนวัด wall-clock; หาก overlap ให้ตรวจ critical path และไม่บวกเวลาซ้ำ

**อ่านสมการนี้ว่า:** แยกเวลางานออกเป็นเตรียมข้อมูล ส่งข้อมูล สั่งงาน คำนวณ รอประสาน และเก็บผล เพื่อเห็นว่าการเร่งขั้นหนึ่งลดเวลาทั้งเส้นทางเท่าไร

**อ่านสัญลักษณ์:**

- **T_transfer:** เวลาขนข้อมูล เช่น ระหว่าง host กับ device ภายในขอบเขตที่วัด
- **T_dispatch / T_sync:** เวลาส่งงานเข้า runtime / เวลารอหรือประสาน completion ที่ยังไม่นับไว้
- **+:** บวกได้เมื่อแบ่งช่วงเวลาไม่ซ้ำและขั้นตอนเรียงต่อกัน

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติของ trace แบบเรียงขั้นและไม่ซ้อนเวลา: prepare 2, transfer 3, dispatch 1, execute 4, sync เพิ่มเติม 1, finish 1 ms

1. รวมทั้งเส้นทางได้ 2+3+1+4+1+1 = 12 ms
2. หากเร่ง execute จาก 4 เป็น 2 ms โดยส่วนอื่นเท่าเดิม เวลาใหม่เป็น 10 ms

**ผลที่ได้:** kernel เร็วขึ้น 2 เท่า แต่เวลา end-to-end เร็วขึ้น 12/10 = 1.2 เท่า

**เชื่อมกลับไปที่สมการ:** ถ้าเวลารอ synchronize รวมเวลาที่ kernel ทำงานอยู่แล้ว ต้องแยกช่วงนั้นก่อน เพื่อไม่บวก execution ซ้ำอีกครั้ง

### 9.3 Zero-copy มี data contract ที่ต้องรักษา

การมอง bytes ชุดเดิมเป็น typed view ลด copy ได้เมื่อ layout, alignment, length และ bit pattern เข้ากับชนิดปลายทาง เช่นไม่ใช่ทุก byte จะเป็น bool ที่ valid และโครงสร้างอาจมี padding ที่ต้องจัดการ การมีชื่อ field เหมือนกันไม่ได้รับรองว่า binary layout เหมือนกัน

Native in-memory layout กับ serialized format เป็นคนละ contract ตัว serializer อาจใช้ variable-length encoding หรือกำหนด endian ของมัน จึงเอา serialized bytes มา cast เป็น struct โดยสมมติว่าตรงกันไม่ได้ การ borrow จาก buffer ได้ก็ยังต้องผูก lifetime กับเจ้าของข้อมูลให้ถูก

แยกวัด parse, allocation, copy และ computation พร้อมผลลัพธ์ที่ได้ ตัวเลข zero-copy ของข้อมูลใน process เดียวไม่ใช่หลักฐานว่าใช้แทน protocol ข้ามเครื่องหรือไฟล์ต่างเวอร์ชันได้ หากต้องเปลี่ยน format ต้องคิดถึง compatibility ของผู้อ่านด้วย

typed_view(bytes) ต้องมี layout + alignment + validity + lifetime ที่สอดคล้องกัน

รายการนี้เป็นแกนของ contract; ข้อกำหนดจริงขึ้นกับภาษา ไลบรารี และชนิดข้อมูลที่เลือก

**อ่านสมการนี้ว่า:** ข้อความนี้เป็น checklist ของการอ่าน bytes เดิมผ่านชนิดข้อมูลใหม่ เครื่องหมาย + หมายถึงต้องมีข้อกำหนดเหล่านี้พร้อมกัน ไม่ใช่การบวกค่าตัวเลข

**อ่านสัญลักษณ์:**

- **layout / alignment:** ตำแหน่งและรูปแบบของข้อมูล / ขอบเขต address ที่ชนิดปลายทางต้องการ
- **validity:** bit pattern ต้องเป็นค่าที่ชนิดปลายทางยอมรับ
- **lifetime:** buffer เจ้าของข้อมูลต้องยังมีชีวิตขณะที่ view ถูกใช้งาน

**ตัวอย่างทีละขั้น:** สถานการณ์สมมติ: buffer มี bytes 01 00 00 00 และระบบทั้งสองฝั่งตกลงใช้ u32 แบบ little-endian ที่ต้องการ alignment 4 bytes

1. ตรวจว่ามีข้อมูลครบ 4 bytes เริ่มที่ address ที่จัด alignment ถูก และ layout ตรงกับชนิด u32
2. ตรวจ bit pattern และ endian; ภายใต้ข้อตกลงนี้ข้อมูลแทนจำนวนเต็ม 1
3. สร้าง view โดยรักษาเจ้าของ buffer ไว้ตลอดช่วงที่อ่าน และไม่ใช้ view หลัง buffer หมดอายุ

**ผลที่ได้:** อ่านค่า 1 ได้โดยไม่จำเป็นต้อง copy ในระบบที่รองรับ contract นี้; ถ้า endian ไม่ตรงก็อาจอ่านได้คนละค่า

**เชื่อมกลับไปที่สมการ:** “ไม่ copy” เป็นผลของการรักษาข้อตกลงข้อมูลครบถ้วน ไม่ใช่สิทธิ์ให้ cast bytes ทุกชุดเป็นชนิดใดก็ได้

### 9.4 Phase ของ model เปลี่ยนจุดที่ควร optimize

สำหรับ dense attention การคำนวณ score ของ prefill ยาว T สร้างความสัมพันธ์ T×T ส่วน decode ของ token ใหม่ใช้ query ใหม่อ่าน K ที่ cache อยู่ T ตำแหน่ง จึงมีโครงต้นทุนต่างกัน นี่ยังไม่รวม projection, FFN ซึ่งเป็นเครือข่าย feed-forward ที่แปลง feature ของแต่ละตำแหน่ง และ layer อื่น การเร่ง attention kernel หนึ่งแบบอาจมีผลต่อสอง phase ไม่เท่ากัน

ตัวอย่าง KV cache ที่ B=1, L=32, T=4096, H_KV=8, d_head=128 และ b=2 ใช้ payload 536,870,912 bytes หรือ 512 MiB ตามสูตรบท memory การแชร์ KV heads หรือลด precision เปลี่ยน memory นี้ได้ แต่ต้องตรวจข้อกำหนด architecture และคุณภาพหลังเปลี่ยน

Runtime เฉพาะ model/hardware อาจรวม operation, เปลี่ยน layout หรือจัด cache ได้เหมาะขึ้น ข้อสรุปต้องผูกกับรุ่นโมเดล phase และ workload ที่วัด เมื่อรู้ต้นทุนระดับนี้แล้ว เราสามารถอ่าน paper ใหม่โดยถามว่ามันแก้ representation, algorithm หรือ execution กันแน่

งานคำนวณ attention-score ต่อ head

$$
\mathrm{prefill}:\quad O(T^2d_k)
$$

$$
\mathrm{decode\ (one\ query)}:\quad O(Td_k)
$$

ระบุเฉพาะ dense score computation โดย key ที่ผ่านมาถูก cache แล้ว; ไม่ใช่ complexity ของโมเดลทั้งหมด

**อ่านสมการนี้ว่า:** prefill คิด score ของ query ทุกตำแหน่งกับ key ทุกตำแหน่ง จึงมีจำนวนคู่โตแบบ T² ส่วน decode หนึ่ง query เทียบกับ key ที่ cache ไว้ T ตำแหน่ง จึงโตตาม T

**อ่านสัญลักษณ์:**

- **O(…):** บอกการโตตามขนาด input โดยละค่าคงที่ ไม่ใช่เวลารันเป็นวินาที
- **T² / T:** จำนวนคู่ query–key สำหรับ prefill / query ใหม่หนึ่งตัว
- **d_k:** จำนวนองค์ประกอบที่ใช้ใน dot product ของแต่ละคู่

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติต่อ head: T=4 และ d_k=2; นับเฉพาะ scalar multiplications ใน score ไม่รวม additions, mask และขั้นอื่น

1. prefill มี query 4 ตัว × key 4 ตัว = 16 คู่ แต่ละคู่คูณ 2 ค่า จึง 32 multiplications
2. decode ของ query ใหม่หนึ่งตัวที่อ่าน cached keys 4 ตัว มี 4 คู่ จึง 8 multiplications
3. ถ้าเพิ่ม T เป็น 8 โดย d_k คงเดิม จะได้ prefill 8×8×2=128 และ decode 8×2=16 multiplications

**ผลที่ได้:** เพิ่มความยาวเป็นสองเท่าทำให้ score work ของ prefill โตสี่เท่า แต่ของ query ใหม่หนึ่งตัวโตสองเท่าในตัวอย่าง dense นี้

**เชื่อมกลับไปที่สมการ:** อย่านำสัดส่วนนี้ไปใช้เป็นความเร็วของโมเดลทั้งหมด เพราะ projection, FFN, memory traffic และ kernel implementation ยังมีต้นทุนของตัวเอง

$$
\begin{aligned}\mathrm{KV}_{\mathrm{bytes}}&=2\times1\times32\times4096\\&\quad{}\times8\times128\times2\\&=512\,\mathrm{MiB}\end{aligned}
$$

สมมติ K/V มี d_head เท่ากัน เก็บเต็มและไม่บีบอัด; 1 MiB = 2²⁰ bytes

**อ่านสมการนี้ว่า:** นับจำนวนค่าที่ต้องเก็บใน K และ V ทุก head ทุก token ทุก layer และทุกตัวอย่างใน batch แล้วคูณ bytes ต่อค่าเพื่อแปลงเป็นขนาด memory

**อ่านสัญลักษณ์:**

- **2 ตัวแรก:** สองชุดข้อมูลคือ K และ V
- **1×32×4096:** batch 1 × layers 32 × tokens 4096
- **8×128×2 ตัวท้าย:** KV heads 8 × ค่าต่อ head 128 × bytes ต่อค่า 2
- **MiB:** หนึ่ง MiB = 1,048,576 bytes หรือ 2²⁰ bytes

**ตัวอย่างทีละขั้น:** ค่าจำลองตามสมการ: เก็บ K/V เต็ม ไม่บีบอัด ใช้ 2 bytes ต่อค่า และยังไม่นับ metadata หรือพื้นที่สำรองของ allocator

1. หนึ่ง token ในหนึ่ง layer ใช้ 2×8×128×2 = 4,096 bytes สำหรับ K และ V รวมกัน
2. 4,096 tokens ในหนึ่ง layer ใช้ 4,096×4,096 = 16,777,216 bytes หรือ 16 MiB
3. ครบ 32 layers และ batch 1 ใช้ 16×32×1 = 512 MiB

**ผลที่ได้:** KV payload รวมคือ 536,870,912 bytes หรือ 512 MiB; หาก batch เพิ่มเป็น 2 โดยอย่างอื่นคงเดิม payload จะเป็น 1,024 MiB

**เชื่อมกลับไปที่สมการ:** แต่ละตัวคูณบอกแกนที่ทำให้ memory โต จึงใช้ประเมินผลของ context length, batch, KV heads และ precision ได้ตรงหน่วย

### นิยามที่ใช้ในบทนี้

- **fixed overhead:** ต้นทุนที่จ่ายก่อนหรือประกอบ computation เช่น dispatch และ synchronization
- **arithmetic intensity:** จำนวน FLOPs ต่อ bytes ที่เคลื่อนผ่าน memory ระดับที่ระบุ
- **SIMD / memory layout:** การทำ operation เดียวหลาย lane / วิธีวางข้อมูลที่กำหนด pattern การอ่านเขียน
- **zero-copy:** การใช้ storage เดิมผ่าน view หรือการ borrow โดยต้องรักษา contract ของข้อมูลและอายุ

### ทดลองกลไก

**ลองทำ:** ใช้ overhead 80 µs เลื่อน work size ใกล้ 41,528 แล้วเพิ่ม overhead เป็น 160 µs โดยคง rate เดิม

**สังเกต:** ดูว่าจุดตัดเพิ่มเป็นประมาณสองเท่าตามสูตร และเวลาฝั่ง GPU มีส่วนคงที่ก่อนเริ่มคุ้ม

### โจทย์

โพสต์ที่ใช้ศัพท์เดียวกันอาจแก้คนละปัญหา และผลที่เกิดจากหลายการเปลี่ยนพร้อมกันยังไม่บอกสาเหตุ เราต้องวาง claim ลงบนส่วนของระบบที่มันเปลี่ยน

### 10.1 สกัดกลไกก่อนสรุปความเกี่ยวข้อง

เริ่มจาก input → mechanism → output แล้วระบุ trainable variables, state ที่เปลี่ยนระหว่าง inference, objective และ stopping condition หากเป็นระบบที่มีหลาย component ให้วาด edge ว่าผลของส่วนหนึ่งเป็นข้อมูลหรือเงื่อนไขให้ส่วนใดต่อ

ตัวอย่าง claim ว่า latent reasoning เร็วขึ้นต้องระบุว่าเปลี่ยน encoder, ลด output tokens, ใช้ recurrent passes, ลด node expansions หรือเปลี่ยน kernel สิ่งเหล่านี้มี dependency และ denominator ของความเร็วต่างกัน ใช้ tensor shape, operation count และ timing boundary ที่เรียนมาเปิดคำอธิบายให้ตรวจได้

เก็บ evidence แยกเป็นผลจาก paper ต้นทาง, ผลจาก implementation/benchmark ของผู้โพสต์ และข้อเสนอที่จะนำมาใช้กับระบบเรา ลิงก์ repo หรือชื่อวิดีโอเป็นทางไปตรวจต่อ แต่ยังไม่ใช่หลักฐานว่า implementation หรือเนื้อหาทั้งหมดมีสิ่งที่เราคาด

research card = claim, source, mechanism, assumptions, artifact, experiment, unknowns

บันทึกสิ่งที่ยืนยันแล้วแยกจากสมมติฐานที่จะทดลอง เพื่อไม่ส่งต่อ claim เกินหลักฐาน

**อ่านสมการนี้ว่า:** สมการนี้ตั้งชื่อชุดข้อมูลที่ควรจดเมื่ออ่านงานหนึ่งชิ้น เครื่องหมาย = และจุลภาคหมายถึงรายการใน research card ไม่ใช่ความเท่ากันทางคณิตศาสตร์

**อ่านสัญลักษณ์:**

- **claim / source:** สิ่งที่งานอ้าง / ต้นทางที่ตรวจข้อความนั้นได้
- **mechanism / assumptions:** วิธีที่ทำให้เกิดผล / เงื่อนไขที่วิธีต้องอาศัย
- **artifact / experiment / unknowns:** สิ่งที่ตรวจรันได้ / การทดลอง / คำถามที่ยังไม่มีคำตอบ

**ตัวอย่างทีละขั้น:** สถานการณ์สมมติ: บทความ A อ้างว่าเพิ่ม search แล้วแก้ maze สำเร็จมากขึ้น บทความนี้เป็นตัวอย่าง ไม่ใช่แหล่งอ้างอิงจริง

1. จด claim และตำแหน่ง source แล้วสรุป mechanism ว่าเพิ่ม node expansion โดย scorer เดิม
2. จด assumptions ว่า transition ถูกต้องและ budget เท่ากัน พร้อม artifact เช่น revision ของ solver และไฟล์โจทย์
3. ออกแบบ experiment ด้วย maze ชุดที่ตรึงไว้ แล้วจด unknowns เช่นผลกับ maze ที่ใหญ่กว่าหรือ heuristic คนละแบบ

**ผลที่ได้:** ได้บันทึกที่แยกสิ่งที่ต้นทางรายงานออกจากสิ่งที่เรายังต้องทดลอง

**เชื่อมกลับไปที่สมการ:** ช่อง unknowns ช่วยหยุดการขยายข้อสรุปเกินหลักฐาน และบอกว่าควรอ่านหรือลองอะไรต่อ

### 10.2 Ablation ต้องตอบคำถามเชิงสาเหตุที่ชัด

Ablation คือการปิดหรือนำส่วนหนึ่งออกเพื่อดูผล ส่วน factorial comparison เปลี่ยนหลายปัจจัยเป็นตารางอย่างมีระบบ ตัวอย่างแยก implementation A/B กับ decision rule greedy/search เป็นสี่ configuration โดยคุม weights, input set, precision และเงื่อนไข evaluation ที่เกี่ยวข้อง

ให้ Y_ij เป็น metric ที่นิยามเหมือนกันในแต่ละ configuration การเทียบ Y_10−Y_00 แสดงผลของปัจจัยแรกเมื่อปัจจัยที่สองคงเดิม ส่วน difference of differences ช่วยตรวจว่าผลของปัจจัยแรกเปลี่ยนเมื่อเปิดปัจจัยที่สองหรือไม่ ต้องดู sampling variability ประกอบก่อนตีความ interaction

งบ wall-clock เท่ากันตอบว่า configuration ใดทำงานได้ดีในเวลาที่มี ส่วนจำนวน model calls เท่ากันตอบเรื่องการใช้ computation หน่วยนั้น ทั้งสองเป็นคำถามที่มีประโยชน์แต่ไม่เท่ากัน อย่าสลับข้อสรุประหว่างตารางที่ตั้ง budget ต่างกัน

$$
\operatorname{interaction}=(Y_{11}-Y_{01})-(Y_{10}-Y_{00})
$$

i ระบุ implementation และ j ระบุ decision rule; ใช้ metric และ scale เดียวกัน เช่น solve rate ที่ budget เท่ากัน

**อ่านสมการนี้ว่า:** วัดผลของการเปลี่ยน implementation เมื่อเปิด decision rule แบบหนึ่ง แล้วลบด้วยผลของการเปลี่ยน implementation เมื่อใช้ rule อีกแบบ เพื่อดูว่าผลของสองปัจจัยขึ้นต่อกันหรือไม่

**อ่านสัญลักษณ์:**

- **Y_ij:** metric เมื่อเลือก implementation i และ decision rule j
- **Y_11−Y_01:** ผลต่าง implementation 1 กับ 0 ขณะที่ตรึง rule j=1
- **difference of differences:** ผลต่างของผลต่างทั้งสอง ต้องใช้ metric และ scale เดียวกัน

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติที่ budget เท่ากัน: Y_00=60%, Y_10=64% เมื่อ greedy; Y_01=70%, Y_11=80% เมื่อ search โดย Y คือ verified solve rate

1. ผลของ implementation เมื่อใช้ search: 80−70 = 10 จุดเปอร์เซ็นต์
2. ผลของ implementation เมื่อใช้ greedy: 64−60 = 4 จุดเปอร์เซ็นต์
3. interaction = 10−4 = 6 จุดเปอร์เซ็นต์ หรือ 0.06 เมื่อเขียนอัตราในช่วง 0–1

**ผลที่ได้:** implementation ใหม่เพิ่ม solve rate มากกว่าเดิม 6 จุดเปอร์เซ็นต์เมื่อใช้ search เทียบกับ greedy บนตารางสมมตินี้

**เชื่อมกลับไปที่สมการ:** นี่เป็น interaction บนสเกลผลต่าง solve rate ไม่ใช่เพิ่ม 6% แบบสัมพัทธ์; ยังต้องดูความแปรปรวนและการควบคุมการทดลองก่อนสรุปเหตุ

control set = input/seed, θ, precision, output contract, budget, evaluator version

เลือกสิ่งที่ตรึงตาม causal question และบันทึกทุกข้อที่เปลี่ยนโดยหลีกเลี่ยงไม่ได้

**อ่านสมการนี้ว่า:** อ่านข้อความนี้เป็นรายการเงื่อนไขที่จะตรึงหรือบันทึก เพื่อให้ผลต่างที่วัดตอบคำถามที่ตั้งไว้ เครื่องหมาย = และจุลภาคไม่ได้สั่งให้คำนวณตัวเลขรวม

**อ่านสัญลักษณ์:**

- **input/seed:** โจทย์และค่าตั้งต้นการสุ่มที่จับคู่เปรียบเทียบกันได้
- **θ / precision:** พารามิเตอร์โมเดล / รูปแบบตัวเลขที่ใช้คำนวณ
- **budget / evaluator version:** งบที่ให้แต่ละวิธี / รุ่นตัวตรวจที่ตัดสินผล

**ตัวอย่างทีละขั้น:** สถานการณ์สมมติ: ต้องการวัดว่าเพิ่ม search ช่วย solver ที่ใช้ scorer เดิมหรือไม่ ภายใต้งบ 30 ms ต่อโจทย์

1. ใช้ maze 100 แผนที่และชุด seed เดียวกัน พร้อม weights revision เดียวกันและ precision เดียวกัน
2. กำหนดสัญญาผลลัพธ์เป็น path ที่ถูกต้อง งบ 30 ms เท่ากัน และใช้ verifier รุ่นเดียวกัน
3. เปลี่ยนเฉพาะ greedy เป็น search แล้วบันทึกจำนวน model calls ที่เกิดจริง เพราะภายใต้งบเวลาเดียวกันจำนวน calls อาจต่างกัน

**ผลที่ได้:** ผลที่ได้ตอบเรื่องคุณภาพภายในเวลาเท่ากัน โดยมีตัวแปรควบคุมที่ตรวจย้อนกลับได้

**เชื่อมกลับไปที่สมการ:** เลือก control ให้ตรงคำถาม; งบเวลาเท่ากันกับจำนวน calls เท่ากันเป็นคนละเงื่อนไข จึงไม่จำเป็นต้องตรึงทั้งสองพร้อมกัน

### 10.3 ออกแบบ mini-repro ที่มี counterexample

เลือกสมมติฐานแคบหนึ่งข้อ เช่น search ช่วย maze ที่มีทางลวงภายใต้งบเวลาที่กำหนด เริ่มจาก solver ที่ตรวจ path ได้ ใช้ชุดโจทย์ที่กำหนดก่อนเลือกวิธี และแยกชุดที่ใช้ปรับ heuristic ออกจากชุดประเมินสุดท้าย ไม่จำเป็นต้องสร้างทั้ง agent stack เพื่อทดสอบกลไกเดียว

เก็บ found-valid-path rate, path length, node expansions, timeout และ latency เลือกฉากที่ challenge สมมติฐานด้วย เช่น goal อยู่ใกล้แต่มีสิ่งกีดขวาง หรือ heuristic ชี้ผิด ถ้าเพิ่ม recurrent scorer ต้องมี model ที่ฝึกและ input/state interface ชัด จึงค่อยเทียบกับ search เดิม

เมื่อผลดีเฉพาะบางกลุ่ม ให้บันทึก boundary นั้นแทนสรุปกว้าง โปรแกรมกฎเล็กและเกมจำกัดมีประโยชน์เพราะสำรวจ case ได้ชัด การสร้างตัวอย่างที่ล้มเหลวช่วยระบุว่าต้องเพิ่มข้อมูล เปลี่ยน algorithm หรือแก้ implementation ซึ่งเป็นคนละการปรับ

$$
\begin{gathered}\operatorname{verified\ success\ rate}\\=\frac{N_{\mathrm{verified}}}{N_{\mathrm{all\ problems}}}\end{gathered}
$$

ตัวเศษ = จำนวนโจทย์ที่ได้คำตอบผ่านตัวตรวจอิสระ; ตัวส่วน = จำนวนโจทย์ทั้งหมด

รวม timeout และ abstention ใน denominator เพื่อเห็นความสามารถตลอดชุด; ตัวตรวจยังต้องมี specification ที่ถูกต้อง

**อ่านสมการนี้ว่า:** นับโจทย์ที่มีคำตอบผ่านตัวตรวจอิสระ แล้วหารด้วยจำนวนโจทย์ทั้งหมดที่ส่งเข้า evaluation รวมโจทย์ที่ระบบหมดเวลาหรือไม่ตอบด้วย

**อ่านสัญลักษณ์:**

- **ตัวเศษ:** จำนวนโจทย์ที่ได้คำตอบและผ่าน specification ที่ตัวตรวจใช้
- **ตัวส่วน:** จำนวนโจทย์ทั้งหมด ไม่ตัด timeout หรือ abstention ออก
- **rate:** อัตราส่วน 0–1; คูณ 100 เพื่อแสดงเป็นเปอร์เซ็นต์

**ตัวอย่างทีละขั้น:** ตัวเลขสมมติ: ประเมิน 20 maze ได้ path ผ่านตัวตรวจ 12, path ผิด 3, timeout 3 และ abstain 2

1. ตรวจยอดทั้งหมด: 12+3+3+2 = 20 โจทย์
2. ใช้เฉพาะ 12 คำตอบที่ผ่านเป็นตัวเศษ แล้วหารด้วย 20 ได้ 0.6
3. แปลงเป็นเปอร์เซ็นต์: 0.6×100 = 60%

**ผลที่ได้:** verified success rate คือ 60% ของชุดที่ประเมินทั้งหมด

**เชื่อมกลับไปที่สมการ:** เกณฑ์นี้แสดงความสามารถตลอดชุด ส่วนจำนวนผิด หมดเวลา และไม่ตอบควรรายงานร่วมกันเพื่ออธิบายว่าอีก 40% เกิดจากอะไร

### 10.4 จัดความรู้ตาม prerequisite และใช้ recall ตรวจช่องว่าง

เขียนสรุปหนึ่งกลไกโดยตอบว่าใช้ state อะไร, เปลี่ยนตัวแปรใด, รับประกันอะไรภายใต้สมมติฐานใด และต้นทุนมาจากไหน หากตอบไม่ได้ให้ตาม source เฉพาะจุดนั้น เช่น LoRA ต้องย้อนหา factor shapes ส่วน recurrence ต้องหา update กับ halting condition

ทบทวนด้วยการ derive แทนจำชื่อ: คำนวณจำนวนพารามิเตอร์ LoRA จาก shape, อธิบายทำไม fixed point อาจผิด, วาดตำแหน่ง ACL ก่อน context และคำนวณ Amdahl จากเวลาแต่ละส่วน Lab flashcards เป็นจุดเริ่มให้เรียกคำตอบเอง แล้วใช้สมการและ failure case ในบทอธิบายให้ครบ

คิวงานใหม่ควรตามปัญหาที่ยังไม่ตอบ, ความชัดของหลักฐาน และต้นทุนทำซ้ำ เมื่อเลือกมาแล้วเก็บ source กับ experiment ที่ปิดคำถามได้ ลำดับนี้ทำให้ความรู้ใหม่ต่อจากสิ่งที่เข้าใจอยู่ โดยไม่ต้องคอยเดาความหมายของศัพท์ที่อยู่ถัดไป

understanding check = mechanism + assumptions + worked example + failure case

ความสามารถอธิบายสี่ส่วนนี้ช่วยหา prerequisite ที่ขาด; ยังต้องตรวจ implementation และผลวัดแยกต่างหาก

**อ่านสมการนี้ว่า:** นี่เป็น checklist ตรวจความเข้าใจหนึ่งกลไก เครื่องหมาย + หมายถึงอธิบายองค์ประกอบให้ครบ: วิธีทำ สมมติฐาน ตัวอย่างที่คำนวณได้ และกรณีที่วิธีมีข้อจำกัด

**อ่านสัญลักษณ์:**

- **mechanism / assumptions:** ระบบทำอะไร / การอธิบายนั้นต้องอาศัยเงื่อนไขใด
- **worked example:** แทนค่าหรือไล่ขั้นตอนจริงจนได้ผล
- **failure case:** กรณีที่แสดงขอบเขตของกลไก ไม่ใช่แค่จำชื่อข้อดี

**ตัวอย่างทีละขั้น:** ตัวอย่างสมมติ: ใช้ LoRA กับ W รูปร่าง 3×4 และ rank r=1 โดยพิจารณาเฉพาะเมทริกซ์ ไม่รวม bias

1. อธิบายกลไกและสมมติฐาน: ตรึง W เดิม แล้วเรียน A ขนาด 1×4 กับ B ขนาด 3×1 เพื่อสร้าง update แบบ low rank
2. คำนวณตัวอย่าง: เรียน 4+3=7 พารามิเตอร์ แทนการเรียน W ทั้ง 3×4=12 พารามิเตอร์
3. ยกข้อจำกัด: หาก update ที่ต้องการมี rank 2 ผลคูณ BA ที่ rank ไม่เกิน 1 จะแทน update นั้นได้ไม่ตรงทุกค่า

**ผลที่ได้:** คำอธิบายครบทั้งรูปแบบการปรับ จำนวนพารามิเตอร์ และข้อจำกัดด้าน rank จึงใช้ตรวจจุดที่ยังไม่เข้าใจได้

**เชื่อมกลับไปที่สมการ:** การ derive ตัวอย่างเล็กช่วยเชื่อมสัญลักษณ์กับการทำงานจริง ส่วนคุณภาพของโมเดลหลังฝึกยังต้องวัดแยกจากการนับพารามิเตอร์

### นิยามที่ใช้ในบทนี้

- **dependency graph:** กราฟที่ระบุว่าส่วนใดต้องใช้ข้อมูล แนวคิด หรือเงื่อนไขจากส่วนใดก่อน
- **ablation:** การนำส่วนหนึ่งออกหรือปิดเพื่อวัดบทบาทของมันเมื่อเงื่อนไขอื่นคุมไว้
- **factorial comparison:** ตารางทดลองที่แยกหลายปัจจัยเป็นทุกชุดผสมเพื่ออ่านผลแต่ละแกนและ interaction
- **counterexample / mini-repro:** กรณีที่ทำให้ claim ล้มเหลว / การทำซ้ำขนาดเล็กเพื่อทดสอบกลไกหรือข้อสรุปที่เฉพาะเจาะจง

**ลองทำ:** ใช้ flashcard ถามก่อนเฉลย แล้วขยายคำตอบทุกข้อเป็นกลไกหนึ่งข้อ สมมติฐานหนึ่งข้อ และ counterexample หนึ่งข้อ

**สังเกต:** แยกข้อที่เพียงจำคำตอบสั้นได้ออกจากข้อที่ derive สูตรหรืออธิบาย failure case ได้โดยไม่เปิดโน้ต

**ขอบเขตของแบบจำลอง:** การ recall ตรวจความเข้าใจของผู้อ่าน ส่วนการรับรอง implementation หรือ paper claim ยังต้องใช้หลักฐานและการทดลองที่ตรงคำถาม

### ตรวจความเข้าใจก่อนต่อยอด

งานใหม่เปลี่ยนทั้ง search, runtime และ cache แล้วเร็วขึ้นพร้อม accuracy สูงขึ้น เรารู้สาเหตุของผลดีนั้นหรือยัง?

<details>
<summary>แนวคำตอบ</summary>

รู้เพียงผลของ configuration รวมภายใต้เงื่อนไขที่รายงาน ต้องแยก ablation/factorial comparison ให้แต่ละปัจจัยเปลี่ยนบนฐานเดียวกัน ตรวจ interaction และคุมคุณภาพกับ workload ก่อนระบุว่าส่วนใดทำให้ผลดีขึ้น

</details>

**ข้อสรุป:** วาง claim ลงบนกลไกที่ระบุ input, state, objective และต้นทุนได้ แล้วใช้การเปรียบเทียบที่แยกเหตุพร้อม counterexample เพื่อกำหนดขอบเขต
