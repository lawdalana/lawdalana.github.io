## สกัดจากโพสต์

ผู้เขียนจะนำ paper เรื่อง agent และ evaluator ที่วิวัฒน์ร่วมกันมาทดลอง พร้อมยกตัวอย่างความเชื่อในโลกเกมที่อาจเก่าแล้ว เช่น วางแผนขึ้นรถไฟ แต่เมื่อไปถึงรถออกไปแล้ว ภาพเป็นแผนผัง workspace tree, การเลือก node, evaluator ที่ถูกตรึงในแต่ละช่วง และการเปลี่ยน evaluator ที่ checkpoint

มีสองปัญหาที่เกี่ยวข้องแต่ควรแยก: ความเชื่อเกี่ยวกับโลกอาจล้าสมัย และเกณฑ์ตรวจ agent อาจไม่พอเมื่อ agent เก่งขึ้น การแก้ปัญหาหลังไม่ได้รับประกันว่าโลกภายนอกจะตรงกับความเชื่อเก่า

## Paper เสนออะไร

RQGM เสนอให้ค้นหาการปรับปรุงทั้ง task agent และ evaluator แทนการถือว่าเกณฑ์ประเมินคงที่เสมอ โดยตรึง evaluator ภายใน epoch แล้วประเมินผู้ท้าชิงด้วย ground-truth anchor ก่อนเปลี่ยนใน checkpoint ที่กำหนด ภาพยังแสดงการล้างบันทึกคะแนนบางส่วนที่อิง evaluator เดิม เพื่อไม่เอาคะแนนคนละมาตรฐานมาปนกัน [paper และรูป 2](https://arxiv.org/pdf/2606.26294)

**Epoch** ในที่นี้คือช่วงที่เกณฑ์ประเมินคงที่ **Checkpoint** คือจุดพิจารณาเปลี่ยน **Anchor** คือข้อมูลอ้างอิงสำหรับตรวจผู้ตรวจอีกที ผลที่รายงานเป็นการทดลองของ preprint ไม่ใช่ข้อรับรองว่า agent สามารถปรับตัวไปได้ตลอดโดยไม่หลุดเป้าหมาย

## ตัวอย่างออกแบบเอง: ผู้เขียนเควสต์กับผู้ตรวจเควสต์

รุ่นแรก ผู้ตรวจให้ผ่านหากเควสต์มีผู้ให้ เป้าหมาย และรางวัล ผู้เขียนเรียนรู้สร้างเควสต์ที่องค์ประกอบครบ แต่บางรางวัลไม่มีอยู่จริง คะแนนจึงดีขึ้นทั้งที่เกมไม่ได้ดีขึ้น

รุ่นถัดมาเราเพิ่ม evaluator ที่ตรวจ inventory และ timeline ก่อนเปลี่ยนใช้ต้องให้ทั้งผู้ตรวจเก่าและใหม่ตัดสินชุดตัวอย่างที่รู้คำตอบแล้ว มิฉะนั้น evaluator ใหม่อาจเข้มเกินจนปฏิเสธทุกอย่าง

ตัววัดอย่างน้อยสองด้านคือ **false accept** ยอมรับงานผิด และ **false reject** ปฏิเสธงานถูก การเพิ่ม acceptance rate อย่างเดียวจึงยังสรุปว่า generator ดีขึ้นไม่ได้

## เทคนิคสำคัญ: version ของความจริงที่ใช้ตัดสิน

บันทึกผลทุกครั้งพร้อม:

~~~text
agent_version, evaluator_version, dataset_version,
world_snapshot, คะแนน, เหตุผลที่ผ่านหรือไม่ผ่าน
~~~

นี่เป็นข้อเสนอสำหรับประยุกต์ ไม่ใช่ schema ที่ paper บังคับ หากเปลี่ยน evaluator แล้วคะแนนจาก 70 เป็น 90 ต้องรันชุดเปรียบเทียบร่วมเพื่อแยกว่า agent ดีขึ้นหรือผู้ตรวจเปลี่ยนมาตรฐาน

กรณีรถไฟในโพสต์เพิ่มอีกชั้น: ความเชื่อควรมีเวลาที่สังเกตและความมั่นใจ พร้อมตรวจ precondition ตอนลงมือ เช่น ขบวนยังอยู่และขึ้นได้หรือไม่ แผนที่ดีเมื่อห้านาทีก่อนอาจใช้ไม่ได้แล้วแม้ evaluator เดิมจะให้คะแนนสูง

## แบบฝึกหัด

สร้างเควสต์ตัวอย่าง 20 ชิ้นที่รู้ว่าถูกหรือผิด ให้ผู้ตรวจรุ่นหนึ่งดูแค่รูปแบบและอีกรุ่นดูความเป็นไปได้ในโลก เทียบข้อผิดพลาดแต่ละชนิด จากนั้นเปลี่ยนสถานะโลกหนึ่งเหตุการณ์แล้วประเมินใหม่

**คำถามทบทวน:** คะแนนสูงขึ้นเพราะผู้ทำเก่งขึ้น ผู้ตรวจอ่อนลง หรือโจทย์ง่ายลง? ถ้าข้อมูลที่เก็บยังแยกสามกรณีนี้ไม่ได้ วงรอบ self-improvement ยังตีความผลไม่ได้ชัด

## ตรวจสอบและค้นคว้าเพิ่มเติม — รอบ 2

ตรวจวันที่ 2026-09-20 · อ่านแหล่งต้นทางเพิ่มและเทียบกับคำอธิบายเดิม

### งานวิจัยเพิ่ม: ปรับ agent กับตรวจคุณภาพผู้ตัดสิน

**Darwin Gödel Machine: Open-Ended Evolution of Self-Improving Agents — Zhang และคณะ, preprint 2025** ค้นหาการแก้โค้ดของ coding agent แล้วประเมินด้วย benchmark พร้อมเก็บ archive ของหลายรุ่นให้เป็นจุดตั้งต้นการค้นหาต่อ งานที่ทดลองปรับเครื่องมือและ workflow รอบ foundation model ที่ตรึงไว้ ไม่ได้แสดงการฝึก foundation model ใหม่เอง ผลบน SWE-bench/Polyglot เป็นผลเชิงทดลองตามชุดประเมิน [วิธีการและขอบเขตที่ผู้วิจัยระบุ](https://arxiv.org/html/2505.22954v3)

**Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena — Zheng และคณะ, 2023** ตรวจการใช้ LLM ให้คะแนนคำตอบ เทียบกับคนและเปลี่ยนเงื่อนไขการให้คะแนน พบข้อจำกัด เช่น position bias และความไวต่อรูปแบบ prompt จึงมีเหตุผลต้องตรวจผู้ประเมินเองก่อนใช้คะแนนเป็นเป้าหมายของการปรับ agent [paper โดยเฉพาะ Appendix D](https://arxiv.org/html/2306.05685v4)

### ประเด็นที่เพิ่มจาก RQGM

DGM ทำให้เห็นการค้นหา agent หลายรุ่นภายใต้เกณฑ์ประเมิน โดยแก้โค้ด/เครื่องมือของ agent รอบ foundation model ที่ตรึงไว้ ไม่ใช่ฝึกฐานโมเดลใหม่ ส่วน RQGM ในโพสต์เพิ่มปัญหาว่า evaluator ก็เปลี่ยนได้ และ paper เองระบุว่าเป็น preliminary empirical investigation หากเปลี่ยนทั้งผู้ทำและผู้ตรวจพร้อมกัน คะแนนดีขึ้นจะแยกสาเหตุยาก ควรมีผลจากผู้ตรวจชุดอ้างอิงร่วม และชุดโจทย์ที่ไม่ถูกใช้เลือกการแก้รุ่นล่าสุด

คำว่า Gödel ในชื่อไม่ใช่หลักฐานว่าทุก self-modification ได้รับการพิสูจน์ทางตรรกะ หรือว่า agent แก้ weight ของ foundation model เอง งาน DGM/RQGM ใช้การค้นหา variant และการประเมินเชิง empirical ภายใต้ benchmark/judge ที่กำหนด ขณะที่ผลตรรกะต้องมีข้อความและสมมติฐานที่จะพิสูจน์แยกต่างหาก

### ตัวอย่างตรวจ judge โดยยังไม่เปลี่ยน agent

นำคำตอบ A กับ B คู่เดิมให้ judge สองรอบ โดยสลับว่าอันใดแสดงก่อนและปิดชื่อผู้สร้าง หากผู้ชนะเปลี่ยนตามตำแหน่งบ่อย ต้องแก้กระบวนการประเมินหรือรายงานความไม่แน่นอนก่อนนำไปใช้คัดเลือกรุ่น agent

อีก control คือสร้างคำตอบที่เนื้อหาเดียวกันแต่ยาวต่างกัน แล้วดูว่าคะแนนความถูกต้องเพิ่มเพราะมีข้อมูลถูกมากขึ้นหรือแค่คำอธิบายยาวขึ้น การทดสอบนี้สร้างขึ้นเพื่อแยกสิ่งที่ judge ให้รางวัล ไม่ได้ใช้ตัดสินว่า judge รุ่นใดดีกว่าโดยไม่มีผลทดลอง

**สิ่งที่ควรเก็บเพิ่ม:** หมายเลขคู่คำตอบ ลำดับที่แสดง รุ่น judge prompt ที่ใช้ ผลตรวจจากกฎหรือเฉลย และคะแนนก่อน/หลัง หากใช้ archive ให้เก็บคุณสมบัติที่ต่างกัน ไม่ใช่เฉพาะรุ่นที่ชนะคะแนนเดียว เพื่อเรียนรู้ว่าทางเลือกใดเป็นจุดตั้งต้นที่มีประโยชน์

**ผลการตรวจ:** ผู้ตรวจที่เปลี่ยนได้เพิ่มความยืดหยุ่น แต่ต้องมีการเทียบมาตรฐานข้ามรุ่น ความสำเร็จของวงรอบควรวัดบนโจทย์ใหม่และคุณภาพจริงของงาน ไม่ใช่คะแนนที่วงรอบกำหนดเองเพียงอย่างเดียว
