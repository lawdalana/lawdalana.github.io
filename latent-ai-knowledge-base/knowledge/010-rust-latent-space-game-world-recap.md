# 010 — Rust EP4: ออกแบบเมืองจำลองจากสถานะ กฎ และพฤติกรรม

อ่านเพิ่ม: [ผลตรวจและงานวิจัยรอบ 2](#research-review-2)

ต้นฉบับ: [post.md](../original/post.md) บรรทัด 427–507 · โพสต์สรุป session โดยผู้เข้าฟัง · ตรวจแหล่งข้อมูล: 2026-09-20

โพสต์นี้ไม่มีภาพแทรกในส่วนของตน เป็น recap ยาวที่รวมหลายเรื่อง จึงสกัดเป็นประเด็นย่อยก่อน ตัวเลขและคำอธิบายระบบ KatGPT มาจากผู้บันทึก session ไม่ใช่ผลที่ทดลองซ้ำในชุดเอกสารนี้

## 1. โลกจำลองที่เกิดจากตัวละครหลายตัว

โพสต์เล่าถึงสัตว์ที่ตอบสนองต่อผู้ล่า กลางวันกลางคืน อาชีพ ร้านค้า ระบบการเงิน และเครื่องมือ GM ที่เปลี่ยนเหตุการณ์ได้ ตัวละครแต่ละตัวมีสถานะ ความจำ และแรงจูงใจ เมื่อหลายตัวปฏิสัมพันธ์กัน พฤติกรรมระดับเมืองจึงเกิดขึ้น

แนวคิดใกล้เคียงที่มีงานต้นทางชัดคือ Boids ซึ่งทำให้เกิดฝูงจากการหลบชน จัดทิศทางใกล้เพื่อน และเข้าหาศูนย์กลางเพื่อนในระยะใกล้ ไม่ต้องเขียนเส้นทางของทั้งฝูงล่วงหน้า [Craig Reynolds: Boids](https://www.red3d.com/cwr/boids/index.html)

ข้อเรียนรู้คือแยก **กฎระดับตัวละคร** ออกจาก **ผลที่เกิดระดับกลุ่ม** การเห็นฝูงเคลื่อนไหวเองไม่ได้บอกทันทีว่ามีการอัปเดตน้ำหนักโมเดลหรือเรียนรู้แบบมนุษย์ ต้องตรวจ state update จริง

## 2. Latent space เป็นตัวแทนเพื่อทำงาน

โพสต์เสนอใช้ตัวแทนขนาดเล็กแทนข้อมูลโลกทั้งหมด ตัวอย่างที่ออกแบบเองสำหรับกระต่ายคือ (ความหิว, อันตราย, ระยะถึงที่หลบ, ระยะถึงลูก) จากนั้นเลือก action ที่ได้คะแนนเหมาะกับสถานการณ์และผ่านเงื่อนไขการเคลื่อนที่

ประเด็นที่ควรปรับความเข้าใจ:

- Latent มีได้หลายมิติ ไม่จำกัด 2–3 มิติ และ 768 ไม่ใช่จำนวนมิติสากลที่เหมาะที่สุด
- การลดมิติอาจทิ้งข้อมูล การแปลงกลับไม่จำเป็นต้องได้ต้นฉบับครบ
- Neural network ไม่ได้กลายเป็น neuro-symbolic เพียงเพราะทำงานกับ latent ต้องมีส่วนแทนความรู้หรือกฎเชิงสัญลักษณ์ผสมด้วย
- จำนวน layer ที่พอใช้ขึ้นกับโจทย์ ไม่มีข้อสรุปจาก recap ว่า 2–3 layer พอสำหรับทุกงาน

งาน DeepMDP ให้ตัวอย่างเกณฑ์เลือก representation โดยดูว่าทำนาย reward และสถานะอนาคตได้ดีเพียงใด จึงช่วยเปลี่ยนคำถามจาก “กี่มิติดี” เป็น “ยังเหลือข้อมูลพอทำงานหรือไม่” [DeepMDP](https://arxiv.org/abs/1906.02736)

## 3. ความกลัว ความมั่นใจ และ curiosity

ในระบบเกม คำเหล่านี้อาจเป็นค่าหรือฟังก์ชันให้คะแนน เช่น ความกลัวเพิ่มน้ำหนักการหลบภัย ความหิวเพิ่มน้ำหนักหาอาหาร และ curiosity ให้คุณค่าการสำรวจพื้นที่ที่ยังไม่รู้

ตัวอย่างสมมติ:

~~~text
คะแนน(action) = ประโยชน์เรื่องอาหาร + ประโยชน์ต่อลูก
               + คุณค่าการสำรวจ − ความเสี่ยง − ต้นทุนเดินทาง
~~~

ปรับน้ำหนักแล้วพฤติกรรมเปลี่ยนโดยไม่เพิ่มกรณี if/else ทุกชุดได้ แต่ยังต้องออกแบบกฎและตรวจว่าไม่มีเป้าหมายใดทำให้ NPC ติดวงจร เช่น สำรวจอย่างเดียวจนอดอาหาร ความทรงจำที่ส่งถึงรุ่นลูกก็ต้องมีช่องทางข้อมูลชัดเจน เช่น บันทึกตำแหน่งอันตราย ไม่ใช่เกิดจากคำว่า latent โดยอัตโนมัติ

## 4. เศรษฐกิจในเกมและการควบคุมโลก

ตัวอย่างนมกับกาแฟในโพสต์สอนการเชื่อม supply chain: จำนวนวัว → ปริมาณนม → ต้นทุน → ราคา → การเลือกซื้อของ NPC ส่วนเพดานราคา การกู้เงิน และการถือหุ้นร้านเป็นกฎที่ผู้ออกแบบกำหนด

ข้อเสนอทดลอง: ลดปริมาณนมครึ่งหนึ่งแล้วดูทั้งราคา สินค้าขาด และจำนวนผู้ซื้อที่ต้องเปลี่ยนเมนู หากตั้งเพดานราคาแต่ไม่จำลองสินค้าหมด ระบบอาจแสดงผลที่ขัดกับกฎทรัพยากรของตัวเอง

Wallet และธุรกรรมควรมีสถานะอ้างอิงที่ตรวจยอดและสิทธิ์ได้ เวกเตอร์ความจำของ NPC ใช้ช่วยตัดสินใจได้ แต่ไม่ควรใช้ค่าความคล้ายของ embedding แทนข้อเท็จจริงว่าเงินถูกโอนไปแล้วหรือยัง นี่เป็นข้อเสนอการออกแบบเกม ไม่ใช่คำแนะนำการลงทุน

## 5. Rust, Unity, schema และ WASM

Recap ย้อน EP1 เรื่องแชร์หน่วยความจำ Rust/Unity, EP2 เรื่องสร้าง schema จาก struct, และ EP3 เรื่อง game center กับการคำนวณเฉพาะงาน ตลอดจนชื่อ DFlash/DDTree ที่ไม่ได้ให้รายละเอียดในส่วนนี้

สิ่งที่นำไปเรียนต่อได้คือการกำหนด **ขอบเขตข้อมูลระหว่างระบบ**: struct ใน Rust ต้องมีรูปแบบหน่วยความจำและอายุข้อมูลที่อีกฝั่งเข้าใจ การสร้างหลาย schema จากนิยามเดียวช่วยลดความซ้ำ แต่ยังต้องจัดการการเปลี่ยนรุ่นข้อมูล ฐานข้อมูล และโปรโตคอล ไม่ได้ทำให้ทุกชนิดข้อมูลข้ามภาษาได้ทันที

Rust ช่วยตรงการจัดการหน่วยความจำผ่าน ownership rules ที่ compiler ตรวจ เช่น value มี owner เดียวในเวลาหนึ่งและถูก drop เมื่อออกจาก scope ตาม Rust Book; สิ่งนี้ช่วยลดบั๊ก memory บางชนิด แต่ไม่ได้พิสูจน์ว่า logic ของเกมถูกต้องเอง ([Rust Book: ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)). WASM เป็นรูปแบบโค้ดสำหรับ runtime ไม่ใช่ตัว Transformer เอง และ security model ของ WebAssembly เน้น sandboxed execution กับข้อจำกัดของ module ตามเอกสาร WebAssembly ไม่ได้แปลว่า module ที่เราโหลดปลอดภัยทางธุรกิจหรือ logic เสมอ ([WebAssembly security](https://webassembly.org/docs/security/)). ส่วนโมดูลคำนวณที่เสียบกับ policy ต้องระบุ input/output และเงื่อนไขที่เรียกได้ การแชร์ memory ช่วยลดการคัดลอกได้แต่ไม่ได้ทำให้การเข้าถึง memory ไม่มีเวลาใช้จ่าย

ชื่อ DFlash/DDTree ใน recap EP3 ไม่ได้ถูกอธิบายในโพสต์นี้ แต่ตรวจแยกได้ว่า DFlash และ DDTree เป็น speculative decoding papers สาธารณะ ส่วนการผูกกับเกม/latent runtime ของ KatGPT ยังเป็น claim ของ session ไม่ใช่ผลจาก paper เหล่านั้นโดยตรง ([DFlash](https://arxiv.org/abs/2602.06036), [DDTree](https://arxiv.org/abs/2604.12989)).

## 6. SIMD และการวัดประสิทธิภาพ

โพสต์ยกตัวอย่างคำนวณสี่ค่าพร้อมกัน การทำงานหลาย lane ช่วยลดจำนวนคำสั่งบางส่วนได้ แต่ไม่รับประกันเร็วขึ้นสี่เท่าทั้งโปรแกรม และไม่ได้เปลี่ยน Big-O โดยตัวมันเอง

Rust `std::simd` เป็น portable SIMD API ที่ยังอยู่บน nightly/experimental และเอกสารระบุว่า operation อาจถูก compile ไปยัง instruction ที่เหมาะกับ target ไม่ใช่หลักประกันว่าโค้ดทุกส่วนจะเร็วขึ้นเท่าจำนวน lane ([Rust `std::simd`](https://doc.rust-lang.org/std/simd/index.html)). ดังนั้น claim “SIMD 4 ค่าเร็วกว่า 4 เท่า” ต้องอ่านเป็น intuition ของ kernel บางส่วน ไม่ใช่ผล end-to-end

คำนวณตัวอย่างด้วยกฎ Amdahl: ถ้า 80% ของเวลาเร็วขึ้น 4 เท่า ส่วนที่เหลือเท่าเดิม อัตราเร็วทั้งงานคือ 1/(0.2+0.8/4) = 2.5 เท่า การจัดข้อมูลให้ต่อเนื่อง ลด allocation และลดการส่งข้อมูลอาจสำคัญกว่าการเพิ่ม lane อย่างเดียว

ตัวเลขหน่วยความจำ 46 MB และคำว่าไม่มี latency เป็นคำรายงานในโพสต์ ต้องแยกขนาด artifact, หน่วยความจำขณะรัน และเวลาครบ pipeline การไม่เรียก API ภายนอกตัดเวลารอเครือข่ายส่วนนั้นได้ แต่ยังมีเวลาคำนวณในเครื่อง

## 7. Novel Fusion, agent และ feature flag

โพสต์เรียกการผสมแนวคิดหลาย paper ว่า Fusion/Novel Fusion และสังเกตว่า AI อาจทำงานไม่ครบ เทคนิคที่นำไปใช้คือทำรายการข้อกำหนดก่อนเริ่ม แล้วเทียบสิ่งที่ส่งมอบกับรายการเดิม โดยไม่ใช้การอธิบายว่าโมเดล “ขี้เกียจเพราะพลังงานจำกัด” เป็นข้อเท็จจริงทางกลไก

Feature flag ช่วยเปิดปิดวิธีใหม่เพื่อทดลอง แต่จะทราบว่าคุ้มจริงต้องเก็บ baseline, คุณภาพ, เวลา และหน่วยความจำภายใต้โจทย์เดียวกัน การผสมแนวคิดใหม่ยังไม่เท่ากับมีผลดีกว่าเดิม

## 8. Lore และ Merkle tree

ตรวจพบ Lore ของ Epic Games จริง เอกสารทางการอธิบายระบบ version control ที่เน้นข้อมูลขนาดใหญ่ ใช้ content-addressed storage, chunks, Merkle trees และดาวน์โหลดเมื่อจำเป็น โดยแกนสถาปัตยกรรมเป็นบริการรวมศูนย์ [Epic Games/Lore](https://github.com/EpicGames/lore)

Merkle tree ใช้ hash ของส่วนย่อยมารวมเป็น hash ของโครงสร้าง ทำให้ตรวจได้ว่าส่วนไหนเปลี่ยนและใช้ข้อมูลซ้ำได้ ข้อกล่าวว่าระบบดัดแปลงทำ distributed/NFT ได้ในคืนเดียวเป็นเรื่องที่ผู้เล่าสรุป ไม่ใช่คุณสมบัติของ Lore ที่ตรวจยืนยันจากเอกสารนี้ การใช้ Merkle tree อย่างเดียวไม่ได้ทำให้มี consensus หรือสิทธิ์ความเป็นเจ้าของครบระบบ

## แบบฝึกหัดรวม

สร้างฉากบนกระดาษหรือ simulation เล็ก ๆ มี 10 NPC, อาหาร, ที่หลบ และรอบกลางวันกลางคืน เริ่มจาก state กับคะแนน action แล้วเพิ่มข้อจำกัดและความจำทีละส่วน จดว่าแต่ละส่วนเพิ่มพฤติกรรมอะไรและใช้ต้นทุนเท่าใด จากนั้นจึงเพิ่ม cache หรือ SIMD เมื่อรู้ว่าคอขวดอยู่ที่ไหน

**สิ่งที่ควรได้จากโพสต์นี้:** เห็นวิธีแตกโลกใหญ่เป็นสถานะและการเปลี่ยนสถานะเล็ก ๆ ที่ตรวจได้ แยกการแทนข้อมูล การเลือกพฤติกรรม การบังคับกฎ และการวัดผลออกจากกันก่อนนำมาประกอบ

## ตรวจสอบและค้นคว้าเพิ่มเติม — รอบ 2

ตรวจวันที่ 2026-09-20 · อ่านแหล่งต้นทางเพิ่มและเทียบกับคำอธิบายเดิม

### งานวิจัยเพิ่มสำหรับเมืองที่มี agent หลายบทบาท

**The AI Economist: Improving Equality and Productivity with AI-Driven Tax Policies — Zheng และคณะ, 2020** สร้างเศรษฐกิจจำลองที่มี agent และ social planner เรียนรู้คนละระดับ โดย planner ปรับนโยบายภาษีและ agent เปลี่ยนพฤติกรรมตามสิ่งแวดล้อม ผลที่รายงานเป็นการประเมินภายในระบบจำลองและการตั้งค่าที่ระบุ จึงช่วยเป็นตัวอย่างว่ากฎเศรษฐกิจกับพฤติกรรมประชากรต้องประเมินร่วมกัน ไม่ใช่หลักฐานว่าสูตรนั้นย้ายไปเมืองหรือเกมอื่นแล้วได้ผลเดิม [paper ต้นทาง](https://arxiv.org/abs/2004.13332)

**Scalable Evaluation of Multi-Agent Reinforcement Learning with Melting Pot — Leibo และคณะ, 2021** เน้นทดสอบ social generalization โดยเปลี่ยนสถานการณ์และประชากรที่ agent ไปเล่นด้วย เพราะพฤติกรรมของ agent อื่นเป็นส่วนหนึ่งของ environment ผลดีเมื่อเล่นกับเพื่อนชุดเดิมจึงไม่พอรับรองการร่วมมือกับกลุ่มใหม่ [paper และแนวออกแบบการประเมิน](https://arxiv.org/pdf/2107.06857)

### ประเด็นใหม่ต่อจากเมืองในโพสต์

เมื่อเปลี่ยนราคาสินค้าหรือรางวัล เราไม่ได้เปลี่ยนแค่ตัวเลขในร้าน แต่เปลี่ยน incentive ของผู้ผลิต ผู้ซื้อ และผู้ขนส่งด้วย ถ้า NPC ปรับ policy ไปพร้อมกัน distribution ของประสบการณ์ก็เปลี่ยน ทำให้ผลจากรอบก่อนใช้เป็น baseline ตรง ๆ ไม่ได้เสมอ ควรตรึงรุ่น policy หรือระบุช่วงการปรับตัวให้ชัดเมื่อเทียบกฎสองแบบ

ตัวอย่างออกแบบเอง: ทดสอบเมืองเดิมกับประชากรสามชุด—ทุกตัวร่วมมือ, มีตัวกักตุนบางส่วน, และมีพ่อค้าที่เพิ่งเข้ามาซึ่งใช้ policy อีกแบบ ดูทั้งผลรวมการผลิต จำนวนตัวละครที่ขาดอาหาร ความแออัดของเส้นทาง และการกระจายสินค้า การมีผลตอบแทนรวมสูงอาจซ่อนกลุ่มที่ไม่ได้รับบริการ

### กฎบัญชีทรัพยากรช่วยตรวจ simulation

กำหนดสมการตรวจอาหารของทั้งเมือง:

~~~text
stock_next = stock_now + production − consumption − spoilage
~~~

ถ้ามีอาหาร 30 หน่วย ผลิต 5 กิน 4 และเสีย 1 ต้องเหลือ 30 การซื้อขายภายในเมืองเปลี่ยนผู้ถือ แต่ไม่ควรเพิ่ม stock รวม หากยอดไม่ตรง ต้องแก้กลไกเปลี่ยนสถานะก่อนสรุปว่าเศรษฐกิจหรือการเรียนรู้เกิดพฤติกรรมใหม่

ในตัวอย่างนม/กาแฟ แยกวัตถุดิบกับสินค้าสำเร็จรูปและใช้สูตรผลิตที่ระบุอัตราแปลง อย่าบวกจำนวน “ชิ้น” ต่างชนิดโดยไม่กำหนดหน่วย สมการนี้เป็นข้อเสนอออกแบบเกม ไม่ใช่สูตรที่ยืนยัน implementation ของโพสต์

**แบบทดลองต่อ:** เปลี่ยนกฎทีละอย่างแล้วรันหลาย seed พร้อมประชากรที่ไม่ใช้ฝึกรวมอยู่ด้วย เก็บทั้งผลเฉลี่ยและกรณีล้มเหลว เพื่อแยกภาพฝูงที่ดูสมจริงออกจากความสามารถปรับตัวต่อผู้เล่นใหม่

**ผลการตรวจ:** ส่วน emergent behavior ในบทเดิมยังใช้เป็นภาพรวมได้ งานเพิ่มชี้ว่าต้องตรวจทั้งความถูกต้องของโลกจำลองและความทนทานของพฤติกรรมต่อประชากรใหม่ ก่อนนำตัวเลข performance มาอ้างกับทั้งระบบ
