# Agentic Code Review: เมื่อการเขียนโค้ดเร็วขึ้นกว่าการทำความเข้าใจ

> ฉบับแปลภาษาไทยจาก [Agentic Code Review](https://addyosmani.com/blog/agentic-code-review/) โดย Addy Osmani — 15 มิถุนายน 2026

![ภาพปก Agentic Code Review](/assets/img/LLM/Agentic-Engineering/agentic-code-review.jpg)

*ภาพปก: [Addy Osmani](https://addyosmani.com/assets/images/agentic-code-review.jpg)*

*Coding agents เก่งมากแล้วและยังพัฒนาอย่างรวดเร็ว ผลที่น่าสนใจคือส่วนยากของงานวิศวกรรมย้ายจากการเขียนโค้ดไปเป็นการตัดสินว่าจะเชื่อโค้ดนั้นได้หรือไม่ ทำให้ review กลายเป็นทักษะที่ให้ leverage สูงมากในตอนนี้ วิธี review ที่เหมาะขึ้นกับว่าเราเป็นใครอย่างยิ่ง นักพัฒนาเดี่ยวที่ยังไม่มีผู้ใช้ กับทีมซึ่งดูแลแอปอายุสิบปี กำลังแก้คนละปัญหา*

ผมมอง agentic engineering ในแง่ดีกว่าที่เคย Agents เก่งจริง ดีขึ้นทุกเดือน และในวันทำงานปกติผมส่งมอบสิ่งที่เมื่อปีก่อนคงไม่กล้าลอง บทความนี้คือแผนที่ว่างานที่น่าสนใจย้ายไปอยู่ที่ไหน เพราะมันย้ายแล้ว และหลายทีมยังปรับตัวตามไม่ทัน

Code review เคยทำงานได้เพราะ “อุบัติเหตุที่โชคดี” เรื่องความเร็วสัมพัทธ์ วิศวกรอาวุโสอ่านโค้ดได้เร็วกว่าวิศวกรรุ่นน้องเขียน Review จึงตามทันโดยไม่ต้องออกแบบระบบพิเศษ และทีมซึมซับความเข้าใจว่าระบบประกอบกันอย่างไรจากการอ่าน diff ของกันและกัน ผลลัพธ์นี้ไม่ได้เกิดจากความตั้งใจทั้งหมด แต่มาจากข้อเท็จจริงข้อเดียว: การเขียนโค้ดคือส่วนที่ช้าและแพง ส่วนการอ่านถูกและเร็ว

ข้อเท็จจริงนั้นไม่จริงอีกต่อไป Agent สร้างโค้ดที่มักดีและจัดรูปแบบเรียบร้อยหนึ่งพันบรรทัดได้เร็วกว่าที่ผมใช้อ่านย่อหน้านี้ แต่ความเร็วการอ่านของมนุษย์ไม่เปลี่ยนไปตั้งแต่วันที่เราเริ่มจ้องหน้าจอเป็นอาชีพ

ข้อจำกัดจึงย้ายลงปลายน้ำ ไปยังขั้นเดียวที่ไม่ได้เร็วขึ้น: การทำให้มนุษย์มั่นใจว่า change นี้ถูกต้อง ผมไม่ได้มองว่านี่เป็นการสูญเสีย ตรงกันข้าม มันคือจุดที่ให้ leverage สูงที่สุดในงานซอฟต์แวร์ตอนนี้ และเป็นจุดที่ผมทุ่ม attention มากที่สุดในปีนี้

เรื่องมีมุมหักที่ดี: เครื่องมือชุดเดียวกับที่สร้างโค้ดเพิ่มมหาศาลก็เป็นเครื่องมือดีที่สุดที่ช่วยผมตามให้ทัน ในโปรเจกต์ของตัวเองรวมถึง open-source ยอดนิยม ผมชี้ Claude Code หรือ Codex ไปยัง PRs ที่เข้ามาเป็นชุด ให้มัน triage คิว และนั่นเปลี่ยนวิธีใช้เวลาไปจริง ๆ ดังนั้นนี่ไม่ใช่บทความต่อต้าน AI และผมจะอธิบายวิธีใช้โดยตรงในภายหลัง

นี่ไม่ใช่บทความ dump ตัวเลขหรือถกอีกรอบว่าให้โมเดลเขียนโค้ดเป็นเรื่องมหัศจรรย์หรือจุดจบของงานฝีมือ เพราะกรอบนั้นไม่มีประโยชน์ คำตอบเดียวที่อยู่รอดเมื่อเจอ codebase จริงคือ **ขึ้นอยู่กับว่าเราเป็นใคร** คนที่ vibe-code side project ซึ่งอาจมีผู้ใช้สิบกว่าคน กับทีมที่ต้องพยุง enterprise system อายุสิบปีต่ออีกไตรมาส แทบไม่มีข้อจำกัดร่วมกัน คำแนะนำจำนวนมากบนอินเทอร์เน็ตคือคนกลุ่มหนึ่งพยายามบอกอีกกลุ่มว่าควรใช้ชีวิตอย่างไร

## ข้อมูลปี 2026 บอกอะไรจริง ๆ

**Productivity gains จาก AI มีจริง แต่ raw output ทำให้มันดูมากเกินจริง: โค้ดเพิ่มประมาณสี่เท่า แต่ delivered value เพิ่มราวหนึ่งในสิบ ช่องว่างระหว่างสองตัวเลขคือ review work และนี่คือเหตุผลที่ leverage ย้ายมาอยู่ตรง review**

สองสามปีก่อนเรื่องนี้ยังเป็นเพียง anecdotes กับการโต้เถียง ตอนนี้มีการวัดในระดับใหญ่จากหลายองค์กรซึ่งไม่ได้มี agenda ร่วมกัน และบางรายเป็นคู่แข่งทางธุรกิจ ข้อมูลชี้ทิศทางเดียวกัน: AI ดัน output ขึ้นอย่างมาก และกดทั้ง quality กับ reviewability ลง

### Faros AI

[Faros AI](https://www.faros.ai/blog/ai-acceleration-whiplash-takeaways) ติดตามนักพัฒนา 22,000 คนจาก 4,000 ทีม และวัดสิ่งที่เกิดขึ้นเมื่อทีมเปลี่ยนจากการใช้ AI ต่ำไปสูง ข้อมูลเดือนมีนาคม 2026 แสดงด้านบวกชัดเจน: นักพัฒนา merge PRs มากขึ้น ทำงานเสร็จมากขึ้น และ throughput ต่อวิศวกรสูงขึ้น

แต่รายงานยังพบว่า:

- code churn เพิ่ม **861%**
- อัตราส่วน incidents ต่อ PR เพิ่ม **242.7%**
- defect rate ต่อนักพัฒนาเพิ่มจาก **9% เป็น 54%**
- ระยะเวลา review มัธยฐานเพิ่ม **441.5%** ขณะที่ time-to-first-review และเวลา review เฉลี่ยเพิ่มประมาณสองเท่า
- PRs ที่ merge โดยไม่มี review เพิ่ม **31.3%**

ตัวเลขสุดท้ายยากที่สุดที่จะมองข้าม เพราะไม่มีใครตั้งใจเลือกหยุด review Reviewers เพียงตาม volume ไม่ทัน โค้ดจึงเริ่ม merge โดยไม่มีใครอ่านและกลายเป็นเรื่องปกติ รายละเอียดที่ผมกลับมาคิดซ้ำคือ ทีมที่มีวินัยและ engineering practices แข็งแรงก็ได้รับผลกระทบพอ ๆ กับคนอื่น Process ที่ดีไม่ช่วย เพราะ volume มาเร็วกว่าที่ process เดิมถูกออกแบบให้รองรับ

ข้อควรระวังที่ต้องถือไว้ตลอดคือ CodeRabbit และ Faros ต่างขายผลิตภัณฑ์ในตลาดนี้ การ framing จึงไม่เป็นกลาง นั่นไม่ได้แปลว่าตัวเลขผิด—effect sizes ใหญ่และสอดคล้องกับแหล่งอื่น—แต่ vendor research ควรถูกอ่านโดยคำนึงถึงแรงจูงใจนั้น

### CodeRabbit

[CodeRabbit](https://www.businesswire.com/news/home/20251217666881/en/CodeRabbits-State-of-AI-vs-Human-Code-Generation-Report-Finds-That-AI-Written-Code-Produces-1.7x-More-Issues-Than-Human-Code) ศึกษา open-source PRs 470 รายการในเดือนธันวาคม 2025 แบ่งเป็น AI-coauthored 320 รายการและ human-only 150 รายการ พบว่า changes จาก AI มี issues ราว **1.7 เท่า**:

- ปัญหา logic และ correctness เพิ่มประมาณ 75%
- security issues พบมากขึ้น 1.5–2 เท่า
- readability problems เพิ่มมากกว่าสามเท่า

David Loker ผู้อำนวยการ AI ของบริษัทเรียกสิ่งเหล่านี้ว่า “จุดอ่อนที่คาดการณ์และวัดได้ ซึ่งองค์กรต้องลดผลกระทบอย่างจริงจัง” คำว่า *คาดการณ์ได้* สำคัญ เพราะถ้ารู้ตำแหน่งและรูปแบบ เราก็ออกแบบ review process—ทั้งมนุษย์และ automation—ให้เล็งไปที่มันได้

### GitClear

[GitClear](https://www.gitclear.com/research/ai_tool_impact_on_developer_productive_output_from_2022_to_2025) มีตัวเลขเดียวที่ผมจะใช้ขึ้นต้นการนำเสนอ ในข้อมูล productivity ถึงปี 2025 ผู้ใช้ AI รายวันสร้าง raw output ราว **4 เท่า** ของผู้ไม่ใช้ แต่เมื่อเทียบกับ output ของตัวเองในปีก่อน productivity จริงเพิ่มเพียงประมาณ **12%**

เรากำลังสร้างโค้ดราวสี่เท่าเพื่อ delivered value เพิ่มประมาณหนึ่งในสิบ และยังต้องมีมนุษย์ review โค้ดทั้งสี่เท่านั้น Bill Harding ระบุเองว่าบางส่วนของ 12% อาจมาจาก selection bias เพราะนักพัฒนาที่แข็งแรงกว่ากระจุกตัวในกลุ่มใช้ AI ช่องว่างระหว่าง 4x code กับมูลค่าที่เพิ่มเพียงหนึ่งในสิบคือ review problem ในประโยคเดียว

### GitHub

[GitHub](https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/) รายงานว่า Copilot review ทำงานไปแล้วมากกว่า 60 ล้าน reviews เพิ่มขึ้น 10 เท่าในเวลาไม่ถึงปี และมากกว่าหนึ่งในห้าของ reviews บน platform มี agent เกี่ยวข้อง นี่ไม่ใช่ practice เฉพาะกลุ่มอีกต่อไป แต่มันคือวิธีที่โค้ดถูกสร้าง

ข้อมูลสี่ชุด วิธีวัดสี่แบบ และข้อสรุปเดียวกัน: เราเท output ความเร็วระดับเครื่องเข้าไปในระบบที่สร้างมาสำหรับงานความเร็วมนุษย์ Bottleneck ไม่ได้หายไป แต่ [ย้ายไปที่ verification](https://addyosmani.com/blog/verification-bottleneck/) และ review คือจุดที่ต้องจ่ายต้นทุน

## ทุกคนกำลังแก้คนละปัญหา

**ปริมาณ review ที่ change หนึ่งต้องการขึ้นกับ blast radius เกือบทั้งหมด และคำแนะนำส่วนใหญ่ที่เราอ่านมาจากคนซึ่งทำงานที่ blast radius ต่างจากเราอย่างมาก**

ข้อมูลน่ากังวลข้างต้นส่วนใหญ่มาจาก enterprise telemetry และ open-source maintainers ที่ถูก volume ถล่ม ถ้าเราอยู่ในสถานการณ์นั้น ตัวเลขก็เป็นจริงเต็มรูปแบบ แต่ถ้าเป็นคนเดียวที่ส่งซอฟต์แวร์ซึ่งมีผู้ใช้เพียงหยิบมือ หลายเรื่องอาจยังไม่ตรงกับเรา และไม่ควรถูกทำให้รู้สึกผิดเพราะเลือกวิธีเบากว่า

ตัวแปรสามข้อกำหนดตำแหน่งบน spectrum:

1. **Blast radius** — ถ้าพังแล้วเกิดอะไรขึ้น? ไม่มีอะไร หรือมีผู้ใช้โกรธ เงินสูญ และ PII อยู่ในความเสี่ยง
2. **อายุของโค้ด** — prototype ที่อาจเขียนใหม่สัปดาห์หน้า หรือ codebase ที่ต้องดูแลอีกหลายปี
3. **จำนวนคนที่ต้องเข้าใจ** — มีเพียงเราที่ถือระบบทั้งหมดในหัว หรือทีมที่ต้องแบ่ง ownership ระยะยาว

เมื่อเอา diff เดียวกันผ่านตัวแปรสามข้อนี้ คำว่า “review ที่ดี” จะหมายถึงคนละอย่างจริง ๆ

### นักพัฒนาเดี่ยวบน Greenfield ที่ยังไม่มีผู้ใช้

หน้าที่ที่สองของ review—กระจายความรู้ทั่วทีม—ยังไม่มี เพราะเราคือทั้งทีม ทางเลือกสมเหตุสมผลคือพึ่ง tests และ automation อย่างมาก ตรวจเฉพาะส่วนสำคัญจริง และใช้ touch ที่เบากับส่วนอื่น Duplication และ churn มีต้นทุนต่ำกว่าเมื่อโค้ดอาจหายไปในหนึ่งเดือน และไม่มีใครถูกปลุกตอนตีสามเมื่อระบบพัง

แต่มีเงื่อนไข: tests ต้องเป็นของจริง การข้าม review โดยไม่มี safety net ไม่ได้ลบงาน แต่เพียง [เลื่อนไปจ่ายแพงกว่าในภายหลัง](https://addyosmani.com/blog/intent-debt/) และ standards จะค่อย ๆ ลดเมื่อไม่มีใครคัดค้าน

> ไม่มีผู้ใช้คือสิทธิ์ให้เลื่อน review ไม่ใช่สิทธิ์ให้ข้าม verification

### ช่วงอันตรายเมื่อเริ่มมีผู้ใช้

การข้ามเส้นนี้มักเกิดขึ้นโดยไม่มีใครสังเกต หน้าที่จับ bug ของ review เริ่มสำคัญเพราะ bugs ทำร้ายคน และหน้าที่แบ่งปันความรู้เริ่มทำงานเพราะไม่ได้มีแค่เรา Teams มักรักษานิสัยจากยุค solo นานเกินไปสองสามเดือน จากนั้นเกิด postmortem และตัวเลขของ Faros ก็หยุดเป็นกราฟ กลายเป็น dashboard ของตัวเอง

### องค์กรใหญ่กับ Codebase เก่า

ที่ปลาย spectrum นี้ ตัวเลขน่ากังวลทั้งหมดมีผลเต็มแรง Helper ซ้ำไม่ใช่ style nit แต่เป็น bug surface และ maintenance cost ที่ทบไปหลายปี Change ที่ไม่มีใครเข้าใจคือ [comprehension debt](https://addyosmani.com/blog/comprehension-debt/) ซึ่งกลายเป็น incident ของคน on-call Review ทำหลายหน้าที่พร้อมกัน และ volume จาก agents ทำลายหน้าที่เหล่านั้นอย่างเงียบ ๆ ผลของ Faros เรื่อง mature teams มุ่งตรงมาที่กลุ่มนี้

ประเด็นจึงไม่ใช่ “enterprise ต้องระวัง ส่วน solo ผ่อนคลายได้” แต่คือจุดประสงค์ของ review เปลี่ยนตามตำแหน่งบน spectrum กฎจึงต้องเปลี่ยนตาม การเอา pipeline หนักระดับ enterprise ซึ่งมี lock-down, multi-agent และ evidence requirements ไปใส่ prototype สองคนคือ friction ที่ไม่ให้ประโยชน์ แต่การใช้ “tests ผ่านก็ ship” บน payment system คือเครื่องสร้าง incident ที่มีเครื่องหมายถูกสีเขียวติดอยู่

คำแนะนำแย่จำนวนมากเกิดจากคนที่อยู่จุดหนึ่งบน spectrum สั่งคนที่อยู่อีกจุดให้ทำเหมือนกัน

## ตอนนี้ Review มีไว้ทำอะไรจริง ๆ?

**Review ถูกสร้างมาเพื่อตรวจ reasoning ของผู้เขียน Agent ก็ reasoning แต่ reasoning นั้นมักถูกทิ้งแทนที่จะติดไปกับโค้ด Reviewer จึงต้องสร้าง rationale ที่ไม่อยู่ใน diff ขึ้นใหม่ ข่าวดีคือ นี่เป็น tooling problem และการเก็บ reasoning ทำให้ review ง่ายขึ้นมาก**

เมื่อมนุษย์เขียนโค้ด intent ติดมากับงานโดยธรรมชาติ Reasoning ทางเลือกที่ชั่งน้ำหนักและปฏิเสธ อยู่ในหัวผู้เขียน และ review คือการตรวจ reasoning นั้น

Modern agents ก็ reasoning และหลายครั้งแสดง thinking traces ชั่งทางเลือกและอธิบายตัวเองระหว่างทำงาน แต่ reasoning นี้มักถูกทิ้งทันทีที่ได้ diff ไม่ค่อยถูกเก็บ ไม่ค่อยแนบ PR และถึงเก็บไว้ก็เป็น reasoning ว่าจะ implement task อย่างไร ไม่ใช่ judgment ของมนุษย์ว่าควรสร้าง task นี้หรือไม่

Review จึงเปลี่ยนจากตรวจ reasoning ที่อยู่ตรงหน้า เป็นสร้าง intent ที่ไม่เคยเขียนขึ้นใหม่ ซึ่งยากและช้ากว่า แล้วเราก็ยังประหลาดใจที่มันใช้เวลานานขึ้น 441%

งานวิจัยปี 2026 [AI Slop and the Software Commons](https://arxiv.org/html/2604.16754v1) วิเคราะห์โพสต์ 1,154 รายการจาก Reddit และ Hacker News 15 threads ซึ่งนักพัฒนาคุยเรื่อง “AI slop” ประโยคหนึ่งจากนักพัฒนาติดอยู่ในใจผม: การ review PR ของ agent ทำให้เขาเป็น *“มนุษย์คนแรกที่เคยเห็นโค้ดนี้”*

ใน review ปกติ ผู้เขียนเข้าใจ change อยู่แล้ว และ reviewer ตรวจงาน แต่ใน agent PR ยังไม่มีใครสร้างความเข้าใจว่า “ทำไม” Reviewer จึงเป็นคนแรกที่พยายาม งานวิจัยสรุปว่า review *“ไม่ได้ถูกสร้างมาเพื่อกู้คืน intent ที่หายไป”*

ส่วนที่ให้ความหวังคือ intent กู้คืนได้ Reasoning เคยมีอยู่ เพียงแต่เราทิ้งมัน ให้ agent ระบุว่ากำลังพยายามทำอะไรและปฏิเสธทางเลือกใด แล้วเก็บเป็น [decision log](https://addyosmani.com/blog/intent-debt/) บน PR ต้นทุนในการ reconstruct จำนวนมากก็หายไป นี่เป็น tooling problem และ tooling problem แก้ได้

อย่างไรก็ตาม “ให้ AI review AI” ยังไม่ใช่คำตอบทั้งหมด โมเดลตัวที่สองซึ่งมี priors ต่างกันจับ bugs ได้จริงและจับได้มาก จึงควรใช้ แต่สิ่งที่มันไม่ให้คือ human judgment ว่านี่คือ change ที่ควรสร้างตั้งแต่แรกหรือไม่ Judgment นี้ยังเป็นของคน และบังเอิญเป็นส่วนที่น่าสนใจที่สุดของงาน—ส่วนที่ควรเก็บไว้

## เครื่องมือดี แต่ไม่ใช่ด้วยเหตุผลที่โฆษณาเสมอไป

**AI reviewers ปัจจุบันเก่งจริง และบางครั้งไม่ flag บรรทัดเดียวกันเลย ดังนั้นทางเลือกที่ดีไม่ใช่หาเครื่องมือที่ดีที่สุดหนึ่งตัว แต่คือรันสองตัวที่สร้างต่างกัน**

Dedicated AI review tools ดีพอแล้ว และผมคิดว่าควรใช้อย่างน้อยหนึ่งตัวกับทุก change รวมถึง side projects

- [CodeRabbit](https://www.coderabbit.ai/) ใช้งานแพร่หลายที่สุดและได้อันดับสูงสุดใน [Martian benchmark](https://www.coderabbit.ai/blog/coderabbit-tops-martian-code-review-benchmark) ช่วงมกราคม–กุมภาพันธ์ 2026 ด้าน F1 ด้วย precision ราว 49% และ recall ดีที่สุดในกลุ่ม
- [Greptile](https://www.greptile.com/) แลก precision กับ recall โดย benchmark หนึ่งให้ bug-catch rate ราว 82% เทียบกับ CodeRabbit 44% แต่ false positives มากกว่า
- [Anthropic Code Review](https://claude.com/blog/code-review) รายงานว่าต่ำกว่า 1% ของ findings ถูกวิศวกรทำเครื่องหมายว่าผิด และเพิ่มอัตรา PRs ภายในที่ได้รับ substantive review จาก 16% เป็น 54%

Changes หางยาวที่เคยได้เพียง glance กับ approval ตอนนี้ถูกอะไรบางอย่างอ่านจริง

ผลลัพธ์ที่มีประโยชน์ที่สุดที่ผมเห็นในปีนี้ไม่ได้มาจาก vendor วิศวกรคนหนึ่ง [รัน reviewers สี่ตัวขนานกัน](https://dev.to/_vjk/best-ai-code-reviewer-in-2026-we-ran-4-in-parallel-for-3-weeks-146-prs-679-findings-1c0f)—CodeRabbit, Sentry Seer, Greptile และ Cursor BugBot—กับ PRs จริง 146 รายการและ findings 679 รายการในเวลาสามสัปดาห์ครึ่ง:

> จากตำแหน่งที่ถูก flag ไม่ซ้ำ 617 จุด **93.4% ถูกจับโดยเครื่องมือเพียงหนึ่งในสี่ตัว** 6% ถูกจับโดยสองตัว แทบไม่มีจุดใดถูกจับโดยสามตัว และ **ไม่มีแม้แต่จุดเดียวที่ทั้งสี่ตัวจับพร้อมกัน**

เครื่องมือทั้งสี่ไม่เคย flag บรรทัดเดียวกันพร้อมกันเลย แต่ละตัวเก่งปัญหาคนละประเภท: Greptile มี false positive ใกล้ศูนย์สำหรับ correctness และ architecture, CodeRabbit กวาดกว้างที่สุดและมี one-click fixes ส่วน Seer เก่งกับความรุนแรงระดับ production failure

นี่คือเหตุผลของ adversarial review ที่แสดงบน codebase จริงแทนทฤษฎี **Heterogeneity คือหัวใจ** สี่ copies ของโมเดลเดียวกันคือ reviewer คนเดียวที่ invoice ใหญ่ขึ้น แต่ reviewers สี่แบบซึ่งต่างกันจริงเปิดเผยชุด bugs ที่สมาชิกคนเดียวหาไม่ได้ รวมถึงมนุษย์ด้วย

ในทางปฏิบัติ อย่าหมกมุ่นหา tool ที่ดีที่สุดเพียงหนึ่ง เพราะไม่มี ที่ฝั่ง high-stakes ให้รันสองตัวซึ่งมี character ต่างกันโดยตั้งใจ เช่น Greptile สำหรับ everyday correctness และ Seer สำหรับ production-failure severity หากเป็น solo เครื่องมือดีหนึ่งตัวบวก tests จริงก็เพียงพอ และไม่ว่า marketing จะพูดอย่างไร ต้องวัดบน codebase ของเราเอง เพราะทุกผลข้างต้นเฉพาะกับ codebase หนึ่ง และของเราก็จะต่างเช่นกัน

## เราควรปล่อยให้ AI Review มากกว่านี้หรือไม่?

**เครื่องกำลัง review โค้ดมากกว่าที่มนุษย์อ่านอยู่แล้ว การตัดสินใจจริงจึงไม่ใช่จะอนุญาตหรือไม่ แต่คือเราจะทำอย่างตั้งใจหรือปล่อยให้เกิดโดยปริยาย และสัดส่วนมนุษย์ควรเพิ่มตาม blast radius**

ผมได้ยินคำถามที่เมื่อปีก่อนคงถือเป็นเรื่องต้องห้ามจากวิศวกรมีประสบการณ์: ควรให้เครื่องทำ review มากขึ้นหรือแม้แต่ส่วนใหญ่หรือไม่? ตอนนี้ผมไม่คิดว่านี่เป็นคำถามโง่อีกแล้ว

ส่วนที่ชวนไม่สบายใจคือ AI review ใช้ได้จริง Findings ของ Anthropic ต่ำกว่า 1% ถูกทำเครื่องหมายว่าผิด เครื่องมือจับ bugs ที่มนุษย์อ่านผ่าน และไม่เหนื่อยกับ PR ที่สามสิบของวัน—ช่วงที่มนุษย์น่าเชื่อถือน้อยที่สุด

ขณะเดียวกันมนุษย์ตามไม่ทันอย่างเห็นได้ชัด: zero-review merges เพิ่ม 31% และเวลา review เพิ่มเป็นเลขสามหลัก ในความหมายจริง เครื่องกำลัง review code มากกว่าเรา Framing ที่ซื่อสัตย์จึงไม่ใช่ “ควรให้ AI review เพิ่มไหม” แต่คือ “มันทำอยู่แล้ว เราจะออกแบบให้ตั้งใจ หรือปล่อยให้เกิดโดย default ขณะที่ยังแกล้งเชื่อว่าคนอ่านทุกอย่าง?”

[Loop engineering](https://addyosmani.com/blog/loop-engineering/) ทำให้คำถามคมขึ้น Premise คือเราหยุดเป็นคน prompt agent แล้วสร้างระบบที่ prompt มันแทน ส่วนกลางของระบบคือ judge: agent ที่ตัดสินว่างานเสร็จหรือยังก่อนเดินต่อ Reviewer คือบทบาทถัดไปที่กำลังถูกออกแบบออกจาก inner loop อย่างตั้งใจ

เราใช้เวลาหนึ่งปี automate การเขียน ตอนนี้ loops กำลัง automate การตรวจ และมนุษย์ถูกผลักขึ้นและออกไปเรื่อย ๆ คำถามว่า “มนุษย์ควรอยู่ตรงไหน” ไม่ใช่หัวข้อสัมมนา แต่เป็นสิ่งที่เราตัดสินทุกครั้งเมื่อ wiring loop ไม่ว่าจะรู้ตัวหรือไม่

ตำแหน่งที่ผมยืนตอนนี้—และพร้อมเปลี่ยนเมื่อมีข้อมูลใหม่—ไม่ใช่ “มนุษย์อ่านทุกบรรทัด” ยุคนั้นจบแล้ว Volume ทำให้เป็นไปไม่ได้ คนที่ยืนยันตรงข้ามกำลังอธิบายโลกที่ไม่มีอยู่

แต่คำตอบก็ไม่ใช่ “ปล่อยให้ loop review ตัวเองแล้วเดินหนี” เมื่อ agent ตัวหนึ่งเขียน อีกตัว review และตัวที่สาม judge เราได้ closed loop ของโมเดลที่มี blind spots สัมพันธ์กัน โดยเฉพาะถ้ามาจาก family เดียวกัน คำตอบ “ดูดี” อย่างมั่นใจโดยไม่มีมนุษย์อยู่เลยคือ [borrowed confidence](https://addyosmani.com/blog/cognitive-surrender/): ความแน่ใจของระบบกลายเป็นของเรา ทั้งที่ไม่มีใครเข้าใจจริง Loop อาจมั่นใจมากและผิดมากพร้อมกัน โดยไม่มีมนุษย์แยกความต่าง

ดังนั้นมนุษย์ไม่หายไป แต่มนุษย์ย้ายขึ้นหนึ่งระดับ เราหยุด review ทุก diff และเริ่มเป็นเจ้าของสิ่งที่โอนไปให้โมเดลไม่ได้:

- **Accountability** — โมเดลถูก page ตอนตีสามไม่ได้
- **Judgment ว่าควรสร้าง change นี้หรือไม่** ต่างจาก code ถูกหรือไม่
- **High-blast-radius gates** ที่ความผิดมีราคาแพง
- **Behavior ที่ไม่มีใครระบุ** เพราะโมเดล review code ที่มีอยู่ แต่แทบไม่ flag requirement ที่ไม่มีใครคิดเขียน

Human in the loop เปลี่ยนเป็น **human on the loop**: sampling, spot-checking และ auditing ระบบ แทนการอ่านทุก PR และใช้ attention จำกัดกับจุดที่ผิดแล้วเจ็บจริง

นี่คือวิธีที่ผมทำกับโปรเจกต์ของตัวเอง รวมถึง open source ที่ตอนนี้มี PRs ต่อวันมากกว่าที่ผมอ่านละเอียดได้ในหนึ่งเย็น ผมให้ Claude Code หรือ Codex ตรวจ PRs เป็น batch รอบแรก สรุปว่าอะไรน่าจะ merge ได้ อะไรต้องแก้ และอะไรเสี่ยงจริง

ผมไม่ auto-merge ตามผล และไม่ lazy-merge ทุกสิ่งที่มันอนุมัติ สิ่งที่ได้คือวิธีจัดสรร attention ผมใช้เวลาไม่กี่นาทียืนยัน changes ที่มันมองว่า low-risk และลงเวลาจริงกับสิ่งที่ถูก flag ว่าอันตราย รายละเอียดสำคัญคือ นี่ไม่ใช่ review hour แบบเก่าที่เร็วขึ้นเล็กน้อย แต่มันเป็นชั่วโมงคนละรูปทรง และที่ volume ปัจจุบันมันคือเหตุผลหลักที่คิวยังอยู่รอด

[![Claude Code และ Codex คัดแยก pull requests ตามความเสี่ยง](/assets/img/LLM/Agentic-Engineering/code-review.jpg)](/assets/img/LLM/Agentic-Engineering/code-review.jpg)

*Codex และ Claude Code ทำ first-pass แบบเรียง PRs ตามความเสี่ยง การ triage คือสิ่งที่ช่วย ส่วน merge decision ยังเป็นของผม — [ภาพต้นฉบับ](https://addyosmani.com/assets/images/code-review.jpg)*

เวอร์ชันสุดขั้วของแนวทางเดียวกันคือ Kun Chen อดีตวิศวกร Meta ระดับ L8 ซึ่งตอนนี้ส่งราว 40 PRs ต่อวันในฐานะ solo builder และแทบหยุด review code แล้ว การ dismiss เรื่องนี้ทำได้ง่าย แต่เขาเป็น L8 และเก่งมากกับงานที่หยุดทำ นั่นทำให้กรณีนี้น่าสนใจ

เขารัน agents 20–30 ตัวขนานกัน และย้าย effort ไปอยู่ที่ plan: เขียนแผนละเอียดล่วงหน้า ปล่อย agents ทำงานหลายชั่วโมง และบอกว่าคุณภาพแผนกำหนดว่ามันรันโดยไม่มีคนดูได้นานแค่ไหน นี่คือการย้ายที่อธิบายข้างต้นในรูปบริสุทธิ์

ควรแยกให้ชัดว่าเขาไม่ได้หยุด verification Intent ไม่หายไป เพราะเขาเขียนลง plan ด้วยตัวเอง ปัญหา “มนุษย์คนแรกที่เห็นโค้ด” จึงถูกแก้ครึ่งหนึ่ง มนุษย์เข้าใจ why ล่วงหน้าแทนภายหลัง และเขาไม่ได้ทำงานโดยไม่มี safety net แต่สร้าง automated review gate ที่เรียกว่า No Mistakes เพื่อตรวจ code ก่อน merge และยังรับ escalation เมื่อ agent ติดขัด

มนุษย์ทำ expensive thinking ก่อน code เกิด เครื่องทำ line-by-line หลังจากนั้น นี่อาจเป็นรูปแบบของอนาคต

แต่เขาเป็น solo builder ไม่มีทีมใหญ่หรือระบบอายุสิบปีซึ่งมี landmines อยู่ใต้พื้น เงื่อนไขที่ทำให้ 40 PRs ต่อวันโดยไม่ review สมเหตุสมผลสำหรับเขา ไม่ใช่เงื่อนไขของผู้อ่านส่วนใหญ่ หาก copy workflow นี้ไปทีมที่ส่งของให้ผู้ใช้จำนวนมาก เราจะสร้างตัวเลข Faros บน dashboard ของตัวเอง เขาไม่ได้ผิด แต่อยู่ปลาย spectrum ที่เฉพาะมาก

กลับมาที่ spectrum อีกครั้ง:

- **Solo ไม่มีผู้ใช้** — ให้ AI review เกือบทั้งหมดเป็นจุดยืนที่ปกป้องได้ในปี 2026 ไม่ต้องรู้สึกผิด
- **ระบบใหญ่สำหรับคนจำนวนมาก** — ให้เครื่องจัดการ first pass, second pass และ 90% ที่น่าเบื่อ แต่ต้องมีมนุษย์จริงบน load-bearing paths และอย่าปิด loop สมบูรณ์กับสิ่งที่ทำร้ายคนได้

ปริมาณมนุษย์คือ dial ซึ่งตั้งตาม blast radius ไม่ใช่ความรู้สึกผิด

## สิ่งที่ควรทำจริง

**หยุด review ทุกอย่างด้วยความลึกเท่ากัน ใช้ attention ของมนุษย์เฉพาะจุดที่ผิดแล้วแพง และให้ deterministic gates กับ AI reviewers จัดการส่วนที่เหลือ**

หลักจัดระบบคือจับคู่ effort กับต้นทุนเมื่อผิด ผลักงาน deterministic ราคาถูกไปต้น pipeline และเก็บ attention มนุษย์ไว้กับสิ่งที่มนุษย์เท่านั้นทำได้

### แบ่ง Tier ตามความเสี่ยง ไม่ใช่ตามผู้เขียน

Config change อาจต้องเพียง linter กับ glance แต่ payment path ต้องได้ full stack: types, tests, AI reviewers ต่างชนิดสองตัว มนุษย์ที่เป็นเจ้าของระบบ และ security pass

อย่าใช้ heavy review กับ boilerplate และอย่าปล่อย auth change ผ่านเพียงเพราะ tests เขียว [Layered approach](https://addyosmani.com/blog/verification-bottleneck/) เหมือนกันทุกที่ สิ่งที่ต่างคือจำนวน layers ที่ diff ต้องผ่าน

### Fast-Fail งานปลายหางที่แพง

งานวิจัย [Early-Stage Prediction of Review Effort](https://arxiv.org/html/2601.00753) เดือนมกราคม 2026 ศึกษา agent-authored PRs 33,707 รายการ พบว่า agents ทำ changes เล็กและนิยามชัดได้ดี ราว 28% merge เกือบทันที แต่มีแนวโน้ม “ghost” เมื่อได้รับ subjective feedback และละทิ้ง back-and-forth ซึ่งเป็นแก่นของ review งาน companion ปี 2026 พบว่า [reviewer abandonment เป็น 38% ของ agent PRs ที่ถูกปฏิเสธ](https://arxiv.org/html/2601.15195)

นักวิจัยสร้าง “circuit breaker” ทำนาย PRs ที่ต้องดูแลสูงจาก signals ราคาถูกอย่าง file types และ patch size ก่อนมนุษย์เปิดดู และทำงานได้ดี

จึงควร triage agent PRs ตั้งแต่ต้น fast-track งาน trivial และอย่าปล่อยให้คนใช้หนึ่งชั่วโมงกับ sprawling change ซึ่ง agent จะทิ้งทันทีเมื่อถูกทัก

### ยกระดับเกณฑ์ก่อนยอม Review

ทางแก้เมื่อถูก PRs ฝังไม่ใช่ lock repository แต่คือ [ปฏิเสธ review changes ที่มาโดยไม่มีหลักฐาน](https://www.builder.io/blog/developers-drowning-in-ai-prs) ก่อนเข้า review ต้องมี:

- ข้อความว่า change มีไว้ทำอะไร
- Diff ที่ไม่ใช่ 3,500 บรรทัดโดยไร้คำอธิบาย
- Test output
- หลักฐานว่า tests ถูก execute จริง

นี่คือวิธีหยุดเป็นมนุษย์คนแรกที่อ่าน code เราผลัก intent-reconstruction กลับไปยังผู้ส่ง ซึ่งทำได้ถูกกว่า แทนดูดซับไว้ที่ reviewer ซึ่งแพงกว่า

### ทำ PR ให้เล็กโดยตั้งใจ

Agent PRs มักใหญ่กว่า—ข้อมูล Faros ระบุว่าเฉลี่ย **51%**—และ reviewer engagement เป็น predictor สำคัญว่า PR จะ merge หรือไม่ PR ใหญ่ที่ review ไม่ไหวมัก [ถูกปฏิเสธ](https://addyosmani.com/blog/comprehension-debt/) หรือแย่กว่านั้นคือ rubber-stamp

สั่ง agents ให้สร้าง commits เล็ก Diff ที่มนุษย์อ่านได้กลายเป็น design constraint ไม่ใช่มารยาท

### อ่าน Test Changes ละเอียดกว่า Code

นี่คือ failure mode ที่ต้องจับตา Agent เปลี่ยน behavior แล้ว “แก้” test ด้วยการเปลี่ยน assertion ให้ตรง behavior ใหม่ที่ผิด เครื่องหมายเขียวเหนือ tests ที่ถูกแก้ 200 รายการไม่มีความหมายจนยืนยันว่า edits ถูกต้อง

ถือ diff ที่ rewrite tests จำนวนมากเป็น flag และอ่านมันก่อน Mutation testing มีที่ยืนตรงนี้ Coverage บอกว่าบรรทัดหนึ่งถูก execute แต่ mutation testing บอกว่า test จะสังเกตหรือไม่หากบรรทัดนั้นผิด

### ถือ CI เป็นกำแพงที่ห้ามขยับ

จับ patterns ที่ [GitHub เตือน reviewers](https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/):

- tests ถูกลบ
- lint ถูก skip
- coverage threshold ถูกลด
- helper ถูกสร้างซ้ำทั้งที่มีอยู่แล้ว
- untrusted input ไหลเข้า prompt

ข้อสุดท้ายสำคัญมาก Agent-built features เป็นแหล่งใหม่ของ [prompt injection](https://simonwillison.net/series/prompt-injection/) หาก change ส่ง user-controlled text เข้า LLM call โดยไม่คิดว่าข้อความนั้นสั่งโมเดลทำอะไรได้ vulnerability จะไม่เห็นใน diff แต่นอนรออยู่ในข้อมูลที่จะมาภายหลัง

Agents ยังอาจทำให้ CI อ่อนลงเพื่อให้ตัวเองผ่าน ไม่ใช่เพราะประสงค์ร้าย แต่เพราะ gradient descent หาเส้นทางถูกที่สุดไปสู่สีเขียว Deterministic gates คือส่วนเดียวของ pipeline ที่ย่อหน้ามั่นใจไม่สามารถเกลี้ยกล่อมให้เปลี่ยน verdict ได้ จึงต้องรักษาให้เข้ม

### มนุษย์เป็นเจ้าของ Merge

โมเดลถูก page ไม่ได้และรับผิดชอบสิ่งที่ส่งไม่ได้ ดังนั้นคนที่คลิก merge เป็นเจ้าของ เมื่อ AI review พูด “looks good” ด้วยเสียงสงบมั่นใจ มันกำลังส่ง [confidence ที่อาจไม่ได้ earn](https://addyosmani.com/blog/cognitive-surrender/) มาให้เรา

ถือทุก AI review เป็น **sensor ไม่ใช่ verdict**: เป็นข้อมูล ไม่ใช่การตัดสินใจ

ถ้าเป็น solo และไม่มีผู้ใช้ Risk tiering, test discipline และ CI คือสิ่งหลักที่ต้องมี ส่วนอื่นอาจยังเป็น overhead จนกว่าจะมีคนเข้ามา หากเป็นองค์กรใหญ่ ทุกข้อคือ baseline และ triage กับ intake bar คือความต่างระหว่าง review process ที่ scale ได้กับระบบที่ยุบตัวเงียบ ๆ

## ถ้าคุณบริหารทีม สิ่งนี้หมายถึงอะไร

**Bottleneck ไม่ใช่ความเร็วการเขียนโค้ด แต่คือความเร็วที่มนุษย์ซึ่งได้รับความไว้วางใจสร้างความมั่นใจกับ review การลดคนเหล่านี้เพราะ “AI ทำให้เราเร็วขึ้น” เป็นเพียงการแปลงเงินประหยัดวันนี้เป็น incidents ในอนาคต**

Binding constraint ของ shipping ไม่ใช่ความเร็วการเขียน แต่คือความเร็วที่คนไว้ใจได้มั่นใจว่า change ถูกต้อง แผนใดที่ถือ generation เป็น bottleneck และ review เป็นของฟรี จะหยุดชะงักอย่างเงียบ ๆ ขณะที่ velocity dashboard ยังเขียว

Faros พูดตรงว่า QA และ review work เพิ่มตาม output ดังนั้นลด engineering headcount เพราะ “AI ทำให้เร็วขึ้น” อันตราย หากยังไม่ปิด review gap Senior-engineer tax ซึ่งเวลา review เพิ่มเป็นเลขสามหลัก ตกหนักที่สุดกับคนที่เราไม่ควรทำให้เป็น bottleneck และไม่ปรากฏใน metric ที่นับเพียง merged PRs

Open-source maintainers ชนกำแพงนี้ก่อนและหนักที่สุด [กระแส contributions ที่ดูน่าเชื่อแต่กลวง](https://arxiv.org/html/2604.16754v1) ใช้เวลา triage จริงแม้เจตนาดี และเป็น canary บริษัทจะตามมา

องค์กรที่รับมือดีมอง review capacity เป็นทรัพยากรจริงที่ต้องวัด ปกป้อง และใช้โดยตั้งใจ ไม่ใช่ slack ที่ AI ปลดปล่อยให้เหลือ

## การเขียนถูกลง แต่ความเข้าใจไม่ได้ถูกลง

Code review ไม่ได้สำคัญน้อยลงเมื่อ agents มาถึง แต่มันกลายเป็นกิจกรรมศูนย์กลาง การเขียนโค้ดถูกแก้ไปมากแล้วและถูกลงทุกเดือน ความได้เปรียบที่ยั่งยืนคือระบบที่ทำให้เราเชื่อสิ่งที่ถูกเขียนได้

อย่าใช้คำตอบเดียวกับทุกตำแหน่งบน spectrum:

- ถ้าเป็น solo ไม่มีผู้ใช้ เรื่อง horror ของ enterprise เกี่ยวกับ churn และ duplication คือความเสี่ยงอนาคต ไม่ใช่ไฟวันนี้ พึ่ง tests ตรวจสิ่งสำคัญ และยอมรับอย่างซื่อสัตย์ว่างานที่เลื่อนไปยังคงเป็นหนี้
- ถ้าดูแลระบบใหญ่สำหรับคนจำนวนมาก ตัวเลขน่ากังวลทั้งหมดหมายถึงเรา สิ่งที่อยู่รอดคือ review process แบบ tiered, evidence-required และ intentionally heterogeneous โดยมีมนุษย์เป็นเจ้าของ merge

สิ่งคงที่คือเศรษฐศาสตร์พื้นฐาน:

> เราทำให้การเขียนถูกลง แต่ความเข้าใจยังแพงเท่าเดิม

ทีมที่จะไปได้ดีในอีกไม่กี่ปีไม่ใช่ทีมที่ generate code มากที่สุด แต่คือทีมที่สร้าง review system ซึ่งเชื่อถือได้ และไม่สับสนระหว่าง “tests ผ่าน” กับ “มีคนเข้าใจว่าสิ่งนี้ทำอะไรและทำไม”

หรืออย่างที่ Simon Willison ย้ำว่า [งานของเราคือส่งมอบโค้ดที่พิสูจน์แล้วว่าทำงานได้](https://simonwillison.net/2025/Dec/18/code-proven-to-work/) Agents ไม่ได้เปลี่ยนข้อกำหนดนั้น เพียงทำให้การพิสูจน์กลายเป็นศูนย์กลางของงานแทนภาคผนวก และผมคิดว่านั่นเป็นการแลกที่ดี

การเข้าใจระบบมากพอที่จะยืนอยู่ข้างมันเป็นทักษะที่ทนทานและน่าสนใจที่สุดใน software และไม่เคยมีเวลาใดเหมาะกว่านี้ในการฝึกให้เก่งเป็นพิเศษ
